# proni-official-precheck

PRONI 公式テックブログ記事を、広報へ提出する前に自分で点検する。**記事は編集しない（review-only）**。修正するかどうかは著者が決める。

## 入力

- `$1` = 対象記事（例: `articles_note/new/PRONI-plangate-team-rollout.md`）。`PRONI-` で始まらないファイルなら止めて報告する

## 手順

1. `articles_note/checklists/proni-official-precheck.md` を読む。判定基準と検索語はこのファイルが正本。本スキルには書き写さない
2. 対象記事を頭から読み、§0 の記事タイプを 1 行で判定する
3. 機械的に確かめられる項目を先に実行する。パスは引用符で囲む
   - 文体（敬体・常体）の混在: `npm run check:article-sentence-style -- "<記事>"`。時制（です／でした）の混在はこのコマンドでは検出できないので、手順 4 の通読で確かめる
   - 言語密度: `npm run check:article-language-density -- "<記事>"`
   - チェックリストの各「検索語」: `grep -nE '<検索語>' "<記事>"`。ヒットは候補で、判定は前後の文脈で行う
   - 外部リンク: `grep -nE 'https?://' "<記事>"`（Markdown のリンクと裸の URL の両方）。引用・参照のリンクについて、近くに著者名・日付があるか確かめる
   - 末尾の採用告知: `grep -n '【PR】エンジニアの積極採用を実施中です' "<記事>"` と、その下の告知文・求人一覧リンク
4. 本文を通読し、§1〜§5 と §6 の時制を判定する。カテゴリごとに「問題なし／要確認／要修正」と、根拠になる本文の逐語引用（短く）を書く
5. §6 のうち、リポジトリの外にあるもの（エンジニアレビューの承認、Google ドキュメントの権限・ハイパーリンク、カバー画像）は確認できない。「著者が確認」と書き、推測で埋めない

## 出力

チャットに次の形で返す。ファイルは作らない。

```markdown
## PRONI 提出前チェック: <記事タイトル>

記事タイプ: <1 行>
総合判定: 提出可 / 要確認あり / 要修正あり

| カテゴリ | 判定 | 根拠・該当箇所 |
| --- | --- | --- |
| 1. 中立性・ステークホルダー配慮 | | |
| 2. IR・ガバナンス・セキュリティ | | |
| 3. 事例の主語と匿名化 | | |
| 4. データの信頼性・著作権 | | |
| 5. ビジネスモデル整合性 | | |
| 6. 社内レギュレーション | | |

### 広報へのメモ候補
（提出時に添えると差し戻しが減る事項）

### 著者が確認すること
（リポジトリ外の項目）
```

## 境界

- 公開可否は判断しない。最終判断は広報
- 記事・Google ドキュメント・note 下書きは変更しない
- 主張の正誤や、書かれていない話題の追加は提案しない
