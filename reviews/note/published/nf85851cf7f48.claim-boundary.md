## 指摘

### must-1: 「配布前のレビューゲートが存在しない」は一次情報と矛盾する

**該当**: 「ゲートを作ったのに、チームでは配線していなかった」節の末尾
**照合**: GitHub branch protection API（`required_approving_review_count: ◯`、`dismiss_stale_reviews: true`、`allow_force_pushes: false`）、社内の承認ポリシー
**問題**: GTA の main には PR レビュー◯名承認が必須で、変更種別ごとの承認要件も文書化されている。
「レビューゲートが存在しない」は事実として誤り。この一文の上に記事最大の決め台詞
「ゲートを作る道具を、ゲートなしで配っている」が乗っているため、主張の芯が誤情報で支えられている。
**提案**: 欠けているのは *マージ承認* ではなく *配布の制御*。次のように限定する。

> マージにはレビュー承認◯名が必要ですが、**承認された変更はマージと同時に全員へ配布されます**。
> 利用側がバージョンを固定して段階的に上げる経路も、問題が出たときに前のバージョンへ戻す経路もありません。

決め台詞も「ゲートなしで配っている」→「**段階配布とロールバックのない経路で配っている**」に置換する。

### must-2: 「バージョンを固定する仕組みがなく」は実装と不一致

**該当**: 同上
**照合**: 社内のプラグイン定義 = `version: ◯`、社内のバージョン更新スクリプト
**問題**: バージョン番号は付与され、bump スクリプトも運用されている。無いのは
「**利用側がバージョンを pin する手段**」（`marketplace.json` が `source: local` のパス参照であるため）。
**提案**: 「バージョンを固定する仕組みがなく」→「バージョン番号は付けていますが、**利用側がそれを固定して入れる経路がなく**」（1語の置換で足りる）

### must-3: 評価カバレッジの「実測」が現行の主指標ではなく Legacy 指標

**該当**: 「評価ケースは追いついていなかった」節、`◯/◯ = ◯%（記録） → ◯/◯ = ◯%（実測）`
**照合**: 社内の集計スクリプト（K1）の出力

```
K1 Review Coverage Rate (実行系): ◯/◯ = ◯%  [PASS]
K1 Legacy (静的代理指標):         ◯/◯ = ◯%  [BELOW TARGET]
Skills with canary fixtures: ◯ / ◯
```

**問題**: 記事が引いた ◯/◯ は、スクリプト自身が「Legacy（静的代理指標）」と明示している側。
現行の主指標は実行系 ◯/◯ = ◯% で **PASS**、canary フィクスチャは ◯/◯ = ◯% 揃っている
（K1 の実行系改訂は 2026-08-27 / 社内リポジトリの PR）。「追いついていなかった」という断定は、
不利な代理指標だけを選んだ結果になっている。
**提案**: 落ちを認めるなら、落ちている場所を正しく指す。

> 静的な代理指標では ◯/◯ = ◯%、実際に走らせる実行系では ◯/◯ = ◯% でした。
> フィクスチャ自体は全スキルに揃っている一方、**通っていないケースが◯件残っている**。
> 「◯%を維持できている」という手記録だけが、どちらの実測とも一致していませんでした。

これなら事実に沿ったまま、記事の論旨（記録と実測がずれていた）は保持できる。

### high-1: codex-first-guard の ◯回 は古いスナップショット

**該当**: 「ガードを強くしすぎて摩擦になった」節
**照合**: 社内台帳の項目（block ◯件 → v5 で ◯件を追加確認 / `CODEX_FIRST_OK` ask ◯件、最終確認 2026-07-30）
**問題**: ◯ は途中計測。台帳は以後 ◯件の追加ブロックを記録しており、現況は ◯件規模。
記事は ◯ を現在値として提示し、母数・基準日がない。
**提案**: 「ブロック記録が◯回」→「**2026-07 時点の集計で、ブロックが延べ◯件以上、例外を許可する操作が◯件以上**」。
数字を1つ直し、基準日を1語足すだけで済む。

### high-2: ◯件を「hookを配線していないこと」の証拠にしている

**該当**: 「ゲートを作ったのに、チームでは配線していなかった」節
**照合**: 社内台帳の項目（再発 ◯+）。台帳の根本原因欄は「**計画・意図の事前すり合わせ不足**」。hook 未配線への言及なし
**問題**: 台帳が記録している因果と、記事が付けた因果が違う。
記事は「機械的に止めていないから◯件起きた」と読めるが、台帳は「事前合意が足りないから起きた」と書いている。
一次情報を超えた帰属。
**提案**: 断定を接続に落とす。

> 改善バックログには、実行がユーザーの意図より先に進み、手動で止めて差し戻した記録が◯件以上あります
> （台帳上の根本原因は事前のすり合わせ不足として記録されているもので、hook 未配線が原因だと確かめたわけではありません）。
> ただ、機械的に止まっていれば手動介入は要らなかったはずのケースです。

### high-3: アンバサダー制が一次情報で確認できない

**該当**: 「2. リポジトリ別のアンバサダー制」節
**照合**: GTA の全 Markdown に「アンバサダー」の語なし。社内の担当一覧はレイヤー担当（Tech Lead / QA Champion / Scrum Master）と Skill担当（全件 "Growth Team"）のみ
**問題**: 記事は「置きました」と実施済みの制度として書いているが、GitHub 上に定義が無い。
記事の中核主張が「知識を個人の頭から出す」であるだけに、
**その体制自体が個人の頭にある**状態は自己矛盾に見える。
**提案**: どちらかを選ぶ。(a) 口頭運用なら「役割は決めていますが、**担当の明文化はまだ GTA に入れていません**」と1文足す。
(b) 記事公開前に 社内の担当一覧 にリポジトリ別担当の行を足して、事実を記事に合わせる。(b) のほうが記事の主張と整合する。

### medium-1: 分母 ◯ の出所を明示していない

**該当**: 計測節の ◯/◯、◯/◯
**照合**: 社内のスキル置き場A = ◯、社内のスキル置き場B = ◯（K1 実行系の分母）
**問題**: 同じ「スキル」で ◯ と ◯ の2系統があり、記事は ◯ 側だけを使っている。読者が再現できない。
**提案**: 初出で「（社内のスキル置き場A 配下の◯件）」と括弧1つ。

### medium-2: 数値に基準日がない

**該当**: 計測節全体
**問題**: 統計は 2026-08-18 集計、backlog は 2026-08 最終確認、K1/K2 は再実行値。
時点の違う数字が同じ段落に並んでいる。
**提案**: 節冒頭に「以下は 2026-08-18 集計のチーム統計と、2026-09-02 に再実行した計測値です」の1文。

### low-1: PRメトリクスの現況

**該当**: 「次に測るのは、利用量ではなく成果」節
**照合**: 社内のPRメトリクス置き場に 2026-07 の週次スナップショット◯本のみ。2026-08 分は未コミット
**問題**: 「動かし始めました」は正しいが、直近スナップショットが7月で止まっている。
**提案**: 「収集は7月の◯スナップショットまで。ここから継続させるのが直近の宿題です」を1文。
