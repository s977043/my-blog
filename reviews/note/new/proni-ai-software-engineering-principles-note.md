# PRONI公式版レビュー記録

対象: `articles_note/new/proni-ai-software-engineering-principles-note.md`

目的: 会社公式記事として、中心主張を変えずに、広報・技術編集・PdM・アジャイルコーチ・スクラムマスター・新規読者の6視点でレビューと改善を5ループ行う。

## Loop 1 — 会社公式としての主語・公開境界

### 広報
- 会社全体の標準と、一つの開発チームの実践が混ざって見える箇所がある。
- 「かなりうまく機能しています」は、定量根拠がない会社公式記事では強く見える。
- 個人記事由来の固有ツール名は、説明なしだと読者に不要な内部情報に見える。

### 技術編集
- 冒頭でSDD/TDD/DDDを同時に出すと、今回の焦点がぼやける。
- 記事の核は「DiscoveryとDeliveryで先に定義するものが違う」なので、早めに一本化したい。

### PdM
- Discoveryを「何を作る価値があるか」と表現すると、ややSolution起点に見える。
- 課題・価値仮説を確かめる活動であることを前面に出した方がよい。

### アジャイルコーチ
- デュアルトラックを独立した工程と誤読させないため、「考え方」として扱う表現がよい。

### スクラムマスター
- Scrumの標準プロセスのように見せないことが重要。
- チーム固有の実践であることを主語で明示したい。

### 新規読者
- 冒頭で用語が多い。
- 「この記事で何が分かるか」は伝わるが、SDD以外の用語が注意を散らす。

### 改善
- 冒頭を `PRONIの開発チームでは` に変更し、対象範囲を明確化。
- SDDに焦点を絞り、TDD/DDDは結論側へ移動。
- Discoveryを「どの課題や価値仮説を確かめるべきか」と再定義。
- `かなりうまく機能` を「実装前提を揃え、レビューしやすくするうえで役立つ」に変更。
- PlanGateの記述を会社公式版から外し、記事単体で成立させた。

## Loop 2 — Product Discovery / Outcomeの境界

### 広報
- PoC事例は会社の実践感が出ていて強い。公開範囲を明示している点もよい。
- ただし「AIは区別できない」と読める断定は避けたい。

### 技術編集
- 「価値仮説を要件として渡せば忠実に実装する」は意味は通るが、エージェント一般への強い断定に見える。

### PdM
- Acceptance Criteriaで実装完了を確認することと、価値仮説を検証することの違いが記事の核心。
- 「利用できるようにする」は実装条件として正しいが、それだけではOutcomeを検証できないことを明示したい。
- 「十分な根拠」が何を意味するか補足が必要。

### アジャイルコーチ
- 仮説検証は学習を目的にし、次の意思決定に必要な情報を得ることが重要。

### スクラムマスター
- Acceptance CriteriaとDefinition of Doneの区別は維持してよい。
- Acceptance CriteriaはScrum公式要素ではなくチーム実践として書けている。

### 新規読者
- 「学習条件」が何をするものか、一文で定義されると理解しやすい。

### 改善
- `AIが区別してくれない` ではなく `明示しなければ常に正しく区別してくれるとは限らない` に統一。
- `価値仮説を実装要件のように渡せば、その前提に沿って実装を進める` と表現を厳密化。
- 学習条件を「実装完成の判定ではなく、次の判断に必要な情報を得られるかを明らかにする条件」と定義。
- 「十分な根拠」は仮説の不確実性・リスク・次の実装コストに応じて判断すると補足。

## Loop 3 — Agile / Scrumの意味整合

### 広報
- 技術的な厳密さは会社記事の信頼性につながる。Scrum用語は公式用語との差を明確にしたい。

### 技術編集
- フロー図が一方向工程に見えやすいが、本文の往復説明で補えている。
- Discovery→Deliveryの矢印は「引き渡し」ではなく「判断」と表現した方がよい。

### PdM
- DiscoveryとDeliveryの境界は状態・不確実性の違いとして説明できている。
- 「根拠が十分ならDeliveryへ」より「Deliveryへ進む判断」の方がProduct Discoveryの実態に近い。

### アジャイルコーチ
- Contractを増やすことが目的ではなく、透明性・検査・適応を支える補助的な実践である点は良い。
- 「最初から完全な仕様を作らない」という一文は残すべき。

### スクラムマスター
- `作成物`、`Inspection`、`Adaptation` の位置づけは適切。
- PBIを固定要求にしない説明も維持したい。

### 新規読者
- Discovery / Deliveryが部署や工程の分割ではないことは十分伝わる。

### 改善
- `デュアルトラックに近い形` を `デュアルトラックに近い考え方` へ調整。
- `根拠が十分ならDeliveryへ進む` を `Deliveryへ進む判断` に統一。
- PBIの説明を口語的な「くらいの意味」から、記事内定義として明確化。
- 仕様・計画は往復しながら更新する説明を維持。

## Loop 4 — 技術的な最新性・読みやすさ

### 広報
- 外部プロジェクトの説明が古いと会社記事全体の信頼性を下げるため、一次情報との整合が重要。

### 技術編集
- Spec Kitの説明で `Specify → Plan → Tasks → Implement` だけを書くと、現在の `clarify` / `analyze` を含むワークフローと差が出る。
- ただし記事の主張に必要なのは「実装前にwhat/whyを外部化する」という骨格。

### PdM
- `assess` の存在を紹介することで「Discoveryを無視したSDD批判」ではないことが伝わる。

### アジャイルコーチ
- 外部フレームワークを正解として持ち込むのではなく、自分たちの実践との差分を説明できている。

### スクラムマスター
- Scrum Guideの説明とチーム固有の学習条件を混同していない。

### 新規読者
- Harnessが終盤で急に出てくるため、短い定義が欲しい。

### 改善
- Spec Kitの現行フローに `clarify` / `analyze` があることを明記しつつ、記事では骨格だけ説明。
- `assess` の `go / needs-clarification / kill` と、ソースコードを変更しない境界を維持。
- Harnessを「指示、コンテキスト、ツール、検証、権限、実行フローなど」と一文で定義。

## Loop 5 — 公開直前の会社記事レビュー

### 広報
- 会社公式として、宣伝ではなく現場の試行錯誤が中心になっているのが良い。
- PoCの固有情報を抽象化しつつ、失敗から学んだ構造は残せている。
- 個人noteへの依存を外したことで、会社記事単体で完結した。

### 技術編集
- タイトルと本文の主張が一致している。
- `間違った仮説を、高い品質で、速く実装する` が記事の記憶点として機能する。
- 同じ結論の反復はあるが、長文noteとして許容範囲。終盤で再度2点に収束している。

### PdM
- OutputとOutcomeの混同を、Acceptance CriteriaとLearning Conditionsの対比で説明できている。
- Discoveryを「何も決めない場所」にしていない点がよい。

### アジャイルコーチ
- Discovery / Deliveryを工程分割せず、往復可能な状態として扱っている。
- Contractを固定化ではなく、学習に応じて更新するものとして扱っている。

### スクラムマスター
- Product Goal / Sprint Goal / PBI / Definition of Doneとの関係を崩していない。
- 学習条件をScrum公式要素として誤認させない境界が明確。

### 新規読者
- 冒頭で記事のテーマが分かり、途中のPoC例で問題が具体化し、最後の2つの問いで持ち帰れる。
- Contract / Harnessは専門用語だが、記事内定義があるため追える。

### 最終改善
- 個人関連記事を参考欄から削除し、会社記事を自己完結させた。
- 冒頭の用語密度を下げた。
- 定量根拠のない成功表現を抑えた。
- Product Discoveryの表現をSolution起点からProblem / Hypothesis起点へ寄せた。
- 会社全体の標準ではなく、PRONIの開発チームの実践として語る範囲を維持した。
