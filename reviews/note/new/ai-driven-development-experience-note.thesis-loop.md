## 実施条件

最新の `main` にある `note-thesis-review-loop` と `note-article-review` を併用した。通常3ループの論旨レビューを、依頼に合わせて5ループへ拡張している。

各ループは次の順序で実施した。

1. 3つの異なるAIペルソナが独立にレビュー
2. 指摘を重要度とArticle Contractへの寄与で選別
3. 記事本文を改善
4. 編集に参加していない別のAIペルソナがThesis Gateを実施

ここに記録するペルソナの見解はAIによる模擬レビューであり、外部の専門家や実在読者による監修・調査結果ではない。

## 固定したArticle Contract

### Topic

PdM、PjM、テックリード、EM、スクラムマスターという5つの役割で得た経験が、AI駆動開発の判断とオーケストレーションにどう接続するか。その判断が欠けると、なぜAIに翻弄されるのか。

### Claim

AIは経験を不要にしていない。経験の価値は、コードを書くことから、AIの仕事を設計し、その結果を検証することへ前面化した。重要なのは肩書きではなく、目的、進行、技術、委譲、学習という判断機能を、個人・チーム・仕組みのどこかで担うことである。

### Audience

- メイン: AIエージェントを個人利用からチーム運用へ広げたいシニアエンジニア、EM
- サブ: AI時代に獲得すべき力を知りたい若手・中堅エンジニア

### Reader Promise

読者は、5つの役割と5つの判断機能の対応、判断が欠けたときの罠、AIへ仕事を渡す前後に使える5つの確認欄を理解できる。

### Emphasis

- もっともらしいAIの誤りと、それを成果として受け入れてしまう構造
- 5つの役割と5つの判断機能の対応
- AIを人間チームにたとえる場合の限界
- 必要なのは役職名ではなく、学習・分担・外部化できる判断機能であること
- 個人の暗黙知を、ゲート、テスト、ルール、チェックリストへ変えること

## ループ1: 論旨と因果関係

### レビューペルソナ

- Thesis Guardian: 主張の一貫性と競合する論旨を確認
- Logic Editor: 原因と結果のつながり、概念の分類を確認
- Skeptical Senior Engineer: 過度な一般化、AI比喩、技術的反論を確認

### 主な指摘

- 5つの役割が複数の分類語で説明され、記事の中心軸が揺れていた。
- 「経験が欠けるとAIに翻弄される」という因果が、経験者の直感に依存して見えた。
- AIをジュニアからミドル層の人間チームにたとえる範囲が広く、人間の能力や成長まで同一視する誤読があり得た。
- 未マージのプルリクエスト例が実体験なのか一般例なのか不明瞭だった。
- 「人間の判断が増えた」は、AI導入前との量的比較を断定していた。

### 適用した改善

- 分類を「目的、進行、技術、委譲、学習」に統一した。
- 判断基準の欠落、AIによる前提補完、もっともらしい出力の高速な蓄積、検証遅延、誤採用という因果を追加した。
- 見出しを「人間の判断が前面に出てきた」へ変更した。
- AIの速度に関する記述を、仕様が明確な変更や定型作業、大量変更を許可した場合へ限定した。
- プルリクエストの事例を、失敗を単純化した仮想例と明記した。
- 人間チームとの類似を、仕事の分解とレビューの構造に限定した。
- 責任主体、承認ゲート、経験の外部化を追加した。

| 競合する主張がない | 合格 |

| 結論が弱まっていない | 合格 |

## ループ2: 実務上の責任境界

### レビューペルソナ

- Coding Agent Practitioner: エージェント運用の現実性を確認
- Product Manager: 目的、成果、受け入れ条件の境界を確認
- Engineering Manager / CTO: 権限、責任、組織運用を確認

### 主な指摘

- 役割ごとの説明が、PdMやEMが単独で判断するように読める箇所があった。
- AIが実行主体になっても、判断と結果の責任を誰が持つのかが弱かった。
- 「外部から検証する」の外部が曖昧だった。
- どの状態ならAIだけで進めず、人間へ戻すかが明示されていなかった。
- 個人向けの5つの問いをチーム運用へ移す際の責任項目が不足していた。

### 適用した改善

- PdMは技術制約、非機能要件、検証方法をテックリードや開発チームと共同設計すると明記した。
- EMは技術境界をテックリード、認可・監査を基盤やセキュリティ担当者と分担すると明記した。
- スクラムマスターは改善を単独所有せず、チームで担当者と完了条件を決めると明記した。
- AIは実行できても、判断と結果の責任は人間が持つと明記した。
- 外部検証を、テスト結果、実際のリポジトリ状態、人間または別経路のレビューとして具体化した。
- 現在状態を確認できない、計画やスコープが変わった、必要な検証を実行できない場合を停止条件にした。
- チーム用タスクに、判断担当者、承認者、必要な証拠、停止時の連絡先を追加した。
- タスクの受け入れ条件と、提供後に観測する成果を分けた。

## ループ3: note上の密度と読みやすさ

### レビューペルソナ

- note Editor: 構成、重複、モバイルでの可読性を確認
- First-time Reader: 略語、初出用語、理解の引っかかりを確認
- Thesis Guardian: 削減後も主張が維持されるかを確認

### 主な指摘

- 5つの失敗と対策、冒頭の質問、最後の確認欄に重複があった。
- 後半に同じ趣旨の説明が集中し、主張の強さに対して文章量が多かった。
- 受け入れ条件、非機能要件など、初見読者には補足が必要な用語があった。
- 終盤に新しい概念語を出すと、まとめへ向かう流れを弱める可能性があった。

### 適用した改善

- 5つの失敗は失敗内容だけに絞り、対策は最後の5つの確認欄へ集約した。
- 冒頭にあった別の質問リストを削除した。
- 役割説明前の総論と、終盤の「肩書きではない」という重複を削った。
- 長い段落を分け、運用説明を圧縮した。
- 「完成とみなす条件（受け入れ条件）」「性能やセキュリティなどの非機能要件」と初出で説明した。
- まとめ直前に出ていた新しい専門語を削除した。
- まとめを「設計する力」だけでなく「結果を検証する力」まで含む表現にした。

## ループ4: 独自性、包摂性、組織学習

### レビューペルソナ

- Content Portfolio Editor: リポジトリ内の関連記事との差別化を確認
- Early / Mid-career Engineer: 役職経験のない読者への包摂性を確認
- Organizational Enablement Lead: 個人技から組織能力への変換を確認

### 主な指摘

- 一般的なAI開発論と重なる説明が長く、5つの役割という独自の切り口へ入るまでに時間がかかった。
- 役職経験がなくても判断機能を学べるという説明を、より早い位置へ置く必要があった。
- 見出しに「経験が欠ける」とあると、経歴が不足している読者を指しているように見えた。
- 実践部分が抽象的で、チームのタスク設計へ転用する意図を強められた。

### 適用した改善

- 導入で、AI駆動開発の仕組みそのものではなく、5役割の判断がどこで再利用されるかを扱う記事だと限定した。
- 一般的な失敗説明を圧縮し、5役割の経験へ早く到達する構成にした。
- 役職に就かなくても、課題確認、受け入れ条件、レビュー、振り返りから判断を学べる説明を、役割説明の前へ移した。
- 見出しを「経験から得た判断が欠けると」から「判断機能が欠けると」へ変更した。
- 実践見出しを「5つの役割で得た判断を、タスクの5つの確認欄へ変える」とし、チームで再利用する目的を明確にした。
- 関連記事との差を、5役割から5判断、さらに5確認欄へ変換する個人のキャリア回顧として維持した。

### 採用しなかった提案

- 新しい「4段階の組織学習フレーム」を加える提案は、5つの判断というArticle Contractと競合するため採用しなかった。
- 人間チームの比喩を完全に削る提案は、原案の重要な記憶点を失うため採用せず、比喩の適用範囲を限定した。

## 改善後に聞いた各ペルソナの感想

### ループ1のペルソナ

**Thesis Guardian**

「肩書きの価値」ではなく「判断機能の再利用」へ主張が絞られ、導入から5項目、まとめまで軸が一貫した。AIを人間のチームにたとえる範囲も限定され、誤解への備えが増えた。仮想例が一例に集中する点は留保として残る。「AIは経験を消したのではない。実装の中に隠れていた経験の中身を、表に出した」という一節が残った。

**Logic Editor**

ツール実行、ワークフロー、本来の目的という三層の成功定義が加わり、「もっともらしい誤り」から判断機能の必要性までの因果が明快になった。後半に同趣旨の反復がわずかに残るが、読後には、AI活用とは出力速度ではなく、目的、進行、技術、委譲、学習を閉じる設計だという理解が残る。

**Skeptical Senior Engineer**

比喩の限界、権限境界、停止条件、外部検証まで明示され、「経験者なら見抜ける」という精神論から実務的な安全設計へ改善された。個人体験の記事として筋は通るが、効果を示す実測や複数事例がない点は留保する。「操作できたことと、目的を達成したことは同じではない」が最も現場に残る。

### ループ2のペルソナ

**Coding Agent Practitioner**

人間チームとの比喩の限界と、ツール実行、ワークフロー、目的の三層が明示され、エージェント運用の実感に近づいた。5つの確認欄を使った実例がもう一つあるとさらによい。次のタスクテンプレートには5項目と停止条件を組み込みたい。

**Product Manager**

冒頭で「肩書きではなく判断機能」と先に限定したことで、経験者だけを持ち上げる記事ではなく、学び方を示す記事になった。成果指標と受け入れ条件の違いをさらに例示できる余地はある。AIに渡す案件へ「誰の課題か、対象外、提供後の観測」を追加したくなった。

**Engineering Manager / CTO**

権限委譲を認可、停止、復旧、追跡まで具体化し、個人の勘を組織の仕組みに変える主張が明瞭になった。導入規模別の責任分界までは扱っていない。AI利用の承認ゲートと証跡、エスカレーション先を棚卸しし、チーム標準に落としたい。

### ループ3のペルソナ

**note Editor**

導入で結論と射程が先に示され、5役割が5判断へ収束するため現在地を見失わない。仮想例と確認欄で抽象論が実務へ着地した。公開時に見出し一覧が長く見える可能性はあるが、「経験を判断機能として外部化する」という主張が残る。

**First-time Reader**

人間チームの比喩について、似ている範囲と違いが明記され、誤解せずに読めた。未マージのプルリクエストという仮想例で、操作成功と目的達成の違いを理解できた。冒頭の略語は少し多いが、AIへ任せる前の5つの判断を覚えられる。

**Thesis Guardian（ループ3）**

主張が「5役職経験者だけが有利」から「肩書きではなく判断機能」へ精密化された。経験の価値を語りつつ排他的ではなく、「経験があっても安全ではない」という反証も回収している。AIは経験を消さず、暗黙の判断を可視化・仕組み化するという核が残る。

### ループ4のペルソナ

**Content Portfolio Editor**

5つの判断と具体的な失敗例によって、一般的なAI活用論との差別化が鮮明になった。「肩書きではない」という限定で包摂性が生まれ、確認欄で組織導入につながる。関連記事との役割分担を公開文で一言示す余地はあるが、シリーズの中核記事として配置できる。

**Early / Mid-career Engineer**

「役職経験がなければ使えない」という圧がなく、自分も判断機能を一つずつ学べると感じた。失敗例と確認欄が独自性と実務性を高め、組織で使う場面も想像できる。次のAIタスクで5項目を書き出してみたい。

**Organizational Enablement Lead**

個人の熟練談から、判断機能を役割、ゲート、証拠、停止条件へ外部化する組織設計論に進化した。経験年数に依存せず導入対象を広げられ、類似記事との差別化も明確である。実運用上の責任者や例外時の連絡経路は別途詰める必要があるが、5項目をタスクテンプレートへ試験導入したい。

### ループ5のペルソナ

**note Director**

公開品質は十分である。導入で問題意識を示し、5つの役割から5つの確認欄へ明快に進む。事実の境界も「私の経験」「比喩の範囲」「仮想例」と明示された。公開時も仮想例の表記を維持したい。読後には、自分の暗黙知を確認欄へ変えたくなる。

**Claim Boundary Reviewer**

主張と根拠の距離は適切である。人間比喩の範囲、役割責任、「嘘」の意味を限定し、観察、仮想例、一般論を混同していない。仮想例の表記を維持する限り公開できる。AIの完了報告ではなく、外部状態で検証する姿勢が残る。

**Main Target Reader**

公開品質は十分である。AIによって実装は速くなる一方、レビューが追いつきにくいという実感に重なった。肩書きではなく判断機能として書かれているため排他的でもない。次のAIタスクに、目的、進行、技術、委譲、学習の5つの欄を作りたい。

## 最終判定

5回のThesis Gateはすべて合格し、公開を妨げる未解決指摘はない。記事の中心は最後まで、5つの役割から得た経験を、AIの仕事を設計・検証する5つの判断機能へ変換することに置かれている。
