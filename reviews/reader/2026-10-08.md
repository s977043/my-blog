## 1. AIエージェントの『進めて』問題：自走と確認の境界をmemoryで永続化する

- URL: https://zenn.dev/minewo/articles/ai-agent-autonomy-boundary-with-memory
- 原稿: `articles/ai-agent-autonomy-boundary-with-memory.md`
- 本文: live（Zenn API `api/articles` の body_html）/ 3,194 文字
- ペルソナ: Z1 実装担当のエンジニア。タイトルが「memoryで永続化する」という手段を約束しているので、「Claude Code memory 設定」のような検索で来て、書き方と置き場所を探す読者がいちばん多いと考えた

### 読むのをやめそうな箇所

- **「memory で永続化する」の「Claude Code には、conversation（セッション）を跨いで維持される memory 機能……」**: memory ファイルをどこに置くのか、どう作るのか（パス、作成コマンド、自動で読み込まれるか）が書かれていない。サンプルは frontmatter つきの本文だけである。手元で試したい Z1 は「再現できるか判断できない」状態になり、ここで記事を離れて公式ドキュメントを探しに行く可能性が高い。記事の中心となる答えなので、離脱の影響が最も大きい
- **「「進めて」を自走合図として扱う記法」の具体例**: ルールは「確認なしで実行する」なのに、例のエージェント発話が「どれから進めますか？」で終わっている。さらに「人間確認必須」の節には「PR の作成（`gh pr create`）と マージ」とあるが、例の計画には「3. コミット + PR 作成」が入っていて「1 から順に実行（確認なし）」になっている。境界の一覧と例が噛み合わず、線引きのどちらを信じればよいか分からなくなる
- 冒頭の前提: 対象のツールとバージョン、memory 機能の前提環境が冒頭に書かれていない。Codex 利用者には自分が対象かどうか判断しにくい

### 分かりにくい用語

- 「memory 機能」（冒頭）: 括弧で補足はあるが、保存先と読み込みのタイミングの説明がない
- frontmatter の `type: feedback`（memory の例）: ほかにどんな type があるか、type で挙動が変わるかの説明がない
- 「edge case」（memory 例の直後）・「reversible」（自走 OK の節）: 英語のまま出てくる
- `AGENTS.md` / `CLAUDE.md`（補足の節）: 「2 層構成」と書かれているが、各ファイルがどのツールに読まれるかの前提は説明がない

### 導線

- 冒頭 3 段落: 「この記事で得られること」と「はじめに」のループ例で、何の問題を扱う記事かはすぐ分かる。対象の環境とバージョンは書かれていない
- 読後: 「まとめ」に要点は並んでいるが、次に読むもの（memory 機能の公式ドキュメントや関連記事）へのリンクがない。試す手順もないので、読後に「手元で試せる」状態にならない
- コードブロック: 原稿で確かめると、言語指定があるのは冒頭のループ例（text）と memory 例・AGENTS.md 例（markdown）の 3 つで、計画の具体例と報告例の 2 つには言語指定がない

| P1     | 「memory で永続化する」のサンプルの直前 | 置き場所と読み込まれ方を 1〜2 行で示す（例:「このファイルを `<memory ディレクトリ>/feedback_proceed_signal.md` に置くと、次のセッションから読み込まれる」）。前提にしたバージョンも添える | タイトルが約束する「永続化」の手順が見つからないと、Z1 はここで離脱する |

## 4. AIレビューの指摘が多すぎて読まれないとき、どこで絞り、どこから読むか

- 冒頭の第1段落「自分で作っているAIレビューのRiver Reviewを」: 最初の一文から自作の製品名が出てくるので、I1 の「冒頭から製品紹介に見えるとき」に当たるおそれがある。続く第2段落「読まれない指摘は、0件と同じ結果になります」で課題が言葉になるので、読むのをやめる可能性は中程度
- 第1章「ここで区別したいのが、「根拠の置き場所」と「問題の所在」です。」の段落: 抽象的な区別を説明する文が具体例なしに続き、I1 の「課題が自分のものか分からないまま仕組みの説明が続く」に当たる。スマホでは 1 段落でおよそ 8〜10 行になる見込み（推定）
- 第4章「自分でも踏みました。」の段落: 抑制の不具合と、直した後の逆の不具合が 1 段落に詰まっていて、River Review の内部経緯として読まれやすい。読むのをやめるほどではない

### 分かりにくい用語

- 「River Review」（第1段落）: 何をするツールなのか、OSS なのかが冒頭で説明されない。リポジトリへのリンクは末尾にしか無い
- 「観点」「観点で宣言した上限」（第1章の箇条書き）: River Review の内部の概念で、説明が無い
- 「工程（設計・実装・テスト）」（第1章の箇条書き）: 括弧で補っているが、「観点の宣言」と照らし合わせる仕組みは読み取りにくい
- 「合意度」「複数のレビュアー」（第2章）: AI レビュアーが複数並んで動く前提が書かれていない
- 「resolve」（第4章の冒頭）・「Experimental」（第4章）: 説明なしで英語のまま出てくる
- 「採用率」「GO_WITH_OBSERVATION」などの信号: 本文・表で説明されており問題なし

### 導線

- 冒頭 3 段落: 第2段落で課題、第3段落で測り方、第4段落で記事の構成が示されるので、何の記事かは冒頭で分かる。River Review が何で、読者がそれを試す対象なのかは冒頭で分からない
- 読後: 各章の「持ち帰る問い」と、まとめの「着手は手間の小さい順」で、試す行動ははっきりしている。各章に「既製ツールを使う場合」もあり、River Review を使わない読者も置いていかない。River Review を試す入口は参考リンクの 1 行だけ
