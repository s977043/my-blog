## 1. 推測で書いた学びが次の罠になった — AGENT_LEARNINGS.md の運用設計

- URL: https://zenn.dev/minewo/articles/agent-learnings-md-operation
- 原稿: `articles/agent-learnings-md-operation.md`
- 本文: live（zenn api/articles body_html）/ 3191 文字
- ペルソナ: Z2 設計判断を比べるテックリード（記事の中心が「訂正をどう残すか」の選択肢比較と、チームで回す運用ルールの設計にあり、手順を探しに来る Z1 より採否を決める Z2 の関心に近いため）

### 読むのをやめそうな箇所

- **「## 前段: 推測ベースで学びを断定した」の書き出し「あるセッションで、WXR（WordPress エクスポート形式）の著者フィールドについて」**: 直前の「はじめに」は AGENT_LEARNINGS.md の運用の話だったのに、何を作っていた場面なのか説明がないまま WXR と note の話に入る。続く「## 次セッション」の「同じスクリプトを別の記事で実行したところ、note 側で」の「同じスクリプト」も、それより前に出てこない。Z2 は「採用理由が書かれず、手順だけが並ぶとき」に読むのをやめる。note 連携をしていない読者には自分と関係のない事例に見えて、ここで見切る恐れがある
- **「## 追記時のセルフチェック 5 項目」の「追記する前に、以下を自問します。」**: 自問するのが人間か AI エージェントか、どの時点で誰が確認するのかが書かれていない。チェックを担う人が分からないと導入の見積もりができず、判断材料が足りないと感じやすい

### 分かりにくい用語

- `<dc:creator>` / `author_login` / `<wp:author_display_name>`: 「## 前段」が初出で説明がない。比較表を読まないと「著者を表すフィールドが 2 つある」ことが分からない
- note: 「## 次セッション」の「note 側で」が初出。ブログサービスで、取り込みに WXR を使うという関係が本文に書かれていない
- 前段 / 後段 / 次セッション: 見出しは「前段:」と「次セッション:」なのに、訂正例のコードブロックでは「2026-04-18 前段」「2026-04-18 後段」になっている。同じ出来事を指しているか、読み手がつなぎ合わせる必要がある
- lessons-learned、ElementTree: 説明はないが、一般的な語・例の中の語なので影響は小さい

### 導線

- 冒頭: 「この記事で得られること」の 3 項目と「はじめに」の 3 段落で、何の記事か分かる。目次の箇条書きもあり、見出しを拾うだけで流れを追える
- 判断材料: 「## 訂正の残し方」で、削除する案と並べて書く案の欠点を示してから、採用した方法（打ち消し線と訂正エントリ）を出している。Z2 が求める「選ばなかった理由」に応えている
- 読後: 「## エントリ形式のテンプレート」はそのまま使える形。末尾の「### 関連記事」に 2 本が、アンカーテキストで主題が分かる形で置かれている

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 「## 前段」の書き出し | 何を作っていた場面かを 1 文足す。例:「note へ記事を取り込むファイル（WXR、WordPress エクスポート形式）を生成するスクリプトを書いていたセッションで、著者フィールドについて……」 | 「同じスクリプト」が何を指すか分からないまま事例に入り、note を使っていない読者は自分に関係のない話と受け取って離脱しやすい |
| P2 | 「はじめに」の目次、各見出し、訂正例のコードブロック | 「前段 / 後段 / 次セッション」の呼び方をそろえる。例: 見出しを「## 最初のセッション: ……」「## 次のセッション: ……」にして、コード内のエントリ名と対応が分かる一言を添える | 同じ出来事に 3 通りの呼び方があり、訂正例が本文のどの場面にあたるかを読み手が照合しなければならない |
| P2 | 「## 追記時のセルフチェック 5 項目」の「以下を自問します」 | 誰がいつ確認するかを 1 行で書く。例:「エージェントが追記するときも、人間がレビューするときも、次の 5 項目を確認します」（実態に合わせる） | チェックを担う人が分からないと、自チームへ入れるときの運用コストを見積もれない |
| P2 | 比較表の直前 | 2 つのフィールドの役割を一言添える。例:「著者を表すフィールドは `<dc:creator>` と `<wp:author_display_name>` の 2 つあり、どちらに何を入れるかが逆でした」 | 「完全に逆」の驚きは、フィールドの意味が分かって初めて伝わる |
| P3 | 訂正例・根拠欄・テンプレートのコードブロック | 長い行（「~~`<dc:creator>` には author_login を入れる~~ **← 2026-04-18 後段で訂正**」など）を短くする | 60 字を超える行があり、スマホで横スクロールになると推定される |

- スマホでの長さは実画面で見ておらず、段落の文字数とコード行幅からの推定。段落はおおむね 1〜3 文と短い
- 比較表とコードブロックの言語指定は、取得した本文（body_html の変換結果）では区切り行・言語指定が見えなかった。変換で落ちた可能性があり、公開ページの表示は確かめていない
- 関連記事 2 本のリンク先が開くかは確かめていない

## 2. 仕様を揃えて止めない：マルチエージェント開発の3原則（SDD・TDD・ノンブロッキング）

- URL: https://qiita.com/s977043/items/05934596111b9065465d
- 原稿: `Qiita/public/sdd-tdd-nonblocking-agent.md`
- 本文: live（qiita api/v2/items body (markdown)）/ 6572 文字
- ペルソナ: Q1 症状から検索してきた実務者（Qiita のペルソナは Q1 だけ。はじめにが「CI が通らない」「解釈が違う」という症状から入っており、Q1 の読み方と合うため）

### 読むのをやめそうな箇所

- **「3原則を支えるツール：Serena MCP」の「ここで紹介するのが **Serena MCP** です。」から始まる節**: 「Serena を導入することで、今回紹介した 3 原則がより確実に機能するようになります」とあるが、本文にはリンクも導入手順も無い。Q1 は「コピーして試せる手順・設定を持ち帰れる」ことを求めて読みに来るので、試したくなった時点で次の一手が見つからず、ここで離脱しやすい
- **「実際の開発フロー」の sequenceDiagram**: 参加者が 6 つ（人間＋エージェント A〜E）並ぶ横長の図。スマホでは横に縮むか、横スクロールになると推定する（実画面では見ていない）。直後の「ログ例」も同じ流れをなぞっているので、図で止まった読者は先に進まないかもしれない
- 冒頭の TL;DR とはじめにで結論も症状も早めに分かるため、序盤での離脱要因は小さい

### 分かりにくい用語

- **SDD / TDD**: タイトルと TL;DR に略語だけで出てくる。正式名は「原則 1: SDD（仕様駆動開発）」「原則 2: TDD（テスト駆動開発）」の見出しで初めて示される
- **MCP / MCP サーバ**: 「Serena は、オープンソースの MCP サーバで」が初出で、説明が無い（同じ文の LSP には正式名が添えてある）
- **ブロッキング / ブロック要素**: はじめにの「つい人間がブロッキングしてしまいます」が初出。意味は「人間がブロッキングしてしまう」節を読むまで分からない
- **インターフェーステスト と 契約テスト**: 「テストの種類」では「**インターフェーステスト**」、例の見出しは「契約テスト例：contract.clock.md」。同じものを指すのかどうか判断できない
- **OpenAPI**: 「SDD 実装例：OpenAPI 仕様書」で説明なしに出てくる（Q1 には既知のことが多いので軽微）

### 導線

- **冒頭**: TL;DR で対象・課題・アプローチ・結果が 4 行にまとまり、はじめにの箇条書きが症状を具体的に示している。冒頭 3 段落で何の記事かは分かる
- **コピペできる素材**: `requirements.md`、`acceptance.alarm.md`、`contract.clock.md` の例はテンプレートとして持ち帰れる。ただし時刻の書き方が例ごとに違う（`requirements.md` は「07:00」、OpenAPI は `pattern` が HH:MM:SS で `example: "07:00:00"`）。仕様を揃えることが主題の記事なので、写して使う読者はどちらに合わせればよいか迷う
- **読後**: 「実際に試してみてほしいこと」は一般的な行動に留まる。具体的な次の一歩は末尾の「参考・関連」が担っている。本文で導入を勧めている Serena MCP へのリンクは、記事のどこにも無い

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 「3原則を支えるツール：Serena MCP」節 | 公式リポジトリへのリンクを 1 行置き、導入手順を書かないならその旨を明記する。例: 「導入手順は [Serena の README](…) を参照」 | 「導入することで…機能する」と勧めながら入口が無く、試そうとした Q1 が行き止まりになる |
| P2 | 「requirements.md」と「OpenAPI 仕様書」の例 | 時刻表記を片方にそろえる。例: requirements.md を「アラーム時刻 = 07:00:00（HH:MM:SS、ユーザー指定可能）」にする | 「仕様を揃える」例のあいだで表記が食い違っており、テンプレートとして写すと迷う |
| P2 | 「テストの種類」と「契約テスト例」 | 用語を一つに統一する。例: 「**インターフェーステスト（契約テスト）**」 | 同じものか別物か判断できない |
| P2 | 「エージェント間のやり取りフロー」の sequenceDiagram | 参加者を減らすか、図の前に「同じ流れを下のログ例でも示す」と一言添える | スマホでは横長の図が読みにくいと推定する。直後のログ例で内容は追える |

## 3. AIにコードを書かせる前に、人間が承認する場所を作る

- URL: https://note.com/mine_unilabo/n/n02992266d622
- 原稿: `articles_note/published/n02992266d622.md`
- 本文: live（note api/v3/notes data.body）/ 4452 文字
- ペルソナ: N1 開発チームを預かる EM・PM（主題が「チーム開発で人間がどこで判断・承認するか」という意思決定の設計で、ツール操作より判断の理由を求める読者に近いため）

### 読むのをやめそうな箇所

1. **「## プロンプトだけでは足りない」の 4 段落目**（「そのため、執筆時点（2026年5月）のPlanGate v8.6.0 では、HookやCLIで検査するだけでなく、Metrics v1 と Issue governance で……」）。判断の話から、急にバージョン番号と機能名が並ぶ段落に変わる。N1 の「ツールの操作説明が続き、判断の話が出てこないとき」に当たる。続く「最初はwarningで十分です。このバージョンでは、そこで見えた境界越えを metricsとbaseline で振り返りやすくしています。」も説明のない英語の名詞が続く。前後の段落は N1 向けの判断の話なので、間の 2 段落だけが浮いている
2. **冒頭のリードと「## この記事で書きたいこと」**。リードで結論を一度出したあとに、「この記事で書きたいこと」が同じ問いを列挙し、さらに前置きが続く。最初の具体的な場面（「## AIは親切にスコープを広げる」）までが長いと感じたら、N1 の「前置きが長く結論が見えないとき」に当たる。1 段落ずつは短いので、離脱リスクは中程度
3. 上記以外は「なし」。「## 実際に何が変わるのか」「## 承認はブレーキではなく、合意点」は実装前と実装後の問いを対で示していて、N1 が求める判断の材料になっている

### 分かりにくい用語

| 用語 | 初出の位置 | 補足 |
| --- | --- | --- |
| PlanGate | リード「そのために作っているのが PlanGate です。」 | ツールなのか手順なのか（OSS であること）は「## OSSとして公開する理由」まで出てこない |
| Hook / CLI | 「## この記事で書きたいこと」の本文 | 説明なし |
| Metrics v1 / Issue governance | 「## プロンプトだけでは足りない」4 段落目 | 説明なし。固有の機能名に見える |
| warning / metrics / baseline | 同節「最初はwarningで十分です。」の段落 | 説明なし |
| 後方互換 | 「## AIは親切にスコープを広げる」 | N1 なら通じる範囲 |
| plan → approve → exec | 「## 興味があれば」 | 本文の「計画→承認→実装」と同じ流れだと明示されていない |

### 導線

- **冒頭 3 段落で何の記事か分かるか**: 一部だけ分かる。冒頭 3 段落は自己紹介と開発速度の話で、テーマがはっきりするのは 5 段落目の「「AIにどこまで書かせてよいか」のほうが気になっています」以降。タイトルがテーマを言い切っているので、タイトルから来た読者は補える
- **読後に試すもの**: ある。「## まずは一つのタスクからでいい」のプロンプト例と「その計画を人間が読む。納得できたら、実装に進める。」は、N1 が自チームで試す 1 つの行動として持ち帰れる。説明に使える言葉も「承認はブレーキではなく、合意点」として本文にある
- **次に読むもの**: ある。「## 参考」と「## 関連記事」。ただし本文の「技術的な説明はZenn向けの記事に寄せる」がどの記事かは示されていない
- **スマホでの長さ（推定。実画面は見ていない）**: 段落は短く、表はない。気になるのは箇条書き 3 か所（「## この記事で書きたいこと」の 1 項目、「## 実際に何が変わるのか」の 2 項目）で、複数の問いが 1 項目に入った 80〜100 字程度の塊になっている
- **図**: 図 3 点に alt がない。キャプションに「lanGate基本フロー図」（P が欠けている）、「なぜ「AIコードを書かせる前に承認が必要」なのか」（「に」が欠けているように読める）がある

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 「## プロンプトだけでは足りない」4 段落目と「最初はwarningで十分です。」の段落 | バージョン名と機能名を判断の言葉に置き換える。例:「そこで、プロンプトでお願いするだけでなく、仕組みとして検査し、あとから運用を振り返れるようにしています（執筆時点の2026年5月、PlanGate v8.6.0）。」「最初は止めずに警告を出すだけで十分です。どこで境界を越えそうになったかを、あとからまとめて振り返れれば足ります。」 | N1 が読むのをやめる条件（ツールの説明が続く）に直接当たる。前後の段落は判断の話なので、ここだけ言い換えれば節全体の流れが保てる |
| P1 | 「## 実際に何が変わるのか」の箇条書き 2 か所 | 1 項目に詰まった問いを分ける。例:「- この計画で進めてよいか」「- 今回やらないことは明確か」「- テスト観点は判断できる粒度か」「- リスクは人間が見られる形になっているか」 | 実装前と実装後の問いの対比が記事の要点なのに、スマホでは区切りのない長い 1 文に見えると推定される |
| P2 | 「## この記事で書きたいこと」の箇条書き | 4 つの「なぜ」を 1 項目ずつに分けるか、節ごと短くしてリードに統合する | 前置きが長く見える原因になっている |
| P2 | リード「そのために作っているのが PlanGate です。」 | PlanGate の形を一言添える。例:「そのために作っているのが、AIエージェント向けの開発フローを定めたOSS（オープンソースソフトウェア）、PlanGate です。」 | 何なのかが分からないまま読み進めることになる |
| P2 | 図のキャプション | 「lanGate基本フロー図」を「PlanGate基本フロー図」に、「AIコードを書かせる前に」を「AIにコードを書かせる前に」に直す。図 3 点に alt を付ける | 誤字は信頼感に影響する。alt がないと、画像が表示されない環境で図の意味が伝わらない |
| P3 | 「## 興味があれば」の「plan → approve → exec」 | 本文の言葉と対応させる。例:「READMEの plan → approve → exec（計画 → 承認 → 実装）の流れだけ見てもらえれば十分です。」 | 英語の 3 語が、本文の流れと同じものだとすぐに結びつく |

- 箇条書きが note の実画面でどう表示されるか（行数は推定）

## 4. AIレビューを開発フローにどう組み込む？任せる範囲と責任者の決め方

- URL: https://izanami.dev/post/a168c992-159d-4b2c-9e7c-32ea98080174
- 原稿: `articles_izanami/ai-review-responsibility.md`
- 本文: live（izanami page html `.markdown-post`）/ 3105 文字
- ペルソナ: I1 自分のプロダクトやチームに使えるものを探す個人開発者（izanami のペルソナは I1 のみ。主題の「AIコードレビューの取り入れ方」が I1 の関心と一致する）

### 読むのをやめそうな箇所

- **「## 指摘を返す責務と、止める責務を分ける」の 3 段落目（「指摘は開発者が修正要否を考える材料、実行状態は……」）**: 1 段落に「Review Coverage」「予定したレビュー単位」「修正ループを終えられる」という信号、「実行記録そのものがない場合は、この変更の対象外」が詰め込まれている。7 文あり、本文で最も長い段落。I1 は「課題が自分のものか分からないまま仕組みの説明が続くとき」にやめる。課題の話から River Review 内部の仕様説明へ移るので、離脱しやすい。「この変更の対象外」の「この変更」が何を指すかも本文からは読み取れない
- それ以外の区間は、冒頭の結論、表、段階別の箇条書きと続き、課題起点で読み進められる

### 分かりにくい用語

| 用語 | 初出の位置 | 補足 |
| --- | --- | --- |
| 呼び出し側（のワークフロー） | 冒頭 3 段落目「呼び出し側のワークフローや人が担います」 | 何がレビューを「呼び出す」のか（CI、エージェントの実行基盤など）の説明がない。全体で 8 回近く出てくる中心語 |
| River Review | 「## 指摘を返す責務と、止める責務を分ける」2 段落目 | 説明なしで固有名として出てくる。OSS だと分かるのは末尾のリンクからだけ |
| GO / NO-GO | 同上 | 略語の説明なし |
| Review Coverage | 同 3 段落目「実験段階のReview Coverage」 | 機能名なのか概念名なのか判別しにくい |
| `approve` / `no findings` | 同 1 段落目 | どのツールの出力値かが書かれていない |
| 監督境界 | 同 2 段落目 | 一般的な語ではなく、説明がない |
| リスク受容 / 例外承認 | 表の 4 行目、4 つのことの 3 番目 | 個人開発者には馴染みが薄い可能性がある |

### 導線

- **冒頭 3 段落**: 1 段落目の太字で結論、2 段落目で課題（「未完了のレビューを完了扱いして、誰も確認しないまま次へ進む」）が示されていて、何の記事かは分かる。製品紹介から始まらない
- **製品への言及と課題の結びつき**: River Review は「レビュー実行の記録とループ制御を分ける実装例」として位置づけられ、直後に「見落としゼロや変更の安全性を証明しません」と限界も書かれている。ただし River Review が何か（OSS か、どう試すか）は本文中に一言もない
- **読後の行動**: 「## AIレビューをチームの工程にする」で「一つのリポジトリかPR種別を選び」と最初の一歩が示されている。末尾にリンクがあるが、試す場合にどれから開くとよいかの案内はない

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 「## 指摘を返す責務と、止める責務を分ける」3 段落目 | 「材料の区別」（前半 2 文）と「River Review の Review Coverage の挙動」（後半）で段落を分ける。「この変更の対象外」の指示対象を明示する。例: 「River Reviewでは、実験段階の機能『Review Coverage』が……」 | スマホでは 1 画面を超える推定の段落で、課題の話から内部仕様の話へ切り替わる地点。I1 の離脱条件に当たる |
| P2 | River Review の初出（同見出し 2 段落目） | 初出で一言説明を添える。例: 「筆者が開発しているOSSのAIレビューツールRiver Reviewは、……」 | 何者か分からない固有名が主語になると、製品紹介なのか例示なのかを読者が判断できない |
| P2 | 冒頭 3 段落目の「呼び出し側」 | 初出で例を添える。例: 「AIレビューを起動する側（CIやエージェントの実行ワークフローなど）」 | 記事の中心語なのに指すものが曖昧 |
| P3 | 「参考・関連リンク」 | 試す人向けの入口を 1 つ示す。例: 「試すならリポジトリの README から」 | I1 は「試す場合の入口」を探している |
| P3 | `GO / NO-GO`・「監督境界」 | 平易な言い換えに置き換える。例: 「先へ進めるか止めるかの判断」 | 略語や造語に近い語で、説明なしでは読む速度が落ちる |

## 5. AIエージェントの並列運用、PRリードタイムだけでは在庫の増加が見えない

- URL: https://zenn.dev/minewo/articles/agent-utilization-vs-flow-efficiency
- 原稿: `articles/agent-utilization-vs-flow-efficiency.md`
- 本文: live（zenn api/articles body_html）/ 10289 文字

### 読むのをやめそうな箇所

- **「なぜ気づけなかったのか」の「PR のリードタイムは、開発生産性の文脈で〜」以降**: 「そこは実際に改善していました。1.2分でマージできている。数字は良くなっている」と書かれている。一方「限界と、測れていないこと」には「**PR工程が『速くなった』とは言えません**」「比較のベースラインがありません」とある。Z2 は判断の理由と適用範囲・限界を突き合わせながら読むので、この食い違いに気づくと根拠の読み方が定まらず、手が止まる。TL;DR などは「読める」と書いているので矛盾しない。言い切っているのは本文の 1 か所だけ
- **「10.5時間、着手宣言だけを返したエージェント」の冒頭「在庫の話とは別に」**: 在庫の論証がここで一度切れ、節の後半に留保が続く。この話を自チームの採否判断にどう使うかが節の中で示されないため、読み飛ばすか、ここで離れる地点になりうる
- **TL;DR の最終項と記事末尾の対応**: TL;DR では「エージェントを待たせるのは無駄ではなく、WIP を制限するという設計判断です」を対策として挙げているが、本文でこれに当たるのは「自分のリポジトリを測る」末尾の 1 段落だけ。最後まで読んで「対策は測定手順だった」と分かると期待外れになりやすい

### 分かりにくい用語

- `growth-lab` / `PlanGate` / `river-review`（初出: 「この記事で得られること」の 2 項目め）: 何をするリポジトリかの説明がない。「issue 駆動の運用で起票数がもともと多く」という性質の違いは「限界」節まで出てこない
- **枠**・**並列度の1枠**（初出: TL;DR「10.5時間ぶんの枠を占有」）: 何の上限を指すのか（同時起動数なのか、人間の注意なのか）が説明されていない
- **スループット**（初出: 「なぜ気づけなかったのか」の式）: 説明がないが、直後の使い分けで意味は取れる
- **worktree**（初出: 得られること）: 説明がない
- 表の description 欄「River Review on learnings PR」「Security and ops review」: 何の作業かは本文から読み取れない

### 導線

- **冒頭 3 段落で何の記事か分かるか**: 分かる。1 段落目の太字に主張があり、対象読者、得られること、測定対象（単独運用・チーム開発ではない）と並ぶ。ただし「得られること」の 2 項目めは 1 文に要素を 5 つ詰めていて、拾い読みしにくい

- **読後の行動**: 「自分のリポジトリを測る」に、試せるコマンドと見るべき観点が示されている。末尾の関連記事 2 本は同じ Zenn 内の相対リンク
