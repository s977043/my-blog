## 1. AIが迷わないリポジトリ設計：長いプロンプトより先に整える4つの置き場所

### 読むのをやめそうな箇所

- 冒頭第1段落「この記事は、[Growth Lab]…の『AIが迷わないリポジトリ設計』メモをもとに、Zenn向けに最小構成へ落とし込んだ下書きです。」: 公開記事の1文目に「下書き」とあり、比較して採用を決める Z2 は未完成の記事と受け取って他へ移りうる
- 「## 3. 強制する仕組み」: 「事故はあまり減りません」「運用として強い」と言い切るが、筆者の体験した場面が無い。Z2 は「採用理由が書かれず手順だけが並ぶとき」にやめる。ここで流し読みに変わりやすい
- 「## 1.」〜「## 4.」の後に「完成形」「チェックリスト」「おすすめの順番」「まとめ」「FAQ」と続き、FAQ「何から始めればよいですか？」の答えが「おすすめの順番」とほぼ同じ。FAQ の手前で読み終える人が出そう

### 分かりにくい用語

- hooks（TL;DR で初出）: Git hooks か Claude Code の hooks か分からない
- CODEOWNERS（「## 3.」のコードブロック）: 説明なし
- MCP（「## 4.」の「GitHub、Notion、MCP、APIなど」）: 説明なし
- 正本（TL;DR「正本と外部参照」）: 「## 4. 正本を明記する」で伝わるが、TL;DR 時点では定義なし
- ADR（「## 4.」のコードブロック）: 説明なし
- Growth Lab（冒頭第1段落）: 何のサイトか一言なし

### 導線

- 冒頭3段落: 「長い指示ファイルに詰め込むと起きる問題」と「置き場所を分ける」主旨は伝わる。対象読者・前提ツール（Claude Code / Codex）を示す `:::message` は無い。TL;DR は早い位置にある
- 読後: 「最小チェックリスト」と「おすすめの順番」で次に試すことは明確。「## 参考」の関連記事5本に、次にどれを読むかの一言が無い。絶対 URL と相対パスが混在（公開ページでは両方機能するとみられるが未確認）
- 適用範囲: 合わないケース（小さなリポジトリ等）はほぼ無い。FAQ 1問目だけが単一エージェント運用に触れる

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 冒頭第1段落 | 「下書き」をやめる。例:「Growth Lab（筆者の技術メモサイト）の『AIが迷わないリポジトリ設計』をもとに、Zenn向けに最小構成へまとめた記事です。」 | 1文目で「未完成」と受け取られ、比較対象から外される |
| P2 | TL;DR の直前 | 対象読者と前提を1〜2行の `:::message` で示す。例:「Claude Code / Codex をチームのリポジトリで使い始めた人向け。入口ファイルが長くなってきたときの分け方を扱います。」 | 冒頭で前提と対象が分かることが判断の起点 |
| P2 | TL;DR・「## 3.」・「## 4.」の初出 | hooks / CODEOWNERS / MCP / ADR に一言の説明。例:「CODEOWNERS（変更時のレビュアーを指定するGitHubのファイル）」 | 略語で手が止まる。hooks は2通りに取れる |
| P2 | 「## 3. 強制する仕組み」の冒頭 | 自然言語のルールだけでは守られなかった場面を1つ示すか、一般論であると明示する | 「強い」と言い切るだけでは採用の判断材料にならない |
| P3 | FAQ「何から始めればよいですか？」 | 「おすすめの順番」への参照にまとめる | 終盤のくり返しで離れやすい |

## 3. コードを1行も書かずに、子供と見たクラゲ水槽をAIと作った話

- URL: https://note.com/mine_unilabo/n/n27a5594f65a4

- 本文: live（note api/v3/notes data.body）/ 4508 文字
- ペルソナ: N2 AI 駆動開発に関心のある現場エンジニア（中心が Codex への頼み方とモデルの変化による開発感覚で、個人で AI 開発を試す読者に近いため）

### 読むのをやめそうな箇所

- 冒頭（最初の見出しより前）: 「子供達と水族館に行った日、」から「そう伝え続けることでした。」まで短い段落が約25個続く。そのうえ「メインで使ったのはCodexです。」「調査にはGeminiも使いました。」が `## 使ったAI` でもう一度出てくる。同じ話だと感じたところで、具体的な場面を待つ N2 は読み飛ばすか閉じそう
- `## この記事は、すごいAI活用術ではありません`: 「きれいな設計論も、再現性の高いベストプラクティスも、まだありません。」が、明日の作業で変えることを持ち帰りたい N2 には「持ち帰れるものはない」と読める
- `## 作ってみて思ったこと` から `## 完璧ではないけれど`: 「コードは1行も書いていません。」「クラゲは泳いでいます」と同じ趣旨の締めがくり返され、`## 明日できること` の前で読み終えたと判断されそう

### 分かりにくい用語

- Codex（冒頭）: どの製品か（CLI、IDE 拡張、Web 版など）の説明なし
- Antigravity（冒頭「開発の一部ではAntigravityも使いました。」）: 何のツールか説明なし
- GPT-5.2 / GPT-5.4（`## 途中でモデルが変わった`）: Codex で使うモデル名だと読み取りにくい

### 導線

- 冒頭3段落: 水族館の情景で、AI で作った話と分かるのは約20段落後の「しかも今回は、自分ではコードを1行も書いていません。」。タイトルで補えてはいる
- 読後: `## 明日できること` に相談の書き出し例と試す行動があり明確。アプリの URL は冒頭と末尾の2か所。次に読む記事への案内は無い
- 画像: 2枚とも alt なし

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 冒頭と `## 使ったAI` | ツールの紹介を1か所にまとめる。例: 冒頭は「調査も実装も、AIに任せました。」だけにし、Codex・Gemini・Antigravity の内訳は `## 使ったAI` に寄せる | 同じ内容が2回出てきて、具体例を待つ読者が離れる |
| P2 | 冒頭の最初の1〜2段落 | 情景の前に中身を1文で示す。例:「コードを書かずに、AIへの指示と子供の感想だけでブラウザのクラゲ水槽を作った記録です。」 | 冒頭3段落だけでは AI 開発の記事だと分からない |
| P2 | 冒頭の Antigravity、`## 途中でモデルが変わった` | 初出に一言添える。例:「Codexで使うモデルが、GPT-5.2からGPT-5.4に変わりました。」 | 固有名で止まる |
| P2 | `## この記事は、すごいAI活用術ではありません` | 持ち帰れるものを1文で予告する。例:「その代わり、AIに違和感を返すときの言い方は、実例をそのまま載せています。」 | 持ち帰るものが無い記事と受け取られるのを防ぐ |
| P3 | 画像2枚 | alt を付ける。例:「クラゲが漂う水槽画面」「表示数や速度を変える設定パネル」 | 図の意味が本文から確定できない |
| P3 | 末尾 | 関連する技術記事があれば末尾のリンク集に置く | 次に読むものが無い |

## 4. AIエージェントのPR自動化はどこで止めるか。マージを人間に残すGitHub運用

- URL: https://zenn.dev/minewo/articles/ai-merge-ready-state-machine
- 原稿: `articles/ai-merge-ready-state-machine.md`
- 本文: live（zenn api/articles body_html）/ 10976 文字
- ペルソナ: Z2 設計判断を比べるテックリード（主題が「マージを AI に任せるか」という設計上の選択で、11-02 追加の比較表も代替案と比べる読み方を前提にしているため）

### 読むのをやめそうな箇所

- 「限定条件で自動マージする運用との違い」節（「この記事の設計は『マージは常に人間が行うべき』という一般ルールではありません。」）は「まとめ」の直前にあり、冒頭の「この記事で得られること」2項目にも入っていない。Z2 は「採用理由が書かれず、手順だけが並ぶとき」にやめるので、中盤の実装寄りの節（intent／receipt など）で離れるとこの表に届かない
- 「allowlistだけでは、AIのマージを完全には防げない」節の後半（「GitHubのfine-grained tokenでは、操作ごとに必要な権限が異なります。」から3段落）: 結論（「同じ認証情報のまま『pushは許可するが、マージは禁止する』という境界をトークンスコープだけで作るのは困難です」）が2段落目の末尾に埋もれている。スマホでは長い塊に見えると推定
- それ以外は無し。限界の表（層／守ること／守れないこと）と fail-closed の但し書きは、Z2 の確かめたい適用範囲・限界にそのまま答えている

### 分かりにくい用語

- `Delivery`（「AIが動かす状態機械にMERGEDへの遷移を置かない」節冒頭）: PlanGate のどの層か説明なし
- `exit`（同節の表の直前）: 状態との違いの説明なし
- `head SHA`（「1本のPRがMERGE_READYへ進むまで」の手順1）: stale・snapshot には括弧の説明があるのに、この語だけ無い
- `Executor`（「外部作用はallowlistへ閉じ込める」節）: 役割の説明が「判定と外部作用を分離する」節まで無い
- `record`（手順6）: 次の節の表まで何か分からない
- `in-process`: 英語のまま説明なし

### 導線

- 冒頭3段落: 1行目の太字で主張を言い切り、想定読者と得られることも示されている。ただし得られることの一覧に比較表の節が無く（原稿 L30-33 で確認）、比較のある記事かを冒頭で判断できない
- 読後: 「自分の環境へ転用するときの確認項目」のチェックリストと着手の順番がある。末尾に実装への参照6本と関連記事3本。比較表の節は「その部分だけ前者を組み合わせる余地はあります」で終わり、確認項目とつながっていない（チェックリストが比較表より前にある）

### 改善案

| 優先度 | 箇所 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 冒頭「この記事で得られること」 | 比較の節を3項目目として足す。例:「- 限定条件で自動マージする運用と比べたときの使い分け」 | 代替案との比較があるかで読み進めるかを決める。11-02 の追加が冒頭の予告に反映されていない |
| P2 | 「限定条件で自動マージする運用との違い」節の位置 | 「実装から得た3つの設計原則」の前などへ移す。移さないなら冒頭で「末尾で自動マージ運用と比較します」と予告する | 比較が終盤にしか無く、中盤で離れた読者に届かない |
| P2 | 「AIが動かす状態機械に…」節の表の直前 | `Delivery` と `exit` を一言で説明する | 表の前に用語で止まる |
| P2 | 手順1の `head SHA` | 「head SHA（PRの最新コミットのハッシュ）」のように括弧で説明 | 同じ手順でこの語だけ説明が無い |
