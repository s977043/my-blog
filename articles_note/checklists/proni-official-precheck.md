# PRONI 公式テックブログ 提出前チェックリスト

会社公式（PRONI）の note 記事（`articles_note/new/PRONI-*.md`）を、広報の事前確認ワークフローへ出す前に自分で点検するためのチェックリスト。

- 公開可否を最終判断するのは広報。このリストは差し戻しを減らすための事前点検で、広報の判断を置き換えない
- 骨格は、広報の AI 自動チェックが返すレポートの 5 カテゴリ。そこに社内のテックブログ投稿レギュレーションと、独自に足した項目（「（独自追加）」と付記）を重ねている。広報側やレギュレーションが更新されたら、このファイルを追従させる
- 広報チェックで観測した判定は「問題なし」だけ。本リストの「要確認／要修正」は、こちらで置いた段階
- このリポジトリは公開されている。社内の担当者名・チャンネル名・社内ページ名は書かない
- 実行は `proni-official-precheck` スキル（`.claude/skills/proni-official-precheck/SKILL.md`）。下の「検索語」はスキルが grep に使う。語を足すときはこのファイルだけを直す

## 0. 記事タイプの判定

広報チェックはまず記事タイプを判定する。提出前に自分でも 1 行で書いておく。

- 例: 「ハウツー型（AI 開発プロセスのノウハウ解説）＋自社主語型（PRONI プロダクト開発部の内部 AI 活用経験を自社視点で共有）」
- 自社主語型の場合、「なぜ自社の内部事情を公開するのか」が本文から読み取れるか

## 1. 中立性・ステークホルダー配慮

- [ ] 特定のベンダー・パートナー・競合への批判や否定がない
- [ ] ツール名（Claude Code、Codex など）は「使った道具」として中立に書いている。優劣の比較になっていない
- [ ] 根拠のない断定表現がない。ヒットした箇所は、根拠が同じ段落にあれば問題なし
  - 検索語（断定）: `圧倒的|唯一|必ず|絶対|最強|No\.1`

## 2. IR・ガバナンス・セキュリティ

- [ ] 未公表の業績・業績予測・M&A・資本政策に触れていない
  - 検索語（IR）: `業績|売上|利益|上場|IPO|買収|M&A|提携予定|未発表|未公表|株価|資金調達`
- [ ] 内部の運用数値（件数、合格率、利用回数など）が、開発チームの業務指標に留まっている。売上・顧客数・取引額など事業の規模を推測できる数値なら「要確認」
- [ ] （独自追加）社内システムの構成・認証情報・内部 URL・社内チャンネル名を出していない

## 3. 事例の主語と匿名化

- [ ] 主語が「自社（PRONI）」か「著者個人」かが明確で、混ざっていない
- [ ] 著者は PRONI 社員として明示されている（名前 / アカウント）
- [ ] 他社・顧客・パートナー・社外の第三者の実名や、特定できる情報が出ていない
- [ ] （独自追加）社内メンバーの実名を出す場合は本人の了承がある

## 4. データの信頼性・著作権

- [ ] 数値には前提条件と限界（期間、母数、計測方法、「体感ベース」など）が書かれている
- [ ] 曖昧な量の表現が、データの限界を書いた文脈の中にある。そうなっていれば判定は「問題なし」で、広報へのメモ候補に挙げるだけにする（具体化は任意。広報チェックも同じ扱い）。限界の説明がないまま使っている場合だけ「要確認」
  - 検索語（曖昧な量）: `数倍|大幅|劇的|激減|激増`
- [ ] 外部の引用・参照に、著者名・日付・リンクが付いている。自己紹介や採用告知のリンクは対象外
- [ ] 社内レビュー用の Google ドキュメントでも、外部リンクがハイパーリンクとして残っている（プレーンテキストではリンクの有無を確かめられないため、広報チェックで確認を求められる）
- [ ] 他者の図・画像・文章を転載していない。引用するなら引用元を、参考にしたなら出典元を明記している

## 5. ビジネスモデル整合性

- [ ] 内容が自社の内部開発プロセスに限られているか、顧客向け機能・営業プロセスに触れる場合はその記述が正確か
- [ ] 発注側・受注側（出稿パートナー）の関係性に触れる場合、どちらかを下げる・排除する表現がない
- [ ] 出稿パートナーや顧客の立場で読み直し、「自分たちが軽く扱われている」と取れる一文がない。迷った文は「要確認」にして広報へのメモに書く

## 6. 社内レギュレーション（テックブログ投稿レギュレーション）

- [ ] エンジニアレビュー: 部長（副部長）の承認は必須。加えて所属グループ内 1 名以上。特定技術に特化した記事は、その分野に詳しい人にも見てもらう
- [ ] 留意事項: 社外秘を書かない、顧客のことを書かない、炎上しやすい話題（差別・政治・宗教など）を避ける。強い内容は一晩置いてから出す
- [ ] note 執筆ガイドラインを適用した（JTF スタイル、`articles_note/checklists/note-article-quality-checklist.md`）
- [ ] 文体（敬体・常体）の混在がない（`npm run check:article-sentence-style`）
- [ ] （独自追加）時制（です・ます／でした・ました）がそろっている。過去の出来事は過去形。機械チェックでは検出できないので通読で確かめる
- [ ] カバー画像はデザイン室のテンプレートから選んだ。レイアウトを変えたい場合はレビュー用チャンネルで相談した
- [ ] 画像に、公序良俗に反するもの・権利を侵害するもの・PRONI 以外の特定の個人や法人を想起させるものがない。AI 生成画像には文字列・PRONI ロゴに似たもの・ペンギンを入れない（画像は目視で確かめる）
- [ ] 末尾に公式テックブログ共通の採用告知（見出し「【PR】エンジニアの積極採用を実施中です」と告知文、求人一覧へのリンク）がある
- [ ] 社内レビュー用の Google ドキュメントに、広報担当者の編集権限がある

## 提出後

- 広報の AI 自動チェックは、テスト運用中は参考扱い。広報担当者の返信を確認してから、修正や公開に進む
- 公開したら、公式テックブログのマガジンに追加し、社内 Slack で共有する
