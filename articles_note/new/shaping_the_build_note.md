# AI時代の開発で短くすべきは、Time to CodeではなくTime to Learning

> 区分: 個人

先日、「[AIがコードを書くほど、エンジニアリングは『何を作るか』に戻っていく](https://note.com/mine_unilabo/n/n103182c44979)」という記事を書きました。

そこで考えたのは、AIによってコードを書く速度が上がったあと、エンジニアリングのボトルネックはどこへ移るのか、ということでした。

実装が速くなるほど、「何を作るのか」「なぜ作るのか」「何をもって正しいとするのか」といった、コードを書く前後の判断が相対的に重要になります。

その記事を公開して約2週間後、Andrew Ngが「The AI Engineering Skills Map」を公開しました。

そこで挙げられていた重要な能力は、次の4つです。

1. Building and deploying AI applications
2. Software engineering fundamentals
3. Using coding agents
4. Shaping the build

特に目に留まったのが、最後の **Shaping the build** でした。

Andrew Ngは、Coding Agentによって明確な仕様を実装する能力が高まるほど、エンジニアにはプロダクト感覚、ビジネスの文脈、顧客のゴールを理解し、何を作るかという段階から開発を前へ進める能力が重要になると整理しています。

前の記事で考えていたことと近い一方で、ここからもう一段掘り下げたい問いがあります。

**AIによってBuildが速くなったとき、開発全体では何を速くすべきなのでしょうか。**

私の答えは、コードを書く時間だけではありません。

**Time to Codeではなく、Time to Learningを短くする。**

ここでいうLearningは、人が知識を身につけることではありません。

この記事では、最初のProblemを観測してから、**次の意思決定に使えるEvidenceを得るまでの時間**を、便宜上 **Time to Learning** と呼びます。

仮説を続けるのか、変えるのか、止めるのか。その判断に使えるEvidenceを、どれだけ早く得られるか。

AI時代の開発で短くすべきなのは、そこだと考えています。

---

## Time to Codeは、Time to Learningの一部分にすぎない

AI Codingの生産性を考えるとき、「実装に何時間かかったか」「コードをどれだけ速く書けたか」に目が向きます。

もちろん、それも重要です。

ただ、プロダクト開発全体で見ると、Time to Codeはもっと長い流れの一部分です。

**Problem → Hypothesis → Shape → Build / Experiment → Evidence**

Evidenceを得たあと、その結果を使ってNext Decisionへ進みます。この記事でいうTime to Learningの終点は、その判断に使えるEvidenceを得た時点です。

コードを書く時間は、主にBuild / Experimentに含まれます。

しかし、Buildだけが10倍速くなっても、

- 何を作るか決めるまでに何週間もかかる
- 検証方法が決まっていない
- リリース後に結果を見ていない
- Evidenceがあっても次の判断につながらない

のであれば、プロダクトとしての学習速度は大きく変わりません。

反対に、小さく作り、すぐにEvidenceを取り、次の判断を変えられるなら、一つひとつのBuildを学習へつなげられます。

だから私は、AI時代の開発生産性を考えるとき、**Time to CodeだけではなくTime to Learningを見る必要がある**と考えています。

では、そのTime to Learningをどう短くするのか。

そこで重要になるのが、Shaping the buildです。

---

## Shaping the buildを、7つの問いに分ける

「何を作るかを考える」と聞くと、プロダクトマネージャーや企画職の仕事を想像するかもしれません。

もちろん、プロダクトマネジメントの重要な仕事です。

一方で、AIによって実装コストが下がり、試せる回数が増えると、「何を作るか」と「どう作るか」を完全に分離することは難しくなります。

たとえば、

> 問い合わせ画面にAI回答機能を追加したい。

という要望があったとします。

今ならCoding Agentに要件を渡し、既存コードを調査させ、実装計画を作り、UIやAPIを変更し、テストまで進めること自体はかなり速くできます。

しかし、**実装が速いことと、作るものが正しいことは別です。**

私はShaping the buildを、普段の開発で行っている判断に置き換えると、次の7つの問いになると考えています。

![Shapingを考える7つの問い](../assets/shaping-decision-loop.png)

これはAndrew NgのSkills Mapをそのまま分解したものではありません。Shaping the buildという考え方を、自分の実務に引き寄せて整理したものです。

先ほどの「AI回答機能」を例に、最初の要望をそのままSolutionとして実装する前に問い直してみます。

**Problem**  
困っているのは、本当に「AI回答機能がないこと」なのか。それとも、問い合わせから回答までの時間が長いことなのか。

**Evidence**  
回答待ちによる離脱や、同じ問い合わせの繰り返しは実際に起きているのか。

**Outcome**  
問い合わせ件数を減らしたいのか。自己解決率を上げたいのか。解決までの時間を短くしたいのか。

**Scope**  
まずはFAQで回答できる質問だけを対象にするのか。自由質問まで扱うのか。

**Trade-off**  
回答速度と誤回答リスクをどう扱うのか。どこから人間へ引き継ぐのか。

**Verification**  
自己解決率、再問い合わせ率、解決までの時間など、何を見て効果を判断するのか。

**Stop**  
誤回答が一定の条件を超えたら停止するのか。効果がなければ機能そのものを撤回するのか。

Evidenceが足りなければ、最初に作るべきものはAI回答機能ではないかもしれません。

問い合わせ理由を分類する計測を追加する。既存FAQの利用状況を取る。限定したユーザーに小さなプロトタイプを試してもらう。

**「何を作るかを決める」には、機能を作らない判断や、先にEvidenceを作る判断も含まれます。**

技術調査そのものが「何を作るか」を変えることもあります。

問い合わせログやデータ構造を調べた結果、回答に必要な情報が顧客ごとの権限付きデータに依存すると分かれば、FAQを検索するだけのAI回答機能では成立しません。

先にデータアクセスの境界や権限制御を確かめる。対象にする質問を限定する。場合によっては解決策そのものを変える。

ここでは、ユーザーの課題を示すEvidenceだけでなく、**技術的なEvidenceもScopeやSolutionを変えています。**

Shapingは、アイデアを出すことでも、要望をそのまま仕様書へ変換することでもありません。

**「何を作るか」を、実装可能かつ検証可能な状態まで形づくる仕事です。**

---

## Shapingは、開発前に一度だけ行う仕事ではない

ここまで読むと、

> それは昔からProduct Discoveryや要件定義でやってきたことではないか。

と思うかもしれません。

その通りです。

問題を理解することも、仮説を作ることも、成果を測ることも、AIによって突然生まれた仕事ではありません。

変わったのは仕事の有無ではなく、**ボトルネックの位置と反復速度**です。

従来から、実装には一定の時間とコストが必要でした。だから実装へ入る前に問題や要件を整理し、手戻りを減らすことには大きな合理性があります。この原則は今も変わりません。

一方で、AIによって調査、試作、定型的な実装、テストなどを短い時間で回せる場面は増えています。

小さなプロトタイプを作ること自体が調査になることもあります。

動かして初めて制約が分かる。既存システムへ接続して初めてデータの不足に気づく。ユーザーに触ってもらって初めて仮説が外れていたと分かる。

すると開発は、「考える → 作る」で終わる一方向の流れではなくなります。

**Shape → Build → Verify → Learn → Decide → Shape**

Shapeした内容をBuildし、VerifyでEvidenceを取り、そこからLearnする。その結果によって次のDecisionを変え、再びShapeへ戻す。

**作ること自体が、次に何を作るかを決めるためのEvidenceになります。**

ここからはAndrew Ngの分類そのものではなく、私自身の実務上の解釈です。

Shapingは、開発前に一度だけ行う工程ではありません。BuildやVerifyで得たEvidenceを、次のScopeやSpecへ戻す継続的な仕事です。

要件定義が不要になるわけではありません。

むしろ、**要件を一度決めて固定する能力より、Evidenceを見ながら要件を更新する能力の価値が上がる。**

この反復を短くできるほど、Time to Learningも短くなります。

## 「何を作るか」は誰の仕事なのか

ここでもう一つ、疑問が残ります。

> それはPdMの仕事ではないのか。

Shapingの最終的な意思決定を誰が担うかは、チームの役割や責任設計によって異なります。ここで言いたいのは、エンジニアがその責任をすべて引き取ることではありません。

重要なのは、Shapingの判断材料に **プロダクトのEvidenceと技術のEvidenceの両方が必要になる** ことです。

「この機能に価値があるか」という問いと、「このデータなら安全に実現できるか」「この運用コストを許容できるか」という問いは、互いに影響します。

技術調査で分かった制約からScopeが変わることもあれば、小さな実装で得たEvidenceからOutcomeを見直すこともあります。

Engineeringの仕事は、決められたSolutionを実装するだけではありません。技術的な可能性や制約を、次のプロダクト判断へ返すところまでつながっています。

PdM、デザイナー、エンジニアの責任を曖昧にするのではなく、それぞれの専門性を持ち寄って、**Problem、Outcome、技術制約、リスクを一つの意思決定としてつなぐ。**

AIによってBuildが速くなるほど、この接続が遅いこと自体が新しいボトルネックになり得ます。

エンジニアに求められるのは企画職への転身ではなく、技術的なEvidenceを持って「何を作るか」の判断へ参加することだと考えています。

これも、Time to Learningを短くするためのエンジニアリングです。

## 前の記事とSkills Mapを重ねると

前の記事は、AIと仕事をするために **何を設計する必要があるのか** を整理しました。一方、Andrew NgのSkills Mapが描いているのは **人間が何をできる必要があるのか** です。

両者を重ねると、ShapingでProblem、Outcome、Scope、Specを形づくり、Coding AgentへContextやHarnessを通じて実行を任せ、その結果をVerificationで観測して次のShapingへ戻す、という関係が見えてきます。

これはAndrew Ngの公式な対応表ではなく、前の記事とSkills Mapを私なりに重ねた見方です。Buildを任せられる範囲が広がるほど、その前後にあるShaping、Verification、Learningの質が効いてきます。

## 短くすべきは、Time to CodeではなくTime to Learning

AIによってBuildが速くなることには、大きな価値があります。

ただ、それだけではプロダクト開発全体が同じ比率で速くなるとは限りません。

実装前の判断が遅い。何を測るか決まっていない。結果が観測できない。観測しても次の判断につながらない。

そこが残れば、Time to Codeだけを短くしても、学習のループは速くなりません。

だから、AI時代の開発で短くすべきは、**Time to CodeではなくTime to Learning**です。

Problemを観測する。Hypothesisを置く。Shapeする。小さくBuild / Experimentする。Evidenceを得る。**ここまでが、この記事でいうTime to Learningです。** そのEvidenceを使って、次のDecisionを変える。

重要なのはBuildの回数を増やすことではありません。

**一つのBuildから、次の判断に必要なEvidenceをどれだけ早く得られるか。**

Evidenceは成功を示すものだけではありません。

仮説が外れていた。期待した効果が出なかった。そもそも作るべきではなかった。

そう判断できることもLearningです。

AIによってコードを書く時間が短くなるほど、次に向き合うべきなのは、その前後にある意思決定の速度です。

**Time to Codeではなく、Time to Learningを短くする。**

「何を作るか」を決めることも、そのためのエンジニアリングです。
