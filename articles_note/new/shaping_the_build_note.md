# AIがコードを書く時代、エンジニアは「何を作るか」をどう決めるのか

> 区分: 個人

先日、「[AIがコードを書くほど、エンジニアリングは『何を作るか』に戻っていく](https://note.com/mine_unilabo/n/n103182c44979)」という記事を書きました。

そこで考えていたのは、AIによってコードを書く速度が上がったあと、エンジニアリングのボトルネックはどこへ移るのか、ということでした。

実装そのものが速くなるほど、「何を作るのか」「なぜ作るのか」「何をもって正しいとするのか」といった、コードを書く前後の判断が相対的に重要になります。

その記事を公開して約2週間後、Andrew Ngが「The AI Engineering Skills Map」を公開しました。

そこで挙げられていた重要な能力は、次の4つです。

1. Building and deploying AI applications
2. Software engineering fundamentals
3. Using coding agents
4. Shaping the build

特に目に留まったのが、最後の **Shaping the build** でした。

Andrew Ngは、Coding Agentによって明確な仕様を実装する能力が高まるほど、エンジニアにはプロダクト感覚、ビジネスの文脈、顧客のゴールを理解し、何を作るかという段階から開発を前へ進める能力が重要になると整理しています。

前の記事を書きながら考えていたことと、かなり近いものでした。

ただ、今回考えたいのは「Andrew Ngも同じことを言っていた」という話ではありません。

もう一段、具体的な問いがあります。

**「何を作るかを決める」とは、実際には何をすることなのでしょうか。**

先に結論を書くと、私はこれを、問題を定義し、証拠を集め、作る範囲を決め、結果を検証し、次の判断へ戻すまでの **意思決定のループ** だと考えています。

AI時代に速くしたいのは、コードを書く時間だけではありません。

**問題を見つけてから、次の判断に使える証拠を得るまでの時間です。**

---

## Shaping the buildは、単なる「企画力」ではない

「何を作るかを考える」と聞くと、プロダクトマネージャーや企画職の仕事を想像するかもしれません。

もちろん、プロダクトマネジメントの重要な仕事です。

一方で、AIによって実装コストが下がり、試せる回数が増えていくと、「何を作るか」と「どう作るか」を完全に分離して考えることは難しくなっていくと感じています。

たとえば、

> 問い合わせ画面にAI回答機能を追加したい。

という要望があったとします。

今ならCoding Agentに要件を渡し、既存コードを調査させ、実装計画を作り、UIやAPIを変更し、テストまで進めること自体はかなり速くできます。

しかし、実装が速くなったからこそ、その前に確認したいことがあります。

- **Problem**: 本当に解くべき問題は何か
- **Evidence**: その問題が存在する証拠はあるか
- **Outcome**: 何が変われば成功なのか
- **Scope**: 今回どこまで作るのか
- **Trade-off**: 速度、品質、コスト、リスクをどう配分するか
- **Verification**: 結果を何で確認するのか
- **Stop**: どの条件なら止めるのか

![Shapingを考える7つの問い](../assets/shaping-decision-loop.png)

これはAndrew NgのSkills Mapをそのまま分解したものではありません。

Shaping the buildという考え方を、自分が普段の開発で行っている判断へ置き換えると、この7つの問いになります。

先ほどの「AI回答機能」を例にすると、最初の要望をそのままSolutionとして実装する前に、問いを具体化できます。

**Problem**  
ユーザーが困っているのは、本当に「AI回答機能がないこと」なのか。それとも、問い合わせから回答までの時間が長いことなのか。

**Evidence**  
回答待ちによる離脱や、同じ問い合わせの繰り返しは実際に起きているのか。

**Outcome**  
問い合わせ件数を減らしたいのか。自己解決率を上げたいのか。解決までの時間を短くしたいのか。

**Scope**  
まずはFAQで回答できる質問だけを対象にするのか。自由質問まで扱うのか。

**Trade-off**  
回答速度と誤回答リスクをどう扱うのか。どこから人間へ引き継ぐのか。

**Verification**  
自己解決率、再問い合わせ率、解決までの時間など、何を見て効果を判断するのか。

**Stop**  
誤回答が一定の条件を超えた場合に停止するのか。効果がなければ機能そのものを撤回するのか。

ここでEvidenceが足りなければ、最初に作るべきものはAI回答機能ではないかもしれません。

問い合わせ理由を分類するための計測を追加する。既存FAQの利用状況を取る。限定したユーザーだけに小さなプロトタイプを試してもらう。

**「何を作るかを決める」には、機能を作らない判断や、先に証拠を作る判断も含まれます。**

さらに、技術調査そのものが「何を作るか」を変えることもあります。

問い合わせログやデータ構造を調べた結果、回答に必要な情報が顧客ごとの権限付きデータに依存すると分かれば、FAQを検索するだけのAI回答機能では成立しません。

先にデータアクセスの境界や権限制御を確かめる。対象にする質問を限定する。場合によっては解決策そのものを変える必要があります。

ここでは、ユーザーの課題を示すEvidenceだけでなく、**技術的なEvidenceもScopeやSolutionを変えています。**

つまりShapingは、アイデアを出すことでも、要望をそのまま仕様書へ変換することでもありません。

**「何を作るか」を、実装可能かつ検証可能な状態まで形づくる仕事です。**

## Shapingは昔からあった。それでも今、重要になる理由

ここまで読むと、

> それは昔からProduct Discoveryや要件定義でやってきたことではないか。

と思うかもしれません。

その通りです。

問題を理解することも、仮説を作ることも、成果を測ることも、AIによって突然生まれた仕事ではありません。

変わったのは、**その重要度と反復速度**だと考えています。

従来から、実装には一定の時間とコストが必要でした。そのため、実装へ入る前に問題や要件を整理し、手戻りを減らすことには大きな合理性があります。

この原則は今も変わりません。

一方で、作業によって差はあるものの、AIによって調査、試作、定型的な実装、テストなどを短い時間で回せる場面は増えています。

小さなプロトタイプを作ること自体が調査になる場面も増えました。

動かしてみて初めて制約が分かる。既存システムへ接続して初めてデータの不足に気づく。ユーザーに触ってもらって初めて仮説が間違っていたと分かる。

すると開発は、「考える → 作る」で終わる一方向の流れではなくなります。

Shapeした内容をBuildし、Verifyで証拠を取り、そこからLearnする。その結果によって次のDecisionを変え、再びShapeへ戻す。

**作ること自体が、次に何を作るかを決めるためのEvidenceになります。**

ここからはAndrew Ngの分類そのものではなく、私自身の実務上の解釈です。

私はShapingを、開発前に一度だけ行う工程ではなく、BuildやVerifyで得たEvidenceを次のScopeやSpecへ戻す、継続的な仕事として捉えています。

重要なのは、「要件定義が不要になる」ということではありません。

逆です。

**要件を一度決めて固定する能力より、Evidenceを見ながら要件を更新する能力の価値が上がる。**

## ProductとEngineeringの境界で、判断をつなぐ

Shapingの判断には、プロダクトと技術の両方が関係します。

「この機能に価値があるか」という問いと、「このデータなら安全に実現できるか」「この運用コストを許容できるか」という問いは、実際の開発では互いに影響します。

技術調査で分かった制約からScopeが変わることもあれば、小さな実装で得たEvidenceからOutcomeを見直すこともあります。

Engineeringの仕事は、決められたSolutionを実装するだけではありません。技術的な可能性や制約を、次のプロダクト判断へ返すところまでつながっていきます。

これは、エンジニアがプロダクトマネージャーになる、という話ではありません。

PdM、デザイナー、エンジニアなどの責任を曖昧にすることでもありません。

むしろ、それぞれの専門性を持ち寄り、**Problem、Outcome、技術制約、リスクを一つの意思決定としてつなぐ必要が増える**、という話です。

AIによってBuildが速くなるほど、この接続が遅いこと自体が新しいボトルネックになり得ます。

エンジニアに求められるのは企画職への転身ではなく、技術的な制約や可能性を持って「何を作るか」の判断へ参加することだと考えています。

## Skills Mapと、前の記事で整理した「設計対象」は別の地図だった

前の記事では、Problem、Intent、Specから、Context、Harness、Verification、Learningまで、AIと仕事をするために**何を設計する必要があるのか**を整理しました。

Andrew NgのSkills Mapが描いているのは、それとは別の軸です。

**人間が何をできる必要があるのか。**

前の記事はDesign Target、Skills MapはHuman Capabilityの地図だと考えると、両者を重ねて見られます。

- **Shaping the build**: Problem、Outcome、Scope、Specを形づくる
- **Software engineering fundamentals**: Trade-offやSafetyを判断する
- **Using coding agents**: ContextやHarnessを通じて実行を任せる
- **Verification / Learning**: 結果を観測し、次のShapingへ戻す

これはAndrew Ngの公式な対応表ではなく、前の記事の設計対象とSkills Mapを私なりに重ねた見方です。

この見方をすると、Coding Agentを使うことはAI駆動開発の一部分にすぎません。

ContextやHarness、Verificationが整うほど、最初と最後にある「何を変えたいのか」「結果を見て次に何をするのか」という判断の質が効いてきます。

## エンジニアの仕事は、実装から「意思決定のループ」へ広がる

AIがコードを書く話では、「エンジニアの仕事がどこまでなくなるのか」という議論になりがちです。

しかし、自分でAIを使って開発していると、少し違う感覚があります。

コードを直接書く時間は減っています。

その代わり、

- 問題を整理する
- AIへ渡すContextと制約を決める
- 複数の設計を比較する
- 実行結果を見る
- 失敗の原因を探す
- 続けるか止めるか判断する
- 次の実行方法を変える

といった時間が増えています。

実装という一つの作業が減り、その前後にあった意思決定のループへ仕事が広がっています。

先ほどの反復ループで言えば、人間の仕事はBuildの外側へ消えるのではありません。Shape、Verify、Learn、Decideまで含むループ全体へ広がっていきます。

AIがBuildを担う範囲が広がるほど、人間はどこで判断し、何をAIへ任せ、どこで止めるのかを設計する必要があります。

重要なのは、人間がすべてを細かく指示することではありません。

AIが自律的に進められる範囲を広げながら、方向を決めるための情報、制約、観測方法、停止条件を用意することです。

エンジニアリングの対象がコードだけではなく、**価値へ到達するための意思決定と実行のループそのもの**へ広がっている、と考えると理解しやすくなります。

## 速くしたいのは、コードを書く時間だけではない

前の記事では、

> AIがコードを書くほど、エンジニアリングは「何を作るか」に戻っていく。

と書きました。

Andrew NgのSkills Mapを見て、今はもう少し先まで考えています。

**「何を作るか」を決めること自体が、AI時代の重要なエンジニアリング能力になる。**

これは、何を作るかがエンジニアだけの仕事になる、という意味ではありません。

プロダクト、デザイン、エンジニアリングそれぞれの専門性をつなぎながら、問題を観察する。証拠を集める。仮説を作る。Scopeと制約を決める。小さく作る。結果を検証する。止めるべきなら止める。学びから次の判断を変える。

その意思決定のループに、エンジニアリングがより深く関わるという意味です。

AI Codingの生産性を考えるとき、「実装に何時間かかったか」「コードをどれだけ速く書けたか」に目が向きます。

もちろん、それも重要です。

ただ、プロダクト開発全体で見れば、本当に短くしたい時間はもう少し長いはずです。

ここでは、最初のProblemを観測してから、**次の意思決定に使えるEvidenceを得るまでの時間**を便宜上 **Time to Learning** と呼びます。

![Time to CodeとTime to Learning](../assets/time-to-learning.png)

Evidenceは、成功を示す証拠だけではありません。

仮説が外れていた。期待した効果が出なかった。そもそも作るべきではなかった。

そう判断できるEvidenceも、次の意思決定に使えるLearningです。

Buildだけが10倍速くなっても、何を作るかを決めるまでに何週間もかかり、結果の検証にも何週間もかかるなら、プロダクトとしての学習速度は大きく変わりません。

逆に、Problemを観察し、Hypothesisを置き、Shapeし、小さくBuild / Experimentし、Evidenceを得てNext Decisionを変えるところまでを短くできれば、AIが生み出す速度を価値へつなげやすくなります。

AIによって本当に速くしたいのは、コードを書く時間だけではない。

**問題を見つけてから、次の判断に使える証拠を得るまでの時間を短くする。**

「何を作るか」を決めることも、そのためのエンジニアリングです。
