# AIがコードを書く時代、エンジニアは「何を作るか」をどう決めるのか

> 区分: 個人

先日、「[AIがコードを書くほど、エンジニアリングは『何を作るか』に戻っていく](https://note.com/mine_unilabo/n/n103182c44979)」という記事を書きました。

そこで考えていたのは、AIによってコードを書く速度が上がったあと、エンジニアリングのボトルネックはどこへ移るのか、ということでした。

実装そのものが速くなるほど、「何を作るのか」「なぜ作るのか」「何をもって正しいとするのか」といった、コードを書く前後の判断が相対的に重要になります。

その記事を公開して約2週間後、Andrew Ngが「The AI Engineering Skills Map」を公開しました。

そこで挙げられていた重要な能力は、次の4つです。

1. Building and deploying AI applications
2. Software engineering fundamentals
3. Using coding agents
4. Shaping the build

特に目に留まったのが、最後の **Shaping the build** でした。

Andrew Ngは、Coding Agentによって明確な仕様を実装する能力が高まるほど、エンジニアにはプロダクト感覚、ビジネスの文脈、顧客のゴールを理解し、何を作るかという段階から開発を前へ進める能力が重要になると整理しています。

前の記事を書きながら考えていたことと、かなり近いものでした。

ただ、今回考えたいのは「Andrew Ngも同じことを言っていた」という話ではありません。

もう一段、具体的な問いがあります。

**「何を作るかを決める」とは、実際には何をすることなのでしょうか。**

先に結論を書くと、私はこれを、問題を定義し、証拠を集め、作る範囲を決め、結果を検証し、次の判断へ戻すまでの **意思決定のループ** だと考えています。

AI時代に速くしたいのは、コードを書く時間だけではありません。

**問題を見つけてから、価値があるかどうかを学べるまでの時間です。**

---

## Shaping the buildは、単なる「企画力」ではない

「何を作るかを考える」と聞くと、プロダクトマネージャーや企画職の仕事を想像するかもしれません。

もちろん、プロダクトマネジメントの重要な仕事です。

一方で、AIによって実装コストが下がり、試せる回数が増えていくと、「何を作るか」と「どう作るか」を完全に分離して考えることは難しくなっていくと感じています。

たとえば、

> 問い合わせ画面にAI回答機能を追加したい。

という要望があったとします。

今ならCoding Agentに要件を渡し、既存コードを調査させ、実装計画を作り、UIやAPIを変更し、テストまで進めること自体はかなり速くできます。

しかし、実装が速くなったからこそ、その前に確認したいことがあります。

| 観点 | 問い |
| --- | --- |
| Problem | 本当に解くべき問題は何か |
| Evidence | その問題が存在する証拠はあるか |
| Outcome | 何が変われば成功なのか |
| Scope | 今回どこまで作るのか |
| Trade-off | 速度、品質、コスト、リスクをどう配分するか |
| Verification | 結果を何で確認するのか |
| Stop | どの条件なら止めるのか |

これはAndrew NgのSkills Mapをそのまま分解したものではありません。

Shaping the buildという考え方を、自分が普段の開発で行っている判断へ置き換えると、このような問いになります。

先ほどの「AI回答機能」を例にすると、最初の要望をそのままSolutionとして実装する前に、次のように問い直せます。

**Problem**  
ユーザーが困っているのは、本当に「AI回答機能がないこと」なのか。それとも、問い合わせから回答までの時間が長いことなのか。

**Evidence**  
回答待ちによる離脱や、同じ問い合わせの繰り返しは実際に起きているのか。

**Outcome**  
問い合わせ件数を減らしたいのか。自己解決率を上げたいのか。解決までの時間を短くしたいのか。

**Scope**  
まずはFAQで回答できる質問だけを対象にするのか。自由質問まで扱うのか。

**Trade-off**  
回答速度と誤回答リスクをどう扱うのか。どこから人間へ引き継ぐのか。

**Verification**  
自己解決率、再問い合わせ率、解決までの時間など、何を見て効果を判断するのか。

**Stop**  
誤回答が一定の条件を超えた場合に停止するのか。効果がなければ機能そのものを撤回するのか。

AIが速く実装できるからこそ、「AI回答機能を作る」というSolutionを、そのままProblemとして扱わないことが重要になります。

制約の中で問題を定義し、仮説を置き、実装可能な範囲を決め、結果を観測できる状態にする。

これは単なるアイデア出しではありません。

**「何を作るか」を、実装可能かつ検証可能な状態まで形づくる仕事です。**

---

## Shapingは昔からあった。それでも今、重要になる理由

ここまで読むと、

> それは昔からProduct Discoveryや要件定義でやってきたことではないか。

と思うかもしれません。

その通りです。

問題を理解することも、仮説を作ることも、成果を測ることも、AIによって突然生まれた仕事ではありません。

変わったのは、**その重要度と反復速度**だと考えています。

従来は、実装そのものに大きな時間とコストがかかっていました。

そのため、ある程度考えてから作ることに合理性がありました。企画、要件、設計、実装という工程を分け、それぞれで精度を上げてから次へ渡す必要がありました。

ところがAIによって、調査、試作、定型的な実装、テストなどに必要な時間が短くなっています。

小さなプロトタイプを作ること自体が調査になる場面も増えました。

動かしてみて初めて制約が分かる。既存システムへ接続して初めてデータの不足に気づく。ユーザーに触ってもらって初めて仮説が間違っていたと分かる。

すると、開発は、

```text
考える → 作る
```

だけではなく、

```text
Shape → Build → Verify → Learn
  ↑                         ↓
  └──────── Decide ────────┘
```

という循環になります。

ここで重要なのは、「要件定義が不要になる」ということではありません。

逆です。

**要件を一度決めて固定する能力より、証拠を見ながら要件を更新する能力が重要になる。**

Shaping the buildは、開発の前に一度だけ行う工程ではなく、開発中も続く仕事になります。

そして、この判断にはプロダクトと技術の両方が関係します。

「この機能に価値があるか」と、「このデータなら安全に実現できるか」「この運用コストを許容できるか」を、別々の世界として扱いにくくなるからです。

これは、エンジニアがプロダクトマネージャーになる、という話ではありません。

職種の境界をなくすことでもありません。

**ProductとEngineeringの境界をまたいで、「何を作るか」の判断に関与する場面が増える**、という話です。

## Skills Mapと、前の記事で整理した「設計対象」は別の地図だった

前の記事では、AIを使った開発で設計する対象を、次のように整理しました。

```text
Problem / Intent / Spec
        ↓
Prompt / Contract / Context
        ↓
Tool / Harness / Runtime / Safety
        ↓
Loop / Workflow / Graph
        ↓
Verification / Eval / Observability
        ↓
Memory / Trust / Learning
```

Andrew NgのSkills Mapを見て、これは違う対象を描いた地図なのだと気づきました。

Skills Mapが表しているのは、

**人間が何をできる必要があるのか。**

一方、前の記事で整理していたのは、

**AIと仕事をするために、何を設計する必要があるのか。**

という地図です。

この2つは競合しません。

むしろ、Human CapabilityとDesign Targetという別の軸として重ねられます。

たとえば、Shaping the buildでProblem、Outcome、Scope、Specを形づくる。

Software engineering fundamentalsを使ってArchitecture、Trade-off、Safetyを判断する。

Coding AgentにはContext、Contract、Harnessを通じて仕事を任せる。

その結果をVerificationやEvalで観測し、Learningとして次のShapingへ戻す。

これはAndrew Ngの公式な対応表ではなく、前の記事の設計対象とSkills Mapを私なりに重ねた見方です。

この見方をすると、Coding Agentを使うことはAI駆動開発の一部分にすぎません。

モデルへうまく指示を出すことも重要です。Contextを整えることも、Harnessを設計することも、Verificationを自動化することも重要です。

ただ、それらが高速になればなるほど、最初と最後にある「何を変えたいのか」「結果を見て次に何をするのか」という判断の質が効いてきます。

## エンジニアの仕事は、実装から「意思決定のループ」へ広がる

AIがコードを書く話では、「エンジニアの仕事がどこまでなくなるのか」という議論になりがちです。

しかし、自分でAIを使って開発していると、少し違う感覚があります。

コードを直接書く時間は減っています。

その代わり、

- 問題を整理する
- AIへ渡すContextと制約を決める
- 複数の設計を比較する
- 実行結果を見る
- 失敗の原因を探す
- 続けるか止めるか判断する
- 次の実行方法を変える

といった時間が増えています。

実装という一つの作業が減り、その前後にあった意思決定のループへ仕事が広がっています。

```text
Problem
  ↓
Shape
  ↓
Build
  ↓
Verify
  ↓
Learn
  ↓
Decide
  ↺
```

AIがBuildを担う範囲が広がるほど、人間はこのループのどこで判断し、何をAIへ任せ、どこで止めるのかを設計する必要があります。

重要なのは、人間がすべてを細かく指示することではありません。

AIが自律的に進められる範囲を広げながら、方向を決めるための情報、制約、観測方法、停止条件を用意することです。

エンジニアリングの対象がコードだけではなく、**価値へ到達するための意思決定と実行のループそのもの**へ広がっている、と考えると理解しやすくなります。

---

## 作る力が安くなるほど、判断の質が差になる

AIモデルもCoding Agentも、これからさらに強くなるでしょう。

より長い仕事を任せられるようになれば、人間がすべての実装手順を指定する必要はさらに減っていきます。

一方で、

- 誰の問題を解くのか
- 何を変えたいのか
- どのリスクを許容するのか
- 何をもって成功とするのか
- どの条件なら止めるのか
- 結果を見て次に何をするのか

という判断は残ります。

むしろ、AIが速くなるほど、一つの判断から生み出される変更量も大きくなります。

前の記事では、

> AIがコードを書くほど、エンジニアリングは「何を作るか」に戻っていく。

と書きました。

Andrew NgのSkills Mapを見て、今はもう少し先まで考えています。

**「何を作るか」を決めること自体が、AI時代の重要なエンジニアリング能力になる。**

そして、その能力は「センス」という曖昧な言葉だけで片付けるものではありません。

問題を観察する。証拠を集める。仮説を作る。Scopeと制約を決める。小さく作る。結果を検証する。止めるべきなら止める。学びから次の判断を変える。

このループそのものを設計し、速く回せることが重要になります。

---

## 速くしたいのは、コードを書く時間だけではない

AI Codingの生産性を考えるとき、「実装に何時間かかったか」「コードをどれだけ速く書けたか」に目が向きます。

もちろん、それも重要です。

ただ、プロダクト開発全体で見れば、本当に短くしたい時間はもう少し長いはずです。

```text
Problem
  ↓
Hypothesis
  ↓
Shape
  ↓
Build
  ↓
Verify
  ↓
Learn
```

問題を見つけてから、何かを作り、それに価値があるのかを学べるまでの時間。

私は、AI時代には **Time to Codeだけでなく、Time to Learningを短くする** という視点が重要になるのではないかと考えています。

Buildだけが10倍速くなっても、何を作るかを決めるまでに何週間もかかり、結果の検証にも何週間もかかるなら、プロダクトとしての学習速度は大きく変わりません。

逆に、問題を観察し、仮説を作り、小さく試し、証拠を見て次の判断を変えるところまでを短くできれば、AIが生み出す速度を価値へつなげやすくなります。

AIによって本当に速くしたいのは、コードを書く時間だけではない。

**問題を見つけてから、価値があると確認できるまでの時間を短くする。**

そこまで含めて、AI時代のエンジニアリングなのだと思います。
