# AIに記事を書かせる前に、「学びが戻る仕組み」を作ることにした

> 区分: 個人

## 自動投稿の記事を読んで、気になったのは「投稿」ではなかった

最近、「1日3回、noteをAIエージェントが自動投稿する仕組み」を公開している記事を読みました。

https://note.com/like_tulip76/n/n7548bacaf90b

そこでは、URLを情報インボックスへ集め、AIが翌日の記事を作り、決まった時間に投稿し、その日の反応を次の生成へ戻す流れが紹介されていました。

最初は「かなり自動化されているな」と思いました。

ただ、読み進めるうちに、自分が一番気になったのは自動投稿ではなくなりました。

面白かったのは、次の流れです。

```
集める
  ↓
書く
  ↓
公開する
  ↓
結果を見る
  ↓
次の記事へ戻す
```

記事を書く処理ではなく、**公開した結果が次の入力へ戻っていること**でした。

自分の記事作成環境にも、テーマ発掘、記事の種、執筆、複数観点レビュー、公開前の確認、媒体別の運用、公開後のメトリクス取得はすでにありました。

でも、よく見ると、それぞれが「ある」だけでした。

「この外部情報から、どの記事の種が生まれたのか」

「その種から、どの記事が公開されたのか」

「公開後の数字から、何を学んだのか」

「その学びが、次の記事や運用ルールへ戻ったのか」

ここが一本につながっていませんでした。

そこで、自動投稿を増やす前に、まずこの流れを閉じることにしました。

先に結論を書くと、今回増やしたかったのは記事を書く能力ではありません。

**自動化する中心を「文章生成」から「状態・根拠・結果をつなぐこと」へ移しました。**

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine\_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善や、個人のメディア運用を実験しています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。

## 問題は記事を作ることではなく、途中のつながりが消えることだった

記事制作は、工程ごとに見るとかなり自動化できます。

調査をAIに任せることもできます。

構成を作らせることもできます。

本文を書かせることもできます。

レビューも複数のAIへ分けられます。

公開前チェックもスクリプト化できます。

ただ、工程を増やすほど別の問題が出てきました。

**なぜその記事を作ったのかが、途中で消えやすい。**

たとえば、XやnoteやGitHubで面白い情報を見つけます。

その場では「これは記事にできそう」と思います。

数日後、そのテーマで記事を書きます。

さらに時間が経って公開し、数字を確認します。

ここまで進むと、元のきっかけと公開結果の関係がかなり薄くなります。

記事単体は残っていても、その前後にある判断が残っていません。

これは、コードで言えばログがない状態に近いと感じました。

何かが成功しても、

- どの入力が効いたのか
- どの判断が効いたのか
- 次も再現できるのか

が分かりません。

記事制作を自動化したいのに、学習だけが毎回人間の記憶に戻っていました。

## まず「記事の種」に出典を持たせた

最初に変えたのは、記事本文ではありません。

記事の種です。

これまでの記事の種（Seed）は、

- タイトル
- 日付
- テーマ
- 状態
- 本文メモ

くらいでも運用できていました。

そこへ、最低限の由来を持たせるようにしました。

```yaml
seed_id: seed-20260923-content-closed-loop
source: external
source_url: https://note.com/...
evidence_status: verified
promoted_to:
```

ここで大事なのは、単にURLを残すことではありません。

**観測した事実と、自分の解釈を分けること**にしました。

たとえば外部記事を読んだ場合、

「その記事に何が書いてあったか」

と

「それを読んで自分が何を考えたか」

は別です。

AIで記事を作ると、この2つは簡単に混ざります。

引用元に書かれていない解釈が、いつの間にか元記事の主張として扱われることもあります。

そのためSeedでは、

- 観測事実
- 自分の解釈
- 違和感
- 仮説
- 次に試すこと

を分けました。

記事の質を上げるというより、後から判断の経路を追えるようにするためです。

## 次に、Seedと記事の関係を「関係図」として見えるようにした

Seedが増えると、今度は別の問題が出ます。

どのSeedがどの記事になったのか分からなくなります。

そこで、Seedから再生成できる読み取り専用のArticle Graph（記事の関係図）を作りました。

新しいデータベースは増やしていません。元データはあくまでSeedで、Article Graphはその情報を読みやすく並べ直した派生物です。

```
Seed A
 ├─ Article A
 ├─ Tutorial候補
 └─ Insight候補

Seed B
 └─ Article B
```

ここで意識したのは、Article Graphを新しい正本にしないことでした。

Article Graphを直接編集すると、Seedと関係図のどちらが正しいのか分からなくなります。

そのため、

```
Seed
  ↓
自動生成
  ↓
Article Graph
```

という一方向だけにしました。

導入直後の時点では12件のSeedがあり、そのうち新しい契約で作ったものが3件、既存形式のまま残しているものが9件です。

既存9件を一括移行しなかったのも意図的です。

仕組みを入れた瞬間に過去データを全部きれいにしたくなりますが、移行作業そのものが目的になりやすいからです。

新しく作るものから適用し、必要になったものだけ後から移すことにしました。

## さらに、公開後の反応データへSeed IDをつなげた

次にやったのが、公開後のメトリクス（反応データ）との接続です。

もともと、Zenn、Qiita、noteの公開記事から反応数を取得する仕組みはありました。

でも、そこには「どのSeedから生まれた記事か」という情報がありませんでした。

ここでも新しい台帳は作りませんでした。

Seedが持っている `promoted_to` を使います。

```
Seed
  ↓ promoted_to
公開URL
  ↓
媒体API
  ↓
Metrics + seed_ids
```

公開URLと媒体APIが返すURLを照合して、記事側へ `seed_ids` を付けます。

たとえば、

```json
{
  "title": "記事タイトル",
  "like_count": 10,
  "seed_ids": [
    "seed-20260923-content-closed-loop"
  ]
}
```

という形です。

これで初めて、

「この数字は、どのSeedから生まれた記事の結果なのか」

を辿れるようになります。

共有URLには余分なパラメータが付くことがあるため、照合前に同じ記事を同じURLとして扱えるよう正規化します。

また、過去Seedに自動付与した不安定なIDはメトリクスへ使わないことにしました。

ファイル名を変えただけでIDが変わってしまうからです。

メトリクスにつなぐのは、明示的に固定した `seed_id` だけです。

## 自動化したのに、公開は自動化しなかった

ここまでやると、そのまま公開まで自動化したくなります。

実際、最初に読んだ記事では、ブラウザ操作を使ってnote投稿まで自動化していました。

でも、今回はそこを取り込みませんでした。

理由は単純です。

**今のボトルネックは投稿ボタンではなかったからです。**

公開直前には、

- 事実関係
- 主張の境界
- 読者に伝えたい中心メッセージ
- 媒体との相性
- 公開してよい内容か

を見ます。

ここは、現在も人間の承認として残しています。

同じ理由で、公開後の数字を見てSkillや記事戦略を自動更新することもしませんでした。

1本の記事が伸びたからといって、

「このタイトル構造が正解」

「このテーマを増やすべき」

と自動的に一般化すると、かなり危険です。

数字は観測結果であって、原因ではありません。

そこで、次は直接ルールを書き換えるのではなく、

```
公開後のメトリクス
  ↓
学びの提案（Learning Proposal）
  ↓
人間が採用 / 棄却
  ↓
次のSeed / 運用ルール
```

という一段を挟む予定です。

## この記事自体をCanaryにしている

ここまで書いてきた仕組みには、まだ一つ欠けているものがあります。

新しい `seed_id` を持つSeedから、実際に公開された記事がまだありません。

つまり配線はできましたが、端から端まで流した実績はまだありません。

そこで、**この記事そのものを最初のCanary（本番の流れを最初に通す試験記事）にしています。**

元になっているSeedは、

```
seed-20260923-content-closed-loop
```

です。

この記事を公開したら、そのURLをSeedの `promoted_to` に追加します。

その後、次回のメトリクス取得でこの記事に同じ `seed_id` が付くことを確認します。

そこで初めて、

```
Signal
  ↓
Seed
  ↓
Article
  ↓
Publish
  ↓
Metrics
  ↓
Learning
```

が一周します。

これは少し面白い状態です。

この記事は「閉ループの記事」ではなく、**閉ループを成立させるためのテストデータそのもの**でもあります。

## 作ってみて分かったのは、自動化より「追跡可能性」が先だということ

今回の実装で、記事を書くAIは増やしていません。

新しい執筆エージェントも作っていません。

レビュー担当も増やしていません。

新しいGraph DBも入れていません。

自動投稿も入れていません。

増やしたのは、

- Seedの安定ID
- 出典
- 事実と解釈の境界
- Seedと記事の関係
- 記事とメトリクスの関係

です。

つまり、能力を増やしたというより、**途中で情報が消えないようにした**だけです。

でも、今の自分にはこちらの方が重要でした。

AIを使うと、作れるものは急速に増えます。

記事も増やせます。

レビューも増やせます。

調査も増やせます。

一方で、「なぜそれを作ったのか」「結果から何を学んだのか」が追えなければ、速く回しているだけで学習は積み上がりません。

これはソフトウェア開発で、実装速度だけを上げてもユーザー価値の学習速度が上がるとは限らないのと似ています。

記事制作でも、自分が見たいのは本数ではなく、

**きっかけ（Signal）から学び（Learning）までがどれだけ途切れず流れたか**

なのだと思います。

## 次にやること

次は、このCanaryを最後まで流します。

1. この記事を公開する
2. Seedへ公開URLを記録する
3. メトリクス取得で `seed_id` が付くことを確認する
4. 結果から学びの提案を1件作る
5. 採用するか、人間が判断する

ここまで通れば、記事制作は「書いて公開する流れ」から、

**観測して、作って、届けて、学んで、次へ戻す流れ**

になります。

AIにもっと記事を書かせるのは、そのあとでも遅くありません。

まずは、作ったものから学べる状態を作る。

今はその方が、メディアを育てるうえで大事だと考えています。
