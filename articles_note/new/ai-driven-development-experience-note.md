# AIは経験を不要にしなかった。実装が速くなるほど、判断が前に出た

> 区分: 個人

## AIがコードを書くほど、人間の判断は前に出る

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善と、チームでの意思決定の進め方を考えています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。

AIがコードを書けるようになれば、開発経験の差は小さくなるように見えます。

現場で使い続けると、私の感覚は少し違いました。任せる作業が増えるほど、人間の仕事が消えるのではなく、**判断のタイミングが前に移る**。

何を作るのか。どこまで任せるのか。どの状態なら次へ進めるのか。何を証拠として「完了」とみなすのか。実装が速くなるほど、こうした判断を後から考える余地は小さくなります。

テックリード、プロジェクトマネージャー（PjM）、プロダクトマネージャー（PdM）、エンジニアリングマネージャー（EM）、スクラムマスター。

当時は別々の仕事だと思っていました。AIエージェントと開発するようになってから、それらの経験が、目的・進行・技術・委譲・学習という5つの判断として一本につながって見えるようになりました。

この記事は、AI駆動開発のツール解説ではありません。5つの役割で身につけた判断が、個人のAI活用をチームへ広げるときにどこで再利用されるのか。欠けると何が起きるのか。そして経験を、次のタスクでも使える形へどう外部化するのか。そこまでを書きます。

先に結論です。

**AIは経験を消していません。実装の中に埋もれていた判断を、表に出しました。**

5つの役職をすべて経験しないとAIを使えない、という話ではありません。必要なのは肩書きではなく、その判断を個人・チーム・仕組みのどこかが引き受けることです。

## 実装が速くなるほど、判断は前倒しになる

使い始めは、実装をどこまで任せられるかに目が向きます。

仕様が明確な変更や定型作業なら、要件を渡してコードを書き、テストを足し、エラーを直すところまで短時間で進みます。これは大きな価値です。

ただ、任せる範囲が広がるにつれて、人間側の仕事は減るというより、実装の前後へ移っていきました。

- 何を目指すか
- どういう順番で進めるか
- どの技術基準を守るか
- どこまで委譲するか
- 失敗を次の実行へどう残すか

AIエージェントを「非常に速く動くが、文脈の継続が自動ではないチーム」にたとえると、構造の一部は伝わります。目的を共有し、仕事を分け、途中で確認し、安全に働ける環境を整える必要があるからです。

ただし、比喩はそこまでです。

AIは人間のメンバーではありません。結果に責任を負わず、必要な文脈を常に安定して保持するとは限らず、一度の指摘が次の実行へ確実に引き継がれるわけでもありません。人間と同じように任せられる、という意味ではありません。

## 「成功」が3つある。取り違えると、失敗を成果として採用する

AI活用で厄介なのは、失敗が失敗に見えないことです。

前提を誤解したまま、もっともらしい説明や実装を返す。テストが通る範囲だけ満たして、本来の要件を外す。局所的には正しく見えても、既存の設計や運用を壊す。

たとえば、「マージ済みならブランチを削除する」という後処理を任せたとします。典型的な失敗を単純化した仮想例です。

AIがマージ状態を確認せずにブランチを削除し、未マージのプルリクエストまで閉じる。操作自体は完了しています。しかし、依頼の目的は達成していません。

```
ブランチ削除の後処理を任せる
  |
  +- 期待した流れ
  |    マージ状態を確認
  |      -> 未マージ : 停止
  |      -> マージ済 : 削除
  |
  +- 失敗する流れ
       確認せず削除・PRクローズ
         ツール実行   : 成功
         ワークフロー : 失敗（事前条件）
         本来の目的   : 未達
```

ここでは、3つの「成功」を分けて考える必要があります。

1. **ツール実行**：削除やクローズという操作を実行できたか
2. **ワークフロー**：次へ進む事前条件を満たしていたか
3. **本来の目的**：守るべき成果を失わず、依頼を達成できたか

操作できたことと、目的を達成したことは同じではありません。

**「動いた」と「採用できる」も同じではありません。**

コード生成の上手さだけを見ても、この失敗は防げません。事前条件を満たさなければ止める制御、権限の境界、実際の状態を外部から確かめる検証が必要です。

判断基準が曖昧なまま実行速度だけ上がると、AIは不足した前提を補いながら先へ進みます。出力がもっともらしく、しかも短時間で積み上がるほど、人間の検証が追いつかず、誤りを成果として採用しやすくなります。これが、ここでいう「AIに翻弄される」状態です。

## 先に残すもの。次のAIタスクの5つの確認欄

経験は、暗黙知のままでは、その人がその場で確認している間しか働きません。

そこで私は、経験から得た判断を、次のAIタスクにも残せる5つの確認欄として捉えています。

1. **目的**：誰のどの課題か。受け入れ条件は何か。提供後に観測したい成果は何か。今回やらないことは何か
2. **進行**：どの順番で進めるか。どこで計画と実態を確認するか。計画が変わったら誰に戻すか
3. **技術**：守る設計と非機能は何か。何をもって妥当とするか。「動いた」と「採用できる」を何で分けるか
4. **委譲**：AIだけで進めてよい範囲はどこか。承認・停止・復旧が必要なのはどこか。完了報告以外に何を見るか
5. **学習**：失敗を次のルール、テスト、ツールのどこに残すか。チャットで終わらせない置き場はどこか

すべてを詳細に埋める必要はありません。ただし、空欄を無視しないことが重要です。

判断者や検証手段がない欄があるなら、そこは「経験不足の告白」ではなく、**AIに任せる範囲を狭めるか、別の確認手段を置く場所**です。

次のような最小テンプレートでも使えます。

```md
## AIタスク確認

- 目的
  - 解決する課題:
  - 受け入れ条件:
  - 対象外:

- 進行
  - 実行順序:
  - チェックポイント:
  - 計画変更時の戻し先:

- 技術
  - 守る境界・非機能:
  - 検証方法:
  - 採用基準:

- 委譲
  - AIだけで進めてよい範囲:
  - 人間承認が必要な操作:
  - 停止・復旧条件:

- 学習
  - 今回の学びを残す場所:
  - 次回の再発確認:
```

チームで使うなら、ここに担当者、承認者、通過に必要な証拠、停止時の連絡先を足します。

以下は職能の標準定義ではありません。私自身の経験から、AI駆動開発で再利用している判断を抜き出したものです。

### PdMの経験 → 目的と完成条件

**タスクに残すもの**

- 誰の、どの不便を減らすか
- 出すもの / 出さないもの
- 観測できる受け入れ条件
- 迷ったときの優先順位（速度 / 精度 / 範囲 / 互換）
- 提供後に見たい変化。見ないなら「今回は見ない」

**証拠**

- 受け入れ条件を満たす出力、画面、API応答
- 対象外への影響がないと確認できるテストや差分

**止める条件**

- 課題が「実装したいこと」にすり替わった
- 受け入れ条件が「動いた」だけになった

受け入れ条件はPdMが一人で閉じるものではありません。非機能、検証方法、技術制約はテックリードや開発チームと一緒に、実際に確認できる形へ落とします。

ここが曖昧なまま指示だけ詳しくしても、AIは不足した目的を補完して走ります。

### PjMの経験 → 分解と進行

**タスクに残すもの**

- 段階（調査 → 設計 → 実装 → テスト → 検証）と、今どこまで許可するか
- 先に必要な情報、PR、権限、環境
- 次へ進むチェックポイント
- 計画変更時の再確認先

**証拠**

- 今の段階の完了記録
- 次へ渡す前提が、推測ではなく明示されていること

**止める条件**

- 大きな要求を一括で渡し始めた
- 計画が変わったのに再確認していない
- 途中成果が見えず、完了報告だけが来ている

段階を分ける理由は管理のためだけではありません。AIが一度に推測しなければならない範囲を小さくし、逸脱を早く見つけるためです。

### テックリードの経験 → 境界と採用基準

**タスクに残すもの**

- 壊してはいけない境界（モジュール、データ、API、移行）
- 非機能（セキュリティ、性能、互換、運用）
- 検証手段
- 「動いた」と「採用できる」を分けるレビュー観点
- より小さく単純にできないかという基準

**証拠**

- 要求を検証するテスト、または再現手順
- 既存設計を壊していないことの確認方法

**止める条件**

- テストが実装の存在確認だけになっている
- 局所最適のために責務の境界をまたいでいる
- 採用判断をAIの説明文だけに頼っている

AIは局所的な実装を高速に作れます。しかし、その変更がコードベース全体にとって妥当かどうかは別の問題です。

ここで必要なのは、コードを書けるかではなく、**どの証拠があれば採用してよいかを定義すること**です。

### EMの経験 → 委譲してよい範囲

**タスクに残すもの**

- 参照してよい情報 / 禁止する情報
- 使ってよいツールと権限
- AIだけで進めてよい操作
- 人間承認が必要な操作
- 失敗時の戻し方と、判断を返す相手
- 実行過程の残し方（ログ、PR、計画差分）

**証拠**

- 許可範囲内だけで実行された記録
- 完了報告以外の外部状態（リポジトリ、CI、環境）

**止める条件**

- 権限が「便利だから全部」になっている
- 現在状態を確認できない
- 承認なしで、取り消しが難しい操作や異常が見えにくい操作に入った

自律性を上げることと、権限を無制限に渡すことは違います。

また、「技術的には戻せる」という理由だけで承認対象から外すのも危険です。復元できても、異常に気づくまで時間がかかる操作があります。先ほどのブランチ削除の仮想例は、その一つです。

### スクラムマスターの経験 → 検査と適応

**タスクに残すもの**

- 見る失敗の観点（コンテキスト不足、観測不能、レビュー遅れ、責任分界、再発）
- 学びの置き場（ルール、テスト、チェックリスト、ツール）
- 次の実行で再発を見る方法
- 完了報告以外に観測するもの

**証拠**

- 失敗から得た学びが外部化された差分
- 次のタスクの確認欄に、今回の学びが反映されていること

**止める条件**

- 「AIが悪かった」で閉じている
- 指摘がセッション内だけで消えている
- 同じ確認を、また人が記憶だけで繰り返している

検査と適応は、透明性が前提です。AIの完了報告しか見えない状態で振り返っても、正しい改善にはつながりません。

また、セッション内で伝えた指摘は、そのままでは次の実行に安定して再利用できません。ルール、テスト、チェックリスト、ツールなどへ外部化して初めて、次の人や次のエージェントが使える学びになります。

## 空欄のまま速くすると、判断の欠落も増幅する

ここでいう「判断機能が欠ける」とは、経歴が足りないという意味ではありません。

その判断が、人にも仕組みにも存在しない状態です。

```
役割             判断   欠けたまま進めたときに起きやすいこと
----------------------------------------------------------------
PdM             : 目的 : 間違った課題を速く実装する
PjM             : 進行 : 途中の逸脱を見逃す
テックリード     : 技術 : 動くが採用できないコードを作る
EM              : 委譲 : 権限と停止条件のない委譲になる
スクラムマスター : 学習 : 同じ失敗を次の実行で繰り返す
```

AIは実装の一部を担えます。しかし、目的、設計、検証、責任に関する判断まで自動的に正しく担うとは限りません。

自分たちで妥当性を評価できない領域ほど、委譲する範囲を狭くし、知見のある人のレビューか、客観的な検証手段を先に置きます。

確認の頻度と手段を変えないまま、大量の変更や自動実行だけ許可すると、判断が欠けた状態で先へ進む距離も伸びます。実行速度が上がるほど、ガードレールの価値も上がります。

もちろん、役職経験があれば安全というわけでもありません。流暢な説明を信じる。大量の差分にレビューが追いつかない。そうなれば、経験者でも同じように誤りを見逃します。

経験は免許証ではありません。どこにリスクがあり、何を確認すべきかを考える材料です。

## 経験を勘で使っているうちは、組織の仕組みにならない

AIに作業を実行させても、組織としての最終的な採用判断と結果への責任は人間側に残ります。

だからこそ、担当者、最終決定者、条件を満たさなければ次へ進めないゲートを決める。レビュー、テンプレート、テスト、ツールとして仕組みに埋め込む。

経験がある人だけが勘で止められる状態では、チームとして再現できません。判断基準を外に出せれば、経験の浅いメンバーでも「どこで止めるべきか」を共有できます。

私の運用では、受け入れ条件をタスクに残し、実装前の計画レビューと、計画変更時の再確認をワークフローに入れています。

実行後はAIの完了報告をそのまま根拠にせず、テスト、リポジトリの実際の状態、人間または別経路のレビューで確認します。現在状態を確認できない、計画やスコープが変わった、必要な検証を実行できない場合は、AIだけで先へ進めず判断者へ戻します。

振り返りで見つけた失敗は、次のルールや回帰テストへ移します。

これはAIの自由を奪うためではありません。人が経験的に行っていた「疑う」「止める」「確かめる」を、次のタスクや次の人でも使える形に変えるためです。

なお、この記事では、この確認欄によって品質や速度がどれだけ改善したかという効果測定までは示していません。現時点で言えるのは、**判断の置き場を先に決めることで、AIの出力をそのまま成果として受け取らずに済む**ということです。

## まとめ

PdM、PjM、テックリード、EM、スクラムマスターとして培った経験は、AI駆動開発では、**エージェントが成果を出せる開発システムを設計し、結果を検証する力**として一本につながりました。

AIは実装を速くできます。

だからこそ、目的・進行・技術・委譲・学習の5つの判断を後回しにしない。判断が空欄のままなら、埋めてから進むか、AIに任せる範囲を狭める。

次のAIタスクを始める前に、この5つを書き出してみてください。

AIは経験を消していません。

**実装が速くなったことで、これまで実装の中に隠れていた判断の価値が、むしろ見えやすくなりました。**

それを個人の勘で終わらせず、チームが再利用できる仕組みへ変えていく。私は、そこがAI駆動開発を個人技から組織能力へ変える境目だと考えています。
