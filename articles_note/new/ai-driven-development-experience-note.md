# AIは経験を不要にしなかった。5つの役割がAI駆動開発で一本につながった

> 区分: 個人

## AIがコードを書くほど、人間の判断が問われる

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine\_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善や、チームでの意思決定の進め方について考えています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。

AIがコードを書けるようになれば、開発経験の差は小さくなるように見えます。

しかし、AI駆動開発を現場で続けるなかで、私は逆の感覚を持つようになりました。AIに任せる作業が増えるほど、過去の経験を使っていることに気づいたからです。

テックリード、プロジェクトマネージャー（PjM）、プロダクトマネージャー（PdM）、エンジニアリングマネージャー（EM）、スクラムマスター。

それぞれを担っていたときは、別々の仕事をしているつもりでした。AIエージェントと開発するようになってから、それらが目的・進行・技術・委譲・学習という5つの判断で一本につながり始めました。

この記事で扱うのは、AI駆動開発の仕組みそのものではありません。私が5つの役割で身につけた判断が、AI活用を個人からチームへ広げるときにどこで再利用されているかを振り返ります。その判断が欠けると何が起きるのか、経験をどう仕組みに変えられるのかも整理します。

先に結論を言えば、AIによって過去の経験が不要になったのではありません。

**経験の価値が、コードを書く力だけでなく、AIの仕事を設計・検証する力として現れるようになりました。**

これは、5つの役職を経験しなければAIを使えないという話ではありません。必要なのは肩書きではなく、それぞれの役割が担ってきた判断を、個人、チーム、開発の仕組みのどこかで引き受けることです。

## 任せる範囲が広がるほど、人間の判断が前面に出る

AIエージェントを使い始めた頃は、実装をどれだけ任せられるかに目が向きやすい状態でした。

仕様が明確な変更や定型作業であれば、要件を渡してコードを書き、テストを追加し、エラーを修正するところまで短い時間で進められます。

ただ、任せる範囲が広がっても、人間側の仕事がなくなるわけではありませんでした。何を目指し、どう進め、どの技術基準を守り、どこまで委譲し、失敗からどう学ぶか。この5つが、人間側に残る仕事として前に出てきます。

AIエージェントを「非常に速く動くが、文脈を持ち越さないチーム」にたとえると、この感覚の一部は伝わりやすいかもしれません。

目的を共有し、仕事を分け、途中で成果を確認し、安全に働ける環境を整える構造はよく似ています。ただし、これは仕事の分解とレビューの構造を説明する範囲に限った比喩です。

AIは人間のメンバーではありません。結果に責任を負わず、必要な文脈を安定して持ち続けるとは限らず、一度の指摘が次の実行へ引き継がれる保証もありません。人間の能力や成長過程と比べているのではなく、同じように任せられるという意味でもありません。

## 返ってくるのは、もっともらしい次の一手

AIは、ときどき嘘をつくと言われます。

ここでいう「嘘」は、意図的な欺瞞ではありません。前提を誤解したまま、もっともらしい説明や実装を生成する現象、一般にハルシネーションと呼ばれるものを指しています。

しかも、その誤りは明らかな失敗として現れるとは限りません。存在しない仕様を断定的な口調で説明することもあれば、テストが通る範囲だけを満たして本来の要件を外すこともあります。局所的には正しく見えても、既存の設計や運用を壊す場合もあります。

たとえば「マージ済みならブランチを削除する」という後処理を任せたとします（典型的な失敗を単純化した仮想例です）。AIエージェントがマージ状態を確認せずにブランチを削除し、未マージのプルリクエストまで閉じれば、操作自体は完了していても依頼の目的は達成していません。

```
ブランチ削除の後処理を任せる
  |
  +- 期待した流れ
  |    マージ状態を確認
  |      -> 未マージ : 停止
  |      -> マージ済 : 削除
  |
  +- 失敗する流れ
       確認せず削除・PRクローズ
         ツール実行  : 成功
         ワークフロー: 失敗（事前条件）
         本来の目的  : 未達
```

この例では、3つの「成功」を分けて考える必要があります。

1. **ツール実行**：ブランチ削除とプルリクエストのクローズを実行できたか
2. **ワークフロー**：次へ進む事前条件を満たしていたか
3. **本来の目的**：守るべき成果を失わず、依頼を達成できたか

操作できたことと、目的を達成したことは同じではありません。

この問題は、コード生成能力だけを評価していても防げません。事前条件を満たさなければ次へ進めない制御、危険な操作の権限境界、実際の状態を外部から確かめる検証がワークフロー側に不足していると、この失敗は起こり得ます。

判断基準がなければ、AIは不足した前提を補って進めます。その出力がもっともらしく、しかも短時間で積み上がるほど、検証が追いつかず、誤りを成果として採用しやすくなります。これが、私の考える「AIに翻弄される」状態です。

## 5つの役割の経験は、どこで活きているか

5つの役割はそれぞれ、目的・進行・技術・委譲・学習という異なる判断を担っていました。

実際の責任範囲は組織によって異なり、役割同士も重なります。ここで示すのは一般的な職務定義ではなく、私自身の経験がAI駆動開発のどこに接続したかという整理です。

この5つのうちスクラムマスターだけはスクラムガイドに定義のある役割ですが、ここで借りているのはその定義全体ではなく、検査と適応という経験主義の考え方です。残る4つは、組織ごとに定義の異なる職名として扱います。

これらの観点は、役職に就かなければ身につかないものでもありません。ユーザー課題を確認する、受け入れ条件を書く、計画や設計のレビューに参加する、インシデントを振り返る。そうした実践を通じて、一つずつ獲得できます。

また、ここに挙げる判断は、いずれも一人で所有するものではありません。PdMが定める受け入れ条件は、技術的な制約や性能・セキュリティなどの非機能要件、検証方法とあわせてテックリードや開発チームと共同で受け入れ可能な形へ落とし込みます。

権限や停止条件の設計は認可や監査を扱う基盤・セキュリティの担当者と分担し、改善項目はチームで担当者と完了条件を決めて、次の実行で再発の有無を確かめます。

### PdM（目的と完成条件を定める）

PdMとしての経験は、「何を作るか」よりも、その手前にある「なぜ作るのか」を明らかにするときに活きています。

AIへの指示で重要なのは、文章をうまく書くことだけではありません。

- 解決したいユーザーの課題
- 期待する成果
- 今回のスコープと対象外
- 守るべき制約
- 完成とみなす条件（受け入れ条件）
- 判断に迷ったときの優先順位

これらを定義するほど、AIが目的に沿って実装できたかを判断しやすくなります。

### PjM（仕事を分解し、進行を制御する）

PjMとして培ったタスク分解や依存関係の整理も、そのままAIエージェントの実行計画に使えます。

大きな要求を一度に渡すと、AIは多くの前提を自分で補います。実装が進んでから前提の違いに気づけば、手戻りも大きくなります。

そこで、調査、設計、実装、テスト、検証と段階を分けます。依存関係を整理し、途中にチェックポイントを設け、計画が変わったら再確認します。

段階を分けるのは、AIが一度に推測しなければならない範囲を小さくし、逸脱を早く見つけるためです。

### テックリード（技術的な境界と品質基準を作る）

AIは局所的な実装を高速に作れます。一方で、その変更がコードベース全体にとって妥当かどうかは、別の問題です。

既存のアーキテクチャと整合しているか、責務の境界を壊していないか、将来の変更に耐えられるか。セキュリティや性能上の問題はないか、テストが本当に要求を検証しているか、もっと小さく単純な実装にできないか。

テックリードとしての設計・実装・レビュー経験があると、こうした点を確かめたうえで、「動いた」という報告と「採用できる」という判断を分けられます。

### EM（安全に委譲できる環境を整える）

EMの仕事は、目的と期待値を共有し、必要な権限を渡し、成果を確認できる状態を作ることだと思っています。

AIエージェントへの委譲でも構造は似ています。

- 参照してよい情報を明確にする
- 実行できるツールや権限を制限する
- 自動実行してよい範囲を決める
- 人間の承認が必要な操作を定義する
- 失敗しても戻せる状態を用意する
- 実行過程と結果を追跡できるようにする

承認が必要な操作を決めるとき、基準は「戻せるかどうか」だけではありません。戻せる操作でも、誤りに気づくまでに時間がかかるなら、実行前に状態を確認する対象になります。ブランチやプルリクエストの状態のように、技術的には復元できても完了報告からは異常が見えない操作がその例です。

自律性を高めることと、無制限に権限を与えることは違います。

### スクラムマスター（検査と適応を仕組みにする）

AI駆動開発では、一度で完璧な指示やワークフローを作ることは難しいものです。実際に動かし、結果を観察し、失敗の原因を見つけ、次の実行方法を変えていく必要があります。

ここで活きるのが、スクラムマスターとして培った検査と適応の考え方でした。もとはスクラムの経験主義の柱で、検査と適応は透明性を前提に置きます。何が起きているかが見えていなければ、検査は誤った適応を生みます。

AI駆動開発でも同じで、AIの完了報告しか見えていない状態で振り返りを回せば、改善の方向自体がずれます。

問題が起きたとき、単に「AIが間違えた」で終わらせません。

- 必要なコンテキストが不足していなかったか
- 成功条件を観測できる状態だったか
- レビューのタイミングが遅すぎなかったか
- 人間とAIの責任分界が曖昧ではなかったか
- 同じ失敗を防ぐテストやルールを追加できないか

失敗をモデルの能力だけに帰属させず、開発システムの改善材料として扱います。

AIは、一度指摘しても、その指摘自体を次のセッションへ持ち越すわけではありません。セッションをまたいで残るのは、プロンプト、ルール、テスト、チェックリスト、ツールとして外に書き出したものだけです。振り返りから得た学びをそこへ反映して初めて、次の人が使える学びになります。

## 判断機能が欠けると、AIは間違いまで増幅する

ここでいう「判断機能が欠ける」とは、個人の経歴が足りないという意味ではありません。経験から生まれた判断が、担当者にも開発の仕組みにも存在しない状態を指します。

5つの役割を並べると、その状態で起きやすい失敗との対応関係が見えてきます。

```
役割             判断   欠けたときの失敗
---------------------------------------
PdM             : 目的 : 間違った課題を速く実装
PjM             : 進行 : 途中の逸脱を見逃す
テックリード     : 技術 : 動くが保守できないコード
EM              : 委譲 : 権限と停止条件のない委譲
スクラムマスター : 学習 : 同じ失敗が再発する
```

テックリード的な判断が欠ければ、保守できないコードだけでなく技術的な欠陥も見逃します。スクラムマスター的な判断が欠ければ、一度直したはずの失敗が次のセッションで再発し、同じ確認を毎回属人的に繰り返すことになります。

AIは実装作業の一部を担えます。しかし、目的設定、設計、検証、責任に関する判断まで自動的に正しく担うとは限りません。自分やチームで妥当性を評価できない領域ほど、委譲する範囲を狭くし、知見のある人のレビューや客観的な検証を先に用意する必要があります。

そして、確認の頻度と手段を変えないまま大量の変更や自動実行まで許可すれば、判断の欠落が事故へ到達するまでの時間は短くなります。

## 必要なのは肩書きではなく「判断機能」

反対に、役職経験があれば安全というわけでもありません。経験があっても、流暢な説明を信じたり、大量の差分にレビューが追いつかなかったりすれば、AIの誤りを見逃します。経験は免許証ではなく、どこにリスクが潜み、どんな確認が必要かを考える材料です。

AIに作業を実行させても、判断と結果の責任は人間が持ちます。チームで分担し、各判断の責任者、最終決定者、条件を満たさなければ次へ進めないゲートを決めてもかまいません。レビュー、テンプレート、テスト、ツールとして仕組みに埋め込むこともできます。

経験がある人だけが勘でAIを制御できる状態では、組織として再現できません。逆に、経験から得た判断基準を外部化できれば、経験の浅いメンバーも安全にAIを活用しやすくなります。

この考えから、私は受け入れ条件をタスクに残し、実装前の計画レビューと、計画変更時の再確認をワークフローへ組み込んでいます。実行後はAIの完了報告を根拠にせず、テスト結果や実際のリポジトリ状態、人間または別経路のレビューで確かめます。

現在状態を確認できない、計画やスコープが変わった、必要な検証を実行できないという場合は、AIだけで進めず判断者へ戻します。振り返りで見つけた失敗は、次のルールや回帰テストへ反映します。

これはAIを細かく管理し、自由を奪うためではありません。これまで人間が経験的に行っていた「疑う」「止める」「確かめる」という判断を、チームで再利用しやすい開発の仕組みへ変えるためです。

## 経験を、タスクの5つの確認欄へ変える

経験は、暗黙知のままではその人が確認し続けるかぎりでしか働きません。

まずは、AIへ仕事を渡す前後に5つの質問を置けます。

1. **目的**：誰のどんな課題を解決するのか。作業完了の受け入れ条件と、提供後に観測したい成果は何か。今回は何をしないのか
2. **進行**：どの順番で進め、どこで計画と実態を確認するのか
3. **技術**：守るべき設計や非機能要件は何か。何を使って妥当性を検証するのか
4. **委譲**：AIだけで進めてよい範囲はどこまでか。承認、停止、復旧が必要なのはどこか
5. **学習**：今回の失敗や発見を、次回のルール、テスト、ツールへどう残すのか

チームで使う場合は、5つの回答に加えて、各判断の担当者、承認者、通過に必要な証拠、停止時の連絡先をタスクへ残します。

このループを回すことで、個人の経験はその場限りの指示ではなく、目的・進行・技術・委譲・学習を支える周辺の仕組みになっていきます。

## まとめ

PdM、PjM、テックリード、EM、スクラムマスターとして培った経験は、AI駆動開発では、**エージェントが成果を出せる開発システムを設計し、結果を検証する力**として一本につながりました。

AIは実装を速くできます。ただし、5つの判断が欠けたままでは、成果だけでなく間違いも速く増幅します。検証が追いつかないまま、誤りを成果として採用してしまうからです。

次のAIタスクを始める前に、目的・進行・技術・委譲・学習の5つを書き出してみてください。答えの空欄が、そのままいま補うべき判断です。

AIは経験を消したのではありません。実装の中に隠れていた経験の中身を、表に出しました。

それを個人の勘で終わらせず、チームが使える仕組みへ変えていく。それが、現場でAIを活かし、AIに翻弄されないために必要な力なのだと思います。
