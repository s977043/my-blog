# AIは経験を不要にしなかった。消えたのは実装で、残ったのは判断だった

> 区分: 個人

## AIがコードを書くほど、人間の判断が問われる

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善と、チームでの意思決定の進め方を考えています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。

AIがコードを書けるようになれば、開発経験の差は小さくなるように見えます。

現場で使い続けると、感覚は逆でした。任せる作業が増えるほど、過去の経験を引き直している。実装が速くなったのではなく、判断を先に出せないと、速さごと事故側に倒れる。

テックリード、プロジェクトマネージャー（PjM）、プロダクトマネージャー（PdM）、エンジニアリングマネージャー（EM）、スクラムマスター。

当時は別々の仕事だと思っていました。AIエージェントと開発するようになってから、それらは目的・進行・技術・委譲・学習の5つの判断として一本につながりました。

この記事は、AI駆動開発のツール解説ではありません。5つの役割で身につけた判断が、個人のAI活用をチームへ広げるときにどこで再利用されるか。欠けると何が起きるか。経験を、次のタスクで使える確認欄へどう落とすか。そこまで書きます。

先に結論です。

**AIは経験を消していません。実装の裏に隠れていた経験を、表に出しました。**

5つの役職を全部経験しないとAIを使えない、という話ではありません。必要なのは肩書きではなく、その判断を個人・チーム・仕組みのどこかが引き受けることです。引き受け先が空なら、空欄のまま進めてはいけません。

## 速さの正体は、判断を後回しにできる錯覚だった

使い始めは、実装をどれだけ任せられるかに目が向きます。

仕様が明確な変更や定型作業なら、要件を渡してコードを書き、テストを足し、エラーを直すところまで短時間で進みます。ここまでは本当です。

任せる範囲が広がっても、人間側の仕事は減りませんでした。何を目指すか。どう進めるか。どの技術基準を守るか。どこまで委譲するか。失敗を次に残すか。この5つが、残る仕事として前に出ます。

AIエージェントを「非常に速く動くが、文脈を持ち越さないチーム」にたとえると、構造の一部は伝わります。目的を共有し、仕事を分け、途中で確認し、安全に働ける環境を整える。ただし比喩はそこまでです。

AIは人間のメンバーではありません。結果に責任を負わず、文脈を安定して持たず、一度の指摘が次の実行へ引き継がれる保証もありません。同じように任せられる、という意味でもありません。

## 「成功」が3つある。取り違えると、成果に見える失敗を採用する

AIはときどき嘘をつく、と言われます。

ここでの嘘は、意図的な欺瞞ではありません。前提を誤解したまま、もっともらしい説明や実装を出す現象です。

嫁介なのは、失敗が失敗に見えないことです。存在しない仕様を断定する。テストが通る範囲だけ満たして要件を外す。局所的には正しく、設計や運用を壊す。

たとえば「マージ済みならブランチを削除する」後処理を任せたとします。典型的な失敗を単純化した仮想例です。AIがマージ状態を確認せずにブランチを削除し、未マージのプルリクエストまで閉じる。操作は完了しています。依頼の目的は未達です。

```
ブランチ削除の後処理を任せる
  |
  +- 期待した流れ
  |    マージ状態を確認
  |      -> 未マージ : 停止
  |      -> マージ済 : 削除
  |
  +- 失敗する流れ
       確認せず削除・PRクローズ
         ツール実行  : 成功
         ワークフロー:失敗（事前条件）
         本来の目的  : 未達
```

成功は3つに分かれます。

1. **ツール実行**：削除とクローズを実行できたか
2. **ワークフロー**：次へ進む事前条件を満たしていたか
3. **本来の目的**：守るべき成果を失わず、依頼を達成できたか

操作できたことと、目的を達成したことは同じではありません。
**動いたことと、採用できることも同じではありません。**

コード生成の上手さだけ見ていても、この失敗は防げません。事前条件で止めない。権限境界がない。実際の状態を外部から見ない。判断基準がなければ、AIは不足した前提を補って進みます。出力がもっともらしく、短時間で積み上がるほど、検証が追いつかない。誤りを成果として採用しやすくなる。これが、ここでいう「AIに翻弄される」状態です。

## 先に残すもの。次のAIタスクの5つの確認欄

経験は、その人がその場で確認しているあいだしか働きません。先に、タスクへ残す形にします。役割の話は、この欄のあとで対応づけます。

1. **目的**：誰のどの課題か。受け入れ条件は何か。提供後に観測したい成果は何か。今回やらないことは何か
2. **進行**：どの順番で進めるか。どこで計画と実態を確認するか。計画が変わったら誰に戻すか
3. **技術**：守る設計と非機能は何か。何をもって妥当とするか。「動いた」と「採用できる」を何で分けるか
4. **委譲**：AIだけで進めてよい範囲はどこか。承認・停止・復旧が必要なのはどこか。完了報告以外に何を見るか
5. **学習**：失敗を次のルール、テスト、ツールのどこに残すか。チャットで終わらせない置き場はどこか

チームで使うなら、各欄に担当者、承認者、通過に必要な証拠、停止時の連絡先を足します。全部埋まらなくていい。**空欄は経験不足の告白ではなく、今回AIだけで進めてはいけない場所です。**

役割別の中身は、次の通りです。職能定義ではありません。チケットに書く項目です。

### PdM欄：目的と完成条件

残すもの
- 誰の、どの不便を減らすか
- 出すもの / 出さないもの
- 観測できる受け入れ条件
- 迷ったときの優先順位（速度 / 精度 / 範囲 / 互換）
- 提供後に見たい変化。見ないなら「今回は見ない」

証拠
- 受け入れ条件を満たす出力、画面、API応答
- 対象外を壊していないこと

止める
- 課題が「実装したいこと」にすり替わった
- 受け入れ条件が「動いた」だけになった

受け入れ条件はPdMが一人で閉じません。非機能、検証方法、技術制約はテックリードと開発と一緒に、通せる形へ落とします。ここが空のまま指示だけ厚くしても、AIは目的を補完して走ります。

### PjM欄：分解と進行

残すもの
- 段階（調査 → 設計 → 実装 → テスト → 検証）と、今どこまで許可するか
- 先に必要な情報、PR、権限、環境
- 次へ進むチェックポイント
- 計画変更時の戻し先

証拠
- 今の段階の完了記録
- 次へ渡す前提が、推測ではなく書いてあること

止める
- 大きな要求を一括で渡し始めた
- 計画が変わったのに再確認していない
- 途中成果が見えず、完了報告だけが来ている

段階を分ける理由は管理のためだけではありません。AIが一度に推測する範囲を小さくし、逸脱を早く見つけるためです。

### テックリード欄：境界と採用基準

残すもの
- 壊してはいけない境界（モジュール、データ、API、移行）
- 非機能（セキュリティ、性能、互換、運用）
- 検証手段
- 「動いた」と「採用できる」を分けるレビュー観点
- より小さくできないかの基準

証拠
- 要求を検証するテスト、または再現手順
- 既存設計を壊していないことの確認方法

止める
- テストが実装の存在確認だけ
- 局所最適で境界をまたいでいる
- 採用判断をAIの説明文に頼っている

### EM欄：委譲してよい範囲

残すもの
- 参照してよい情報 / 禁止
- 使ってよいツールと権限
- AIだけで進めてよい操作
- 人間承認が必要な操作。とくに、技術的には戻せるが、完了報告から異常が見えない操作
- 失敗時の戻し方と、返す相手
- 実行過程の残し方（ログ、PR、計画差分）

証拠
- 許可範囲内だけで実行された記録
- 完了報告以外の外部状態（リポジトリ、CI、環境）

止める
- 権限が「便利だから全部」になっている
- 現在状態を確認できない
- 承認なしで、取り消しが難しい操作、または異常が見えない操作に入った

自律性を上げることと、権限を無制限に渡すことは違います。ブランチ削除の仮想例がここに刺さります。戻せる操作ほど、承認対象から外れやすい。

### スクラムマスター欄：検査と適応の置き場

残すもの
- 見る失敗の観点（コンテキスト不足、観測不能、レビュー遅れ、責任分界、再発）
- 学びの置き場（ルール、テスト、チェックリスト、ツール）
- 次の実行で再発を見る方法
- 完了報告以外に見えるもの

証拠
- 失敗が外部化された差分
- 次タスクの確認欄に、今回の学びが入っていること

止める
- 「AIが悪かった」で閉じている
- 指摘がセッション内で消える
- 同じ確認を、また人が記憶でやっている

検査と適応は、透明性が前提です。完了報告しか見えない振り返りは、誤った適応を量産します。AIは指摘を次セッションへ持ち越しません。残るのは外に書いたものだけです。

## 空欄のまま速くすると、間違いだけ先に届く

「判断機能が欠ける」は、経歴が足りないという意味ではありません。その判断が、人にも仕組みにもない状態です。

```
欄               判断   空欄のまま進めた失敗
--------------------------------------------
PdM             : 目的 : 間違った課題を速く実装する
PjM             : 進行 : 途中の逸脱を見逃す
テックリード     : 技術 : 動くが採用できないコード
EM              : 委譲 : 権限と停止条件のない委譲
スクラムマスター : 学習 : 同じ失敗が次のセッションで再発する
```

AIは実装の一部を担えます。目的、設計、検証、責任まで自動で正しく担うとは限りません。自分たちで妥当性を見られない領域ほど、委譲を狭くし、知見のあるレビューか、客観的な検証を先に置きます。

確認の頻度と手段を変えないまま、大量の変更と自動実行だけ許可すると、欠落が事故になるまでの時間は短くなります。速さは中立ではありません。判断の外側では、増幅装置です。

役職経験があれば安全、でもありません。流暢な説明を信じる。大量の差分にレビューが追いつかない。その瞬間、経験者も同じ穴に落ちます。経験は免許証ではなく、どこにリスクがあり、何を確認するかを考える材料です。

## 経験を勘で使っているうちは、組織にならない

AIに作業を実行させても、判断と結果の責任は人間が持ちます。担当、最終決定、条件を満たさなければ次へ進めないゲートを、チームで決めてよい。レビュー、テンプレート、テスト、ツールに埋め込んでもよい。

経験がある人だけが勘で止められる状態は、再現できません。判断基準を外に出せれば、経験の浅いメンバーでも、止められる地点が見えます。

私の運用では、受け入れ条件をタスクに残し、実装前の計画レビューと、計画変更時の再確認をワークフローに入れています。実行後はAIの完了報告を根拠にせず、テスト、リポジトリの実際の状態、人間または別経路のレビューで見ます。現在状態が確認できない、計画やスコープが変わった、必要な検証が実行できない場合は、AIだけで進めず判断者へ戻します。振り返りで出た失敗は、次のルールか回帰テストへ移します。

これはAIの自由を奪うためではありません。人が経験的にやっていた「疑う」「止める」「確かめる」を、次の人でも使える形にするためです。効果を数値で示す段階には、この記事では踏みません。言えるのは、判断の置き場を先に決めた方が、翻弄されにくいということです。

## まとめ

PdM、PjM、テックリード、EM、スクラムマスターで培った経験は、AI駆動開発では、**エージェントが成果を出せる開発システムを設計し、結果を検証する力**として一本につながりました。

AIは実装を速くできます。5つの判断が空のままなら、成果だけでなく間違いも速く届きます。検証が追いつかないまま、誤りを成果として採用するからです。

次のAIタスクを始める前に、目的・進行・技術・委譲・学習を書き出してください。答えの空欄が、いま補うべき判断です。空欄を埋めてから走るか、空欄のまま委譲範囲を削るか。どちらでもいい。空欄を無視することだけはやめた方がいい。

AIは経験を消していません。実装の中に隠れていた経験の中身を、表に出しました。

それを個人の勘で終わらせず、チームが使える確認欄へ変える。現場でAIを活かし、AIに翻弄されない力は、そこにあります。
