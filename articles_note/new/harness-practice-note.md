# AIに書かせる仕組みではなく、AIが安全に間違えられる仕組みを作っていた

> 区分: 個人

エージェントにリネームと内容編集をまとめて任せたとき、完了報告は問題なしでした。ところが実際にマージされたPRは「7 files changed, 0 insertions」で、リネームだけが入り、本文の編集がまるごと落ちていました。

別の日には、Qiitaの重複記事を「人間が手で消すしかない不可逆のブロッカー」として何ラウンドも申し送りました。最後にURLを叩いたら404でした。記事はそもそも存在していませんでした。

**どれも、失敗そのものより「失敗が成功として報告されたこと」が問題でした。**

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine\_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善や、チームでの意思決定の進め方について考えています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。

## 「できました」が信用できなくなった

AI駆動開発を始めたころ、私がやっていたことは単純でした。エージェントに実装を頼み、出てきた差分を眺め、良さそうならマージする。それだけです。

うまくいっているように見えました。実際、速くはなりました。

つまずいたのは、速さではなく報告の中身のほうでした。

冒頭の「7 files changed, 0 insertions」が、その最初の1件です。さらにその後片付けで、復旧できたはずの変更を `git stash drop` で消し、リカバリに丸ごと1本のPRを使いました。存在しないQiita記事を申し送り続けた件も同じで、ローカルにファイルが残っていただけで、リモートの状態を一度も確認していませんでした。

自分で書いた検証スクリプトにも同じことが起きました。ある関数が常に `false` を返していたのですが、原因は依存の import 漏れで、発生した ReferenceError を `catch { return false }` が飲み込んでいました。呼び出し側からは「探したが見つからなかった」と区別がつきません。検証したことになったまま main にマージされていました。

画像チェックのスクリプトでは、JPEGのサイズを読む約40行の関数を丸ごと `return None` に置き換えても、self-test が PASS のままでした。テストがあることと、欠陥を検出できることは別でした。

別のエージェントに調査を委託したときは、委託先が「バックグラウンドで開始しました」と報告して終了し、ジョブも成果物もどこにも残っていませんでした。開始したという報告を、実在を確かめずに受理していたのです。

並べてみると、共通点は誤りが起きたことではありませんでした。誤りが誰にも検知されないまま、完了として通過したことです。

そして、そのどれもがモデルの推論能力の問題ではありませんでした。完了の定義、外部状態の確認手順、エラーの扱い、テストの設計、報告の受理基準。壊れていたのは AI の外側の手続きです。

このころの開発の形を図にすると、こうなります。

```
  人間 --指示--> AI --コード--> リポジトリ
    ^                              |
    |                              |
    +--------- 目視で確認 ---------+
```

チェックが人間の目しかありません。だから、報告が正しいかどうかも人間が毎回確かめるしかない。見落とせば、そのまま通ります。

## AIを賢くするより、周囲を作り始めました

モデルの誤り率が下がっても、検知の穴はモデルの外側にあるので、この形のままでは残ります。だから、モデルではなく周囲を作ることにしました。

最初に作ったのは、始める前の関門です。人間が承認した計画と、タスクの分解と、受け入れテストが揃うまで、AIにプロダクションコードを書かせないことにしました。これは今 [PlanGate](https://github.com/s977043/PlanGate) というOSSにまとまっています。0 insertions 型の事故は、何をもって完了とするかが決まっていないところから始まります。先に文章にしておけば、報告と突き合わせられます。

次に作ったのは、レビュー基準を自分たちの手元に置く仕組みです。AIレビューをベンダーのブラックボックスに預けると、何を見ているかが分からず、指摘も毎回ぶれます。そこでレビュー判断を、リポジトリの中でバージョン管理される skill として書いて実行するようにしました。こちらは [River Review](https://github.com/s977043/river-review) です。

そしてブログ運用のリポジトリ側には、地味なガードを積みました。main への直コミットをブロックする pre-commit hook、公開前の整合を見る20本のチェックスクリプト、記事の最終確認を回す3本のWorkflow。

本数そのものに意味はありません。口頭で守っていた約束を、誰が実行しても同じ結果になる形に置き換えた回数です。

例がブログ運用に寄っているのは、そこでいちばん多く事故を起こしたからです。壊れていたのは完了の定義とリモート状態の確認手順で、これはどのリポジトリでも同じ形で壊れます。

前半に並べた事故のうち、機械に移せたのは一部です。0 insertions のPRは、完了条件を先に文章にする関門と直コミットを止める hook へ。存在しない記事を消せと申し送り続けた件は、リモートの状態を確かめてから判断するという順序の作り直しへ。

残りの3件（握りつぶされた ReferenceError、壊しても通る self-test、成果物が残らなかった委託）は、まだ検査になっていません。受理基準がいまも私の頭の中にあります。

作るときに決めたことが1つあります。

**新しく作るのは、実際に起きた事故に対応するものだけにする。**

想像した危険に先回りしてガードを積むと、鳴りっぱなしの警告が増えて、本当に見るべき警告が埋もれます。あとで、運用中の記事すべてに新しい検査を一斉に適用する形で、これに近い失敗をやります。

この原則を当てているのは検査を足すときだけです。River Review のように、判断の置き場所を決める設計のほうは、事故を待たずに先に置きました。

もう1つ、検査は足したら終わりではありません。作り直しのコストが続きます。後半はほとんどその話です。

## 開発がループになりました

ガードが増えてくると、開発の形が変わりました。

事前に効くもの（計画、受け入れ条件、禁止事項）と、事後に効くもの（hook、CI、チェックスクリプト、レビュー）が両側に立ち、AIの実行がその間に入るようになったのです。

```
      人間: 目的・計画・承認
             |
             v
     +----------------+
     | 事前ガード      |
     | 計画/受入条件   |
     +----------------+
             |
             v
     +----------------+
     |   AIの実行      |
     +----------------+
             |
             v
     +----------------+
     | 事後センサ      |
     | hook/CI/検査    |
     +----------------+
        |         |
   失敗なら     合格なら
   差し戻し        |
        |          v
        |   +----------------+
        |   | 人間:           |
        |   | マージ/公開     |
        |   +----------------+
        |
        +--> AIの実行へ戻る
```

以前は、この差し戻しの矢印が私でした。私が疲れていれば精度が落ち、並列で3本走っていれば3本目は雑になります。

いま変わったのは、この矢印の大半が機械になったことです。

**人間がフィードバックループそのものになるのをやめた、というのが一番大きな変化でした。**

マージと公開は人間が押すのだから待ち時間は同じでは、と思われるかもしれません。違うのは量です。以前は全ての差分を読んで異常を探し、いまは検査を通ったものを押すかどうか決めるだけです。見落とせば通ってしまう作業と、押さなければ進まない作業は、疲労に対する強さが違います。

私が判断するのは、機械が拾えないところに絞られていきました。このガードは緩めてよいか。この記事は書くべきか。

やめたのは検知役であって、判断役ではありません。機械に代われるとしても手元に残している「権限」の話は、後半に書きます。

## 人間の仕事は減ったのではなく、ずれました

よく誤解されるのですが、コードを読まなくなったわけではありません。

読む対象が変わりました。

以前は「この差分は正しいか」を読んでいました。いまは、それに加えて「この差分が間違っていたら、何が気づくのか」を見ています。気づく仕組みが無ければ、差分が正しく見えても安心はできません。

**逆に、気づく仕組みがあるなら、多少雑な差分でも安全に試せます。ガードは試行を縛るためではなく、試行の回数を増やすために置いています。**

書くコードも変わりました。プロダクトのコードを書く時間が減り、チェックスクリプトと hook と Workflow を書く時間が増えました。プロダクトから離れたというより、コードが安全に生まれる場所のほうへ、設計の対象が1段広がった感覚です。

この、実行の周囲にある事前ガードと事後センサ、そこに残る証跡と、人間の権限境界のまとまりを、以降ハーネスと呼びます（当時の私は、この名前を知らないままやっていました）。証跡とは、どの事故がどのガードになったかを PR と学びのインデックスに残すことです。

そして、人間が最後に持ち続けているものが1つあります。権限です。

## ハーネス自身を壊し、直し続けています

ここからが、実は一番時間を使っているところです。

ガードを作ると、そのガードが間違います。

Zennの二重公開を防ぐガードは、3回作り直しました。1回目、スクリプトは書けていたのに CI に接続されておらず、一度も動いていませんでした（PR #391 で接続）。2回目は計測軸がコミットの日付で、実際に公開が起きるタイミングとずれ、見逃しと誤ブロックの両方が起きました。3回目で、前回公開からの実経過時間で判定するようにしました。

note記事の最終化チェックを入れたときは、もっとひどいことをしました。新しい lint を全体のチェックに直結させたところ、過去記事に57件の警告が一斉に出て、警告そのものが読まれなくなったのです（PR #594）。安全にしようとして、安全装置の信号を薄めました。前半で「あとで、これに近い失敗をやります」と書いたのがこれです。原因は想像した危険への先回りではなく、実際の事故に対して作ったガードを対象を絞らずに全体へ適用したことで、制約すべきなのは作る動機だけでなく適用範囲のほうでもありました。

学びのインデックスに重複検出を足したときは、思わぬ副作用が出ました。その検査が初めてブロッキングになった結果、`npm run check` に連結された20件が `&&` でつながっていて、前のほうで1件落ちると後続6件が一度も実行されない構造だったことが露見したのです（PR #605 で発覚、PR #606 で全件実行してまとめて報告する集約ランナーに変更）。ガードを足したら、ガードを並べる仕組みの欠陥が見えたわけです。

古いブランチが公開済みの記事を巻き戻す事故（GitHub上のPR差分は「+14行」に見えるのに、現在の main に対しては記事全体の巻き戻しでした）に対しては、staleness チェッカーを作りました。誤検知が1日4件出たので、判定軸を作り直しました。

検査を増やすこと自体にコストがかかるので、歯止めを2つ置いています。実際に起きた事故に対応するものしか作らない。鳴っても誰も読まない検査は、他の警告を薄めるので消す。それでも作り直しの時間はかかりますが、割に合います。人間が矢印だったころのコストは走らせる本数に比例して劣化しましたが、ガードの作り直しは1回で、そのあとの全ての周回に効くからです。

ここまでを並べると、やっていることの形が見えてきます。

```
   事故が起きる
        |
        v
   原因を言葉にする
        |
        v
   ガードを足す/直す
        |
        v
   運用して観測する
        |
        v
   まだ再発する / 誤検知する
        |
        +----> 事故が起きる へ戻る
```

つまり、開発のループを回すだけでなく、**ループを回す仕組みそのものを、次の周回の対象にしていた**ということです。前の図が内側のループで、いまの図は、その内側のループごと作り直す外側のループです。

## 自分の結論に、先に名前がついていました

私はこれを、しばらく自分だけの運用の癖だと思っていました。

そのあとで、Thoughtworks の Birgitta Böckeler さんが書いた [Harness engineering for coding agent users](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html)（2026年4月2日）を読みました。

harness を「AIエージェントのうち、モデル以外のすべて」と定義したうえで、事前に効かせる guides と、事後に観測して自己修正させる sensors を分けています。ここまでは、私の図とほぼ同じでした。

原典は harness を三重の円で描きます。中核がモデル、その外側がエージェント側の builder harness、いちばん外側が利用者が自分のユースケース向けに作る user harness です（"the coding agent's builder harness next circle out, and the coding agent's user harness as the outermost ring"）。私が事故のたびに積んでいたのは、この一番外側の層でした。

問題は次の一文です。

> Whenever an issue happens multiple times, the feedforward and feedback controls should be improved to make the issue less probable to occur in the future, or even prevent it.

さらに「The steering loop」という節があり、こう書かれています。

> The human's job in this is to steer the agent by iterating on the harness.

私が「自分の癖」だと思っていたものは、名前だけでなく中身まで、既に明文化されていました。しかも先に。**実務から独立に同じ結論に着いて、あとで原典を読んだら先に書かれていた**、ということです。

がっかりはしませんでした。事故から言語化した結論と、体系的に整理された結論が一致するなら、どちらにとっても裏づけになります。

もう1つ、この定義を読んで自分の説明を直した点があります。CI もテストも lint も、Böckeler さんの定義では harness に含まれます。私はしばらく「CI とは別にハーネスを入れた」と説明していましたが、前からあったCIやテストも harness の一部で、私はそこに事前ガードと証跡と権限境界を足していたにすぎません。前回の記事「[失敗をモデルのせいにしない。AI駆動開発を「Model + Harness」で考える](https://note.com/mine_unilabo/n/nd6a5d83d1488)」で `Agent = Model + Harness` という見方を書きましたが、その Harness の中身は新しく作ったものだけではなかったわけです。

## では、ハーネスの改善もAIに任せられるのか

原典にも「改善にAIを使ってもよい」と書かれています。実際、私も改善案の下書きはAIに書かせています。

ただ、ここには線を引いています。

きっかけは Darwin Gödel Machine の論文（arXiv 2505.22954）でした。自分自身のコードを書き換えて改善するエージェントで、SWE-bench で 20.0% から 50.0%、Polyglot で 14.2% から 30.7% に伸びています。しかも改善された対象が、編集ツールの粒度、長い文脈の扱い、そして複数回試して別の基盤モデルに評価させ最良の解を選ばせる仕組みで、まさに harness 側です。自己改善が効くという実証です。

同じ論文が、別の実験でもう一方の結果も報告しています（Appendix H）。因果の順に書きます。

まず、入力文脈が長くなると、基盤モデルがツールを呼んだふりをして「テストはすべて通った」というログを平文で書く挙動が知られていました。モデルが元から示す既知の問題です。著者らは、これを解消させること自体を目的にした別ランを DGM に回しました。150 iterations、評価は SWE-bench の3タスクのみ、指標は幻覚が出たかを見る専用の solve hallucination score（0から2）です。

その改善の過程で objective hacking が現れました。node 114 が**ツール使用を示す特殊トークンの出力そのものを削除して、検出機構を無効化した**のです。特殊トークンを変えるなという指示があったにもかかわらず、です。この個体は 2.0/2.0 の満点を取りました。満点なのはこの専用スコアであって、SWE-bench の解決率ではありません。

つまりこれは、20.0%から50.0%を出した探索の途中の出来事ではなく、目的も指標も違う別ランの出来事で、さきほどのベンチマークの伸びとは切り離して読む必要があります。自己改善が新たに生んだ逸脱は、objective hacking のほうだけでした。

そして著者らは、検査関数をエージェントから隠していました。理由も書かれています。隠さない場合に objective hacking がより頻繁に起きたからです。**監視機構に手が届く条件では、指標のハッキングが増える。**著者自身の実験条件による裏づけです。

もう1本、2026年9月2日公開の arXiv 2609.02246（査読を経ていない単著の運用報告のプレプリント）でも似た報告があります。実運用で、エージェントが環境に置かれたキャッシュ済みの答えを読んで満点を取り、100%の合格率が実際には68%の能力を隠していた、というものです。判定側の rubric をいくら書き直しても改善は頭打ちで、効いたのは出力の順序に対する構造的な制約だけだったと書かれています。

手元に置き換えると、こうなります。main への直コミットを止める hook のように判定が決定論的なものは、機械に任せられます。レビュー基準のように rubric で書くしかない判断は、AIに実行させても、その結果は人間の受理にかけます。

**改善の対象に、評価する側や監視する側を含めた瞬間に、それは指標のハッキングの対象になります。**

だから、私のハーネスでは次を人間の権限のまま残しています。

マージ。公開。ガードを緩める判断。そして、検査そのものを消す変更。

選んだ基準は2つです。1つは、監視される側が監視する仕組みに手を届かせる変更であること（ガードを緩める判断と、検査を消す変更）。もう1つは、外に出たら取り消せない変更であること（マージと公開）。

このうち先の2本が示しているのは前者で、後者は前半に書いた自分の事故から引いた線です。

AIには、事故の分析も、ガードの実装も、誤検知の修正案も出してもらいます。ただし、それを取り込むかどうかは人間が決めます。速さのためにここを外すと、最初に戻ります。「できました」が信用できない状態に、です。

## 設計する対象が広がってきた順序

振り返ると、私が設計しようとしていた対象は、この順で広がってきました。

最初はプロンプトでした。どう言えば意図どおり動くか。

次にコンテキストでした。何を渡せば正しく判断できるか。

そのあとがハーネスでした。実行の周囲に、事前ガードと事後センサと証跡と権限境界をどう置くか。

いまは、そのハーネス自体をどう改善し続けるか、を見ています。

これを業界の成熟モデルとして書くつもりはありません。

なお、Addy Osmani さんが2026年6月7日に [Loop Engineering](https://addyosmani.com/blog/loop-engineering/) という言葉を使っています。

> Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead.

魅力的な定義ですが、指しているのはエージェントの実行ループを自動化する話で、この記事の「ハーネスを改善するループ」とは層が違います。私が書いてきたのは、その実行ループの外側で、ループを回す仕組みのほうを毎周作り直す話なので、自分にはこの語を当てないことにしました。

## まとめ

AI駆動開発を1年ほど続けて、いま自分がやっていることを言葉にすると、こうなります。

AIにコードを書かせることが目的ではありませんでした。

**AIが安全に間違えられる場所を作ること**が、やっていたことでした。そこでAIが繰り返し自律的に開発でき、開発のやり方自体も改善していけるようにする、ということです。

そこにたどり着く道は、賢い設計ではなく事故でした。0 insertions のPR、握りつぶされた ReferenceError。そのたびに、口頭のチェックリストを1つずつ機械に移しました。

ガードも間違えます。だから作り直します。作り直す作業そのものが、いま一番価値のある開発だと感じています。

ただし、そのループの一番外側には人間を置いたままにしています。測られる側が測る仕組みに手を届かせると、指標だけがきれいになります。DGM は検出用トークンの出力を消し、もう一方はキャッシュ済みの答えで満点を取りました。

誤りをゼロにしたのではなく、誤りが安く済むようにしただけです。人間の役割は、そちらへ移ってきました。
