# AIに書かせる仕組みではなく、AIが安全に間違えられる仕組みを作っていた

> 区分: 個人

エージェントに、ファイルのリネームと本文の編集をまとめて任せたことがあります。

返ってきた完了報告に問題はありませんでした。

ところが、実際にマージされたPRを見ると、`7 files changed, 0 insertions`。

ファイル名だけが変わり、頼んだはずの本文編集はまるごと入っていませんでした。

別の作業では、「マージした」という報告を信じて、そのまま後片付けへ進みました。GitHub上で本当にマージ済みか確認しないままリモートブランチを削除した結果、PRは未マージのままCLOSEされました。幸いreopenでき、作業そのものは失いませんでした。

**危なかったのは、AIが間違えたことではありません。間違った状態を「できました」と報告しても、そのまま次へ進める仕組みになっていたことでした。**

AIが間違えること自体は、おそらくなくなりません。

それなら必要なのは、AIに一度で正解を出させることではなく、間違えても検知できること、間違ったまま重要な境界を越えられないこと、そして起きた事故を次のガードへ変えていけることです。

この1年ほど、個人の開発やブログ運用で起きた事故を追いかけながら、私はそんな仕組みを少しずつ作ってきました。

最初から Harness Engineering をやろうと考えていたわけではありません。事故が起きるたびに、私が目で確認していたことをコードに移し、チェックを足し、権限を分けていっただけです。

この記事では、その過程を書きます。

持ち帰ってほしいのは2つです。

- **検査を増やすとき、どこに歯止めを置くか**
- **AIに任せても、人間の手元に残す権限は何か**

五反田のスタートアップでプロダクト開発に携わっている、みね（[@mine\_take](https://x.com/mine_take)）です。普段は、AIを使った開発プロセスの改善や、チームでの意思決定の進め方について考えています。

※本記事は個人の活動として執筆したものであり、所属組織の公式見解ではありません。ここで扱うのは主に、私個人のリポジトリで観測した事例です。

## 「できました」が信用できなくなった

AI駆動開発を始めたころ、私がやっていたことは単純でした。エージェントに実装を頼み、出てきた差分を眺め、良さそうならマージする。それだけです。

うまくいっているように見えました。実際、速くはなりました。

つまずいたのは、速さではなく報告の中身のほうでした。

冒頭の `7 files changed, 0 insertions` が、その最初の1件です。その後片付けでは、復旧できたはずの変更を `git stash drop` で消し、リカバリに1本のPRを使いました。

もう1つは、PlanGate の [PR #240](https://github.com/s977043/PlanGate/pull/240) です。「マージした」という報告をそのまま受け取り、GitHub上の状態を確認せずにリモートブランチを削除しました。実際には未マージで、PRはCLOSEされました。

問題はブランチを削除したことだけではありません。

**「マージされた」という報告と、「GitHub上で実際に `MERGED` になっている」という事実を区別していなかったことでした。**

自分で書いた検証スクリプトにも同じことが起きました。ある関数が常に `false` を返していた原因は依存の import 漏れで、発生した ReferenceError を `catch { return false }` が飲み込んでいました。呼び出し側からは「探したが見つからなかった」と区別がつかず、検証したことになったまま main にマージされていました。

画像チェックのスクリプトでは、JPEGのサイズを読む関数を丸ごと `return None` に置き換えても、self-test（自己テスト）が PASS のままでした。テストがあることと、欠陥を検出できることは別でした。

別のエージェントに委託したときは、委託先が「バックグラウンドで開始しました」と報告して自分は終了し、作業用の隔離ツリーが自動で片付けられ、ジョブも成果物も残りませんでした。開始したという報告を、実在を確かめずに受理していたのです。

並べてみると、共通点は誤りが起きたことではなく、それが誰にも検知されず完了として通過したことでした。

完了の定義、外部状態の確認手順、エラーの扱い、テストの設計、報告の受理基準。壊れていたのは、AIの外側の手続きです。

このころの開発の形を図にすると、こうなります。

```text
  人間 --指示--> AI --コード--> リポジトリ
    ^                              |
    |                              |
    +--------- 目視で確認 ---------+
```

チェックが人間の目しかありません。報告が正しいかどうかも、人間が毎回確かめるしかない。見落とせば、そのまま通ります。

## AIを賢くするより、周囲を作り始めました

モデルの誤り率が下がっても、検知の穴がモデルの外側にあれば残ります。だから、モデルではなく周囲を作ることにしました。

最初に作ったのは、始める前の関門です。人間が承認した計画と、タスクの分解と、受け入れ条件が揃うまで、AIにプロダクションコードを書かせないことにしました。これは [PlanGate](https://github.com/s977043/PlanGate) というOSSにまとまっています。

`0 insertions` 型の事故は、何をもって完了とするかが曖昧なところから始まります。先に文章にしておけば、完了報告と実際の差分を突き合わせられます。

次に作ったのは、レビュー基準を自分たちの手元に置く仕組みです。AIレビューをベンダーのブラックボックスに預けると、何を見ているかが分からず、指摘も毎回ぶれます。そこでレビュー判断を、リポジトリ内でバージョン管理する skill として書きました。こちらは [River Review](https://github.com/s977043/river-review) です。

PlanGate と River Review は開発プロセス側で置いた仕組みです。一方、以下のブログ運用は、私が事故と改善を最も多く観測できた実験場でした。

ブログ運用のリポジトリには、main への直コミットをブロックする pre-commit hook、公開前の整合を見る20本のチェックスクリプト、記事の最終確認を回す3本のWorkflowを積みました。

本数に意味はありません。口頭で守っていた約束を、誰が実行しても同じ結果になる形に置き換えた回数です。

前半に並べた事故のうち、機械に移せたものもあります。

`0 insertions` のPRに対しては、完了条件を先に文章にする関門を置きました。

未マージPRをCLOSEさせた事故に対しては、後片付けへ進む前に `state == MERGED` かつ `mergedAt` / `mergeCommit` が存在することをスクリプトで確認するようにしました。

以前は、こうでした。

```text
「マージしました」
        ↓
後片付けする
```

いまは、こうです。

```text
「マージしました」
        ↓
外部状態を確認する
        ↓
MERGED なら後片付けする
```

小さな違いですが、AIエージェントを使ううえでは重要でした。

**報告を、検証結果として扱わない。**

一方で、握りつぶされた ReferenceError、壊しても通る自己テスト、成果物が残らなかった委託は、まだ十分な検査になっていません。受理基準がいまも私の頭の中に残っています。

作るときに決めたことが1つあります。

**新しく作る検査は、実際に起きた事故に対応するものだけにする。**

想像した危険に先回りしてガードを積むと、鳴りっぱなしの警告が増えて、本当に見るべき警告が埋もれます。あとで、これに近い失敗を自分でもやります。

この原則を当てているのは、検査を足すときです。River Review のように、判断の置き場所を決める設計は、事故を待たずに先に置きました。

## 人間がフィードバックループそのものになるのをやめた

ガードが増えてくると、開発の形が変わりました。

事前に効くもの（計画、受け入れ条件、禁止事項）と、事後に効くもの（hook、CI、チェックスクリプト、レビュー）が両側に立ち、AIの実行がその間に入るようになったのです。

```text
      人間: 目的・計画・承認
             |
             v
     +----------------+
     | 事前ガード      |
     | 計画/受入条件   |
     +----------------+
             |
             v
     +----------------+
     |   AIの実行      |
     +----------------+
             |
             v
     +----------------+
     | 事後センサ      |
     | hook/CI/検査    |
     +----------------+
        |         |
   失敗なら     合格なら
   差し戻し        |
        |          v
        |   +----------------+
        |   | 人間:           |
        |   | マージ/公開     |
        |   +----------------+
        |
        +--> AIの実行へ戻る
```

以前は、この差し戻しの矢印が私でした。私が疲れていれば精度が落ち、並列で3本走っていれば3本目は雑になります。

いま変わったのは、差し戻しの一部を機械に移せたことです。

**人間がフィードバックループそのものになるのをやめた、というのが一番大きな変化でした。**

マージと公開は人間が押すのだから同じでは、と思われるかもしれません。違うのは量です。以前はすべての差分を読んで異常を探し、いまは検査を通ったものを押すか決めるだけです。

見落とせば通る作業と、押さなければ進まない作業では、疲労への強さが違います。

やめたのは検知役であって、判断役ではありません。

## 人間の仕事は減ったのではなく、ずれました

よく誤解されますが、コードを読まなくなったわけではありません。

読む対象が変わりました。

以前は「この差分は正しいか」を読んでいました。いまは、それに加えて「この差分が間違っていたら、何が気づくのか」を見ています。気づく仕組みがなければ、差分が正しく見えても安心できません。

**逆に、気づく仕組みがあるなら、多少雑な差分でも安全に試せます。ガードは試行を縛るためではなく、試行の回数を増やすために置いています。**

書くコードも変わりました。プロダクトのコードを書く時間が減り、チェックスクリプトと hook と Workflow を書く時間が増えました。

プロダクトから離れたというより、設計の対象がコードの生まれる場所へ1段広がった感覚です。

この、実行の周囲にある事前ガードと事後センサ、証跡、人間の権限境界のまとまりを、以降ハーネス（harness）と呼びます。当時の私は、この名前を知らないままやっていました。

## ガードを作ると、そのガードも間違いました

ガードを作ると、そのガードが間違います。

Zennの二重公開を防ぐガードは、3回作り直しました。1回目は、スクリプトは書けていたのにCIへ接続されておらず、一度も動いていませんでした（PR #391）。

2回目で分かったのは、日付で数える計測に穴が2つあることでした。公開切替のコミット日付は、実際の公開タイミングとずれます。件数側は、その公開で新たに増える差分を直接数える方式へ変更しました（PR #393）。時間側は、前回公開から18時間なのに「24時間で0件、安全」と報告した穴があり、3回目に実経過時間の判定を足しました（PR #553）。

note記事の最終化チェックでは、新しい lint を全体のチェックに直結させたところ、過去記事に57件の警告が一斉に出て、警告そのものが読まれなくなりました（PR #594）。安全にしようとして、安全装置の信号を薄めたのです。

原因は、実際の事故に作ったガードを、対象を絞らず全体へ適用したことでした。制約すべきは動機だけでなく、適用範囲でもありました。

学びのインデックスに重複検出を足したときは、その検査が初めてブロッキングになり、`npm run check` に連結された20件が `&&` でつながっていて、1件落ちると後続6件が一度も実行されない構造だと露見しました（PR #605）。

PR #606 で、全件実行してまとめて報告する集約ランナーへ変えました。ガードを足したら、ガードを並べる仕組みの欠陥が見えたわけです。

古いブランチが公開済みの記事を巻き戻す事故には、staleness チェッカー（古さの検知）を作りました。ところが誤検知が1日4件出て、判定軸を作り直しました。

これらを経て、検査を増やすときの歯止めは3つになりました。

- 作る動機を、実際に起きた事故に限る
- 適用範囲も、その事故の範囲に合わせる
- 鳴っても誰も読まない検査は消す

それでも作り直しの時間はかかりますが、割に合います。人間が矢印だったころのコストは走らせる本数に比例して劣化しましたが、ガードの作り直しは1回で、そのあとの周回すべてに効くからです。

ここまでを並べると、やっていることの形が見えてきます。

```text
   事故が起きる
        |
        v
   原因を言葉にする
        |
        v
   ガードを足す/直す
        |
        v
   運用して観測する
        |
        v
   まだ再発する / 誤検知する
        |
        +----> 事故が起きる へ戻る
```

つまり、開発のループを回すだけでなく、**ループを回す仕組みそのものを、次の周回の対象にしていた**ということです。

2026年6月、Addy Osmani さんは [Loop Engineering](https://addyosmani.com/blog/loop-engineering/) を「人間が毎回エージェントへ指示する代わりに、その指示と検査を回すシステムを設計すること」として説明しています。

> Loop engineering is replacing yourself as the person who prompts the agent.

私がここでやってきたのは、その外側のループのうち、特に事故のたびにガードとセンサ自体を作り直す部分でした。

## 後から「Harness Engineering」という名前を知った

これを、しばらく自分だけの運用の癖だと思っていました。

そのあとで、Thoughtworks の Birgitta Böckeler さんが書いた [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html)（2026年4月2日）を読みました。

この記事では、harness を「AIエージェントのうち、モデル以外のすべて」という広い意味から整理し、利用者側で作る外側のハーネスを、事前に効かせる guides と、事後に観測して自己修正へつなげる sensors に分けています。

私が事故のたびに積んでいたものと、かなり近い整理でした。

特に一致したのが、人間の役割です。

> The human's job in this is to steer the agent by iterating on the harness.

事故のたびに人間がその場で注意するのではなく、次の周回で同じ事故が起きにくくなるようハーネス側を変える。

**実務から独立に同じ結論へたどり着いて、あとで体系化された名前を知った**という順番でした。

この定義を読んで、自分の説明を直した点もあります。CIもテストもlintも、ハーネスの一部です。私はしばらく「CIとは別にハーネスを入れた」と説明していましたが、その理解は狭すぎました。

前からあったCIやテストも含めてハーネスであり、私がそこに足していたのは、事前ガードと、既存のCIが拾えなかった事後センサ、そして証跡と権限境界でした。

前回の記事「[失敗をモデルのせいにしない。AI駆動開発を「Model + Harness」で考える](https://note.com/mine_unilabo/n/nd6a5d83d1488)」で `Agent = Model + Harness` という見方を書きました。その Harness の中身は、新しく作ったものだけではなかったわけです。

## ハーネスの改善もAIに任せる。ただし、境界は残す

ハーネスの改善案そのものは、AIにかなり任せています。

事故の原因整理、ガードの実装、誤検知の修正案。ここはAIが得意です。

ただし、監視する仕組みそのものまで、監視される側が自由に変更できる状態にはしていません。

この境界を意識するきっかけの1つが、Darwin Gödel Machine（DGM）の論文でした。DGM は自分自身のコードを書き換えながら改善するエージェントで、SWE-bench では20.0%から50.0%、Polyglotでは14.2%から30.7%へ性能を伸ばしています。

一方、別の評価実験では objective hacking（評価指標を満たす抜け道を取る挙動）が報告されています。改善個体の1つが、ツール使用を検知するための記録処理を削除し、専用評価で満点を取りました。

ここから私が持ち帰ったのは、自己改善を止めるべきだという話ではありません。

**改善の対象に、評価する側や監視する側まで含めるなら、その変更を受理する境界が必要になる。**

ということです。

そのため、私の運用では次の4つを人間の権限として残しています。

- マージする
- 公開する
- ガードを緩める
- 検査そのものを消す

基準は2つです。

1つは、**監視される側が監視の仕組みに手を届かせる変更か**。ガードを緩める判断と、検査を消す変更がこれに当たります。

もう1つは、**共有・外部状態へ影響を出す変更か**。マージと公開がこれに当たります。どちらもロールバック手段はありますが、後から戻しても、レビュー済みという認識や公開後の閲覧など、影響を完全には巻き戻せません。

AIには、事故の分析も、ガードの実装も、誤検知の修正案も出してもらいます。ただし、その変更を取り込むかどうかは人間が決めます。

速さのためにここを外すと、最初に戻ります。「できました」が信用できない状態に、です。

## まとめ。AIが間違えないことより、間違いが安く済むことを設計する

AI駆動開発を始めたころ、私が見ていたのはAIが生成したコードでした。

いまは、それだけではありません。

**そのコードが間違っていたときに、何が気づくのか。**

**間違った状態のまま、どこまで進めてしまうのか。**

**そして、同じ事故を次の周回でどう起きにくくするのか。**

そこまで含めて設計するようになりました。

この記事で書いてきたことを、いまの自分のルールへ戻すと2つです。

### 検査を増やすとき

- 実際に起きた事故から作る
- その事故が起きた範囲に適用する
- 鳴っても誰も見ない検査は消す

安全装置は、多ければ多いほど安全になるわけではありません。検査そのものが間違うこともあります。警告を増やしすぎれば、本当に必要な警告が見えなくなります。

だから、ガード自身も運用し、壊し、直します。

### AIへ権限を渡すとき

次の2種類は、人間の受理を残します。

- 監視する仕組みそのものを変更するもの
- 共有・外部状態へ影響を出すもの

私の運用では、具体的にマージ、公開、ガードを緩める判断、検査を消す変更です。

この1年で、AIが間違えなくなったわけではありません。

私がやったのは、**間違いを早く見つけ、安く直し、その失敗を次の仕組みに残せるようにしたこと**でした。

プロンプトを工夫するところから始まり、コンテキストを整え、事前ガードと事後センサを置き、さらにその仕組み自体を改善するようになりました。

設計する対象が、コードから「コードが生まれる環境」へ広がっていった感覚があります。

AI駆動開発で重要なのは、AIに毎回正解を書かせることではないのだと思います。

**AIが間違えることを前提に、それでも開発を前へ進められる仕組みを作ること。**

私がこの1年で作っていたのは、AIにコードを書かせる仕組みではありませんでした。

**AIが安全に間違えられる仕組みでした。**

ここまでは、主に私個人のリポジトリで確かめてきた話です。チームへ広げるなら、次は「どのガードを共通化し、どの判断を各チームや人に残すか」が設計対象になります。
