# note記事の構成ベストプラクティス

note向けの記事を、内容が伝わりやすく、最後まで読み進めやすく、読後に持ち帰りが残る構成へ近づけるための実践ガイド。

2026-08-26時点のnote公式編集ガイド・検索/AI検索向けガイドと、PR #524で実際に行った構成レビューの知見をもとに整理した。特定の「勝ちパターン」を断定するものではなく、記事タイプ・読者・目的に合わせて使う。

## 正本の境界

- **媒体の役割・多媒体展開の方針**: `docs/content-channel-strategy.md`
- **note記事の構成判断**: このファイル
- **品質確認の実行項目**: `articles_note/checklists/note-article-quality-checklist.md`
- **レビューの実行手順・出力形式**: `.claude/agents/note-article-reviewer.md` と `.claude/commands/review-note-article.md`

このガイドは固定テンプレートではない。記事の目的と読者体験を優先する。

## 最重要原則

### 1. 価値を先に出す

長文でも、最初から順番に読んでもらえる前提にしない。

冒頭の早い段階で、必要に応じて次を伝える。

- どんな問題を扱う記事か
- 誰に関係する話か
- 何が分かった、または何を持ち帰れるか

体験記事や技術・組織記事では、問題提起のあとに「先に結論」を置く構成を第一候補にする。

```text
問題提起
↓
先に結論・持ち帰り
↓
背景・前提
↓
具体的な体験・検証
↓
失敗・発見
↓
一般化
↓
読者が使える判断基準や次の行動
```

短い記事や物語性そのものが価値になる記事では、無理に結論を箇条書きにしない。

### 2. 見出しだけでストーリーを追えるようにする

`Phase 1`、`概要`、`詳細` のような管理用ラベルだけではなく、読者にとっての発見・問題・変化を見出しにする。

例:

- `Phase 1：個人で使う` → `個人では回った。でも再現性がなかった`
- `Phase 2：チーム展開` → `チームに広げると、知識の置き場がなくなった`
- `計測結果` → `測ってみたら、計測の仕組みも壊れていた`

スクロールして見出しだけ読んでも、記事の論旨が分かる状態を目指す。note公式の2026年ガイドでも、見出しだけで各セクションの内容が伝わる構成が推奨されている。

### 3. 具体 → 失敗 → 学び → 一般化の順で深める

実体験を主役にする記事では、成功した施策だけを並べるより、読者が再利用できる知識まで進める。

```text
実際にやったこと
↓
うまくいかなかったこと / 限界
↓
なぜ起きたか
↓
何を変えたか
↓
他の状況にも使える原則
```

失敗が実際に存在する場合は、個人の責任追及ではなく、環境・ツール・プロセスの設計課題として扱う。失敗談がない記事に、形式のための失敗を作らない。

### 4. 体験談を「持ち帰れる知識」に変換する

体験・ケース記事の終盤では、抽出した知見を読者が再利用できる形へ変換する。

候補:

- チェックリスト
- 判断基準
- 3〜5個の原則
- Before / After
- 導入時の確認項目
- 自分の状況へ置き換える問い

ただし、記事の主張を言い換えただけのまとめは増やさない。エッセイや物語性を主役にする記事では、チェックリスト化を要求しない。

### 5. ツール説明より読者の問題を先にする

自作ツール、フレームワーク、社内名称が主役に見えると、知らない読者が入りにくい。

原則は次の順序。

```text
読者にも起こる問題
↓
その問題に対して採った考え方
↓
今回使った実装・ツール
```

ツール固有の説明は必要な前提に絞り、その後の知見がツール非依存でも読めるようにする。

## 構成案を作るときの圧縮レビュー

構成案では、扱いたい論点をそのままH2へ並べない。

まず「この記事で読者が追う軸」を一文で決め、その軸に沿ってH2の役割を整理する。H2は論点の目録ではなく、読者の理解が一段進む単位として使う。

構成案を作ったら、本文を書く前にH2だけを抜き出して次を確認する。

- 中心の問いを一文で説明できるか
- H2を上から読むだけで、問題 → 発見 → 改善 → 一般化 → 次、などの流れが見えるか
- 隣り合うH2が同じ役割の具体例を並べているだけになっていないか
- 同じ役割の並列テーマは、より上位の意味で束ねてH3へ下げられないか
- 各H2が新しい論点を増やすだけでなく、前の章を受けて次へ進んでいるか
- 終盤に複数の「次にやりたいこと」「まとめ」「別テーマ」が競合していないか

例えば、次のように個別テーマを横並びにするより、

```text
Aの話
Bの話
Cの話
Dの話
```

読者が追う軸へまとめる。

```text
問題の見方
↓
改善の仕組み
↓
個別テーマへの適用
↓
一般化した原則
↓
次に考えること
```

そのうえでA / B / Cのような個別テーマは、必要ならH3として配置する。

**H2の本数そのものを目標にしない。** 短い記事なら少なくてよく、長い記事では増えてよい。見るべきなのは「見出し数」ではなく「読者が何本の思考軸を同時に追わされるか」である。

## 専門用語は「初出で一度だけ説明する」

技術・AI記事では英語の専門語を避ける必要はない。ただし、読者が意味を推測しないと読み進められない状態は避ける。

基本ルール:

1. **初出**: 対象読者が知らない可能性のある語だけ、短い日本語の意味を添える
2. **2回目以降**: 英語か日本語のどちらか一方で書き、同じ括弧説明を繰り返さない
3. **一覧・分類**: 層名や正式名称は英語を残してよいが、横に一言の役割を置く
4. **用語集**: 用語そのものを参照する記事でない限り、独立セクションを安易に増やさない

例:

```text
初出:
Observability（何が起きたかを説明できること）

2回目以降:
Observability

分類一覧:
Observability: 観測可能性。実行記録、コスト、遅延、失敗Log
```

公開前には、括弧付きの専門語を検索し、同じ語を何度も説明していないか確認する。

特に次の状態は読者負荷になりやすい。

- 1文に未説明の英語名詞が連続する
- 同じ専門語の訳を複数の章で繰り返す
- 固有名詞を理解しないと本論へ入れない
- 用語説明のために章が増え、本来のストーリーが分断される

専門語を減らすことが目的ではない。**読者が本論を追うために必要な説明量だけ残す。**

## 最後に「足すレビュー」ではなく「削るレビュー」をする

内容・事実・論理を確認したあと、別のPassとして「削れるもの」を探す。

確認対象:

- 同じ主張を別の言葉で繰り返していないか
- 同じLoop / 図 / Before-Afterを複数回出していないか
- 既に説明した専門語を再説明していないか
- H2として独立させる必要のない具体例がないか
- 固有ツール名が一般化できる箇所に残っていないか
- 終盤に結論が2つ以上ないか
- 「次の記事の話」が現在の記事の結論より長くなっていないか

削るPassでは、新しい論点を追加しない。目的は情報量を減らすことではなく、**中心主張以外の認知負荷を減らすこと**である。

## タイトル設計

note公式は、タイトルだけで記事内容が想像できること、重要なキーワードを前に置くこと、期待を高めすぎないことを推奨している。

このリポジトリでは次を優先する。

1. 何の話か分かる重要語を前半に置く
2. 問題・変化・発見のどれかを含める
3. 本文で証明していない効果を断定しない
4. 固有名詞や数字は、理解を助ける場合だけ使う
5. 煽りより、内容の想像しやすさを優先する

「数字を入れれば強い」とは限らない。人数や件数が記事の本質でなければ、主題を狭める数字は外す。

## リード設計

冒頭は次の4要素から、記事に必要なものを組み合わせる。

1. **問題**：読者にも起こり得る課題
2. **対象**：どんな読者に関係するか
3. **先に結論**：今回分かったこと、持ち帰り
4. **信頼性の範囲**：実体験、実測、未検証事項、利害関係など

免責や自己紹介が長くなり、記事価値が見える前に離脱させないようにする。重要な開示は残しつつ、先に「読む理由」を出す。

## 技術・組織・AI活用の体験記事で使いやすい骨格

```text
タイトル

問題提起
先に結論・持ち帰り

前提：今回使った仕組み

個人・小規模では成立したこと
↓
広げて初めて見えた問題
↓
問題に対して作った仕組み
↓
うまくいかなかったこと
↓
実測・検証
↓
読者が使える判断基準・チェックリスト
↓
一般化した結論
```

これは比較基準であり、全記事に章を強制しない。実際に存在しない失敗・実測・一般化を、骨格へ合わせるために追加しない。

## スマホでの読みやすさ

- 1段落を長くしすぎない
- 長文では見出しを使う
- 箇条書きは一覧性が上がる箇所に使う
- 長いコードや設定ファイルは最小限にする
- ASCII図や表が横に広がりすぎないか確認する
- 文字だけが続く場合は、図・引用・箇条書きなどで視線の休憩点を作る
- 長文ではnoteの目次設定を検討する

noteの目次は、本文に見出しを設定したうえで公開設定の「目次設定」を有効にすると生成される。

## 図を入れる判断

図は装飾ではなく、文章だけでは関係性が分かりにくいときに使う。

優先候補:

- Before / After
- フロー
- 責務分離
- フィードバックループ
- 3つ以上の要素の関係

記事に図を1枚だけ入れるなら、最も重要な構造・ループ・因果関係を選ぶ。

## 記事終盤

「まとめ」だけで終わらせず、記事タイプに応じて次のどれかを置く。

- 実践チェックリスト
- 判断基準
- 自分の状況へ置き換える問い
- 次に測る指標
- 今後の未解決課題
- 関連記事や一次資料への導線

体験・ケース・ツール記事では、必要に応じて固有事例から一段抽象化し、別の環境でも使える言葉へ変換する。エッセイや短い記録では、余韻や観察そのものを結論としてよい。

## やりすぎないためのガードレール

- すべての記事に「先に結論3点」を強制しない
- 見出しを煽り文句にしない
- チェックリストを追加するためだけに内容を水増ししない
- 同じ主張を導入・各章・まとめで何度も繰り返さない
- 同じ専門語の括弧説明を複数箇所で繰り返さない
- 論点をH2として増やす前に、既存の読者軸へH3として束ねられないか確認する
- note向けだからと技術的正確性を削らない
- 読みやすさのために因果関係を断定しない
- 人気記事の表面的な形式をコピーせず、読者が価値へ到達しやすいかを優先する

## レビュー時の優先順位

以下は**該当する記事タイプ・記事目的に必要な項目だけ**を評価する。項目が存在しないこと自体を欠陥にしない。

### P1

- 冒頭で読む理由・持ち帰りが分からない
- タイトルと本文の主張がずれている
- 見出しを追っても論旨が分からない長文記事
- 体験・検証を主張の根拠にする記事なのに、根拠や限界がなく成功談だけになっている

### P2

- 体験・ケース記事なのに、学びが個別事例の説明だけに閉じており読者が再利用しにくい
- ツール/サービス記事で、固有名詞の説明が読者の問題より前に出すぎている
- 長文なのに視覚的な区切りがなく、読了を妨げている
- 読後に残したい理解・判断・行動が本文と結論から読み取れない

### P3

- タイトルの語順改善
- 図の追加
- 目次設定の公開時確認
- 段落の細かな圧縮
