# 実体験から設計知へ変換する執筆原則

AI駆動開発、開発プロセス、組織運営などの実践記事で、完成したベストプラクティスだけでなく、**なぜ現在の形になったのか**を判断過程として残すための補助方針。

## 正本との関係

- 媒体の役割・多媒体展開: `docs/content-channel-strategy.md`
- note記事の構成判断: `articles_note/guides/note-structure-best-practices.md`
- 品質確認: `articles_note/checklists/note-article-quality-checklist.md`
- 実体験を設計知へ変換する補助原則: このファイル

この文書は新しい構成テンプレートを増やすものではない。既存の「具体 → 失敗 → 学び → 一般化」を、実際の設計変更・運用履歴まで含めて扱う。

## 中心原則

**結果だけでなく、設計が変わった理由を書く。**

読者が再利用できるのは最終形そのものより、そこへ至る判断過程である。

```text
実体験・問題
↓
仮説
↓
実行
↓
失敗 / 限界 / 想定との差
↓
観測
↓
改善
↓
追加したものを再評価し、不要なら削る
↓
現在の形
↓
適用範囲・限界
↓
他でも使える原則
```

これは章構成を強制するテンプレートではない。実際に存在しない段階を、物語を整えるために追加しない。

## 成功談ではなく、学習履歴を書く

完成後の説明だけでは「何を真似すればよいか」は伝わっても、「自分の状況でどう判断するか」は伝わりにくい。

可能なら、次を残す。

- 最初に何を問題だと考えたか
- 最初の設計・仮説は何だったか
- 実運用で何が崩れたか
- 何を観測して設計を変えたか
- 何を追加したか
- 追加したもののうち、後で何を削除・統合したか
- 現在は何を残しているか
- どの条件までなら今回の学びを適用できるか

**何を足したかだけでなく、何を捨てたかも設計判断として扱う。**

## 根拠は一次情報へ寄せる

実体験を根拠にする記事では、利用できる場合は次を優先する。

1. PR / Issue / commit
2. 実行ログ、計測値、CI結果、レビュー記録
3. 当時の設計文書、ADR、振り返り記録
4. 公開済み記事や外部一次資料
5. 記憶に基づく振り返り

主張では、可能な範囲で次を分ける。

- **観測した事実**
- **そこからの解釈**
- **現在の判断・方針**

数字や失敗は、記事を強く見せるために作らない。未検証のものは未検証と書く。

## 一般化しすぎない

「自分の環境では成立した」と「一般に成立する」を分離する。

可能なら次を明示する。

- 個人開発かチーム開発か
- 新規開発か既存本番システムか
- 可逆な操作か不可逆な操作か
- どの程度のリスクを許容していたか
- どの規模・期間・件数で観測したか
- まだ試していない条件は何か

失敗がなかった記事に、形式のための失敗を作らない。個別事例だけから一般原則を断定しない。

## AI駆動開発の記事で特に残すもの

モデル名やプロンプトだけでなく、**AIを含む開発システムがどう変化したか**を残す。

- Agent / Modelの失敗をどう検知したか
- Context / Tool / Memory / Runtime / Gate / Reviewのどこを変えたか
- Guardrailを追加した理由
- Guardrailが過剰になった兆候
- Human Gateをどこへ置いたか
- 自動化した判断と、人間に残した判断
- 失敗からSkill / Agent / Flow / CIへ昇格したルール
- 後から削除・統合したHarness
- 変更前後で観測できた差

「AIツールを使った記事」で終わらせず、**AIを含む開発システムをどう学習・改善したかの記事**にする。

## 企画・レビュー時の問い

- このテーマについて、自分が実際に経験した出来事は何か？
- 最初の仮説と現在の設計はどう違うか？
- その変更を引き起こした観測・事故・違和感は何か？
- 追加したが後で不要になったものはあるか？
- PR / Issue / commit / 実測値など、示せる一次情報はあるか？
- 観測事実と自分の解釈を分けているか？
- 自分の経験を超えて断定していないか？
- 読者が再利用できる判断基準は何か？

答えられない項目を創作しない。

## レビュー優先度

### P1

- 実体験を根拠にしているのに、何が実際に起きたのか分からない
- 観測事実と解釈が混ざり、確認済みの範囲が分からない
- 存在しない失敗・数値・効果を補っている
- 個別事例だけから一般論を断定している

### P2

- 現在の完成形だけが説明され、なぜその設計になったのか追えない
- 削除・統合したものがあるのに、追加した仕組みだけを書いている
- 実体験はあるが、読者が再利用できる判断基準まで進んでいない
- 適用範囲や未検証条件が分からない
