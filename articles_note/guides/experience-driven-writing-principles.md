# 実体験から設計知へ変換する執筆原則

AI駆動開発、開発プロセス、組織運営などの実践記事で、単なる成功談やベストプラクティス紹介ではなく、読者が「なぜ今この設計になっているのか」を追える記事にするための補助方針。

## 正本との関係

- **媒体の役割・多媒体展開の方針**: `docs/content-channel-strategy.md`
- **note記事の構成判断**: `articles_note/guides/note-structure-best-practices.md`
- **品質確認の実行項目**: `articles_note/checklists/note-article-quality-checklist.md`
- **実体験を設計知へ変換する補助原則**: このファイル

この文書は構成テンプレートを増やすためのものではない。既存の「具体 → 失敗 → 学び → 一般化」を、実際の設計変更・運用履歴まで含めて扱うための補助方針である。

## 中心原則

**完成したベストプラクティスだけを書くのではなく、なぜ現在の形になったのかを書く。**

読者にとって価値があるのは、最終形そのものだけではない。

- 何を問題だと考えたか
- 最初に何を試したか
- 何がうまくいかなかったか
- 何を観測したか
- そこから何を変えたか
- 増やした仕組みのうち、何を後から捨てたか
- 現在はどこまで残しているか
- どの条件なら適用でき、どこから先は適用できないか

まで追えると、読者は結果ではなく**判断過程**を再利用できる。

## 基本ループ

実体験を主役にする記事では、必要に応じて次の流れを使う。

```text
実体験・問題
↓
仮説
↓
実行
↓
失敗 / 限界 / 想定との差
↓
観測
↓
改善
↓
過剰だったものを削る
↓
現在の形
↓
適用範囲・限界
↓
他でも使える原則
```

これは章構成を強制するテンプレートではない。実際に存在しない段階を、物語を整えるために追加しない。

## 「追加したもの」だけでなく「削ったもの」を書く

実践から生まれる設計では、学習は追加だけでは進まない。

特にAI駆動開発やHarness Engineeringでは、失敗を受けてルール・Gate・Skill・チェック・CIを増やした結果、仕組み自体が重くなることがある。

そのため記事では、可能なら次の変化も記録する。

```text
事故
↓
ガードを追加
↓
運用コストや認知負荷が増える
↓
再評価
↓
不要なガードを削除 / 統合
↓
必要なものだけ残る
```

**何を足したかだけでなく、何を捨てたかも設計判断である。**

現在の仕組みが簡潔に見える場合でも、そこへ至るまでの削除・統合の履歴が記事の重要な一次情報になる。

## 成功談ではなく、学習履歴を書く

実践記事を次のような「完成後の説明」だけにしない。

```text
この問題にはAが有効です。
AはBとCで構成します。
導入すると改善します。
```

可能なら、次のように時間軸を残す。

```text
最初はAで解決できると考えた
↓
実運用ではBが壊れた
↓
Cを追加した
↓
Cが重くなりDを削除した
↓
現在はEだけ残している
```

この差によって、読者は「真似する対象」だけでなく「自分の状況でどう判断するか」を持ち帰れる。

## 根拠は一次情報へ寄せる

実体験を根拠にする記事では、利用できる場合は次を優先する。

1. 実際のPR / Issue / commit
2. 実行ログ、計測値、CI結果、レビュー記録
3. 当時の設計文書、ADR、振り返り記録
4. 公開済み記事や外部一次資料
5. 記憶に基づく振り返り

数字や事例は、存在するから強いのであって、記事を強く見せるために作るものではない。

主張を書くときは、可能な範囲で次を区別する。

- **観測した事実**
- **そこからの解釈**
- **現在の判断・方針**

この3つを混ぜない。

## 失敗を無理に作らない

失敗談は記事を強くするが、必須要素ではない。

- 実際に失敗や事故があった場合は隠さない
- 原因を個人攻撃ではなく、設計・環境・プロセスの問題として扱う
- 失敗がなかった場合は、形式のために作らない
- 未検証のものは「未検証」と書く
- 再現できない経験を、一般原則として断定しない

## 適用範囲を書く

実体験から得た知見は、条件付きで成立することが多い。

記事では可能なら次を明示する。

- 個人開発かチーム開発か
- 新規開発か既存本番システムか
- 可逆な操作か不可逆な操作か
- どの程度のリスクを許容していたか
- どの規模・期間・件数で観測したか
- まだ試していない条件は何か

「自分の環境では成立した」と「一般に成立する」を分離する。

## AI駆動開発の記事で特に残したいもの

AI駆動開発の記事では、モデル名やプロンプトだけでなく、次の変化を一次体験として残す。

- Agent / Modelの失敗をどう検知したか
- Context / Tool / Memory / Runtime / Gate / Reviewのどこを変えたか
- Guardrailを追加した理由
- Guardrailが過剰になった兆候
- Human Gateをどこへ置いたか
- 自動化できた判断と、残した人間判断
- 失敗からSkill / Agent / Flow / CIへ昇格したルール
- 後から削除・統合したHarness
- 変更前後で観測できた差

これにより、「AIツールを使った記事」ではなく、**AIを含む開発システムをどう改善したかの記事**にする。

## 記事を作る前に確認する問い

体験記事の企画時には、最低限次を確認する。

- このテーマについて、自分が実際に経験した具体的な出来事は何か？
- 最初の仮説・設計は何だったか？
- 現在の設計との間で、何が変わったか？
- 変更のきっかけになった観測・事故・違和感は何か？
- 追加したが後で不要になったものはあるか？
- PR / Issue / commit / 計測値など、根拠として示せるものはあるか？
- 自分の経験を超えて断定している箇所はないか？
- 読者が再利用できる判断基準は何か？

すべてに答えが必要なわけではない。答えられない項目を創作しない。

## レビュー時の優先順位

### P1

- 実体験を根拠にした記事なのに、実際に何が起きたのか分からない
- 観測事実と筆者の解釈が混ざり、どこまで確認済みか分からない
- 個別事例だけから一般論を断定している
- 存在しない失敗・数値・効果を、構成を成立させるために補っている

### P2

- 現在の完成形だけが説明され、なぜその設計になったのか追えない
- 改善のために追加した仕組みは書かれているが、削除・統合したものがあっても触れられていない
- 実体験はあるが、読者が再利用できる判断基準まで抽象化できていない
- 適用範囲や未検証条件がなく、再現可能性を判断しにくい

### P3

- 時系列をより明確にすると理解しやすい
- PR / Issue / commit / 数値への参照を追加すると信頼性が上がる
- Before / Afterや設計変化の図を追加すると理解しやすい
