# AI駆動開発で重要になるのは「作る力」ではなく「作らない判断力」だと思う

## 最近起きたこと

AI駆動開発を続ける中で、実装そのものは以前よりかなり速くなった。

AIにPBIやSpecを渡すと、調査し、設計し、コードを書き、テストまで進めてくれる。

その一方で、PoCのように「新しい体験に価値があるか」を確かめたい場面では、実装上のDONEと価値仮説が混ざる違和感が出てきた。

「価値があるかもしれない」が、いつの間にか「これを作るべき」に変わってしまう。

## そのとき考えていたこと

AIによって作る速度が上がるなら、もっと多く作れば学習も速くなると思っていた。

でも、速く作れることと、正しいものを作っていることは同じではない。

むしろ、間違ったものまで高速に作れてしまう。

## 違和感

実装能力が上がったことで、これまで実装の中に埋もれていた判断が目立つようになった。

- そもそも何を作るのか
- なぜ今それを作るのか
- 何を確かめたいのか
- どこまで作れば十分なのか
- どの結果なら続け、どの結果なら止めるのか

AIに任せられる範囲が広がるほど、こうした判断を曖昧なままにできなくなった。

## 今の仮説

今は、AI駆動開発で重要になるのは「作る力」だけではなく、むしろ「作らない判断力」なのではないかと考えている。

作るコストが下がるほど、何を作るか、なぜ作るか、何をもって正しいとするかを決める力の価値が上がる。

速くしたいのはコード生成だけではない。

Problem → Hypothesis → Shape → Build / Experiment → Evidence → Decision

この一連の学習サイクル全体を短くしたい。

つまり、Time to CodeよりTime to Learningを見る、という感覚に近い。

まだ仮説だが、AIに任せる範囲を広げること自体を成熟と考えるのではなく、「どこまで任せ、何を検証し、どこで止めるか」を再現可能にすることのほうが重要だと思っている。

## 既存の知識との接続

この違和感は、Product Discoveryや仮説検証、Lean Startupで扱われてきたテーマと重なる。

Deliveryでは、Intent / Completion Criteria / Constraints / Verification / Stop Conditionsを明確にする。

一方でDiscoveryでは、Problem / Value Hypothesis / Learning Conditions / Evidence / Decision / 今回固定しないものを先に考える。

AIが高速に実装できるようになったことで、DiscoveryとDeliveryを混ぜたときの問題が、以前より早く、はっきり表面化するようになったのかもしれない。

## 次に試したいこと

- [ ] AgentへPBIやSpecを渡す前に「今必要なのは価値を確かめることか、価値があると判断したものを届けることか」を確認する
- [ ] Deliveryでは完了条件、Discoveryでは学習条件を先に定義する
- [ ] 「何を作ったか」だけでなく「何を作らないと判断したか」も記録する
- [ ] Evidence → Decisionまで含めてTime to Learningを観測する
