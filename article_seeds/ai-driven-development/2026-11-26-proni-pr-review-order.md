# 小さいPRでもレビュー待ちは溜まる。後続をブロックするかでレビューの順番を決める

## 観測事実（著者が 2026-11-26 の会話で共有した内容。原文のまま）

> １つ１つのPRは小さいが、レビュータイミングが遅れてしまうと、PRレビュー待ちが溜まってしまう。
>
> １つのPRレビューが止まることで、後続の作業がBlockされてしまうPRと
> そのPRだけを確認すれば良い、後続をブロックしないPRと
> あるが、１つづつを直ぐレビューする前提なので、後続Blockが発生するなどはPR説明に書かれていない
>
> また、PR待ちが発生するまで、優先順位もきしないていなかったが、PR待ちが発生すると、PRレビューにも優先順が必要になってきた

**注意**: 著者の自己申告による一次体験。待ちの件数・期間・後続がブロックされた実例は未突合。会社リポジトリの PR で確かめてから本文に使う。数値・PR 番号・社内リポジトリ名は公開リポジトリに書かない

## 裏取りの結果（2026-11-26、PJ の記事化セッション経由で照会）

社内の値のため、件数・日数・PR 番号・リポジトリ名はここに書かない。照会元の記録（社内）に測定時刻つきで残っている。

- 上に積んだ子 PR は、依頼から Approve までが短かった。時間がかかったのは**土台の PR の承認待ち**で、その間に子 PR が長く Draft のまま止まっていた。土台の取り込み後、依頼が短い期間に集中した（2026-11-26 の外部レビューで、当初の「レビューの速さではなく依頼を出すまで」が土台と子を混同していたと分かり訂正）
- 後続をブロックした実例がある。土台の PR の Approve を待つ間、その上に積んだ子 PR が Draft のまま待った
- 土台の PR の説明に「子 PR を止めている」という記載はなかった。子 PR の説明にも依存の記載はなかった
- PR テンプレートにも、依頼の必須項目にも、後続ブロック・依存の欄はなかった
- 当時の「見てほしい順」は、マージする順番と期限で並べたもので、後続ブロックやリスクで並べたものではなかった
- 振り返りで「後続を止めるかを書く」「後続ブロック → リスクの順で並べる」「依頼中の本数に上限を置く」「止める PR が決めた日数を超えたら、分割するかもう 1 人に頼む」「1 本ずつすぐ、が崩れた合図を決めておく」などの決まりを案として足した。**まだ実施していない**

記事で書き分けること:

- 著者の体感「レビュータイミングが遅れると溜まる」と、実測「依頼が後ろに寄って溜まった」を分けて書く
- 決まりは未実施なので「こうしたら解決した」ではなく「次はこうする」で書く
- 人のレビューのペースや本数を決めた記録は無い

## 自分の解釈

- 1 本ずつすぐレビューする前提では、レビューに優先順位は要らない。待ちが発生して初めて要る
- 優先順位の軸は「後続をブロックするか」。見る深さは別の軸（変更のリスク）で決める
- 後続ブロックの有無は PR を出す人しか分からないので、PR 説明に書いておく必要がある

## 既存の知識との接続（公開文献）

確認済み（2026-11-26、PDF 本文を pdftotext で照合）:

- Sadowski ほか (2018) "Modern Code Review: A Case Study at Google", ICSE-SEIP（著者版 PDF: https://sback.it/publications/icse2018seip.pdf）
  - §5.2: 変更行数の中央値は 24 行。レビュアー数の中央値は 1 人。レビュー全体の所要時間の中央値は 4 時間未満。最初のフィードバックまでの中央値は、小さい変更で 1 時間未満、非常に大きい変更で約 5 時間
  - §4.1〜4.2: 導入の最大の目的は理解しやすさと保守性。現在の期待は教育・規範の維持・門番・事故防止
  - §7.1: 変更が大きいほど待ちが延びるという先行研究を引くが、速さを小ささだけに帰していない
- DORA "2025 State of AI-assisted Software Development"（https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf）: 2026-11-26 に PDF を pdftotext で照合。Value stream management の節（p.75）「Focus on flow, not just speed」。リードタイム・プロセスタイム・"the ratio of value-add to wait time" を測るよう勧め、コードレビューがボトルネックの例として "rather than using AI to simply generate more code that will only exacerbate the bottleneck" と書く

使わない:

- 「レビュー時間 +91%、PR サイズ +154%」: 第三者のまとめが出典で、DORA の PDF では見つからない
