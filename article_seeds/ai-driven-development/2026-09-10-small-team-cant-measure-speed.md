# 5人チームでは「改善速度」を安定して測れなかった

## 最近起きたこと

5人のチームで、AIの仕組みそのものをどれくらい速く改善できているか測ろうとした。

候補にしたのは、改善のリードタイムだった。

ところが、実際の改善は週次のバッチでまとめて扱っている。改善案が火曜に出ても金曜に出ても、次の週次処理まで待つため、観測される時間には運用上の待ちが大きく混ざる。

5人規模では件数も多くないので、短期間の比較はさらにぶれやすい。

そこで今は、次のように置き換えている。

- 改善PRのマージ率を見る
- 改善の種類（Reuse / Extend / Create / Skip）の分布を見る
- どちらも「改善速度そのものではない」と明記する

## そのとき考えていたこと

最初は、一般的に使われるリードタイムの考え方をそのまま持ち込めば、AI改善の速さも測れると思っていた。

数字が取れれば、改善前後を比較できると考えていた。

## 違和感

実際には、「測りたい対象」と「データが生まれる仕組み」が噛み合っていなかった。

週次バッチで5人規模だと、1件ごとの事情や曜日の影響が大きい。数字は出せても、その変化が本当に改善を表しているのか判断しづらい。

ここで気づいたのは、**計測可能だからといって、意思決定に使えるとは限らない**ことだった。

逆に、代わりに置いたマージ率にも限界がある。

マージ率が高いのは、改善案の質が高いからかもしれないし、単にレビュー基準が緩いからかもしれない。これは速度ではなく、「提案した改善が採用まで進んだ割合」に近い。

Reuse / Extend / Create / Skipの分布も、改善の性質を知るシグナルではあるが、品質そのものを直接測っているわけではない。

## 今の仮説

小さなチームでは、無理に安定した速度指標を作るより、**今あるデータから意思決定に使えるシグナルを選び、何を測れていないかも明示する**ほうがいい。

重要なのは「測れるものから測る」ことではない。

それだけだと、取得しやすい数字に目標が引っ張られる。

今の自分たちには、次の順番が合っていそうだ。

1. 何を判断したいのかを決める
2. その判断に必要なシグナルを考える
3. 追加の計測コストが低いデータから試す
4. 弱い代理指標なら、何を表していないか明記する
5. 件数が増えたら、より直接的な指標へ置き換える

定量化できない期間は、定性的な観測を併記するほうが、数字だけを置くより誠実だと思う。

## 既存の知識との接続

- 小さなサンプル：件数が少ないと、個別事情や運用周期の影響を受けやすい
- Lean：計測のためだけに大きな運用コストを増やさない
- 代理指標：直接測れないものを別の観測値で近似する場合、限界を明示する

ここでの学びは「小さいチームでは速度を測れない」ではない。

**今の運用周期とデータ量では、改善速度を安定して比較できる指標にならなかった**、という話に留めたい。

## 次に試したいこと

- [ ] 改善の種類の分布を数週分並べ、実際にどんな判断に使えたか記録する
- [ ] マージ率が表すもの / 表さないものを書き出す
- [ ] 改善件数が増えたとき、リードタイムを再び使えるか見直す
- [ ] 週次バッチ待ちと、実際の作業時間を分離できるか試す
