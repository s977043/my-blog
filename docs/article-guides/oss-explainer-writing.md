# 他者のOSSを解説する記事の書き方

自分が作っていないOSSを読み、その設計を解説する記事のための実践ガイド。

2026-09-16時点で、AOSA（The Architecture of Open Source Applications）の章構成、技術ブログ一般の作法、および外部読解型の実例分析をもとに整理した。

## 正本の境界

- **媒体の役割・多媒体展開の方針**: `docs/content-channel-strategy.md`
- **Zenn記事の構成判断**: `docs/article-guides/zenn-structure-best-practices.md`
- **他者のOSSを解説する記事の判断**: このファイル
- **自分のOSS設計記事の主張境界レビュー**: `.claude/skills/oss-article-claim-boundary/SKILL.md`
- **一次経験と来歴の扱い**: `.claude/skills/tech-blog-writing/SKILL.md`

このガイドは固定テンプレートではない。記事の目的・読者・対象OSSの性質を優先する。

## まず分ける：中の人が書くか、外から読んで書くか

同じ「OSS解説」でも、書き手の立場で守るべきものが変わる。

| | AOSA型（中の人） | 外部読解型（このガイドの対象） |
| --- | --- | --- |
| 「なぜそう作られたか」の根拠 | 設計判断の当事者記憶 | コードから逆算した推測 |
| 強み | 意図・却下案・歴史を書ける | 利用者視点の評価軸・比較・導入判断 |
| 最大のリスク | 宣伝になる | 推測を事実として書く |
| 必須の防御 | 現在の実装との乖離を書く | 検証対象の固定と、推測の明示 |

AOSAは各章が「主要コンポーネントは何か」「どう相互作用するか」「なぜそう作られたか」「作者は何を学んだか」に答える。外部読解型は4つ目を当事者としては書けない。**代わりに「読む前の予想がどう外れたか」を自分の一次経験として書く**（後述）。

## 必須要件

外部読解型で、これを欠くと記事が成立しない、または誤情報になるもの。

### 1. 検証対象をcommitで固定し、冒頭に書く

記事は公開翌月から陳腐化しうる。読者が追試できる状態にするため、冒頭に次を置く。

- リポジトリURL
- 読んだcommit hash（またはtag）
- 読んだ日付

本文の記述は、そのスナップショット時点の事実として書く。公開後の進展は本文を書き換えず、追記セクションで日付つきで足す。

> 同じ規律を自分のOSS記事側でも要求している（`oss-article-claim-boundary` の Check 4）。外部読解型では、実装が他人の手で変わるぶん、必要性はさらに高い。

### 2. 推測・ドキュメント・実行結果を文体で区別する

外部読解型で最も落ちやすい点。読者が根拠の強さを判別できるように、3層を混ぜない。

| 層 | 書き方 | 添えるもの |
| --- | --- | --- |
| 実行して確認した | 断定してよい | コマンドと出力 |
| ドキュメントに書いてある | 断定してよい | 該当ドキュメントへのリンク |
| コードを読んだ推測 | 「〜のように見える」と明示 | 該当ファイルパス（できれば行） |

「〜のように見える」と書いてあっても、**該当ファイルが示されていなければ読者は追試できない**。ヘッジ表現は免責であって、根拠の提示ではない。

### 3. 最低1回は動かし、出力を1つ貼る

リポジトリを指して数行なぞるだけの記事にしない。副作用のないコマンド（dry-run、preview、`--help`、バージョン表示）でも、実物の出力が1つあると記事の等級が変わる。

動かしていないなら、「実装を読んだだけで、実行していない」と明記する。これは弱点の告白ではなく、読者が記事の射程を判断するための情報である。

## 記事を強くする書き方

必須ではないが、これがあると解説として機能する。

### 4. 一文の設計軸を先に決める

「XがAを担当し、YがBを担当する」の形で、記事全体を貫く軸を1つ決める。以降の個別機能の説明は、すべてこの軸に回収する。

軸が見つからないうちは、まだ読み込みが足りない。機能を並べた記事になっていたら、この軸が無いことを疑う。

### 5. 失敗モードから逆算して機能を説明する

「この機能がある」ではなく「これが無いと何が壊れるか → だからこの機能がある」の順で書く。読者が自分の状況へ写像できるのは後者だけである。

### 6. 弱点は必ず代替案とセットにする

批判だけでは読者が行動できない。「Xを除外するのは妥当。ただしYだけは渡せる構成が望ましい」の形にする。

代替案を書けないなら、それは弱点の指摘ではなく、まだ理解していない箇所である可能性を疑う。

### 7. 検証可能な粒度まで降りる

デフォルト値、閾値、並列数、段数、固有名。抽象論で終わらせず、読者が確認しに行ける具体を出す。ただし出した数値は必ず1の固定commitに紐づく。

### 8. 結論で読者の分類を書き換える

「良い/悪い」で終わらせず、「これはAではなくBと見るのがよい」の形にする。読者の既存の分類を更新する一文が、記事で最も長く残る。

### 9. 予想が外れた点を書く

`tech-blog-writing` の「知識の来歴」（期待 → 実行 → 観測 → 解釈 → 判断変更）を、外部読解型に翻訳したもの。

- 読む前に何を予想していたか
- 読んで分かったこと
- 予想が外れた点と、その理由

これは中の人には書けない、外部読解型だけの一次経験である。ここを持つかどうかが、要約記事との差になる。

## 書かないもの

- 実行していない機能の成功断定
- 一次情報に当たれない性能・効果の数値
- 他プロダクトとの比較で、比較対象の該当バージョンやプランを特定しない記述
- READMEの訳出に自分の解釈を混ぜたもの（訳出なら訳出と書く）

## 公開前チェックリスト

- [ ] 冒頭にリポジトリURL・commit hash・読んだ日付がある
- [ ] 推測箇所に「〜のように見える」と該当ファイルパスの両方がある
- [ ] 実行した出力が最低1つある。無い場合は「実行していない」と明記してある
- [ ] 記事全体を貫く設計軸が一文で書いてある
- [ ] 主要な機能が、失敗モードとセットで説明されている
- [ ] 弱点の指摘に代替案が付いている
- [ ] 比較対象があるなら、そのバージョン・プランを特定している
- [ ] 結論が「良い/悪い」ではなく分類の提示になっている
- [ ] 読む前の予想と、外れた点が書いてある
