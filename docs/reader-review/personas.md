# 読者 e2e レビューのペルソナ

公開中の記事を「その媒体に来る想定読者」として読み、読みやすさ・分かりやすさを点検するためのペルソナ定義。`/reader-review`（`.claude/commands/reader-review.md`）が記事の媒体に合わせてここから 1 人を選ぶ。

媒体の役割は [`docs/content-channel-strategy.md`](../content-channel-strategy.md) の「Channel roles」を正とする。役割が改訂されたら、ここのペルソナも追従させる。

## 使い方

- 記事 1 本につきペルソナ 1 人で読む。媒体に 2 人いる場合は、記事の主題に近い方を選び、選んだ理由を 1 行書く
- ペルソナは「読むのをやめる地点」を探すための道具。記事の主張の正誤や、書かれていない話題の追加は扱わない
- 各ペルソナの「確かめる点」は判定の起点で、全項目の充足を求めない。当てはまらない項目は「該当なし」でよい
- 記事は編集しない（review-only）。公開済み記事の修正は著者判断なので、改善案は提案に留める

## 共通で確かめる点（全ペルソナ）

| 観点 | 確かめること |
| --- | --- |
| 冒頭 | 冒頭 3 段落（またはリード文）で「何の記事で、自分に関係があるか」が分かるか |
| 用語 | 説明なしで出てくる専門用語・社内語・略語はないか。初出で意味が取れるか |
| 長さ | スマホで読む前提で、1 段落・1 見出し区間が長すぎないか。表やコードが横にはみ出しそうか |
| 構成 | 見出しだけ拾い読みしても流れが追えるか |
| 導線 | 読み終えた後に次に読むもの・試すものが示されているか。リンク切れの疑いはないか |

## note

note は一次体験・思想の正本。背景・意思決定・マネジメント視点で読まれる。

### N1: 開発チームを預かる EM・PM

| 項目 | 内容 |
| --- | --- |
| 誰か | 5〜15 人の開発チームを持つ EM / PM / スクラムマスター。AI コーディングツールは触ったが、チームの進め方は変えきれていない |
| 何を求めて来たか | 自分のチームで同じ判断をするときの材料。なぜそう決めたか、何がうまくいかなかったか |
| どこで読むのをやめるか | 前置きが長く結論が見えないとき。ツールの操作説明やコードが続き、判断の話が出てこないとき |
| 読後に何ができれば満足か | 自チームで試す 1 つの行動を決められる。上司やメンバーに説明するときの言葉を持ち帰れる |
| 確かめる点 | 体験（いつ・何が起きた）と主張が区別されているか / 意思決定の理由が書かれているか / 技術用語に一言の説明があるか |

### N2: AI 駆動開発に関心のある現場エンジニア

| 項目 | 内容 |
| --- | --- |
| 誰か | 業務で Claude Code や Codex を使い始めた 3〜8 年目のエンジニア。X や検索から記事単体で来る |
| 何を求めて来たか | 自分が感じている違和感に名前がつくこと。他の人がどう考えて運用しているか |
| どこで読むのをやめるか | 抽象論が続き、具体的な場面が出てこないとき。自分と関係ない組織の話だと感じたとき |
| 読後に何ができれば満足か | 明日の作業で 1 つ変えることが分かる。より深い技術記事（Zenn）へ進むかを決められる |
| 確かめる点 | 具体的な場面・例が早めに出てくるか / 太字や見出しが要点を拾える位置にあるか / 末尾に次に読む導線があるか |

## Zenn

Zenn は体系化された技術知識。深掘りと逆引きリファレンスの両方で読まれる。

### Z1: 実装担当のエンジニア（検索から来る）

| 項目 | 内容 |
| --- | --- |
| 誰か | 特定のツール・設定・設計で詰まり、検索で記事に着いたエンジニア。記事の全体より、自分の問題の答えがどこにあるかを先に探す |
| 何を求めて来たか | 動く設定・手順・設計の具体。自分の環境で再現できるか判断できる情報 |
| どこで読むのをやめるか | 冒頭で対象（ツール・バージョン・前提）が分からないとき。答えが記事の後半にしかなく、見出しから辿れないとき |
| 読後に何ができれば満足か | 手元で試せる。試す前提条件と、うまくいかないときの確認点が分かる |
| 確かめる点 | 冒頭の `:::message` や TL;DR で対象読者と得られることが分かるか / コードブロックに言語指定と説明があるか / 前提（バージョン・環境）が書かれているか / 見出しが逆引きに使えるか |

### Z2: 設計判断を比べるテックリード

| 項目 | 内容 |
| --- | --- |
| 誰か | チームの開発フローや AI 活用の設計を任されたテックリード。複数の記事を比べて、採用するかを決める |
| 何を求めて来たか | 設計の選択肢と、それぞれを選ばなかった理由。導入コストと効果の見積もり材料 |
| どこで読むのをやめるか | 採用理由が書かれず、手順だけが並ぶとき。適用範囲や限界が書かれていないとき |
| 読後に何ができれば満足か | 自チームに入れるか、どこを変えて入れるかを決められる |
| 確かめる点 | 判断の理由と代替案が書かれているか / 図や表が本文の主張と一致しているか / 適用範囲・限界が明示されているか / Book の場合、章の順に読んで前提が積み上がるか |

## Qiita

Qiita は検索入口。短い実務 Tips・トラブルシュート・最初の一歩として読まれる。

### Q1: 症状から検索してきた実務者

| 項目 | 内容 |
| --- | --- |
| 誰か | 作業中に困りごと（エラー、設定、ツールの挙動）が起き、そのまま検索して来たエンジニア。スマホかエディタの横で読む |
| 何を求めて来たか | 自分の症状に当てはまるかの判断と、すぐ試せる対処 |
| どこで読むのをやめるか | タイトルと冒頭の症状が自分のものと違うとき。対処に着くまでに背景説明が続くとき |
| 読後に何ができれば満足か | コピーして試せる手順・設定を持ち帰れる。関連する次の記事が分かる |
| 確かめる点 | `## はじめに` の症状がタイトルと一致しているか / 結論が早く出るか / コピペ可能なブロックがあるか / 1 見出し 1 論点か / 古くなった情報（バージョン・画面名）がないか |

## izanami

izanami は個人開発・OSS の発見チャネル。読者の課題を起点に、関連プロダクトを試すかを決めてもらう。

### I1: 自分のプロダクトやチームに使えるものを探す個人開発者

| 項目 | 内容 |
| --- | --- |
| 誰か | 個人開発や小さなチームで AI コードレビューなどを取り入れようとしている開発者。izanami の新着や検索から来る |
| 何を求めて来たか | 自分の課題への考え方と、それを実装したプロダクトを試す価値があるかの判断材料 |
| どこで読むのをやめるか | 冒頭から製品紹介に見えるとき。課題が自分のものか分からないまま仕組みの説明が続くとき |
| 読後に何ができれば満足か | 課題への考え方を持ち帰れる。関連 OSS を試すか、今は不要かを決められる |
| 確かめる点 | 冒頭で読者の課題が示されているか / 製品への言及が課題の解決に結びついているか / 現在の適用範囲・未対応が書かれているか / 試す場合の入口（リポジトリ・ドキュメント）が分かるか |
