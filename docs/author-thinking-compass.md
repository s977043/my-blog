# 著者の思考・価値観のコンパス

> **状態: 著者レビュー待ちの初版（2026-10-22）**
>
> このファイルは、記事ごとのテクニックではなく、著者が何を大切にして考え、書き、判断しているかを蓄積するためのもの。AIエージェントが執筆・編集・レビューするとき、**著者の中心的な考えを、調査の都合やテンプレートの都合で別の主張に置き換えない**ための参照資料である。
>
> 全項目を著者が一括承認したわけではない。以下の「本人が明示」「公開記事で表現」「整理仮説」という出所の違いを保持する。

## 位置づけと優先順位

- **著者の思考や価値観**: このファイル。記事横断の *Author Intent* を理解するための資料
- **記事ごとの著者意図**: 対応する Article Seed / Article Plan と、著者の最新の明示的な判断。具体的な記事ではこちらが優先する
- **媒体・編集方針の正本**: [content-channel-strategy.md](content-channel-strategy.md)。媒体の役割・掲載可否・編集原則は上書きしない
- **実体験を記事へ変換する原則**: [experience-driven-writing-principles.md](../articles_note/guides/experience-driven-writing-principles.md)。構成や一次情報の確認方法は二重定義しない
- **リポジトリ規約**: [AGENTS.md](../AGENTS.md)。権限・公開・会社情報などの制約は常に優先する

この文書は**著者の考えを置く場所**であって、エージェントへ新しい実行権限を与える設定ファイルではない。主張と事実が矛盾する場合に事実を改変してはいけない。根拠が不足するなら、著者に確認するか、仮説として書く。

## 1. 著者が明示した、変えたくない考え

### 1-1. 記事は「知っていることを全部書く」ためのものではない

**本人が明示（2026-09-27の対話）**

- 読者に伝えたいこと、自分が考えたことが伝わる文章を優先したい
- 嘘は書かない。ただし、調査した情報や例外をすべて網羅しなくてもよい
- 伝わりやすくするための**少し強い表現**は使ってよい。ただし、観測していない事実・数字・効果を盛ることとは違う
- 完全な技術説明にしようとして、記事の中心をぼやかしたくない

ここで優先するのは「正確さより印象」ではなく、**事実を守りながら、中心となる考えが届くこと**。細部の省略はよいが、主張の意味を変える省略や創作は不可。

### 1-2. 実際に経験し、違和感を持ち、考えが変わった過程を大切にする

**本人が明示（2026-09-10、09-27の対話）**

- 仮定だけで説明せず、一次情報と実体験を入れる
- 「実際に起きたこと → 違和感 → 仮説 → 検証・観測 → 学び」の流れを大切にする
- 確かめたこと、まだ考えていること、これから試すことは分ける
- ツールやOSSの機能紹介より、**それを使って何が起き、何を考えたか**を書きたい

失敗を必ず捏造して入れる必要はない。実際に経験した失敗や、取り下げた判断があるなら、完成した結果だけでなく変化の過程を描く。

### 1-3. AIと開発するだけでなく、AIと開発のやり方を改善する

**本人が明示的に支持（2026-10-22の対話、PR #879に対応）**

> **AIに仕事を任せる。その仕事を人が確かめる。そして、AIと一緒に仕事の進め方を振り返り、次の開発で試してみる。**

この3文に対し、著者は「とても良いね！私が書きたかった記事です、自分の考え方に近いです」と表明した。

この言葉は、次の3層を含む。

1. **任せる**: 人が仕事の目的・単位・条件を考え、AIエージェントに実行を任せる
2. **確かめる**: コードや成果物だけでなく、計画・根拠・実行の状態を検証する
3. **振り返って次に試す**: AIと開発プロセスを振り返り、必要な学びをSkill / Workflow / Reviewなどに反映して、次の開発で確かめる

これは「AIが提案し人間が採否を決める」という一部分に還元しない。

同じ対話で著者が好意的に受け止めた記事の結び方は、次の趣旨である。

> AI駆動開発になっても、アジャイルで大切にしてきたことは変わらない。変わるのは、一緒に開発し、学び、改善する相手にAIエージェントが加わったこと。

この章は **PR #879 の記事の中心主張**として承認された。全記事に同じ結論を強制するのではなく、著者の思考を理解する具体例としても参照する。

## 2. 公開記事や継続的な対話で表れている考え

> **根拠の区分**: ここは著者名義の記事で表現され、または複数の対話で繰り返し扱われた考えを整理したもの。「あらゆる場面で常にそう判断する」という恒久的なポリシーとは扱わない。著者の考えが変化したら更新する。

### 2-1. 作る速さだけでなく、次の判断までの学習速度を大切にする

**公開記事で表現**: [AI時代の開発で短くすべきは、Time to CodeではなくTime to Learning](../articles_note/published/n5070e13232ce.md)

- Build（作ること）の目的は、次の意思決定に必要なEvidence（観測可能な根拠）を得ることにもある
- 作って終わりではなく、**Shape → Build → Verify → Learn → Decide → Shape** の循環を見る
- エンジニアリングは「言われたものを実装する」だけでなく、技術的な知見や制約を次のプロダクト判断に返す
- PdM・デザイナー・エンジニアの責任は曖昧にせず、専門性を持ち寄る

### 2-2. AIエージェントはモデル単体でなく、システムとして扱う

**公開記事で表現**: [失敗をモデルのせいにしない。AI駆動開発を「Model + Harness」で考える](../articles_note/published/nd6a5d83d1488.md)

- AIが失敗したとき、モデル性能だけで結論を出さない
- Context / Tool / Memory / Skill / Runtime / Review / Gate / Evalなど、外側の仕組みも原因と改善対象になる
- 失敗を再現可能な評価ケースへつなぎ、何を変えたかと結果を確かめる
- 複数エージェントを増やすこと自体が価値ではない。責務・権限・評価の境界があるから分ける

### 2-3. アジャイルの経験を、新しいAI開発へ適応させる

**今回の著者の明示的な支持 + 過去の実践をもとにした整理**

- アジャイルと段階的な計画・設計は、単純な二者択一ではない
- タスクは小さく分け、計画して実行し、レビューで確かめる。全体では短いフィードバックのループを回す
- 振り返りは会議の形式ではなく、実際に次の作業を変えるための学習である
- 改善がドキュメントに「書かれた」ことと、実際の作業で「使われた」こと、結果が「改善した」ことは違う

### 2-4. 自律性と人間の判断・権限を分ける

**継続的な対話と記事で扱ってきた思想（著者レビュー待ちの整理）**

- AIに委譲する範囲を増やすことと、人間の最終責任を放棄することは違う
- 操作のたびに承認することだけが人間の関与ではない。許可範囲、停止条件、レビュー・検証の位置を設計する
- **AIの観測・提案・判定・最終承認は別のもの**として考える
- Human-in-the-LoopからHuman-on-the-Loopへ変える議論でも、「人間を外す」のでなく「承認の粒度を変える」と捉える
- 状態・証拠・失敗時の復旧可能性を外部化する。AIの「完了しました」という報告だけで完了を認めない

### 2-5. 個人の気づきを、共有できる改善へ育てる

**継続的な対話で表現（著者レビュー待ちの整理）**

- 個人が得た学びは、他の環境でも確かめ、チームに共有できる形へ育てたい
- PRレビューで繰り返される指摘や実行時の失敗を、必要に応じてSkill・Workflow・Review観点へ変える
- 何でもルール化しない。追加した対策は、使われるか、邪魔になっていないかも振り返る
- 最初から組織全体で運用できたかのように語らない。個人での観察とチームでの採用は区別する

### 2-6. できたことと、まだ分からないことを区別する

**継続的な対話・記事執筆での判断基準**

- Evidence（観測）とJudgment（判断）は別。記録、判断、承認、効果の証明を混同しない
- 「実装した」「起動した」「役に立った」を同一視しない
- 率・増減・効果を述べるなら、可能な範囲で母数・期間・観測方法を示す
- 実装済み / 検討中 / 未検証を分ける。仮説は仮説として語る
- 調査の結果、主張の裏付けが弱いと判明しても、**勝手に別の記事へ書き換えない**。不足を共有し、確認を取り、書き方の選択肢を示す

## 3. 記事の声・読み手への届け方

**本人が明示した好みと、既存記事から読み取れる傾向の整理**

- **本人が書いたように読めること**。一般論の解説者や製品の宣伝担当者の声ではなく、自分の経験と、そのときの疑問や判断から書き始める
- **主張は一つ、具体例はそれを支えるために使う**。機能一覧・すべての例外・付随する別テーマで、本文を埋めない
- **少し強い言葉は使ってもよい**。読者が理解しやすくなる強調と、嘘・誇大広告・断定しすぎを区別する
- **固有ツール・プロジェクトは主役にしなくてもよい**。名前を知らない人にも「どんな問題があったのか」が届くタイトルや導入にする
- **体験 → 違和感 → 問い → 実例 → 変わった考え → 次の実験**の流れを候補にする。ただし、固定テンプレートにはしない
- **批判やレビューは前進のために使う**。結論の押しつけではなく、観点を変えた比較案や、読者ペルソナからの反応を使って磨く
- **正確性のための補足が、伝えたい主張を薄めていないか**も編集時に検査する。正しい追加情報であっても、本文に採用する必要はない

既存の具体的な媒体ルール・チェックリストは [content-channel-strategy.md](content-channel-strategy.md) と [note記事チェックリスト](../articles_note/checklists/note-article-quality-checklist.md) を参照し、ここには複写しない。

## 4. エージェントに求める思考と作業の進め方

以下は、上の著者の考えを**記事制作に適用するための運用案**であり、強制的な承認手順を新設するものではない。

1. **書く前に著者意図を特定する**: 誰に何を伝えたいのか、なぜその話を書きたいのか、最後に読者へ残したい1文を確認する。Article Planがあれば照合する
2. **証拠を集めるが、主題を証拠の都合で変えない**: 一次情報が足りない部分を可視化する。調査で書きやすい別論点を見つけても、著者の承認なく中心主張へ昇格しない
3. **思考と経験のつながりを描く**: 何をしたかの記録だけでなく、なぜ始めたか、何に引っかかったか、その結果何を変えたかを書く
4. **検証可能性と表現力を両立する**: 嘘は書かないが、すべてを説明する必要もない。重要な例を選び、読者に届く構成にする
5. **複数視点で読み、削る判断もする**: 技術的正確さ、初見読者の理解、著者らしい声、主題の一貫性、機密・公開境界を分けてレビューする
6. **ズレを学習可能に残す**: 著者が「これが書きたかった / 違う」と言った理由を比較する。**著者の明示的な言葉**とAIによる解釈を混ぜずに追記する

記事レビュー時は、次の3問を特に重視する。

- **これは正しいか。**（最低条件）
- **これは著者が伝えたかったことか。**（記事の中心）
- **それは読者に伝わったか。**（文章の評価）

## 5. 具体的な学習事例: PR #879

**[PR #879](https://github.com/s977043/my-blog/pull/879)** は、Claude Code版とChatGPT版を比較するために並存させている。

- Claude Code版は「AIが改善案を出し、人間が採否・置き場所を決める」という、調査で証拠が得られた実践へ重点が移った
- 著者が当初伝えたかったのは、**アジャイルで培った振り返りをAIとともに続け、開発のやり方そのものを改善する**という考え方だった
- ChatGPT版は、その背景・違和感・経験の連続性を重視した
- 著者は、前掲の「任せる→確かめる→振り返って次に試す」という3文に対し、自分の考え方に近いと明示的に支持した

**ここから残す学び**: 調査で証拠を拾える主張へ記事を最適化しすぎると、著者の意図そのものが失われる。Evidenceは主張を**支える・修正する材料**であって、無断で著者の伝えたい主題を**置き換える権限**ではない。

この事例はClaude Code版の品質を否定するものではない。具体例の豊富さ・境界の慎重さと、著者が伝えたい考えの伝達は、両方を目指す。

比較の詳細は、PR #879 の [比較ブリーフ](https://github.com/s977043/my-blog/blob/docs/proni-ai-agile-retrospective-seed-20261021/docs/article-research/2026-10-22-proni-agile-retrospective-comparison-brief.md) を参照。

## 6. この文書を成長させるルール

- 著者が明示的に考えを語ったら、**本人が明示**として日付・文脈・引用可能な言葉を追記する
- 過去記事の主張から抽出したものは **公開記事で表現** とし、対象記事へのリンクを付ける
- AIが対話を横断して推論したものは **整理仮説（著者未承認）** として区別する。本人の確定ポリシーと表記しない
- 変わった考えを無理に過去へ合わせない。**何をきっかけに変化したか**を追えるようにする
- 個人情報・機密の社内情報・未公開の会社の実態・会話原文の大量転載は載せない
- この文書の内容と特定の記事の著者判断が食い違う場合、最新の**記事ごとの明示的な著者判断**を優先する。必要ならこの文書の修正候補を出す
- **本文を公開しない**という意味ではなく、このファイルを著者の思想のメモとして運用する。公開記事に会社由来の題材を移す際の制限はAGENTS.mdに従う
