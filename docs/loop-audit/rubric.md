# ループ成熟度ルーブリック v1

**目的**: 開発フローを「AI の印象」ではなく **観測可能な条件** で採点する。
各グレードは *検証コマンドで真偽を判定できる条件* のみで定義する。採点者（人でも AI でも）
は条件を上から順に評価し、**満たせなくなった一段下** を採点結果とする。

着想元は Addy Osmani の Loop Engineering にある 5 primitives + memory/state。
本ルーブリックは、それらを A〜F の観測可能な条件へ落とし込んだ独自の評価基準である。

## 共通ルール

- 条件は「〜がある」だけで終わらせず、**外形的に成立 / 不成立を判定できる条件**で書く。実行時のガードにできるものは「失敗したときに止まる」まで定義する。
- 採点者は各条件に **検証コマンドまたは参照パス** を添える。添えられない条件は自動的に不成立とする。
- 差し戻し: 証拠を伴わない評価は無効。「たぶん動いている」は F と同じ扱い。
- **下位グレードは上位グレードの機能の不在を条件にしない。** 「〜が無い」と書くと、上位の
  機能を足した瞬間に下位の条件も不成立になり、梯子が単調でなくなる（v1 初版の実際の欠陥。
  Memory / State に異常停止ステータスを足したら A も B も不成立になった）。上位機能について
  下位グレードが言えるのは「問わない」までとする。

> **v1 の既知の穴**: E を定義しているのは Automations と Memory / State だけで、残り 4 軸
> （Sub-agents / Skills / Connectors / Isolation）は D の次が F になっている。この 4 軸で D を
> 割った対象を F まで落とすか D に留めるかは条件文が決めていない。次版で埋める。

## 評価軸（6モジュール）

### Automations — 人間の起動なしに仕事が進むか

| G | 条件 |
|---|---|
| A | 起動が自動（schedule / hook / CI 等）＋ 仕事の**発見**が自動 ＋ 実行が自動 ＋ 稼働状況が監視され異常が通知される |
| B | 起動が自動 ＋ 仕事の発見が自動 ＋ 実行が自動（稼働監視・通知は問わない） |
| C | 実行または仕事の発見は自動化されているが、起動・次テーマ決定など主要な開始判断の一部を人間が担う |
| D | 一部工程がスクリプト化。工程間の受け渡しは人間 |
| E | 検証だけ自動（CI/hook）。生成・判断は全て人間起動 |
| F | 都度プロンプトで人間が起動する。自動化された停止・進行判断が無い |

### Memory / State — 状態が会話の外にあるか

| G | 条件 |
|---|---|
| A | 台帳がリポジトリにあり、**状態遷移が定義**され、異常停止が専用ステータスで可視 ＋ 機械が読み書きする |
| B | 台帳がリポジトリにあり状態遷移が定義されている（異常停止ステータス・機械の読み書きは問わない） |
| C | 台帳はあるが自由記述で、状態が定義されていない（人が読んで解釈する） |
| D | 決定の記録はあるが、進行中タスクの状態を持たない |
| E | 断片的なメモのみ |
| F | 会話コンテキストにしか状態が無い |

### Sub-agents — 実装者と評価者が分離されているか

| G | 条件 |
|---|---|
| A | 実装者 ≠ 評価者 ＋ 評価者が**合否基準**を持つ ＋ 基準に基づき自動でエスカレーションする |
| B | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ（エスカレーションが人間判断でもよい） |
| C | 実装者 ≠ 評価者。評価は多観点だが**合格条件が「致命的なし」しか無い** |
| D | 役割定義はあるが、同一セッション/同一エージェントが実装と評価を兼ねる |
| F | 書いた者が自分の仕事を採点している |

### Skills — 手順が再利用可能な部品になっているか

| G | 条件 |
|---|---|
| A | 主要手順が Skill/Command 化 ＋ **自己テスト**を持つ ＋ 呼び出し条件が明文化 |
| B | 主要手順が Skill/Command 化され、呼び出し条件も明文化（自己テストは一部でよい） |
| C | Skill/Command 化されているが、いつ呼ぶかが人間の記憶に依存 |
| D | 手順書（散文）はあるが実行可能な部品になっていない |
| F | 毎回プロンプトを書き起こしている |

### Connectors — 外部系に機械が到達できるか

| G | 条件 |
|---|---|
| A | 公開先・計測先すべてに API 経由で到達 ＋ **公開後の反映を機械が検証**する |
| B | 主要な外部系に API/CLI で到達（反映検証は一部手動でよい） |
| C | 一部の外部系のみ機械到達。残りは管理画面での手作業 |
| D | 到達手段はあるが認証・実行が毎回手動 |
| F | すべて人間が画面を操作する |

### Isolation（Worktrees）— 並列作業が互いを壊さないか

| G | 条件 |
|---|---|
| A | 並列作業が物理分離（worktree/コンテナ）＋ 事故が**事後検知**され自動で止まる |
| B | 物理分離されている（事故の事後検知は問わない） |
| C | 物理分離は無いが、事故を検知するガードがあり作業を止められる |
| D | 規約（口頭・文書）で衝突を避けている。機械的な検知は無い |
| F | 対策なし。並列作業が同一ツリーで無防備に走る |
