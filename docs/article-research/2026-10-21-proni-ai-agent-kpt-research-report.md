# 調査レポート（公開用の要約）：AI駆動開発への振り返り導入

- 作成日: 2026-10-21
- 対応Seed: `article_seeds/ai-driven-development/2026-10-21-ai-agent-kpt-retrospective.md`
- 調査期間: 2026-08-22〜2026-10-21
- 調査方法: 読み取り専用。社内のスキル管理基盤（以下「スキル基盤」）の定義・変更履歴・作業記録を確認

> **公開境界**: 本ファイルは公開リポジトリに置くため、一般化した要約だけを記す。社内リポジトリ名・PR 番号・チケット番号・内部パス・社内指標・対話原文・人名は載せない。事例と社内記録の対応は社内側でのみ管理する。記事への使用可否は PRONI の社内レビュー・広報確認で判断する。
> **題材の範囲**: 会社の開発実践のみ。個人開発の事例は含めない。

## 1. 結論

- 振り返りの結果を、チームで共有するスキル・ルールの改訂として反映していることは、変更履歴で確認できた。
- **KPT 形式で出力するスキルはない**。KPT は振り返りを始めるきっかけの言葉として扱われている。「KPT を AI で自動化した」とは書けない。
- 記事の核にできるのは「振り返りで決めた対策が、実際に起動される場所に入っているかまで確かめる」という学び（事例1）。
- 改善後の効果は、どの事例でも未確認。

## 2. 振り返り系スキルの一覧

使い分けは、発話の語ではなく**成果物の形**で判断する。

| スキル | 役割 | 出力 | 人の判断の位置（スキル定義上） |
|---|---|---|---|
| `knowledge-capture` | 気づきをルール・設定にすぐ書き足す | ルール・設定・スキル定義への追記 | 追記内容の確認を求める |
| `engineering-process-improvement` | コード変更直後に開発フローを振り返る | 振り返りの表と改善 PR | 改善内容を合意し、承認後にマージ |
| `retrospective-improvement` | Sprint 境界のチームレトロ | Brief（論点・次の実験・継続すること） | 承認ゲートの明記なし。対策の着地先が呼ばれているかを確認 |
| `work-review` | その会話の作業のセルフレビュー | テキストの応答 | 記載なし |
| `improve-review` | 見落としたレビュー指摘をレビュー項目に足す | 追記案 | ファイル更新前に承認が必須 |
| `repeated-feedback-scan` | 複数 PR の繰り返し指摘を棚卸し（読み取りのみ） | 表 | 対象リポジトリを人が承認 |
| `agent-self-improvement` | 一定期間のログから繰り返し作業を部品化 | 候補表 | 提案と実装を分ける |
| `memory-dream` | memory の重複・矛盾・陳腐化を整理 | 差分と PR | 1 件ずつ人が確認 |

人の判断の位置は**スキル定義に書かれている内容**で、毎回その通りに運用されたかは確認していない。

## 3. 振り返りの実施状況

| 時間軸 | 判定 | 要約 |
|---|---|---|
| セッション単位 | 実施あり | セッション終了時に振り返りを依頼し、学びをルールや memory に保存した記録がある。チケット単位の振り返りからスキルを改訂した例も複数ある |
| 週次 | 部分的 | KPT 形式の週次レトロは見つからない。AI 利用状況の週次集計に、AI が「わかったこと」「次に打つ手」を下書きし人が確認する運用はある |
| 期間横断（約60日） | 単発の実施例あり | 数か月分の観測をもとに振り返りスキル自体を改訂した例、複数 PR の頻出指摘を集約した例がある。定期運用の記録はない |

## 4. 事例（候補3件）

### 事例1: 振り返りの対策が「呼ばれない場所」に入っていた（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | 振り返りで決めた再発防止策を、実際の作業で起動されないスキルに入れていた。2 か月後に同じ事故が再発した |
| 学び | 対策を「入れた」ことと「効く」ことは別（landed ≠ invoked） |
| 改善 | 振り返りスキルの改善アクションに「着地先」欄を設け、着地先の起動回数を確かめる手順を追加 |
| 人の関与 | 変更履歴によれば、起動回数の数え方がレビュー指摘を受けて 2 回修正された |
| 検証 | 改善後の再発有無は未確認 |

### 事例2: AI の改善案 3 件を人が 1 件に絞った（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | 社内プロダクトの作業の振り返りで、AI が詰まった 3 点をセルフレビュー項目の候補として提案 |
| 人の判断 | ユーザー指示で 1 件に絞り、残り 2 件は撤回（変更履歴に明記） |
| 改善 | 「動作を変えないはずのリファクタで、旧実装にない条件を足していないか」を項目化し、検知用のテストケースを追加 |
| 検証 | 実開発での効果は未確認 |

### 事例3: 繰り返すレビュー指摘をルールにした（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | コードコメントに作業経緯を書き、レビュー後に消す手戻りが繰り返されていた |
| 改善 | コード品質スキルに禁止ルールを追加 |
| 検証 | 以後、確認した範囲で同型の手戻りは見つからない。ルールの効果とは断定できない |

## 5. 傾向（確認した範囲）

- 振り返りを経由したと記録上確認できるのは事例1・2。他の改善の多くはレビュー指摘から直接スキルを変更していた（母数は未集計）。
- 振り返り系スキルの使い分けの記述が 2026-09 に繰り返し追記された。スキルが増え、どれを使うか自体が判断コストになっている兆候と読める（推測）。

## 6. 判断の3区分

**確認できた実践**
- 振り返りの結果をスキル改訂として反映している
- 振り返りスキル自体を、観測した失敗をもとに改訂している（事例1）
- AI の改善案を人が採否判断している（事例2）
- スキル定義ごとに人の判断の位置が書かれている（§2）

**著者の考察として書くこと**
- 対策は「入れた場所が実際に使われるか」まで確かめないと効かない
- 振り返りの単位によって見える問題が違う
- 振り返りの仕組みを増やすほど使い分けのコストが増える

**断定しないこと**
- KPT 形式の報告と AI との壁打ちの実録
- 週次・期間横断の振り返りの定期運用
- 改善後の再発減少や生産性向上などの定量効果
- チーム全体での運用範囲

## 7. 構成案（要旨）

1. AI 駆動開発は段階的に進めるプチウォーターフォールに見える
2. それでもアジャイルの「小さく分けて、確かめて、直す」を使っている
3. 振り返りを取り入れた：成果物の形で振り分けるスキル群と、人の判断の位置
4. セッションの詰まりをスキル改訂にする（事例2）・繰り返す指摘をルールにする（事例3）
5. 振り返りを振り返る：対策が効かなかった理由（事例1）
6. 増やしすぎた振り返り（使い分けのコスト）
7. まだ分からないこと（効果測定）
