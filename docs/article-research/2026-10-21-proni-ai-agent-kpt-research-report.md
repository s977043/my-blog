# 調査レポート（公開用の要約）：AI駆動開発への振り返り導入

- 作成日: 2026-10-21
- 対応Seed: `article_seeds/ai-driven-development/2026-10-21-ai-agent-kpt-retrospective.md`
- 調査期間: 2026-08-22〜2026-10-21
- 調査方法: 読み取り専用。社内のスキル管理基盤（以下「スキル基盤」）の定義・変更履歴・作業記録を確認

> **公開境界**: 本ファイルは公開リポジトリに置くため、一般化した要約だけを記す。社内リポジトリ名・PR 番号・チケット番号・内部パス・社内指標・対話原文・人名は載せない。事例と社内記録の対応は社内側でのみ管理する。記事への使用可否は PRONI の社内レビュー・広報確認で判断する。
> **題材の範囲**: 会社の開発実践のみ。個人開発の事例は含めない。

## 1. 結論

- 振り返りの結果を、チームで共有するスキル・ルールの改訂として反映していることは、変更履歴で確認できた。
- **KPT 形式で出力するスキルも、KPT 形式の記録もない**（期間内の PR 全件と会社リポジトリの memory を確認）。YWT 形式の月次ふりかえりが 1 件ある。「KPT を AI で自動化した」とは書けない。
- 実際の振り返りは「何が起きたか → AI が対策案を出す → 人が採用・見送り・取り下げを決める → スキルやルールに 1 件ずつ入れる」という形。期間内に、振り返りを起点にした変更が十数件ある。
- **中心メッセージ（2026-10-21 著者決定）**: AI が案を出し、人が採否を決める振り返り。対策を入れた後、その場所が実際に使われているかまで確かめる（事例1）。
- 改善後の効果を測った記録は、事例1 の起動回数の確認だけ。再発が減ったかは未確認。

## 2. 振り返り系スキルの一覧

使い分けは、発話の語ではなく**成果物の形**で判断する。

| スキル | 役割 | 出力 | 人の判断の位置（スキル定義上） |
|---|---|---|---|
| `knowledge-capture` | 気づきをルール・設定にすぐ書き足す | ルール・設定・スキル定義への追記 | 追記内容の確認を求める |
| `engineering-process-improvement` | コード変更直後に開発フローを振り返る | 振り返りの表と改善 PR | 改善内容を合意し、承認後にマージ |
| `retrospective-improvement` | Sprint 境界のチームレトロ | Brief（論点・次の実験・継続すること） | 承認ゲートの明記なし。対策の着地先が呼ばれているかを確認 |
| `work-review` | その会話の作業のセルフレビュー | テキストの応答 | 記載なし |
| `improve-review` | 見落としたレビュー指摘をレビュー項目に足す | 追記案 | ファイル更新前に承認が必須 |
| `repeated-feedback-scan` | 複数 PR の繰り返し指摘を棚卸し（読み取りのみ） | 表 | 対象リポジトリを人が承認 |
| `agent-self-improvement` | 一定期間のログから繰り返し作業を部品化 | 候補表 | 提案と実装を分ける |
| `memory-dream` | memory の重複・矛盾・陳腐化を整理 | 差分と PR | 1 件ずつ人が確認 |

人の判断の位置は**スキル定義に書かれている内容**で、毎回その通りに運用されたかは確認していない。

## 3. 振り返りの実施状況

| 時間軸 | 判定 | 要約 |
|---|---|---|
| セッション単位 | 実施あり | ある社内プロダクトの開発で、約 1 か月に振り返り系スキルを約 40 回起動。結果の大半は memory、一部がスキルやリポジトリの変更 PR |
| 週次 | 実施あり（2026-10 から週 1 回） | 直近 30 日のセッションから繰り返し作業を探し、スキル化・自動化の候補を出すスキルを週 1 回実行（9 月までは不定期）。候補から新しいスキルが作られた例がある。結果はファイルに残らず、PR 本文に根拠として転記される |
| 期間横断（約60日） | 定期運用なし | 週次の振り返りの対象は直近 30 日。60 日の集計は利用統計の側の設定 |

### 対策を入れた場所と再発（ある社内プロダクト、2026-09〜10、観察の範囲）

| 対策の置き場所 | その後 |
|---|---|
| memory への記録だけ | 同種の問題が再発した例が複数ある |
| hook・設定の変更 PR | 以後の再発は見つかっていない（継続観察はしていない） |
| memory（人への確認手順） | 次の類似場面で手順どおり人に確認できた例が 2 件（観察のみ） |

母数が少なく効果測定でもないため、傾向として扱う。

## 4. 事例（候補4件）

### 事例1: 振り返りの対策が「呼ばれない場所」に入っていた（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | 振り返りで決めた再発防止策を、実際の作業で起動されないスキルに入れていた。2 か月後に同じ事故が再発した |
| 学び | 対策を「入れた」ことと「効く」ことは別（landed ≠ invoked） |
| 改善 | 振り返りスキルの改善アクションに「着地先」欄を設け、着地先の起動回数を確かめる手順を追加 |
| 人の関与 | 変更履歴によれば、起動回数の数え方がレビュー指摘を受けて 2 回修正された |
| 検証 | 改善後の再発有無は未確認 |

### 事例2: AI の改善案 3 件を人が 1 件に絞った（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | 社内プロダクトの作業の振り返りで、AI が詰まった 3 点をセルフレビュー項目の候補として提案 |
| 人の判断 | ユーザー指示で 1 件に絞り、残り 2 件は撤回（変更履歴に明記） |
| 改善 | 「動作を変えないはずのリファクタで、旧実装にない条件を足していないか」を項目化し、検知用のテストケースを追加 |
| 検証 | 実開発での効果は未確認 |

### 事例3: 繰り返すレビュー指摘をルールにした（2026-09）

| 項目 | 内容 |
|---|---|
| 出来事 | コードコメントに作業経緯を書き、レビュー後に消す手戻りが繰り返されていた |
| 改善 | コード品質スキルに禁止ルールを追加 |
| 検証 | 以後、確認した範囲で同型の手戻りは見つからない。ルールの効果とは断定できない |

### 事例4: PR のレビュー指摘から共有スキルへ（2026-10）

| 項目 | 内容 |
|---|---|
| 出来事 | 社内プロダクトの PR で受けた（またはレビューで出した）指摘を、PR を振り返るスキルにかけた。期間中の実質 3 回とも、AI が見落としの原因を分析し、追記案を 3 件ずつ出した |
| 人の判断 | 1 回目は 3 件すべて採用。2 回目は AI 案とは別の置き場所を人が選んだが、作業が中断して反映されなかった。3 回目は AI が自分の案を見直した後、人が承認した |
| 改善 | 1 回目と 3 回目は共有スキルへの PR になり、チームの同僚 1 名のレビューを経てマージされた |
| 検証 | マージから約 1 週間で、再発の有無は判断できない |

PR 指摘 → 振り返り → 人の採否 → チームレビュー → 共有スキルへの反映、までが記録で追える。複数 PR の繰り返し指摘を集めるスキルも用意されているが、実運用での実行はまだない。

### 追加の場面（採否の判断、2026-10-21 原本照合済み）

| 場面 | 判断 |
|---|---|
| 対策の自動化 | 委託手順の文面は CI や hook で検知できないため、自動チェックにせず手順に 2 行足すだけにした |
| 承認ゲート | 一度入れた承認ゲートを取り下げた。承認の要否は実行環境の設定が決めることで、配布するスキルの役割ではないため（判断者は記録になし） |
| 改善案の見送り | 振り返りの改善案のうち 1 件だけ実装し、1 件はユーザー判断で、再発したら再提案する扱いで見送った |
| 機械検知の見送り | 別の振り返りで、既存の違反が数百件あるため静的解析による検知を見送り、ルール案も取り下げた |
| 残さない | 既知の問題 3 件を「認識するだけでチケットにしない」と決めた |
| 週次の候補から新スキル | 週次の振り返りで多数のセッションに繰り返し出ていた依頼を検出し、人が「PR にする」と判断して新しいスキルを作った |
| 月次ふりかえり（YWT） | AI の下書きを人が 3 点直した（担当範囲の取り違え、成果だけの記述、学びの粒度）。その後、同種の誤りを防ぐルールを作った |

事例1 の補足: 確度の高い対策を選んだのは AI 側の分類で、人の判断はその後のレビューで入った。

## 5. 傾向（確認した範囲）

- 振り返りを経由したと記録上確認できるのは事例1・2。他の改善の多くはレビュー指摘から直接スキルを変更していた（母数は未集計）。
- 振り返り系スキルの使い分けの記述が 2026-09 に繰り返し追記された。スキルが増え、どれを使うか自体が判断コストになっている兆候と読める（推測）。

## 6. 判断の3区分

**確認できた実践**
- 振り返りの結果をスキル改訂として反映している
- 振り返りスキル自体を、観測した失敗をもとに改訂している（事例1）
- AI の改善案を人が採用・見送り・取り下げしている（事例2、§4 追加の場面）
- スキル定義ごとに人の判断の位置が書かれている（§2）

**著者の考察として書くこと**
- 対策は「入れた場所が実際に使われるか」まで確かめないと効かない
- 振り返りの単位によって見える問題が違う
- 振り返りの仕組みを増やすほど使い分けのコストが増える

**断定しないこと**
- KPT 形式の報告と AI との壁打ちの実録
- 60 日単位の振り返りの定期運用（週次は 2026-10 から確認できた）
- 改善後の再発減少や生産性向上などの定量効果
- チーム全体での運用範囲

## 7. 構成案（要旨）

1. AI 駆動開発は段階的に進めるプチウォーターフォールに見える
2. それでもアジャイルの「小さく分けて、確かめて、直す」を使っている
3. 振り返りを取り入れた：AI が案を出し、人が採否を決める
4. 採用・見送り・取り下げの実例（事例2・3、§4 追加の場面）
5. 振り返りを振り返る：入れた対策が使われていなかった（事例1）
6. 仕組みを増やさない判断（自動化しない・ゲートを外す・使い分けのコスト）
7. まだ分からないこと（効果測定）
