## 3. 振り返りの実施状況

| 時間軸 | 判定 | 根拠の要約 |
|---|---|---|
| セッション単位 | **実施済み** | セッションやチケットの振り返りを起点にスキルを改訂した commit が複数ある（GTA #445, #473, #484 ほか）。セッション記録では「振り返り実施して」から振り返り系スキルが起動し、AI が知見と追記先の案を出して人間が反映範囲を選ぶ流れを確認した（下記 3.1）。KPT の見出しで報告した例は少ない |
| 週次 | **部分的** | KPT 形式の週次レトロは見つかっていない。GTA では AI 利用状況の週次集計（10/06・10/13・10/21）に「わかったこと」「次に打つ手」を AI が下書きし、人間が確認する運用がある（下記 3.2） |
| 約60日 | **部分的** | 「2026-06〜08 の観測」を根拠に振り返りスキル自体を改訂した例（GTA #440）、複数PRの頻出指摘を集約した例（GTA #456）、横断棚卸しスキルの新設（GTA #479）がある。定期実施かは未確認、#479 の実行記録は未確認 |

### 3.1 セッション単位の実例（GTA のセッション記録、2026-10-14）

- 人間が「振り返り実施して」と依頼すると、AI は `knowledge-capture` を起動した。得られた知見を 2 点に整理し、うち 1 点は既存ルールで足りるので新たに残さないと判断した。残る 1 点について、追記先を「推奨」と「任意」に分けて提示し、承認を求めた。
- 人間は「個人の改善に留める」と答え、リポジトリ共有のルールではなく個人設定にだけ反映させた。
- 示唆: AI は「何を学んだか」と「どこに書くか」まで提案し、**共有範囲（チームのルールにするか個人に留めるか）を人間が決める**。対話の原文は社内記録のため転載しない。

### 3.2 週次の実例（GTA のセッション記録、2026-10-21）

- 各メンバーの利用統計の提出を集約し、週次の集計を社内ドキュメントに追記している（10/06・10/13・10/21 の 3 回分）。
- AI は数値差分から「わかったこと」を下書きし、原因は断定せずに確認項目として「次に打つ手」に入れた。ページには「内容を確認のうえ修正してください」と明記している。
- KPT ではなく利用状況の振り返り。集計値・個人別の値は社内情報のため掲載しない。

## 4. 記事に使える事例（候補3件）

### 事例1: 振り返りの Try が「呼ばれない場所」に入っていた（GTA #440, 2026-09-08）

| 項目 | 内容 |
|---|---|
| 発生した出来事 | 振り返りで決めた再発防止策を、実際の作業で起動されないスキルに入れていた。そのため 2 か月後に同じ事故（PR の起点ブランチ誤り）が再発した。別の対策も、実際の作業経路とは別のスキルに入っていた |
| Problem | 対策を「入れた」ことと「効く」ことが別だった（landed ≠ invoked） |
| Try / 実際の改善 | 振り返りスキルの改善アクションに「着地先（`Lands in:`）」欄を設け、着地先が実行経路上にあるか起動回数で確かめる手順を追加 |
| 人間の関与 | 起動回数の計測方法が PR レビューで 2 回直された（自己一致による過大計上、別経路の起動の取りこぼし） |
| 検証結果 | 改善後に同型事故が再発したかは**未確認** |
| 採用理由 | 「振り返りそのものを振り返った」事例で、記事の中心主張に直結する |

### 事例2: AI の提案3件を人間が1件に絞った（GTA #473, 2026-09-15）

| 項目 | 内容 |
|---|---|
| 発生した出来事 | 社内プロダクトの作業を振り返り、AI が詰まった3点を self-review の追加項目として提案 |
| Problem（採用分） | 「動作を変えないリファクタ」で旧実装にない条件を追加し、既存テストで発覚した |
| 人間の判断 | ユーザー指示で 3 件から 1 件に絞り、残り 2 件は撤回 |
| 実際の改善 | self-review のチェック項目 1 件と、検知を裏付ける canary fixture を追加 |
| 検証結果 | リポジトリ検証スクリプトの通過のみ。実開発での効果は**未確認** |
| 採用理由 | AI の提案と人間の採否判断が commit 上で分かれて記録されている |

### 事例3: 繰り返すレビュー指摘をルール化した（GTA #474, 2026-09-15）

| 項目 | 内容 |
|---|---|
| 発生した出来事 | コードコメントにチケット番号や日付を書き、レビュー後に消す手戻りが繰り返されていた |
| 実際の改善 | clean-code スキルに禁止ルールを追加 |
| 検証結果 | 改善後、同型の削除 commit は調査期間内で見つからない。ただしルールの効果とは**断定できない** |
| 採用理由 | 「同じ指摘の繰り返し」を減らす分かりやすい例 |

## 5. PR指摘→改善の追跡で分かったこと

- 振り返りの Try を経由したと記録上確認できるのは事例1・2のみ。他の多くは、レビュー指摘から直接スキルを変更している。
- 指摘カテゴリでは「既存設計との不整合」「テスト不足」「同一指摘の反復」「スキル指示不足」が多い。「受け入れ条件の確認不足」は記録が見つからない。件数は commit 本文に基づく下限値。
- スキル間の「使い分け」記述の追記が 2026-09 に続いている（#447, #454, #479 ほか）。振り返り系スキルが増え、どれを使うか自体が判断コストになっている兆候と読める（推測）。

## 6. 判断の3区分

**確認できた実践**
- 振り返りの結果を、GTA のスキル改訂として PR 単位で反映している
- 振り返りスキル自体を、観測した失敗をもとに改訂している（事例1）
- AI が出した改善案を、人間が採否判断して絞っている（事例2）
- AI が知見と反映先を提案し、共有範囲を人間が決めている（3.1）

**著者の考察として書くのが適切なこと**
- 改善策は「入れた場所が実際に使われるか」まで確かめないと効かない
- 振り返りの単位によって見える問題が違う（セッション＝直近の詰まり、期間横断＝対策が効いていない構造）
- 振り返りの仕組みを増やすほど使い分けのコストが増える

**まだ確認できないこと（記事で断定しない）**
- KPT 形式での報告と、AI との壁打ち対話の実録
- KPT 形式の週次振り返りの実施（利用状況の週次集計は確認済み）
- 改善後の再発減少や生産性向上などの定量効果
- 60日単位の振り返りが定期運用されていること

## 7. 記事構成への提案（要旨）

1. プチウォーターフォールに見える流れ（要件→計画→実装→レビューをスキルで段階化）
2. それでもアジャイルの「小さく分けて、確かめて、直す」を使っている
3. 振り返りを取り入れた：セッションの詰まりをスキル改訂にする（事例2）
4. 繰り返しを減らす：同じレビュー指摘をルールにする（事例3）
5. 振り返りを振り返る：Try が効かなかった理由（事例1）
6. 人間が決めること：採否・優先度・ルールの撤去
7. まだ分からないこと（効果測定）を正直に書く

## 8. 著者への確認事項（優先度順）

1. KPT 形式で AI と壁打ちした実際のセッションはどれか（記録の場所）。公開できる範囲
2. 週次の振り返りは実施しているか、それとも構想か
3. 事例1〜3 を会社公式記事で扱ってよいか（社内事情の記述範囲）
4. 「60日の振り返り」は事例1の観測（2026-06〜08）を指すか、別に定期実施があるか
5. 事例2で 3 件を 1 件に絞った判断理由
