| 役割 | 所見 |

### H1 著者の判断基準（2026-10-21 著者回答）

学びが**誰に効くか**で残す先を決める。

| 学びの範囲 | 残す先 |
|---|---|
| 自分にだけ必要 | 個人の memory |
| チームやリポジトリの改善に役立つ | commit（スキル・ルール・docs） |
| そのセッションだけの特殊ケース、特定の条件でだけ起きること | どこにも残さない |

編集部メモ: 採否は「採用か見送りか」の二択ではなく、残す範囲の三択になっている。「残さない」を明示的な選択肢にしている点が、ルールが膨らまない理由として書ける。事例1（入れた場所が使われていない）とも「どこに入れるか」でつながる。事例との対応（各場面がどの段に当たるか）は記事化の前に確認する。

### H6 判断の主体（2026-10-21 著者回答）

- 振り返りの結果として社内のスキル管理基盤へ新しくスキルを登録する場合は、チームメンバーがレビューに入る。チームとしての判断になる。
- 既存スキルの修正もチームのレビューを通る。スキル管理基盤はチームで管理し、全員が使うスキルなので、勝手に変わるのを避けるため（著者回答）。
- 編集部メモ: 主語は段で分ける。メモリーに残す・残さないは著者個人の判断、共有スキルの新規登録・修正はチームの判断。「みんなが使うものを勝手に変えない」は、人が判断する理由として記事に書ける。

### 新テーマの Issue

1. **当たり前に見える**: 見出しと冒頭は「見送った」「外した」場面から入る
2. **KPT の扱い**: 導入で「KPT のつもりで始めたが、形式より採否の判断が残った」と触れるかどうか
3. **主語**: 判断者が著者本人のみなら「チームで」とは書かない
4. **アジャイルとの接続が薄くなる**: H5 で補う
5. **効果が言えない**: 「まだ分からないこと」の節を残す
6. **差別化**: 自律的に自己改善するエージェントの記事が多いなか、人のゲートを置く理由を書く（§6）

## 4. Issue（執筆前に解消すべき論点）

1. **タイトルと主張**: KPT を外すか、導入の「考え方の出発点」に留めるか（G1）
2. **主語**: 「私たち」がどこまでを指すか（著者／利用チーム／全社）。広報確認
3. **効果を断定しない書き方**: 定量効果がないまま書くなら「確認中」の節を設ける
4. **匿名化の程度**: 社内固有名を伏せた後も事例として成立するか
5. **スキル紹介の分量**: 8 本の一覧は表 1 枚に留める（機能紹介記事にしない）
6. **社内レギュレーション**: エンジニアレビュー 2 名 → 執筆ガイドライン → 広報事前確認 → カバー画像。提出日の確定
