# PRONI 振り返り記事 2稿の比較レビューと、記事制作の改善案（Claude Code）

- 作成: 2026-10-22
- 対象: PR #879 の Claude Code 版・ChatGPT 版、比較ブリーフ、PR #885 の著者コンパス
- 状態: レビュー記録。原稿は変更していない。正本の決定・Plan の更新・ルール変更は著者判断待ち

## 1. 結論

- 著者が支持した 3 文（任せる・確かめる・振り返って次で試す）に近いのは **ChatGPT 版**。Claude Code 版は、3 文のうち「振り返りの採否」の一部分を記事の中心にしていた
- ズレの原因は Claude Code 側の工程にある。KPT の記録が見つからなかったとき、**KPT という「型」だけでなく、「アジャイルの経験を AI 開発に持ち込む」という主題まで差し替えた**
- 両稿の長所を合わせた第三稿を [別ファイル](2026-10-22-proni-agile-retrospective-third-draft.md) に作った。ChatGPT 版の背骨に、Claude Code 版の実例と限界の記述を入れている

## 2. 各稿の中心主張（一文）

| 稿 | 中心主張 | 3 文との距離 |
|---|---|---|
| Claude Code 版 | AI の改善案を、人が「誰に効く学びか」で残す先を決めることで、振り返りを続けられる | 「振り返る」の一部（採否）に限られる。「任せる」「確かめる」はほぼ無い。アジャイルは導入と結びだけ |
| ChatGPT 版 | アジャイルで培った振り返りを AI との開発に持ち込み、進め方そのものを改善し続ける | 近い。3 文がそのまま結びに入り、プチウォーターフォールとの両立が背骨になっている |
| 第三稿 | 3 文をそのまま中心に置き、各章を「任せる → 確かめる → 振り返る → 次で試す」で並べる | 3 文に合わせて作った。一次情報は Claude Code 版の範囲を超えない |

## 3. 4 つの観点での比較

### 主張のズレ

- Claude Code 版: タイトル「AI が案を出し、人が決める」が、3 文の三つ目の一部分を全体の主題にしている。読後に残るのは「採否と置き場所の判断」で、著者が伝えたかった「アジャイルの経験の連続性」は弱い
- ChatGPT 版: 主題は著者の意図どおり。「確かめる」の章（計画・PR・テスト）はやや短い

### 一次情報

| 箇所 | Claude Code 版 | ChatGPT 版 |
|---|---|---|
| 実例の量 | 採否の実例 5 件・失敗 1 件・傾向 1 件。すべて調査レポートで照合済み | 3 案→1 案、PR 指摘→共有スキル、対策が使われなかった失敗。照合済みの範囲内 |
| 照合が要る記述 | なし | 「以前は 60 日という期間でも考えていました」（著者の発言としては一致。記事に書くかは著者判断）／「すべての問題を次のスプリントのアクションにするわけではなかった」（チームのアジャイル実践の記録は未調査。著者の体験として書くなら著者確認） |
| 抜けている事実 | 「確かめる」の実例 | memory だけの対策は再発し、hook・設定の変更後は未観察という傾向。セッション約 40 回などの規模 |
| 壁打ちの扱い | 書いていない | 問いの例を挙げ、「特定の会話の再現ではない」と明記。創作を避けた良い書き方 |

### 読者への伝わり方

- Claude Code 版: 実例が「採用・見送り・取り下げ」の見出しで 5 件並び、事例集に読める。著者コンパスの「機能一覧・事例の羅列にしない」に当たる
- ChatGPT 版: 体験 → 違和感 → 問い → 実例 → 変わった考え、の流れで読める。「Try を決めることと、Try が仕事を変えることは違う」は記事で最も強い一文
- ChatGPT 版に足りないもの: 冒頭の `> 区分:` 行と自己紹介（PRONI 原稿の書式）。採否の判断基準（3 択）が文章に埋もれ、読者が持ち帰りにくい

### 公開リスク

- 両稿とも社内リポジトリ名・PR 番号・数値は出していない
- ChatGPT 版のファイル冒頭にある「編集用の別案」の注記は、公開時に外す必要がある（比較資料としては適切）
- 「私たち」の範囲（著者本人か、チームか）は両稿とも未確定。判断の主体は「memory は著者個人、共有スキルはチームのレビュー」と分かれている

## 4. ズレが生まれた理由（Claude Code の工程）

時系列で見ると、主題が置き換わった地点は 3 つあった。

1. **調査結果が出た時点**: 「KPT 形式の記録が 0 件」を受けて、中心メッセージの変更を提案した。このとき選択肢を「KPT のまま」か「証拠が多い採否の話へ変える」かの二択で示した。「主題（アジャイルの振り返りを AI 開発へ）は保ち、KPT という型の記述だけを外す」という選択肢を出していなかった
2. **編集部ペルソナの検討**: 「『人が決める』だけでは当たり前に読まれる。判断基準を芯にする」という所見を採り、芯がさらに採否へ寄った。ペルソナは記事の面白さを評価したが、著者の意図との距離は評価していなかった
3. **Article Plan の作成**: `central_claim` を調査で裏付けられた主張から書いた。著者の最初の言葉（Seed の「中心に置きたい主張」）と照らし合わせなかった。Seed には「AI と開発の過程を振り返り、開発方法・スキル・ワークフローまで継続的に改善する」と書かれていた

共通する原因は、**一次情報の確認を、主張を「支える・弱める」材料ではなく、主張を「選ぶ」基準として使ったこと**。著者が「変更して OK」と答えたのは提示した二択の範囲であり、主題全体の変更を承認したものではなかった。

## 5. 改善方針（第三稿で行ったこと）

| 採用元 | 採用したもの |
|---|---|
| 3 文 | 冒頭で提示し、章立てを「任せる・確かめる → 振り返る → 次で試す」に合わせた |
| ChatGPT 版 | プチウォーターフォールとの両立、コードと進め方の確認の区別、壁打ちの問い（創作しない書き方）、「Try を決めることと仕事が変わることは違う」、結びの一文 |
| Claude Code 版 | 判断基準の 3 択の表、チームレビューの理由、増やさない判断の 3 例、memory と hook の傾向、まだ分からないこと 2 点 |
| 削ったもの | 採否の実例の見出し 5 件の並び（本文に溶かした）。「KPT のつもりで始めて残ったのは採否だった」という章（主題を採否に寄せるため） |
