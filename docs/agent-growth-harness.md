# エージェント成長ハーネス設計書

> 運用文書。my-blog 発のテーマなので記事の題材にしない（`AGENTS.md` §題材の出どころ）。実装は含まない。

## 結論

- ループの「検知 → 記録 → 規律化 → 機械化」までは揃っているが、**「どの学びを機械化したか」と「再発したか」を結ぶ台帳が無い**。そのため効果確認と昇格判断が毎回人の振り返り（#763 など）頼みになっている。
- 最初の 1 手は **`AGENT_LEARNINGS.md` のエントリ単位の昇格状態を数える読み取り専用レポート（`report:learnings-promotion`）** を足すこと。既存ファイルを書き換えず、削除すれば元に戻る。
- 自動で回すのは「検出・集計・提案 PR の下書き」まで。規約変更（`.claude/`・`AGENTS.md`）、マージ、公開は人の承認に残す。

### 切れ目の上位 3 つ

1. **効果確認の欠落**: 機械化後に同テーマのエントリが再度追加されたかを見る仕組みが無い。gh account 系はガード追加（#294 → #317 → #689）後も学びが増え続けた。
2. **昇格状態が不可視**: 109 エントリのうち機械ガードに言及するのは 18 件。残りが「文書で十分」なのか「未対応」なのか区別できない。
3. **振り返りの起動が人依存**: 振り返り PR は人の指示でしか始まらない（rubric の Automations 評価も C、`docs/loop-audit/result-after.md`）。

## 4. 安全策（自己改変の上限）

| 項目             | 上限・規則                                                                                                                                          |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 変更してよい種類 | `AGENT_LEARNINGS.md` への追記、`scripts/` への新規の読み取り専用レポート・check の追加、`docs/` の運用文書。既存 check の判定を**緩める**変更は不可 |
| 承認必須         | `.claude/` 配下、`AGENTS.md`・`CLAUDE.md` の規約本文、`npm run check` 集約への組み込み、CI の必須化、hook のブロック条件                            |
| 1 回あたりの件数 | 1 PR につき新規ガード 1 本、学びの追記は 5 件まで。超える場合は PR を分ける                                                                         |
| 導入段階         | 新規ガードはまず WARN（exit 0）で 2 週間運用し、誤検知 0 を確認してから人の承認で exit 1 化                                                         |
| ロールバック     | 1 ガード = 1 squash commit にして `git revert` 1 回で戻せる形にする。バイパス環境変数（既存の `SKIP_*` 方式）を必ず持たせる                         |
| 暴走検知         | 1 セッションで自己改善 PR が 3 本を超えたら止めて人に報告する                                                                                       |

## 5. 最初の 1 手

### 候補比較

| 候補                                                             | 効果                                         | 元に戻しやすさ               | 実装コスト                                             | 判断               |
| ---------------------------------------------------------------- | -------------------------------------------- | ---------------------------- | ------------------------------------------------------ | ------------------ |
| A. 昇格状態レポート `report:learnings-promotion`（読み取り専用） | 切れ目 1・2 を同時に可視化。以後の判断の土台 | 新規ファイル削除で完全に戻る | 小（Node 1 本 + self-test）                            | **採用**           |
| B. エントリテンプレートに状態タグ追加                            | 将来の精度は上がる                           | 既存エントリと不揃いになる   | 小だが `AGENT_LEARNINGS.md` 冒頭の規約変更で承認が要る | A の結果を見てから |
| C. hook 発火ログ                                                 | 「止めた回数」が取れる                       | 戻せるが hook 改修を伴う     | 中、`.claude/settings.json` 周辺に触れる               | 後回し             |

A を選んだ理由: 規約ファイルに触れず、既存データだけで現状の数値（§3）を毎回再現できる。B・C の要否も A の出力で判断できる。

### 変更するファイル

- 新規 `scripts/report-learnings-promotion.js`: `AGENT_LEARNINGS.md` をエントリ単位に分割し、エントリ総数・機械ガード言及数・再発言及数・テーマ別件数（キーワード辞書はスクリプト内）を表示。`--json` 出力と `--self-test` を持つ。常に exit 0
- `package.json`: `report:learnings-promotion` と `test:learnings-promotion` を追加
- `.github/workflows/ci.yml`: `test:learnings-promotion` を self-test 列に 1 行追加（`npm run check` には入れない。`check:due` と同じ理由で、集計は不備ではないため）

### 手順

1. `git switch -c feat/learnings-promotion-report origin/main`
2. スクリプトと self-test（固定のサンプル Markdown で件数が一致すること）を書く
3. `npm run test:learnings-promotion` と `npm run report:learnings-promotion` を実行
4. PR 作成まで。マージは人

### 検証方法

- [ ] `report` の出力が §3 の値（109 / 18 / 8）と一致する
- [ ] self-test が CI で通る
- [ ] `AGENT_LEARNINGS.md` を一切変更しない（`git diff --stat` で確認）
- [ ] スクリプトを削除し package.json の 2 行を戻すだけで元の状態になる
