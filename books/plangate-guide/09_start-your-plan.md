第 3 章から第 7 章で見た欄を、1 枚の骨組みにまとめました。本章では、この骨組みを自分のタスクで埋めるところまでを扱います。

## 自分の計画に貼れる骨組み

Issue や PR のテンプレート、AI への指示書にそのまま貼って、空欄を埋めて使えます。欄の末尾の（人）は人が書く欄で、第 3 章の入力（PBI INPUT）にあたります。（AI）は AI が作って人が確かめる欄です。

```markdown:plan-template.md
- Why（解決したい課題）（人）:
- やること・やらないこと（触らないファイル、追加しない依存も）（人）:
- 受入基準（人）: AC-1 … / AC-2 …
- リスク・不明点・前提（分かっている範囲）（人）:
- 完了の境界（完了の定義）（AI）:
- Mode（数えた根拠つき）（AI）:
- 変更するファイル（AI）:
- 作業の分解（AI）:

| 前提（AI が確かめる） | 確かめ方 | 実測結果 | 判定（支持 / 崩れた） |
|---|---|---|---|
|  |  |  |  |

- 不明点（確かめても残ったもの）（AI）:

| 設計案（A はいちばん単純な案）（AI） | 複雑さ | 利点と欠点 | 判定 |
|---|---|---|---|
| A: |  |  |  |
| B: |  |  |  |

- 最小で足りる理由と、今は作らない拡張（AI）:
- リスクと対策（AI）:

| 受入基準（AI） | テストケース | 入力 | 期待値 | 期待値の出どころ（実測 / 規約 / 既存の実装） |
|---|---|---|---|---|
| AC-1 | TC-01 |  |  |  |

- 人が承認する範囲（AI）:
- 止まる条件（計画を立て直す / 人の判断を待つ）（AI）:
```

人が書くリスク・不明点・前提は、分かっている範囲でかまいません。AI はそれを出発点に前提を確かめ、確かめても残ったものだけを不明点として書きます（第 5 章）。作業の分解は独立して確かめられる単位にし、先頭には実装しないと分からない確認だけを置きます。

## 小さなタスクで埋めてみる

既存の注文一覧 API に status の絞り込みを 1 つ足す、という筆者の作例です。

```markdown
- Why（人）: 問い合わせ対応で未発送の注文を探すのに、一覧を全件めくっている
- やること・やらないこと（人）: status での絞り込みを 1 つ足す。複数 status の同時指定、画面の変更はやらない
- 受入基準（人）: AC-1 `?status=pending` で pending の注文だけを返す / AC-2 未定義の status は 400 を返す
- リスク・不明点・前提（人）: orders に status 列があるはず。今の呼び出し元が status を付けて呼んでいるかは分からない
- 完了の境界（完了の定義）（AI）: TC-01・TC-02 と既存テストが通れば完了。画面の絞り込み UI は別 PBI
- Mode（AI）: standard（ファイル 2 件・AC 2 件の数では light。ただし API に新しい応答（400）を足す機能追加で、変更の種類では standard にあたるため、こちらを採る）
- 変更するファイル（AI）: 注文一覧のハンドラ、その結合テスト
- 作業の分解（AI）: 1. TC-01・TC-02 を失敗するテストとして書く 2. 絞り込みと 400 の分岐を足す 3. 既存テストと合わせて通す（実装しないと分からない確認はないので、確認のステップは置かない）

| 前提 | 確かめ方 | 実測結果 | 判定 |
|---|---|---|---|
| orders に status 列がある | スキーマ定義を読む | status 列あり | 支持 |
| 今の呼び出し元は status を付けていない | 呼び出し元のコードを検索する | 付けている箇所なし | 支持 |

- 不明点（AI）: なし（前提は承認の前に確かめた）
- 設計案（AI）: 案は 1 つ（既存のクエリに条件を 1 つ足す）。絞り込み用の部品を新しく作る案も考えたが、今の受入基準に必要な理由がない
- 今は作らない拡張（AI）: 複数 status の指定。受入基準にないため
- リスクと対策（AI）: 400 の分岐が、status を付けない呼び出しまで弾いてしまう → status なしの既存テストが通り続けることで確かめる

| 受入基準 | テストケース | 入力 | 期待値 | 期待値の出どころ |
|---|---|---|---|---|
| AC-1 | TC-01 | `?status=pending` | pending の注文だけ | 既存の実装 |
| AC-2 | TC-02 | `?status=foo` | 400 と、ほかの API と同じ形のエラー | 既存の実装 |

- 人が承認する範囲（AI）: なし（第 6 章の範囲に触れない。既存の呼び出しの結果は変わらない追加のみ）。計画そのものの承認は別に行う
- 止まる条件（AI）: 計画を立て直す: 既存テストが変更前から失敗していたら。人の判断を待つ: status を付けて呼んでいる既存の呼び出し元が見つかったら（400 を返すと、その呼び出しの結果が変わるため）
```

400 を返すのは status を付けた呼び出しだけです。今の呼び出し元が status を付けていないことを前提の表で確かめているので、「既存の呼び出しの結果は変わらない」と書けます。

設計案が 1 つしか思いつかないときは、表を無理に埋めず、考えたほかの案と採らなかった理由を 1 行で書きます。該当するものがない欄も空欄にせず、「なし（理由）」と書きます。

## 計画を読むときのチェックリスト

レビューでは、骨組みの欄が埋まっているかに加えて、次の点を見ます。

- [ ] 変更するファイル、関数、コマンドは実在するか
- [ ] 実測結果の欄が、予想ではなく確かめた事実で埋まっているか
- [ ] 件数が関わる作業で、実数を数えているか
- [ ] 「適切に」「必要に応じて」のような言葉が残っていないか
- [ ] Mode は、変更の規模とリスクに見合っているか

計画がきれいに書けているかではなく、計画が正しいかを見るのがレビューの役目です。

## ひとりで使う場合

個人開発のように、計画を書くのも承認するのも自分、という場面もあります。このときは骨組みを全部埋めようとせず、次の 4 つだけを使う最小構成から始めるのがおすすめです。

- **前提の表**: AI が置いた前提と、確かめた結果
- **件数を数える**: 変更するファイルや対象の数を、見積もりではなく実数で書く（第 5 章）
- **止まる条件**: どうなったら手を止めて計画に戻るか
- **やらないこと**: 今回は触らないファイル、足さない機能

ひとりで使うときに難しいのは承認です。書いた本人がすぐに読むと、書いたときの思い込みのまま読んでしまい、前提の抜けに気づきにくくなります。別の人に読んでもらう代わりに、次のようにします。

- 計画を書いたら、すぐに承認しない。まず別の AI に前提の表と止まる条件だけを読ませ、抜けを挙げてもらう。それができないときは、時間を置いてから実装する人の目で読み直す
- 実装を始める前に、前提の表だけは必ず埋める。ほかの欄が空でも、ここが埋まっていれば思い込みのまま進むことは減る
- 止まる条件に当たったら、その場で直して進めず、計画に戻って書き直してから続ける

Mode の判定や、計画全体を別の AI のレビューに回すことは任意です。規模の大きい変更や戻しにくい変更のときにだけ足せば十分です。

## チームで始める

チームで取り入れる場合は、いきなり全部の欄をそろえようとすると続きません。次の順で小さく始めるのがおすすめです。

**骨組みの一部だけを Issue テンプレートに入れる。** 最初は「やらないこと」「止まる条件」「前提の表」のように、3 欄ほどに絞ります。AI への頼み方が人によってばらばらなチームでも、この 3 欄がそろえば、頼むときに考えることがそろいます。どの欄から入れるかは、チームでよく起きている失敗に合わせて選んでください。

**承認する人を決める。** 計画を書くようにしても、誰が読むのかが決まっていなければ承認は形だけになります。standard の計画は誰が読むのか、high-risk 以上に上がったら誰に回すのかを先に決めておきます。書いた本人以外が読む形にしておくと、前提の抜けに気づきやすくなります。

**小さく試して測る。** 次のスプリントで standard 相当のタスクを 2 本選び、計画を書いて進めます。そのときに、計画を読むのにかかった時間、コードレビューにかかった時間、手戻りの回数を記録し、今の進め方と比べます。2 本では結論は出ませんが、続けるか、欄を減らすかを話し合う材料にはなります。

**レビューの場所が前に移るだけになっていないかを確かめる。** 計画を読む時間は確実に増えます。その分、コードレビューで確かめることが減っているのか、同じことを 2 回見ているだけなのかは、チームによって違います。上の計測は、この点を確かめるためのものです。計画の段階で決めたこと（やらないこと、受入基準、止まる条件）を、コードレビューでもう一度議論していないかも見てください。

筆者自身の記録では、計画レビューでコードレビューが減ったとは示せませんでした（2026-09-25 時点、PlanGate リポジトリの記録から集計）。別の AI のレビューを計画に通したタスクのうち PR を特定できた 99 件で、計画側の指摘数と PR の指摘数（PR の指摘スレッド数。AI レビュアーの指摘を含む）は、弱い正の相関（順位相関 0.14 程度）でした。難しいタスクほど両方が増えるためと考えられます。相関は因果を示さず、レビューが減った根拠にもなりません。だから、自分のチームで測ってください。

計画を書くのにかかった時間も、筆者の記録では測れませんでした。計画と承認が同じ PR に入っていたり、会話の中で承認してから PR を作ったりしていたためです。計画を書き始めた時刻と承認した時刻は、最初から残しておくと比べられます。

**骨組みは少しずつ育てる。** 欄を足すのは、同じ種類の失敗が 2 回起きたとき、のように基準を決めておきます。逆に、毎回「なし」としか書かれない欄は外してかまいません。骨組みはチームの失敗の記録から育てるもので、最初から完成形を目指す必要はありません。
