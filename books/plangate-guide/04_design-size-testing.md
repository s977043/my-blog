---
title: "設計案・規模・テスト方針を決める"
---

同じメールアドレスの二重登録を、DB の制約で防ぐか、登録前にアプリ側で検索して防ぐか。AI はこうした選択を、黙って最初に思いついた方で済ませがちです。本章では、設計・規模・テストの判断を計画に書き出す方法を扱います。

## 設計案を 2〜3 案並べてから選ぶ

AI に実装を頼むと、最初に思いついた方式でそのまま作り始めることがよくあります。その方式が妥当なこともありますが、なぜそれを選んだのかは残りません。

PlanGate の計画テンプレートには、設計案を 2〜3 案並べて比べる表があります。比べる観点は、おおよそ次のとおりです。

| 観点 | 何を書くか |
|---|---|
| 根拠 | 既存の実装、実測した事実、制約など |
| 複雑さのコスト | 低・中・高と、その理由 |
| 新しく増える抽象化 | なし、または増える部品 |
| 今必要な理由 | どの受入基準・制約・観測された問題のために必要か |
| 確かめ方 | この案が正しいことをどう示すか |
| 利点と欠点 | トレードオフ |

大事なのは、**いちばん単純な案を必ず比較に入れる**ことです。テンプレートにもそう書かれています。より複雑な案を選ぶなら、その複雑さが「今」必要な理由を、受入基準や制約に結びつけて説明します。

こうしておくと、計画を読む人は「なぜこの方式なのか」を追えます。単純な案が比較にないまま複雑な案が選ばれていたら、それだけでレビューで聞くべきことが一つ見つかります。

## 最小で足りる設計にする

AI は、頼まれていない拡張性を足すのが得意です。将来使うかもしれない設定項目、差し替えられるようにするためのインターフェース、まだ一か所でしか使わない共通化などです。一つひとつはもっともらしく見えます。

PlanGate の計画テンプレートには「なぜこれが最小で足りる設計なのか」を説明する欄があり、次のことを書きます。

- この設計が満たす、今の要件と制約
- 新しく増える抽象化・インターフェース・依存と、それぞれが今必要な理由
- 検討した、より単純な案と、採らなかった理由
- **今は作らない将来の拡張と、その理由**

最後の項目が効きます。「将来こういう拡張が考えられるが、今回は作らない」と書いておけば、AI がその拡張を先回りして作る理由がなくなります。今必要ないものを作らない、という考え方（YAGNI に近いもの）を、計画の欄として明示しているわけです。

## 規模に合わせて計画の重さを変える（Mode）

どのタスクにも同じ重さの計画を求めると、小さな修正でも計画書を書くことになり、誰も使わなくなります。逆に、大きな変更を軽い計画で進めると事故が起きます。

PlanGate は、タスクの規模とリスクで計画の重さを 5 段階に分けています。これを Mode と呼びます。

| Mode | 数える目安（変更ファイル数 / 受入基準数） | 計画の重さ（おおまかに） |
|---|---|---|
| ultra-light | 1 件 / 0〜1 件 | 計画を作らず直接実装する |
| light | 1〜2 件 / 1〜2 件 | 簡易な計画。人は差分を確認する |
| standard | 3〜5 件 / 3〜5 件 | 通常の計画と、人による計画の承認 |
| high-risk | 6〜15 件 / 6〜10 件 | 上に加えて、別の AI による計画レビュー |
| critical | 16 件以上 / 11 件以上 | 詳細な計画と、複数の観点でのレビュー |

対象の例:

- ultra-light: typo の修正、設定値の変更、README の更新
- light: バグ修正、1 ファイルの小さな修正
- standard: 小さな機能追加、数ファイルの変更
- high-risk: 複数のファイル・層にまたがる機能追加
- critical: アーキテクチャの変更、横断的なリファクタリング

段階の名前を覚える必要はありません。押さえておきたいのは、規模とリスクで計画の重さを変えることです。

判定には、変更するファイルの数、受入基準の数、見込みのタスク数のような数えられる基準と、変更の種類、影響範囲、戻しやすさのような性質の基準を使います。両方を見て、重い方を採ります。

light の簡易な計画は、目標・変更内容・確認方法が中心です。第 9 章の骨組みでいえば、設計案の比較と、最小で足りる理由・今は作らない拡張の欄は省いてかまいません。ultra-light は計画を作らないので、骨組みも使いません。

規模が小さくても重く扱う変更もあります。たとえばセキュリティに関わる変更や DB スキーマの変更は、ファイル数が少なくても下限が引き上げられます。**判断に迷ったら重い方に倒す**、というのが PlanGate の基本姿勢です。

ただし、これは判断がつかないときの規則で、何でも重くしてよいという規則ではありません。数えて light に収まり、性質の基準（変更の種類、影響範囲、戻しやすさ）にも引き上げる理由がなければ、light で進めてかまいません。「念のため」で一段上げるのは、この規則の使い方ではありません。性質の基準で上げたときは、その理由を Mode の根拠として書いておきます。日常のタスクの多くは light か standard で足ります。

重くしすぎると、次のような損失が出ます。

- **遅くなる**。書く欄が増え、計画の承認や別の AI のレビューを待つ時間が作業ごとに挟まります。短い修正では、作業より待ち時間のほうが長くなることもあります
- **承認が形だけになる**。毎回長い計画が届くと、承認する人は中身を読まずに通すようになります。本当に重いタスクが来たときも、同じ読み方のまま通してしまいます
- **計画を読まなくなる**。「なし」ばかりの欄が並ぶ計画が続くと、書く人も読む人も欄を飛ばすようになります。止まる条件ややらないことのような大事な 1 行も、一緒に飛ばされます

計画の重さは、読む手間と釣り合わせて考えてください。

以下は参考値で、筆者が PlanGate 自身を開発したタスクの記録です（2026-09-25 時点、PlanGate リポジトリの記録から集計）。一般的な分布ではなく、Mode 同士の比較にも使えません。時間は計画の承認から最後のマージまでの経過時間で、待ち時間を含みます（作業時間ではありません）。

| Mode | タスク数 | 計画の承認からマージまで（中央値） |
|---|---|---|
| light | 25 件 | 0.8 時間（13 件） |
| standard | 50 件 | 1.5 時間（32 件） |
| high-risk | 54 件 | 12.6 時間（21 件） |
| critical | 26 件 | 8.8 時間（10 件） |

対象は 202 件で、内訳は表の 4 つの Mode が 155 件、旧分類が 4 件、Mode の記載なしが 43 件（多くは起票のみ）です。ultra-light は記録が 0 件なので行がありません。括弧内は時間を数えられた件数で、表の合計は 76 件です。全体の中央値は 2.5 時間（77 件。表の外の 1 件を含む）です。同じ Mode でも幅は大きく、standard で 0.1〜22 時間、high-risk で 1.3〜75 時間でした。

PlanGate の開発は、計画を守らせる仕組みそのものを作る開発なので、high-risk と critical が多く出ています。日常の多くは light〜standard で足りる、という先の説明とはここが違います。

また、high-risk（12.6 時間、21 件）が critical（8.8 時間、10 件）より長く見えます。これは、時間を数えられた件数が少なく、同じ Mode の中の幅も大きいためです。この表から、Mode 同士でどちらが時間がかかるかを比べることはできません。

サンプルのユーザー登録 API は standard と判定されていますが、この判定が今の目安と合っているかは第 8 章で数え直します。サンプルの判定を手本にせず、自分のタスクは自分で数えてください。

Mode の判定は、規模の見積もりに依存します。第 1 章の事例のように、見積もりそのものが外れていると Mode も外れます。規模の見積もりを実数で確かめる方法は第 5 章で扱います。

## 変更の種類ごとにテストの進め方を変える

テストを先に書く、という考え方は広く知られています。ただ、PlanGate は「いつも失敗するテストを先に書いてから実装する」に固定していません。変更の種類によって、実装前に何を証拠として取るかを変えます。

| 変更の種類 | 実装前 | 実装後 |
|---|---|---|
| 新しい振る舞いを足す | 失敗するテストを書く | テストが通る |
| バグを直す | バグを再現する失敗テストを書く | テストが通る |
| 振る舞いを変えないリファクタリング | 今の振る舞いを押さえるテストが通ることを確かめる | 同じテストが通り続ける |
| ドキュメント・設定・生成物 | 今の状態を決まった方法で記録する | 同じ方法で確かめる |

リファクタリングの行に注目してください。振る舞いを変えない変更で、わざとテストを失敗させてから進めることはしません。先に今の振る舞いを押さえるテスト（特性テスト）が通ることを確かめ、変更後も同じテストが通り続けることを証拠にします。

AI に「テストを先に書いて」とだけ頼むと、変更の種類に合わない手順を機械的に当てはめることがあります。計画の段階で「この変更はどの種類か」「実装前に何を証拠として取るか」を書いておけば、手順がずれることを防げます。

## 作業を、独立して確かめられる単位に分ける

最後に作業の分解です。PlanGate のテンプレートは、各タスクを「独立して検証でき、レビューする人がタスク単位で承認・差し戻しできる粒度」にするよう求めています。各タスクには、目的、変更するファイル、前のタスクから受け取るものと次に渡すもの、手順、完了条件を書きます。

サンプルでは、次の順で作業が並んでいます。

1. 既存の認証ミドルウェアと users テーブルの構造を確認する
2. 入力チェックの関数を作る
3. ハッシュ化と DB 登録、重複検出を行う処理を作る
4. エンドポイントを作り、アプリに組み込む
5. 単体テストと結合テストを作る

作業の分解（todo）では、この 5 つのステップを 15 のタスクに分けています。

最初のステップが「確認」になっている点に注目してください。第 3 章で書いた不明点（認証ミドルウェアが横取りしないか）を、実装より前に片付ける順序です。ただし、この確認は既存コードを読むだけで済むので、今の考え方では承認の前に済ませます（第 5 章）。

## まとめ

- 設計案は、いちばん単純な案を含めて 2〜3 案並べてから選ぶ
- 「今は作らない拡張」を書いて、AI の先回りを防ぐ
- 規模とリスクで計画の重さ（Mode）を変える。重い方に倒すのは判断がつかないときだけ
- 変更の種類に合わせて、実装前に取る証拠を変える
- 作業は独立して確かめられる単位に分ける
