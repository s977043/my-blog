---
title: "Why・スコープ・受入基準・完了の定義を決める"
---

「ユーザー登録 API を作って」とだけ頼まれた AI は、パスワードのリセットまで作るべきでしょうか。答えは頼んだ人の頭の中にしかありません。それを AI に渡すのが、人が書く入力です。PlanGate ではこれを PBI INPUT と呼び、次の欄があります（括弧内はテンプレートでの欄名）。

- **背景・目的（Context / Why）**: なぜやるのか
- **やること・やらないこと（In scope / Out of scope）**: 今回作るものと、作らないもの
- **受入基準（Acceptance Criteria）**: 何ができたら受け入れるか
- **リファインメントで決まったこと（Notes from Refinement）**: 話し合って決まったこと
- **見積もりの根拠（Estimation Evidence）**: リスク、不明点、前提

AI が計画を作る材料はすべてここから来るので、ここが曖昧だと後ろがすべて揺れます。本章では、PlanGate の公開リポジトリにあるサンプル（ユーザー登録 API を追加するタスク、[examples/sample-task](https://github.com/s977043/PlanGate/tree/main/examples/sample-task)）を例に、各欄で何を決めるのかを見ます。

本書でよく使う言葉を先にまとめておきます。

| 言葉 | 意味 |
|---|---|
| PBI INPUT | 人が書く入力。PBI はプロダクトバックログアイテム（作業の単位）の略 |
| 受入基準（AC） | 何ができたら受け入れるか。AC-1、AC-2 と番号を振る |
| テストケース（TC） | 受入基準を確かめるテスト。TC-01 のように番号を振る（第 7 章） |
| 完了の定義 | どこまでやったら作業を終えてよいか（本章の後半） |
| Mode | タスクの規模とリスクに合わせた、計画の重さの段階（第 4 章） |
| 特性テスト | 今の振る舞いをそのまま記録して押さえるテスト（第 4 章） |

## Why: 「便利だから」ではなく課題で書く

PlanGate のテンプレートは、Why を「便利だから」ではなく課題ベースで書くよう求めています。サンプルの Why はこうです。

> 現在アプリにはユーザー登録のエンドポイントがない。新しいユーザーは管理者が DB に直接登録しており、規模が大きくなると回らないうえに運用上のリスクがある。

（原文は英語。筆者訳）

Why が課題で書かれていると、AI が判断に迷ったときの拠り所になります。「管理者の手作業をなくすこと」が目的だと分かっていれば、登録と関係の薄い機能を足す理由はありません。Why が「ユーザー登録があると便利」だけだと、どこまで作れば目的を果たしたのかが決まりません。

## スコープ: やらないことを先に書く

サンプルのやることの欄には、エンドポイントの形、メールアドレスの形式チェック、パスワードの最低文字数、パスワードのハッシュ化、成功時と失敗時のレスポンスが並んでいます。

同じくらい大事なのが、やらないことの欄です。

- メールアドレスの確認フロー（別の PBI で扱う）
- パスワードのリセット
- OAuth・ソーシャルログイン
- レート制限（インフラ側の関心事）
- users テーブルのマイグレーション（テーブルは既にある）

人間のチームなら、「ユーザー登録」と言われてパスワードリセットまで作り始める人はあまりいません。AI は作り始めることがあります。登録機能にリセットがあるのは自然なので、気を利かせて足してしまうのです。やらないことを明示しておけば、この「気の利かせ方」を最初から封じられます。

やらないことの欄は、レビューのときにも効きます。差分に OAuth 関連のファイルが入っていたら、読む前に「範囲外」と判断できます。

## 受入基準: 検証できる粒度で書く

サンプルの受入基準は 7 件あります。いくつか抜き出します。

- AC-1: 正しいリクエストなら 201 Created と `{ id, email, created_at }` を返す
- AC-2: メールアドレスが既に登録済みなら 409 Conflict と `{ error: "Email already registered" }` を返す
- AC-4: パスワードが 8 文字未満なら 400 Bad Request と決まったエラーメッセージを返す
- AC-5: パスワードは平文ではなくハッシュで DB に保存される

どれも、テストを書けば合否が決まる形になっています。「エラー処理を適切に行う」「セキュリティに配慮する」とは書いていません。

受入基準を検証できる粒度で書くのは、アジャイル開発でも基本です。AI 相手だと、これを怠ったときの影響が大きくなります。AI は「動いた」と「受入基準を満たした」を区別できないことがあり、基準が曖昧なら、それらしく動いた時点で完了と報告します。受入基準が具体的なら、AI 自身が「どこまでやれば終わりか」を判断できます。

受入基準は、第 7 章でテストケースに変換します。ここで曖昧に書いた基準は、テストケースにも曖昧なまま流れていきます。

## 完了の定義: どこで終わりにするか

受入基準が「この PBI で何ができたら受け入れるか」なら、完了の定義は「どこまでやったら作業を終えてよいか」です。アジャイル開発の完了の定義（Definition of Done）に近い考え方です。PlanGate の計画テンプレートには「完了の境界（Completion boundary）」という欄があり、どこまで終われば完了か、どこから先は別の PBI かを書きます。

サンプルの作業分解（サンプルでは todo というファイルにまとまっている）を見ると、完了までに次のようなものが並んでいます。

- lint とテストを実行して全件通す
- 受入基準の 7 件をテストケースと突き合わせて、すべて確認する
- 引き継ぎのメモを残す
- PR を人がレビューしてマージする

完了の定義を先に決めておかないと、AI は「コードが書けた」時点で完了を宣言しがちです。テストを実行したか、受入基準と突き合わせたかが曖昧なまま「できました」と報告されると、確認の手間は結局人に戻ってきます。

## リスク・不明点・前提を正直に書く

PBI INPUT の最後の欄は、リスク、不明点、前提です。サンプルではこう書かれています。

- **リスク**: パスワードのハッシュ化は非同期処理で、`await` を書き忘れると平文のまま保存されうる。同じメールアドレスの同時登録は、DB の UNIQUE 制約で防ぐのが最終的な守り
- **不明点**: 既存の認証ミドルウェアが、登録のリクエストを先に横取りしないかを確認する必要がある
- **前提**: users テーブルは既にあり、email 列に UNIQUE 制約がある。テストランナーは Jest

ここで大事なのは、不明点を空欄にしないことです。分からないことが一つもないタスクはほとんどありません。不明点が空欄の計画は、よく調べた計画というより、分からないことに気づいていない計画であることが多いです。

書かれた不明点と前提は、次の段階で AI が確かめる対象になります。「認証ミドルウェアが横取りしないか」は既存コードを読めば分かるので、計画を承認する前に確かめます。前提の確かめ方は第 5 章で扱います。

## AI に確認質問をさせる

PBI INPUT を渡したら、PlanGate の AI はすぐに計画を書き始めるのではなく、先に確認質問をします。質問は最大 3 問に絞ります。

絞るのには理由があります。質問が際限なく続くと、人は答えるのに疲れて、判断の質が落ちます。3 問までと決めておくと、AI は「本当に計画を左右する曖昧さ」を選んで聞くことになります。人の側も、答える価値のある質問にだけ時間を使えます。

確認質問で出てきた答えは、リファインメントで決まったことの欄に残しておきます。サンプルでは、ハッシュ化の強さの設定値や、メールアドレスは小文字にそろえるだけで前後の空白は入力エラーにする、といった決定がここに書かれています。

## まとめ

- Why は課題で書く。AI が判断に迷ったときの拠り所になる
- やらないことを先に書く。AI の「気の利かせ方」を最初から封じる
- 受入基準は、テストで合否が決まる粒度で書く
- どこまでやったら終わりかを決めておく
- 不明点は空欄にしない。空欄は「気づいていない」サインであることが多い

ここまでは、人が書く入力の話でした。次章からは、AI が計画を組み立てるときに使う知識を見ていきます。
