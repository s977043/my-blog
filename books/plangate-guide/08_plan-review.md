title: "1 つの計画をレビューする"
---

第 3 章から第 7 章で、計画に入れる要素を一つずつ見てきました。本章では、それらを 1 つの計画にまとめて読み、レビューしてみます。

題材は、これまでにも使ってきた PlanGate の公開サンプル、ユーザー登録 API を追加するタスクです（[examples/sample-task](https://github.com/s977043/PlanGate/tree/main/examples/sample-task)）。入力、計画、作業分解、テストケース、AI 自身によるセルフレビューの結果がそろっています。

:::message
このサンプルは、PlanGate の計画テンプレートが今の形になる前に作られたものです。そのため、第 5 章と第 6 章で扱った「前提の実測」「止まる条件」「人が承認する範囲」「設計案の比較」などの欄がありません。また、サンプルの Mode は standard と判定されていますが、第 4 章の数える目安では、変更ファイル 6 件（high-risk は 6〜15 件）と受入基準 7 件（同 6〜10 件）のどちらも high-risk の範囲に入ります。本章では、今のテンプレートの観点で読むとどこに指摘が出るかを見ていきます。本章の指摘と修正は、筆者が説明のために作った例で、サンプルに記録されている実際のやり取りではありません。
:::

## 流れ: 入力 → 初稿 → 指摘 → 修正 → 承認

```mermaid
flowchart LR
    A["入力<br/>（人）"] --> B["初稿<br/>（AI）"]
    B --> C["セルフレビュー<br/>（AI）"]
    C --> D["指摘<br/>（人）"]
    D --> E["修正<br/>（AI）"]
    E --> F{"承認<br/>（人）"}
```

## 1. 入力

入力の中身は第 3 章で見たとおりです。受入基準は 7 件（第 7 章の対応表）、やらないことにはテーブルのマイグレーションが入っています。不明点は「既存の認証ミドルウェアが、登録のリクエストを横取りしないか」です。

## 2. 初稿

この入力から AI が作った計画の主な中身は次のとおりです（原文は英語。筆者による要約）。

- **目標**: 登録エンドポイントを実装し、受入基準 7 件をすべて満たす
- **制約・やらないこと**: OAuth、メール確認、パスワードリセットは範囲外。レート制限はインフラの関心事なので扱わない。テーブルのマイグレーションは不要。**既存の認証ミドルウェアは変更しない**
- **進め方**: 入力チェック → 登録処理 → エンドポイント → アプリへの組み込み → テスト、の順に作る。ハッシュ化は必ず非同期で書き、平文のまま保存する事故を防ぐ
- **作業の分解**: 5 ステップ（第 4 章）。最初のステップは「既存の認証ミドルウェアと users テーブルの構造を確認する」
- **変更するファイル**: 新規 5 件、既存の変更 1 件（アプリ本体にルーターを組み込む）
- **リスクと対策**: `await` の書き忘れ、重複登録の競合（DB の UNIQUE 制約を最終的な守りにする）、ミドルウェアの横取り（最初のステップで確認する）
- **不明点**: 「最初のステップでの確認後、残る不明点はない」
- **Mode**: standard（変更ファイル 6 件、受入基準 7 件、新機能、リスク中）

計画と同時に、作業の分解（5 つのステップを 15 のタスクに分けたものと、人が行う 2 つの承認）と、テストケース一覧（13 件）も作られています。

## 3. AI のセルフレビュー

人が読む前に、AI 自身が計画を点検します。サンプルには、その結果が残っています（収録されているのは点検項目の一部です）。

- すべての受入基準が作業のどこかに対応しているか → 対応している
- 不明点に、解消する手段がついているか → ミドルウェアの確認が最初のステップに入っている
- やらないことが明記されているか → 明記されている
- すべての受入基準にテストケースがあるか → ある
- テストケースの期待値が具体的か → 値のレベルで書かれている

結果はすべて合格でした。受入基準・作業・テストケースの対応がとれていることは、ここで機械的に確かめられます。

## 4. 人の指摘

セルフレビューが合格でも、人が読むと気になる点は残ります。セルフレビューが確かめるのは主に「欄が埋まっていて、互いに対応しているか」です。「書かれている前提は正しいか」「想定外のことが起きたらどうするか」は、読む人が考えます。

今のテンプレートの観点で読むと、たとえば次の 4 点を指摘できます。

**指摘 1: 不明点が、確かめる前に「なし」になっている**

不明点の欄は「最初のステップでの確認後、残る不明点はない」と書かれています。しかし計画を書いている時点では、最初のステップはまだ実行されていません。これは確かめた結果ではなく、確かめたらそうなるだろうという予想です（第 5 章）。

**指摘 2: ミドルウェアが横取りしていたら、どうするのかが書かれていない**

制約には「既存の認証ミドルウェアは変更しない」とあります。一方で、最初のステップでは「ミドルウェアが横取りしないか」を確認します。もし横取りしていたら、制約を守ったままでは登録できません。このとき AI がミドルウェアを直して進めてしまえば、制約を破ります。止まるのか、どう進めるのかが書かれていません（第 6 章）。

**指摘 3: 重複登録の防ぎ方を、ほかの案と比べていない**

重複登録は DB の UNIQUE 制約で防ぐ方針です。これ自体は妥当ですが、「登録前にアプリ側で同じメールアドレスを検索する」という案と比べた記録がありません。アプリ側の検索だけだと、同時に 2 件の登録が来たときにすり抜けます。比べて選んだ理由が残っていれば、後で誰かが「事前に検索すればよいのでは」と変更するのを防げます（第 4 章）。

**指摘 4: Mode を数え直すと high-risk 相当になる**

計画の Mode は standard ですが、冒頭の注記のとおり、変更ファイル数と受入基準数はどちらも high-risk の範囲です。重い方を採るので、この計画は high-risk として扱い、承認の前に別の AI による計画レビューも通します（第 4 章）。

## 5. 修正

指摘を受けて、AI が計画に次の欄を足します。以下は筆者が作った例です。

```markdown
## 前提の実測

| 前提 | 確かめ方 | 実測結果 | 判定 |
|---|---|---|---|
| users.email に UNIQUE 制約がある | スキーマ定義を確認する | （Step 1 で記入） | （Step 1 で記入） |
| 認証ミドルウェアが POST /api/users を横取りしない | ミドルウェアの適用範囲を確認する | （Step 1 で記入） | （Step 1 で記入） |

## 不明点

- 上の 2 件は Step 1 で確かめる。どちらかが崩れたら、下の止まる条件に従う

## 止まる条件

- 認証ミドルウェアが登録のリクエストを横取りしていた場合は、実装を止めて人の判断を待つ（ミドルウェアは変更しない制約のため）
- users.email に UNIQUE 制約がなかった場合は、重複登録の防ぎ方を決め直すため、計画を立て直す。代替案の選択やスキーマ変更の可否のように人の判断が要るなら、止まって相談する

## Mode

- high-risk（変更ファイル 6 件、受入基準 7 件がどちらも high-risk の範囲。standard から見直し）

## 設計案の比較（重複登録の防ぎ方）

| 案 | 複雑さ | 同時登録への強さ | 判定 |
|---|---|---|---|
| A: DB の UNIQUE 制約違反を捕まえて 409 を返す | 低 | 強い（DB が保証する） | 採用 |
| B: 登録前にアプリ側で同じメールアドレスを検索する | 低 | 弱い（検索と登録の間にすり抜ける） | 不採用 |
```

変わったのは、主に「分からないこと」と「分からなかったときにどうするか」の書き方です。作業の中身はほとんど変わっていません。それでも、実装の途中で前提が崩れたときに AI がどう振る舞うかは、大きく変わります。

この修正例では、前提の確認をまず Step 1 に回しました。ただ、前提が 2 件とも確かめられていないままでは、まだ承認できません。スキーマやミドルウェアの設定を読むのは実装ではなく、読むだけで済みます（第 5 章）。そこで次の段階として、確認を承認の前に前倒しします。確かめた結果で、次のように分かれます。

- **2 件とも支持された**: 承認に向けたレビューに進める
- **UNIQUE 制約がなかった**: 重複登録の防ぎ方（設計案の比較）を決め直す。スキーマ変更はやらないことに入っているので、代替案の選択やスキーマを変えてよいかのように人の判断が要るなら、止まって相談する。判断が出たら計画を改訂し、もう一度承認を受ける
- **ミドルウェアが横取りしていた**: 「変更しない」という制約とぶつかるので、人が進め方を決める

2 件とも支持された場合、前提の表は次のようになります。これも筆者の作例で、実測結果の値は説明のためのものです。

```markdown
| 前提 | 確かめ方 | 実測結果 | 判定 |
|---|---|---|---|
| users.email に UNIQUE 制約がある | users テーブルのスキーマ定義を読む | email 列に UNIQUE 制約あり | 支持 |
| 認証ミドルウェアが POST /api/users を横取りしない | ミドルウェアの適用範囲の設定を読む | 適用はログイン後の API だけで、/api/users は対象外 | 支持 |
```

実測結果の欄が予想ではなく、読んで確かめた事実で埋まっています。不明点の欄も「なし」と書けるようになり、ここで初めて承認に向けたレビューに回せる状態になります。

## 6. 承認

最後に、人が計画を承認します。PlanGate の承認には 3 つの結果があります。

| 結果 | 意味 | 次に進む先 |
|---|---|---|
| APPROVE（承認） | 計画に問題はない | 実装を始める |
| CONDITIONAL（条件付き承認） | 骨格は有効だが、直す点がある | 指摘を反映し、簡易なセルフレビューを通してから実装を始める |
| REJECT（差し戻し） | 根本的な問題がある | 計画を作り直す |

このサンプルの初稿は、目標、やらないこと、作業の順序、受入基準とテストケースの対応は筋が通っています。足りないのは、前提と止まる条件の書き方で、計画の骨格ではありません。ただし、Mode を high-risk に数え直したので（指摘 4）、条件付き承認のまま簡易なセルフレビューだけで実装に進むのは軽すぎます。指摘を反映した計画を別の AI による計画レビューに回し、その結果を見て人が承認してから実装に進みます。

承認されるまで、実装には 1 行も進みません。承認されたあとで計画を書き換える必要が出たら、もう一度この承認を通します。

## 自分の計画に貼れる骨組み

第 3 章から第 7 章で見た欄を、1 枚にまとめた骨組みです。Issue や PR のテンプレート、AI への指示書にそのまま貼って、空欄を埋めて使えます。欄の末尾の（人）は人が書く欄、（AI）は AI が作って人が確かめる欄です。

```markdown
- Why（解決したい課題）（人）:
- やること・やらないこと（触らないファイル、追加しない依存も）（人）:
- 受入基準: AC-1 … / AC-2 …（人）
- 完了の境界（どこまでで完了、どこから別 PBI か）（AI）:
- Mode（数えた根拠つき）（AI）:
- 変更するファイル（AI）:

| 前提（AI） | 確かめ方 | 実測結果 | 判定（支持 / 崩れた） |
|---|---|---|---|
|  |  |  |  |

- 不明点（確かめられなかった前提。誰が何で判断するか）（AI）:

| 設計案（A はいちばん単純な案）（AI） | 複雑さ | 利点と欠点 | 判定 |
|---|---|---|---|
| A: |  |  |  |
| B: |  |  |  |

- 最小で足りる理由と、今は作らない拡張（AI）:

| 受入基準（AI） | テストケース | 入力 | 期待値 | 期待値の出どころ（実測 / 規約 / 既存の実装） |
|---|---|---|---|---|
| AC-1 | TC-01 |  |  |  |

- 人が承認する範囲（AI）:
- 止まる条件（計画を立て直す / 人の判断を待つ）（AI）:
```

小さなタスクで骨組みを埋めると、次のようになります。既存の注文一覧 API に status の絞り込みを 1 つ足す、という筆者の作例です。

```markdown
- Why（人）: 問い合わせ対応で未発送の注文を探すのに、一覧を全件めくっている
- やること・やらないこと（人）: status での絞り込みを 1 つ足す。複数 status の同時指定、画面の変更はやらない
- 受入基準（人）: AC-1 `?status=pending` で pending の注文だけを返す / AC-2 未定義の status は 400 を返す
- 完了の境界（AI）: TC-01・TC-02 と既存テストが通れば完了。画面の絞り込み UI は別 PBI
- Mode（AI）: standard（ファイル 2 件・AC 2 件は light の範囲だが、小さな機能追加なので重い方を採る）
- 変更するファイル（AI）: 注文一覧のハンドラ、その結合テスト

| 前提 | 確かめ方 | 実測結果 | 判定 |
|---|---|---|---|
| orders に status 列がある | スキーマ定義を読む | status 列あり | 支持 |

- 不明点（AI）: なし（前提は承認の前に確かめた）
- 設計案（AI）: 案は 1 つ（既存のクエリに条件を 1 つ足す）。絞り込み用の部品を新しく作る案も考えたが、今の受入基準に必要な理由がない
- 今は作らない拡張（AI）: 複数 status の指定。受入基準にないため

| 受入基準 | テストケース | 入力 | 期待値 | 期待値の出どころ |
|---|---|---|---|---|
| AC-1 | TC-01 | `?status=pending` | pending の注文だけ | 既存の実装 |
| AC-2 | TC-02 | `?status=foo` | 400 と、ほかの API と同じ形のエラー | 既存の実装 |

- 人が承認する範囲（AI）: なし（認証・課金・データ削除・本番操作に触れないため）
- 止まる条件（AI）: 既存テストが変更前から失敗していたら計画を立て直す
```

設計案が 1 つしか思いつかないときは、表を無理に埋めず、考えたほかの案と採らなかった理由を 1 行で書きます。該当するものがない欄も空欄にせず、「なし（理由）」と書きます。変更の種類まで light 相当なら、設計案の比較と、最小で足りる理由・今は作らない拡張の欄は省いてかまいません（第 4 章）。

## 計画を読むときのチェックリスト

レビューでは、骨組みの欄が埋まっているかに加えて、次の点を見ます。

- [ ] 変更するファイル、関数、コマンドは実在するか
- [ ] 実測結果の欄が、予想ではなく確かめた事実で埋まっているか
- [ ] 件数が関わる作業で、実数を数えているか
- [ ] 「適切に」「必要に応じて」のような言葉が残っていないか
- [ ] Mode は、変更の規模とリスクに見合っているか

計画が綺麗に書けているかではなく、計画が正しいかを見るのがレビューの役目です。
