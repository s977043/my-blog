title: "プラグインが計画のサイクルを支える"
---

ここまで、計画に何を書くかを見てきました。最終章では、PlanGate のプラグインがこのサイクルをどう支えるかを見ます。

第 3 章から第 8 章の内容は、ツールがなくても実践できます。それでも毎回、同じ欄を思い出し、同じ順番で確かめるのは大変です。プラグインは、その手順を毎回同じ形で回せるようにするためのものです。

## 導入する

PlanGate は、Claude Code と Codex のプラグインとして配布されています。導入の手順はツールによって違います。

**Claude Code**（セッションの中で実行します）

```text
/plugin marketplace add s977043/PlanGate
/plugin install plangate
```

**Codex**（マーケットプレイスの登録と、プラグインの追加が別のコマンドです）

```bash
codex plugin marketplace add s977043/PlanGate
codex plugin add plangate@plangate
```

Codex では、1 行目の登録だけではプラグインは読み込まれません。2 行目まで実行してください。

手順は更新されることがあるので、実際に導入するときは[公式 README](https://github.com/s977043/PlanGate/blob/main/README.md) を確認してください。

## プラグインが回すサイクル

プラグインを入れると、第 1 章で見た「入力 → 計画 → レビュー → 実行」を、決まった手順で回せるようになります。Claude Code なら、次のようなコマンドで進めます。

```text
/working-context TASK-0001        タスクの作業用フォルダを用意する（既にあれば状態を読み込む）
/ai-dev-workflow TASK-0001 plan   計画・作業分解・テストケースを作り、レビューの指摘反映まで進める
（人が計画を読んで承認する）
/ai-dev-workflow TASK-0001 exec   承認された計画どおりに実装し、検証する
```

入力を書く前に、アイデアを対話で整理したいときは `brainstorm` から始めることもできます。Codex では、同梱されているスキル（計画づくりの `ai-dev-plan` など）を呼び出して同じ流れを進めます。

各段階で、プラグインは本書で見てきたことを AI に求めます。

| 段階 | プラグインが AI に求めること | 本書の章 |
|---|---|---|
| 計画の前 | 確認質問で曖昧さをつぶす（最大 3 問） | 第 3 章 |
| 計画づくり | 設計案の比較、Mode の判定、変更の種類に合わせたテスト方針 | 第 4 章 |
| 計画づくり | 前提の実測、件数の確認 | 第 5 章 |
| 計画づくり | やらないこと、止まる条件、人が承認する範囲 | 第 6 章 |
| 計画づくり | 計画と同時にテストケースを作る | 第 7 章 |
| 承認の前 | セルフレビュー。Mode によっては別の AI によるレビュー | 第 8 章 |
| 承認 | 人が承認するまで実装に進まない | 第 8 章 |
| 実行 | 前提が崩れたら止まって計画に戻る。決めた方法で検証する | 第 6・7 章 |

作業の記録（入力、計画、承認、検証の結果、引き継ぎのメモ）は、タスクごとのフォルダに残ります。後から「なぜこの実装になったのか」を追えるのは、この記録があるからです。

## Hook は、承認した計画を守らせる手段の一つ

PlanGate には、Hook という仕組みもあります。AI がファイルを編集したりコマンドを実行したりする直前に割り込み、「計画がない」「承認されていない」「触らないと決めたファイルを触ろうとしている」といった状態を検知して、警告したり止めたりします。

Hook は、計画を書くことや読むことの代わりにはなりません。Hook が判定できるのは、計画があるか、承認されているか、決めた範囲の外を触っていないか、のように機械で判定できることだけです。前提が正しいか、受入基準で足りるか、設計が妥当かは判定できません。守らせる価値のある計画があって、はじめて Hook が役に立ちます。

Hook を使う場合は、次の点に注意してください。

- **Hook はプラグインを入れただけでは有効になりません**。別に配線の手順が必要です
- **配線には `jq` が必要です**。入っていない環境では、ファイルの編集やコマンドの実行が止まることがあります
- **Codex では、プラグインが動いていても Hook による検知は効きません**。Codex で使う場合は、計画の承認を人が確かめる運用で補ってください

配線の手順と、Hook ごとの細かな仕様（どの状態で何を検知するか、警告と停止の切り替えなど）は、[公式 README](https://github.com/s977043/PlanGate/blob/main/README.md) と、そこからリンクされているドキュメントを参照してください。本書では、Hook の個別の仕様には立ち入りません。

## 最終判断は人に残る

プラグインを使っても、次のことは人に残ります。

- **要件が正しいかどうか**。PlanGate は、渡された要件を計画と実装に正しく落とすことを助けますが、要件そのものが正しいかは保証しません
- **計画の承認と、成果物の受け入れ**
- **元に戻せない操作**。データの削除、本番環境での操作、マージや公開などは、AI に決めさせません

PlanGate は、AI にどこまで任せ、どこで人が判断するかを、毎回同じ形で決めるための仕組みです。任せる範囲を広げたいときも、まず計画の書き方を見直すところから始めるのが近道です。

## PlanGate を使わない場合でも

本書で扱った内容は、PlanGate に閉じたものではありません。

- 入力に、Why・やらないこと・受入基準・不明点を書く
- 設計案を、いちばん単純な案と比べて選ぶ
- 前提を確かめ、件数を数えてから着手する
- 止まる条件と、人が承認する範囲を書いておく
- テストケースを、実装の前に受入基準から作る

これらは、Issue のテンプレートや PR のテンプレート、AI への指示書にそのまま持ち込めます。PlanGate は、それを毎回同じ形で回すための一つの実装です。

PlanGate の最新情報は[公式リポジトリ](https://github.com/s977043/PlanGate)で確認できます。Issue や Discussion でのフィードバックも歓迎です。
