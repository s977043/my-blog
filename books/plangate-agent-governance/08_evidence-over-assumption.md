---
title: "推測でPlanを埋めず、確認できることはEvidenceを取りに行く"
---

Planを書くと、空欄を埋めたくなります。

対象件数、影響範囲、既存実装、利用しているAPI、設定値。

AIは、それらしい答えをかなり速く出せます。

しかし、実装前に必要なのは「文章として完成したPlan」ではありません。

> **次の判断に必要な前提が、確認できているPlan。**

です。

## きれいなPlanと、判断に使えるPlanは違う

前章の注文一覧APIを例にします。

AIが次のように書いたとします。

> statusは既存のOrderStatus enumを利用できるため、DB変更は不要です。

文章としては自然です。

ただし、実際にコードを見ていなければ、これはAssumptionです。

~~~text
見た目:
断定文

実態:
未確認の仮説
~~~

この差を放置すると、Reviewする側も「確認済みの事実」として読んでしまいます。

だから、安く確認できることは確認します。

## このBookでは「Cheapest Useful Verification」と呼ぶ

ここから先、このBookでは、

> **次の意思決定に必要な範囲で、十分な証拠を最小コストで取りに行く。**

という実践原則を **Cheapest Useful Verification** と呼びます。

これはPlanGateの公式フェーズ名でも、業界標準の用語でもありません。本書内で「調べ尽くすのではなく、次の判断を変える確認を優先する」という考えを短く呼ぶためのラベルです。

何でも徹底調査するのではなく、判断を変えうるUnknownに対して、一番安く有用な確認方法を選びます。

たとえば、

| Unknown | 最初に試す確認 |
| --- | --- |
| 対象ファイル数 | repository search / count |
| enumの定義場所 | code search |
| APIの現在挙動 | test / local request |
| config値 | config file / runtime output |
| package version | lockfile / package manager |
| CI失敗原因 | workflow log |

「考えれば分かりそう」ではなく、「数秒で確認できるなら確認する」です。

## 1,697ファイルだった「規模M」

第1章で扱ったPlanGate #351の事例は、この原則が生まれた理由の一つです。

AIに次の作業候補を相談したとき、ある画像描き直し作業は「規模M」と見積もられました。

しかし実数を取ると、

- 17グループ
- 1,697ファイル

ありました。

ここでの教訓は、「AIの見積もりは一般に信用できない」ということではありません。

この1件が示したのは、

> **プロジェクト固有の数値を簡単に測れるのに、推定だけで意思決定していた。**

という失敗です。

その後PlanGateでは、件数や規模が判断に影響する場合、Plan作成時に実数を確認する考えを取り込みました。

Source:
- https://github.com/s977043/PlanGate/issues/351

## 件数は、数えられるなら数える

「全部」「大量」「残り少し」「数ファイル」といった表現は危険です。

人間にもAIにも、規模感の錯覚があります。

たとえば、

~~~text
「数個の設定ファイル」
→ findで数える

「この関数を使っている箇所は少ない」
→ repository searchで数える

「影響するテストはこの周辺だけ」
→ test referencesを検索する
~~~

と、判断前に測れます。

正確な数字そのものが欲しいというより、**意思決定を変えるほど前提が外れていないか**を見るのが目的です。

## コードは、存在や責務を確認する

AIは存在しないファイル、関数、設定項目を自然に提案することがあります。

これはPlanの文章品質では見抜きにくい問題です。

そこで、

- ファイルは本当にあるか
- interfaceはその形か
- 呼び出し元はどこか
- 既存patternはどうなっているか

をコードで確認します。

「この設計が最善か」を決める前に、「そもそも今どうなっているか」を確認するわけです。

## テスト・ログ・APIを使う

現在の挙動が分からない場合、コードだけ読むより動かした方が早いこともあります。

たとえば、

- endpointを実際に叩く
- failing testを再現する
- workflow logを見る
- CLIの現在出力を確認する

といった方法です。

重要なのは、調査方法を固定しないことです。

Evidenceは文書である必要はなく、**判断したいClaimを確認できる観測結果**ならよい。

## Evidenceにもコストがある

もちろん、すべてを実測するのは逆効果です。

1時間調査しないと分からないことを、5分の修正前に全部確認する必要はありません。

そこで、Unknownを次のように見ます。

~~~text
このUnknownが外れていたら、
Plan / Scope / Mode / Approachは変わるか？
~~~

変わらないなら、今は深掘りしなくてよいかもしれません。

変わるなら、確認する価値が高い。

この「次の判断が変わるか」を見るのが、本書でいうCheapest Useful Verificationの「Useful」の部分です。

## Evidenceは「進める理由」だけでなく「止まらなくてよい理由」にもなる

Evidenceがあると、毎回同じ前提を人間へ聞き直す必要がなくなります。

たとえば、

- 既存enumを再利用できる
- DB schema変更は不要
- pagination併用の既存patternがある

ことが確認できていれば、その範囲の実装を継続する判断材料になります。

Evidenceは、問題を見つけて止めるためだけでなく、**既知の範囲で安全に進み続けるための材料**でもあります。

## 前提が崩れたら、Planへ戻る

Evidenceを取りに行く本当の価値は、Planを正当化することではありません。

**Planを捨てられること**です。

注文一覧APIで、調査した結果、

> status filterを追加するには、実はDB schema変更が必要だった

と分かったとします。

最初のPlanではschema変更をOut of Scopeにしていました。

このときやるべきことは、

~~~text
「でも実装できそうなので進める」
~~~

ではありません。

~~~text
Assumptionが崩れた
        ↓
Planの境界が変わる
        ↓
Review / Approvalへ戻る
~~~

です。

EvidenceはPlanを強くするためだけでなく、**間違ったPlanを早く壊すため**にも使います。

## この章で持ち帰ること

AIへ「もっとよく考えて」と頼む前に、確認すれば分かることがあります。

> **考えれば分かることは考える。確認すれば分かることは確認する。**

ただし、Evidenceを集めること自体が目的ではありません。

次の判断を変えうるUnknownへ絞り、最小限の確認をする。

そして前提が崩れたらPlanへ戻る。

これで、Approvalへ渡すPlanの判断材料が揃います。

次章では、Review済みのPlanと「実行してよいPlan」の間にあるApproval Boundaryを扱います。
