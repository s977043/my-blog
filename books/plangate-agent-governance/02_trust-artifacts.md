---
title: "判断根拠をAIの自己申告から成果物と証拠へ移す"
---

前章では、AIの「規模M」という判断をそのまま採用せず、実際のファイル数を数えたことで判断を変えられた事例を紹介しました。

ここで重要だったのは、どのモデルを使ったかではありません。

**AIの説明とは別に、外から確認できる事実があったこと**です。

この章では、その考えをもう少し一般化します。

## 「完了しました」を、そのまま完了にしない

AIエージェントへ長い仕事を任せていると、次のような報告を受け取ります。

- 実装しました
- テストは通っています
- 問題ありません
- PRを作成しました
- 完了です

これらは便利な要約です。

ただし、要約そのものは証拠ではありません。

「テストは通っています」と言われたなら、確認したいのはテスト結果です。「要件を満たしています」と言われたなら、確認したいのは受入基準と、その基準に対応する検証結果です。

だからといって、AIの自己申告を疑って毎回すべてを人間がやり直す必要もありません。

変えたいのは、**判断根拠の置き場所**です。ここでは、会話の外に残る成果物を **Artifact**、主張を裏づける材料を **Evidence** と呼びます。

```text
Agentの説明
    ↓
そのまま判断
```

ではなく、

```text
Agent
  ↓
Artifact
  ↓
Evidence
  ↓
Judgment
```

という形にします。

## 成果物（Artifact）は「状態を会話の外へ出したもの」

ここでいうArtifactは、AIとの会話の外に残る成果物です。

PlanGateでは、たとえば次のようなものがあります。

- RequirementやPBIの入力
- `plan.md`
- `todo.md`
- `test-cases.md`
- Review結果
- `status.md`
- handoff
- 実装されたコード
- PR
- 検証結果

重要なのは、Markdownファイルであることではありません。

**次の人や次のAgentが、会話履歴をすべて知らなくても状態を確認できること**が大切です。

会話だけに状態があると、「どこまで決まったか」「何が承認されたか」「どの前提が未確認か」がセッションの流れに埋もれます。

Artifactへ出すと、その状態を別の主体が読み直せます。

## 証拠（Evidence）は「その主張を支える材料」

ArtifactとEvidenceは同じではありません。

たとえば、`plan.md`が存在することはArtifactです。

しかし、そのPlanに「対象ファイルは20件」と書いてあったとしても、20件である根拠がなければ、その数字を採用する理由は弱いままです。

そこで必要になるのがEvidenceです。

```text
Claim:
「対象は20ファイル」

Evidence:
find / grep / repository search の結果
```

あるいは、

```text
Claim:
「Acceptance Criteriaを満たした」

Evidence:
ACと対応づいたtest result
```

です。

この区別は地味ですが、重要です。

**Artifactがあることと、その中の主張が確認できていることは別**だからです。

## 成果物があっても、それだけでは十分ではない

本書では、「AIの自己申告だけでなく成果物を見る」という考え方を使います。

ただし、Artifactさえあれば安全という意味ではありません。

PlanGate自身でも、「ファイルがある」「検査がgreenになった」というだけでは不十分だったケースが何度もありました。後の章で詳しく扱いますが、pluginが実際には読み込まれていないのにdoctorが `registered: YES` を返していたこともあります。

つまり、見るべきなのは、

> **成果物の存在ではなく、判断したい主張に対応する証拠**

です。

成果物（Artifact）は、状態や判断材料を置く器です。

証拠（Evidence）は、その中の主張を確認する材料です。

判断（Judgment）は、それらを見て次へ進むか決める行為です。

この3つを分けると、「AIがそう言ったから」という判断から離れやすくなります。

## 人間が全部読むための仕組みではない

ArtifactとEvidenceを増やす目的は、人間が毎回すべてのログを読むことではありません。

むしろ、人間が読む量を減らすために整理します。

たとえば重要な判断の前に、

- 何を作る計画なのか
- どこまでが承認範囲なのか
- 受入基準を満たした証拠があるか
- 未解決のリスクが残っているか

が短く確認できればよい。

そのためには、会話履歴をすべて読み返すより、判断に必要なArtifactとEvidenceが整理されている方が扱いやすくなります。

## この章で持ち帰ること

AIエージェントを「信頼する / 信頼しない」の二択にする必要はありません。

設計したいのは、**Agentの自己申告だけで判断しなくてよい状態**です。

そのために、

- 状態をArtifactへ出す
- 主張にはEvidenceを対応づける
- その材料をもとにJudgmentする

という流れを作ります。

ただし、Evidenceが揃っても最後の問いが残ります。

「テストが通った」と「この変更を採用してよい」は同じでしょうか。

次章では、ここを **検証（Verification） / レビュー（Review） / 判断（Judgment）** の3つに分けます。
