**対象読者**: AIエージェントの運用記録を残し始めた、または始めようとしている開発者

**この記事で分かること**: 個人の8リポジトリで貯めた記録109件のうち、後から集計できなかった項目と、その抜け方の違い

**この記事で扱わないこと**: 品質・速度・コストの改善、エージェント構成の優劣。記録には効果を言える設計がなく、この記事でも効果は主張しません。
:::

## TL;DR

AIエージェントの構成を記録する [Dynamic Agent Topology（DAT）](https://github.com/s977043/dynamic-agent-topology) の観測記録を109件集計すると、次のことが分かりました。

- **記録は自動化せずに続けると、時間と判断の根拠が抜けました。** 所要時間 `wallClockMs` は84件（77.1%）が `unknown` で、終了時刻 `endedAt` も57件（52.3%）が `unknown` でした。
- **抜けには2種類ありました。** 書いていないものと、書く場所がなかったものです。後者は記録期間の途中で仕様に入った項目で、導入版を更新するまで書けません。書き手の注意では防げません。
- **原因が手作業だとは断定できません。** 自動で取った場合との比較はなく、ここで示せるのは自動化せずに続けた記録で起きたことまでです。

## 集計の条件

DATは、タスクに足りる最も単純なエージェント構成（P0、T0〜T3）を選び、実際に動いた構成と結果を `RunObservation` という記録に残すための仕様とSkillです。この記事の数値は、その記録を集計したものです。

| 条件 | 内容 |
| --- | --- |
| 実行日 | 2026-11-06（JST）。集計と照合はAIエージェントが行った |
| 対象 | 個人所有の8リポジトリ（公開: river-review、plangate / private: 6） |
| 期間 | 記録ファイル名の日付で2026-10-22〜2026-11-05（15日間）。日付のない3件は `endedAt` で補った |
| 件数 | 109件。全件が導入していたDAT 0.3.0のvalidatorを通過 |
| 導入版 | プラグインの版で0.3.0。[記録の仕組みを含まないリリースのv0.3.0](https://github.com/s977043/dynamic-agent-topology/blob/main/CHANGELOG.md)とは別物 |

読むときの注意が3つあります。

1. **期間はファイル名の日付で区切りました。** [計測の取り決め](https://github.com/s977043/dynamic-agent-topology/blob/main/docs/OBSERVATION_MEASUREMENT.md)は期間を `endedAt` で判定すると定めていますが、それが57件で `unknown` のため、取り決めどおりには区切れませんでした。
2. **109件は貯まった記録の総数です。** 2026-10-23を境に記録の単位がウェーブ単位から区切り単位へ変わり、それより前が5件、以後が104件あります。取り決めは10-23をまたいで件数を合計・比較しないと定めています。この記事の取得率と件数は前後を合算しており、この規定から外れます。取得状況を見るための数字で、比較には使いません。件数は作業量も表しません。
3. **値は自己申告です。** 記録者は作業者自身である可能性が高いものの、記録からは特定できません。

## 109件を集計して値が取れなかった項目

[設計](https://github.com/s977043/dynamic-agent-topology/blob/main/docs/RUN_OBSERVATION_DESIGN.md)では、`unknown` は未取得、`[]` と `0` は明示値（レビューなしなど）です。任意項目は、項目がなければ未記録と数えます。

| 項目 | `unknown` | `[]` | 項目なし |
| --- | --- | --- | --- |
| `wallClockMs` | 84（77.1%） | - | - |
| `model` | 67（61.5%） | - | - |
| `endedAt` | 57（52.3%） | - | - |
| `startedAt` | 47（43.1%） | - | - |
| `agentInvocations` | 22（20.2%） | - | - |
| `rework.count` | 4 | - | - |
| `reviews` | 1 | 38 | - |
| `humanInterventions` | 1 | 18 | - |
| `artifacts` | - | 5 | - |
| `outcomeReason`（任意） | - | - | 35 |

設計上の一般集計は `unknown` を分母から除きますが、ここでは取得状況を見るために109件を分母にしました。

`[]` は欠損として数えていません。ただし、`humanInterventions: []` が本当に介入なしだったかは確かめていません。

## 時間が抜ける: 77%の `unknown` と、計算すれば埋まった15件

時間の項目で最も多く抜けたのは `wallClockMs` です。

`startedAt` と `endedAt` の両方が分かる記録は40件ありました。そのうち `wallClockMs` が数値なのは25件です。残る15件は、記録の中の2つの時刻の差を計算すれば埋められました。

ファイル名の日付で分けると次のとおりです。10-23で記録の単位が変わるので、最初の行と残りの行は比べないでください。

| ファイル名の日付 | `wallClockMs` の `unknown` |
| --- | --- |
| 10-22 | 0/5 |
| 10-23〜10-27 | 29/39 |
| 10-28〜11-05 | 55/65 |

リポジトリによっても差があります。river-reviewは15/25、plangateは11/14、privateの6リポジトリは3/8〜9/9でした。

手順の版にも差がありました。`endedAt` にほかの確かな時刻がなければ記録時刻を入れるという規則は、DATリポジトリのadapterと個人用のSkillにはあり、導入版のadapterにはありません。

公開中の[Claude Code向けの記録手順](https://github.com/s977043/dynamic-agent-topology/blob/main/adapters/claude-code/RUN_OBSERVATION.md)は、セッションから時刻を取る機能を「未確認」とし、未確認の情報源に頼る項目は `unknown` にすると定めています。DATは記録の自動取得を実装しない方針です（設計 §9）。

そのため、`unknown` には手順どおりに書いたものも含まれている可能性があります。記録からは、取れなかったのか書かなかったのかを区別できません。

## 判断の根拠が抜ける: 書いていないものと、書く場所がなかったもの

判断の根拠の抜けは、一括りにできません。

| 分類 | 項目 | 件数 | 読み方 |
| --- | --- | --- | --- |
| 書いていない | `interrupted` の `outcomeReason` | 4/16件なし | 仕様上の不足 |
| 不足と扱わない | `completed` の `outcomeReason` | 31/93件なし | 設計上は中断・失敗の理由の項目 |
| 書く場所がなかった | `interruptionKind`、`rework.triggers`、`taskDifficulty`、`usage` | いずれも0/109件 | 導入版のスキーマにない |

### 書いていないもの

`outcomeReason` がない記録は35件あります。ただし、この35件をすべて不足とは言えません。`outcomeReason` は中断・失敗の理由の項目なので、仕様上の不足と言えるのは `interrupted` の4件だけです。`interrupted` はHuman判断待ちの区切りを含むので、失敗の件数としても読めません。

一方で、書き方は揃っていません。`outcomeReason` なしの記録は、river-reviewが0/25、plangateが6/14、privateの6リポジトリが0/8〜20/21でした。

レビューの判定 `reviews[].decision` にも、同じ意味の表記が3通りありました。

| 表記 | 件数 | 現行の正規化表 |
| --- | --- | --- |
| `request-changes` | 85 | あり |
| `changes-requested` | 2 | あり |
| `request_changes` | 2 | なし |

### 書く場所がなかったもの

`interruptionKind`、`rework.triggers`、`taskDifficulty`、`usage` は109件すべてで記録がありません。これは書き漏れではありません。

4項目は2026-10-24（UTC）の[DAT #250](https://github.com/s977043/dynamic-agent-topology/commit/0dc907df)で[スキーマ](https://github.com/s977043/dynamic-agent-topology/blob/main/schemas/run-observation.schema.json)に入りました。導入版のスキーマにはこの4項目がなく、`additionalProperties: false` のため、書いても保存を拒否されます。

たとえば `rework` は導入版では `count` だけです。手戻りのある記録は59件ありますが、そのきっかけを残す場所はありませんでした。

ただし、すべてが更新を怠った結果ではありません。#250より前の記録の時点では、仕様にも項目がありませんでした。#250の時点ではプラグインの版も0.3.0のままで、0.3.1に上がったのは2026-10-29（UTC）です。

これが、今回の記録で最もはっきりした失敗です。仕様側に項目が増えても導入版が古いままなら、記録は増えた項目のないまま貯まり続けます。validatorは導入版のスキーマに照らして通すので、全109件が通過していても、この抜けは分かりません。

## 記録そのものは実際のPRと食い違っていたか

抜けとは別に、書かれた値が実物と合っているかも抜き取りで確かめました。公開2リポジトリから5件を選び、2026-11-06に `gh pr view` で照合しました。

- **PRの実在と状態**: 5/5で矛盾なし
- **内容の一致**: 確かめられたのは1/5（関連Issue番号の一致）。残り4件は記録の粒度では確かめられません
- **時刻**: 記録の開始と終了の間にmergeがあると確かめられたのは1件。3件は終了が `unknown`、1件は両記録とも時刻が `unknown` です

矛盾は見つかりませんでしたが、記録が正しいと確かめられたわけでもありません。5件は抜き取りで、記録全体の精度は示しません。

:::details 番号付きrefと仮名refの内訳

公開2リポジトリの番号付きrefは延べ83件で、現在の状態との一致は75件でした。差の8件はすべて記録が `open` で、現在は `MERGED` です。記録時点の状態なら矛盾しませんが、記録時点の状態は全件を確かめていません。

private 6リポジトリのPRは照合に使っていません。`pr-1` のような仮名refはadapterの規定どおりで、延べ319件中48件あります。番号10未満も含む機械的な判定で、実PRとの対応は未確認です。

:::

## 記録を始める前に決めること（未検証の案）

以下は集計結果から考えた案で、いずれも試していません。効果は未検証で、私の記録以外でも同じ失敗が起きるとも言えません。

| 決めること | 案 | 対応する抜け |
| --- | --- | --- |
| 時間をどう取るか | 開始と終了の時刻は、人やエージェントの記入に頼らず機械で取る | `endedAt` の `unknown` 57件 |
| 計算で出せる値をどう扱うか | 差で求まる値は記入させず、保存か集計のときに計算する | 計算で埋められる15件 |
| 集計の基準は取れるか | 期間の判定に使う項目が実際に埋まるかを、最初の数件で確かめる | 期間をファイル名で区切った |
| 導入版をいつ更新するか | 項目の追加を知る経路と更新の時機を決め、集計時に版の差も確かめる | 0/109件の4項目 |
| 値の表記をどう揃えるか | 自由文字列にせず、保存時に選択肢か正規化で揃える | `decision` の3通りの表記 |

自動取得を試すなら、DATの方針どおりDATの外で作ることになります。

なお、これらの案で値が揃っても、記録の件数から構成の優劣は言えません。計測の取り決めも、構成の比較は事前登録した実験で行うと定めています。

## まとめ

- 自動化せずに続けた109件の記録では、`wallClockMs` の84件と `endedAt` の57件が `unknown` でした。
- `outcomeReason` の抜けは仕様上の不足が4件で、それ以外は不足と扱いません。
- 0/109件の4項目は書き漏れではありません。記録期間の途中で仕様に入り、導入版が0.3.0のままだったため、書く場所がありませんでした。
- 原因が手作業かどうかは未検証です。自動化した場合との比較はありません。
