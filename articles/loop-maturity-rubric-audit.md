この記事で得られること

- AI に開発フローを採点させるとき、評価を「印象」から「証拠付きの判定」に変える方法
- Loop Engineering の 6 モジュールを、観測可能な A〜F のルーブリックへ落とした実例
- 実際に Before → 改善 → After を同じ基準で再採点した結果
- 自動化で 34 件の候補を生成して分かった、「何を自動化するか」より「人間に何件判断させるか」が重要という話

前提は Git リポジトリで管理された個人の執筆・公開フロー。Claude Code を使っているが、考え方自体は特定ツールに依存しない。
:::

## この記事の出発点

自分の開発フローを AI に採点させて、低い評価が出たところを改善する。そんな記事を読んで、自分でもやってみようと思った。

ところが、最初に詰まったのは改善ではなかった。

**採点のほうが再現しなかった。**

「この開発フローを 6 つの観点で評価して」と頼めば、AI は普通に答える。F が出る。C が出る。もっともらしい理由もつく。しかし、プロンプトを少し変えたり、別のセッションで聞いたりすると評価が動く。

その F が、どの条件を満たせなかった F なのか。何を直せば C になるのか。返答だけでは追試できない。

Before が F、改善後が B という記事を書いても、測定器そのものが揺れていたら「改善した」とは言い切れない。

そこで、改善する前に採点基準を作ることにした。

今回の 6 モジュールは、Addy Osmani の [Loop Engineering](https://addyosmani.com/blog/loop-engineering/) にある 5 primitives + memory/state を着想元にしている。

- Automations
- Memory / State
- Sub-agents
- Skills
- Connectors
- Isolation（Worktrees）

この切り口自体は自分の発明ではない。この記事で追加したのは、各モジュールを **A〜F の観測可能な条件に落とし、採点者に証拠を提出させる**部分だ。

## 1. 採点を「意見」ではなく「判定」にする

### 「ある」だけでは能力の証明にならない

最初に作った条件は、たとえばこうだった。

```text
B: 評価者が合否基準を持っている
C: 評価者はいるが、合否基準が曖昧
```

これは採点できない。

「持っている」「曖昧」の意味が採点者の解釈に残るからだ。同じ実装を見て、自分は B、AI は C と判断できる。どちらも条件文には反していない。

そこで、基準を次のように変えた。

```text
B: 評価者が合否基準を持つ。
   基準は機械可読なフィールドとして存在し、検証コマンドで確認できる
C: 評価は多観点だが、合格条件が「致命的な指摘がないこと」しかない
```

重要なのは「厳しい基準」にすることではない。

**第三者が同じリポジトリを見て、成立 / 不成立を追試できること**だ。

ルーブリックには次のルールを置いた。

> 条件は「〜がある」だけで終わらせず、外形的に成立 / 不成立を判定できる形で書く。実行時のガードにできるものは「失敗したときに止まる」まで定義する。

### 採点者に証拠を要求する

もう一つ追加した。

> 採点者は各条件に検証コマンドまたは参照パスを添える。添えられない条件は不成立とする。

AI が「できています」と言ったことを信じるか疑うか、という問題にしない。

報告フォーマットそのものを、証拠がないと成立しない形にする。

このルールは思った以上に効いた。実際、この記事の初稿でも「17 本のチェックを `npm run check` に集約している」と書いていたが、確認すると `npm run check` が直接呼ぶのは 13 本だった。

存在するファイル数と、実際にゲートとして動く数は違う。

### ルーブリック全文

v1 はまだ粗い。E を定義していないモジュールもあり、万能な成熟度モデルだとは考えていない。

それでも、今回の採点を追試できるよう全文を載せておく。

:::details ループ成熟度ルーブリック v1（全文）

```markdown
## 共通ルール

- 条件は「〜がある」だけで終わらせず、外形的に成立 / 不成立を判定できる条件で書く。
- 採点者は各条件に検証コマンドまたは参照パスを添える。添えられない条件は不成立。
- 証拠を伴わない評価は無効。
- 下位グレードは上位グレードの機能の不在を条件にしない。

### Automations — 人間の起動なしに仕事が進むか

| G | 条件 |
|---|---|
| A | 起動が自動（schedule / hook / CI 等）＋ 仕事の発見が自動 ＋ 実行が自動 ＋ 稼働状況が監視され異常が通知される |
| B | 起動が自動 ＋ 仕事の発見が自動 ＋ 実行が自動（稼働監視・通知は問わない） |
| C | 実行または仕事の発見は自動化されているが、起動・次テーマ決定など主要な開始判断の一部を人間が担う |
| D | 一部工程がスクリプト化。工程間の受け渡しは人間 |
| E | 検証だけ自動（CI/hook）。生成・判断は全て人間起動 |
| F | 都度プロンプトで人間が起動する。自動化された停止・進行判断が無い |

### Memory / State — 状態が会話の外にあるか

| G | 条件 |
|---|---|
| A | 台帳がリポジトリにあり、状態遷移が定義され、異常停止が専用ステータスで可視 ＋ 機械が読み書きする |
| B | 台帳がリポジトリにあり状態遷移が定義されている（異常停止ステータス・機械の読み書きは問わない） |
| C | 台帳はあるが自由記述で、状態が定義されていない |
| D | 決定の記録はあるが、進行中タスクの状態を持たない |
| E | 断片的なメモのみ |
| F | 会話コンテキストにしか状態が無い |

### Sub-agents — 実装者と評価者が分離されているか

| G | 条件 |
|---|---|
| A | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ ＋ 基準に基づき自動でエスカレーションする |
| B | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ |
| C | 実装者 ≠ 評価者。評価は多観点だが合格条件が「致命的なし」しか無い |
| D | 役割定義はあるが、同一セッション / 同一エージェントが実装と評価を兼ねる |
| F | 書いた者が自分の仕事を採点している |

### Skills — 手順が再利用可能な部品になっているか

| G | 条件 |
|---|---|
| A | 主要手順が Skill / Command 化 ＋ 自己テストを持つ ＋ 呼び出し条件が明文化 |
| B | 主要手順が Skill / Command 化され、呼び出し条件も明文化 |
| C | Skill / Command 化されているが、いつ呼ぶかが人間の記憶に依存 |
| D | 手順書はあるが実行可能な部品になっていない |
| F | 毎回プロンプトを書き起こしている |

### Connectors — 外部系に機械が到達できるか

| G | 条件 |
|---|---|
| A | 公開先・計測先すべてに API 経由で到達 ＋ 公開後の反映を機械が検証する |
| B | 主要な外部系に API / CLI で到達 |
| C | 一部の外部系のみ機械到達。残りは管理画面での手作業 |
| D | 到達手段はあるが認証・実行が毎回手動 |
| F | すべて人間が画面を操作する |

### Isolation（Worktrees）— 並列作業が互いを壊さないか

| G | 条件 |
|---|---|
| A | 並列作業が物理分離（worktree / コンテナ）＋ 事故が事後検知され自動で止まる |
| B | 物理分離されている |
| C | 物理分離は無いが、事故を検知するガードがあり作業を止められる |
| D | 規約で衝突を避けている。機械的な検知は無い |
| F | 対策なし。並列作業が同一ツリーで無防備に走る |
```

:::

## 2. 測られる側 — 記事公開パイプライン

対象は、Zenn / Qiita / note に記事を出している自分の公開パイプラインにした。

測定日は 2026-08-26。改善前のコミットは `8d4c3b0`。

構成は次の通りだった。

- Claude Code の Skill 6 本、Command 14 本、レビュー用サブエージェント 5 本
- 検証スクリプト 17 本。うち `npm run check` が直接実行するのは 13 本
- Git hook 2 本（pre-commit / pre-push）
- 公開台帳 `docs/publish-queue.md`
- `/publish-zenn` / `/publish-qiita` による公開手順

部品の数だけ見ると、それなりに自動化しているように見える。

同じルーブリックで採点した結果はこうなった。

| モジュール | Before | 落ちた条件 |
|---|:-:|---|
| Automations | C | 起動・仕事の発見に人間判断が残る |
| Memory / State | C | 状態遷移が定義されていない |
| Sub-agents | B | 自動エスカレーションがない |
| Skills | B | 自己テストが一部だけ |
| Connectors | C | note のインポートと公開が手作業 |
| Isolation | C | worktree による物理分離がない |

**B が 2、C が 4。**

点数そのものより、落ちた理由を並べたときに共通項が見えたことが重要だった。

> 工程を実行する仕組みはある。しかし、次に何をやるかを決める仕組みと、今どこで止まっているかを機械が扱う仕組みが弱い。

![記事公開パイプライン6工程の担当を Before / After で色分けした比較図](/images/loop-maturity-rubric-audit/pipeline-before-after-ja.svg)

後工程の「公開する」はかなり機械化していた。一方、前工程の「何を書くか」と、横断的な「今どの状態か」は人間の頭に残っていた。

## 3. 直したのは「状態」と「仕事の発見」

### 台帳に state と異常停止を入れる

改善前の台帳は Queue / Done のほぼ 2 値だった。

そこで 7 つの state と遷移条件を定義した。

| state | 次へ進む条件 |
|---|---|
| backlog | 締切が設定され、一次情報の参照先が 1 つ以上ある |
| ready | 対応する `articles/<slug>.md` が存在する |
| drafting | `npm run check` が通る |
| in-review | publish-readiness が `blocked=false` かつ `mustHigh=0` |
| ready-to-publish | `npm run check:zenn-pace` が FAIL でない |
| requires-human | 機械では進めない異常停止 |
| done | 完了 |

`requires-human` に落とす条件も数値で決めた。

- 改善ループが 5 回を超えても `mustHigh > 0`
- 2 回連続で `mustHigh` が減らない
- `check:zenn-pace` が FAIL
- publish-readiness が stale
- 一次情報の参照先が実在しない

「収束しなければ人間へ」ではなく、「何回なら収束していないと判定するか」まで決める。

5 回 / 2 回という値は暫定だが、少なくとも判定者の気分には依存しない。

### 仕事の発見をスクリプトにする

改善前の台帳にはこう書いていた。

> 補充は手動。次テーマが決まったら行を追加

この「次テーマが決まったら」の主語は人間だった。

そこで、リポジトリ内の 3 シグナルから記事候補を作る `suggest-next-theme.js` を追加した。

- S1: 学習ログのうち、まだ記事化されていない識別子
- S2: `scripts/` にあるが記事本文で扱っていない道具
- S3: 同じタグが一定数たまったクラスタ

候補は一次情報の実在を確認できるものだけに絞る。

```js
function isVerifiableEvidence(facts) {
  return Boolean(facts.existsOnDisk || facts.occursOutsideLearnings);
}
```

さらに、候補ごとに採用スコアを付けた。

```js
function scoreCandidate(c, facts = {}) {
  if (c.signal.startsWith("S1")) return 3;
  if (c.signal.startsWith("S2")) {
    return 1 + (facts.hasSelfTest ? 2 : 0) + (facts.lines >= 150 ? 1 : 0);
  }
  if (c.signal.startsWith("S3")) {
    const n = Number(c.signal.split(":")[2] || 0);
    return n >= CLUSTER_THRESHOLD * 2 ? 3 : 1;
  }
  return 0;
}
```

## 4. 自動化したら 34 件出た。人間の仕事はむしろ増えた

最初の実装では、台帳が空の状態で 34 件の候補が出た。

```text
[suggest:theme] 34 件の候補を検出
```

S1 が 8 件、S2 が 20 件、S3 が 6 件。

そのうち 20 件は「`check-doc-freshness.js` が解いている問題」のように、スクリプト名を機械的に題名へ変えただけの候補だった。

**34 件の backlog は、0 件の backlog と実質的に同じだった。人間が読まない。**

そこで `ADOPT_SCORE = 3` 未満を捨て、さらに 1 回で人間へ渡す件数を `ADOPT_LIMIT = 5` に制限した。

34 → 15 → 5 まで絞った。

![34件がスコア足切りで15件に、件数上限で5件に絞られるファネル図](/images/loop-maturity-rubric-audit/adopt-funnel-ja.svg)

ここで重要な注意がある。

**34 → 15 → 5 は、S1 の一次情報実在チェックを追加する前の初回ログで、現在のコードをそのまま実行して再現する値ではない。**

レビューでこの差に気づいたため、現在は raw / scored / adopted の中間件数を毎回標準出力へ残している。

```text
[suggest:theme] raw=21 scored=6 adopted=5 (ADOPT_SCORE=3, ADOPT_LIMIT=5)
[suggest:theme] 5 件の候補を検出
```

この実装で一番大きかった学びは、「仕事の発見を自動化できた」ことではない。

> **自動化は人間の判断を消さない。人間に渡す判断の総量を設計する仕事へ変わる。**

候補生成まで自動化しても、34 件を人間へ投げたら判断コストを増やしただけになる。

何を自動化するかと同じくらい、**最終的に人間へ何件届けるか**を決める必要があった。

## 5. 同じ基準で測り直したら、Automations は上がらなかった

改善後、最新版の同じ v1 ルーブリックで Before / After を再採点した。

| モジュール | Before | After | 変化 |
|---|:-:|:-:|---|
| Automations | C | C | 仕事の発見ロジックは機械化したが、`suggest:theme` の起動は人間のまま |
| Memory / State | C | B | 7 state と遷移条件、`requires-human` を定義 |
| Sub-agents | B | B | 変化なし |
| Skills | B | B | self-test は 3 → 4 本 |
| Connectors | C | C | 変化なし |
| Isolation | C | C | 変化なし |

**B:2 / C:4 → B:3 / C:3。**

`npm run check` は exit 0、`npm run test:suggest-theme` は 20/20 で通過した。

当初は Automations も B に上がったと採点していた。

しかし公開前レビューで、ルーブリックの見出しが「人間の起動なしに仕事が進むか」なのに、実際には `suggest:theme` を人間が起動している、と指摘された。

その通りだった。

仕事の**発見ロジック**は自動化したが、**起動**は自動化していない。

そこで条件を明確化し、Automations は C のままとした。

これは今回、一番重要な結果だったと思う。

**実装を改善したのに点数が上がらなかった。**

自分に都合よく「改善したから B」と付けるのではなく、条件を読み直した結果 C に留まった。評価器を作った意味が、成功した軸よりこちらに出た。

![6軸それぞれのBefore/Afterのグレードと、Aに届かなかった理由の比較図](/images/loop-maturity-rubric-audit/score-before-after-ja.svg)

次に B へ上げるなら、`suggest:theme` を schedule / hook / CI などから起動し、人間が「候補を探す処理を開始する」役割からも抜ける必要がある。

## 6. 公開前レビューで、評価器そのものが 3 回壊れた

この記事を書く過程で、ルーブリックと実装を別系統からレビューした。

その結果、主題そのものに関わる欠陥が 3 つ見つかった。

### 1. 下位グレードが上位機能の「不在」を要求していた

Memory / State の B 条件に、当初は「異常停止ステータスが無い」と書いていた。

ところが異常停止は A の要件だった。

A の機能を追加すると、B の条件も成立しなくなる。改善すると梯子から落ちるルーブリックになっていた。

そこで、

> 下位グレードは上位グレードの機能の不在を条件にしない

というルールを追加した。

### 2. 設計原則を実装が守っていなかった

「一次情報の実在を確認できない候補は起票しない」と決めたのに、初回実装では S1 が無条件で通っていた。

レビュー後に `isVerifiableEvidence` を追加した。

### 3. Automations を自分に甘く B と採点していた

仕事の発見をスクリプト化したことだけを見て B としたが、起動は人間のままだった。

条件を明確化して C に戻した。

この 3 件を通して分かったのは、**「証拠を要求するルーブリックを作った」だけでは、そのルーブリック自体が正しいとは限らない**ということだった。

評価器もレビュー対象にする必要がある。

## 7. 残ったもの

今回、持ち帰るものは 3 つある。

### 1. AI の評価結果ではなく、判定条件と証拠を残す

「AI が B と言った」は再現できない。

「この条件を、このコマンドと、このファイルで成立と判断した」なら追試できる。

なお今回、同一対象を複数モデルで何回も独立採点して一致率を測る実験まではしていない。そのため、「採点のブレが消えた」とまでは言わない。

改善できたのは、**採点理由を再検証可能にしたこと**だ。

### 2. 自動化では、人間へ戻す仕事量まで設計する

34 件を自動生成できても、34 件全部を人間へ渡したら自動化の価値は薄い。

Human-in-the-loop を置くなら、「どこで人間に戻すか」だけでなく、**一度に何件戻すか**まで決める必要がある。

### 3. 改善しても点数が上がらない評価器のほうが信用できる

今回 Automations は改善したが C のままだった。

これは失敗ではなく、むしろ都合の良い自己採点を防げたということだと思う。

## 終わりに

この手の改善で難しいのは、AIにコードを書かせることより「何をもって改善したとするか」を決めることだった。

ルーブリック v1 にはまだ穴がある。特に E が未定義のモジュールや、Connectors / Isolation の環境依存性は残っている。

ただ、少なくとも「AI の印象で採点する」状態から、条件・証拠・反証を残せるところまでは進めた。

そして公開前レビューでもう一度採点が壊れたことで、このアプローチの価値を逆に確認できた。
