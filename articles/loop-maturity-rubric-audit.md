:::message
この記事で得られること

- AI に自分の開発フローを採点させるとき、結果が再現しない原因と、その直し方
- 「観点」ではなく「失敗条件」で評価基準を書くルーブリックの実物（全文）
- 実際に採点 → 改善 → 同じ基準で再採点したときの、測定値の変化
:::

## この記事の出発点

自分の開発フローを AI に採点させて、低い評価を突きつけられ、そこから改善する。この流れの記事をいくつか読んで、自分でもやってみようと思った。

やってみて最初に詰まったのは、改善のほうではなかった。採点のほうだった。

「あなたのフローを 6 つの観点で採点して」と投げると、AI は普通に答えを返す。F が出る。D が出る。もっともらしい理由もつく。しかし、同じことをもう一度聞くと評価が変わる。プロンプトを少し変えても変わる。何より、その F がどういう条件で F なのかが、返ってきた文章のどこにも書かれていない。

改善記事の骨格は「Before で F、After で B」という差分に全体重を預けている。その差分を支える測定が再現しないなら、改善したのかどうかも本当は分からない。

なので、採点を作るところから始めた。

## 1. 採点を採点可能にする

### 条件は「ある」ではなく「止まる」で書く

最初に書いたルーブリックはこうだった。

```
B: 評価者が合否基準を持っている
C: 評価者はいるが、合否基準が曖昧
```

これは採点できない。「持っている」の判定が採点者の解釈に落ちるからだ。実際、同じフローに対して自分は B をつけ、AI は C をつけた。どちらも間違っていない。条件文が判定を決めていないので、判定する側の気分が決めている。

書き直した。

```
B: 評価者が合否基準を持つ。基準は機械可読なフィールドとして存在し、
   値が閾値を超えたときに終了コードが変わる
C: 評価が多観点で行われるが、合格条件が「致命的な指摘がないこと」しかない
```

違いは、条件が外形的に確認できるかどうかだけだ。前者は grep と終了コードで決着がつく。後者はつかない。

この書き換えの過程で使った原則を、ルーブリックの先頭に置いた。

> 条件は「〜がある」ではなく「〜が失敗したときに止まる」で書く。存在は能力の証明にならない。

チェックスクリプトが 17 本あることと、そのチェックが実際に何かを止めていることは別の話だ。前者は ls で数えられるが、能力とは関係がない。

### 採点者に証拠の提出を義務づける

もう一つ足した規則がある。

> 採点者は各条件に検証コマンドまたは参照パスを添える。添えられない条件は自動的に不成立とする。

これは AI の自己申告への対策になる。「〜ができています」という報告そのものを疑うのではなく、報告のフォーマットを、検証コマンドを書かないと成立しない形にする。書けなければ不成立に倒れるので、採点者は無理に高い評価をつけられない。

### ルーブリック全文

6 軸ある。長いが、この記事で唯一そのまま持ち帰れるものなので全部載せる。

```markdown
### Automations — 人間の起動なしに仕事が進むか

| G | 条件 |
|---|---|
| A | 仕事の発見が自動（シグナルからタスクが起票される）＋ 実行が自動
      ＋ 稼働状況が監視され異常が通知される |
| B | 仕事の発見が自動 ＋ 実行が自動。監視・通知が無い |
| C | 実行は自動だが、仕事の発見は人間。人間が起動トリガを引く |
| D | 一部工程がスクリプト化。工程間の受け渡しは人間 |
| E | 検証だけ自動（CI/hook）。生成・判断は全て人間起動 |
| F | 都度プロンプトで人間が起動する。自動化された停止・進行判断が無い |

### Memory / State — 状態が会話の外にあるか

| G | 条件 |
|---|---|
| A | 台帳がリポジトリにあり、状態遷移が定義され、異常停止が専用ステータスで
      可視 ＋ 機械が読み書きする |
| B | 台帳がリポジトリにあり状態遷移が定義されている。異常停止ステータスが無い |
| C | 台帳はあるが自由記述で、状態が定義されていない（人が読んで解釈する） |
| D | 決定の記録はあるが、進行中タスクの状態を持たない |
| E | 断片的なメモのみ |
| F | 会話コンテキストにしか状態が無い |

### Sub-agents — 実装者と評価者が分離されているか

| G | 条件 |
|---|---|
| A | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ
      ＋ 基準に基づき自動でエスカレーションする |
| B | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ。エスカレーションは人間判断 |
| C | 実装者 ≠ 評価者。評価は多観点だが合格条件が「致命的なし」しか無い |
| D | 役割定義はあるが、同一セッションが実装と評価を兼ねる |
| F | 書いた者が自分の仕事を採点している |

### Skills — 手順が再利用可能な部品になっているか

| G | 条件 |
|---|---|
| A | 主要手順が Skill/Command 化 ＋ 自己テストを持つ ＋ 呼び出し条件が明文化 |
| B | 主要手順が Skill/Command 化され、呼び出し条件も明文化。自己テストは一部 |
| C | Skill/Command 化されているが、いつ呼ぶかが人間の記憶に依存 |
| D | 手順書（散文）はあるが実行可能な部品になっていない |
| F | 毎回プロンプトを書き起こしている |

### Connectors — 外部系に機械が到達できるか

| G | 条件 |
|---|---|
| A | 公開先・計測先すべてに API 経由で到達 ＋ 公開後の反映を機械が検証する |
| B | 主要な外部系に API/CLI で到達。反映検証は一部手動 |
| C | 一部の外部系のみ機械到達。残りは管理画面での手作業 |
| D | 到達手段はあるが認証・実行が毎回手動 |
| F | すべて人間が画面を操作する |

### Isolation — 並列作業が互いを壊さないか

| G | 条件 |
|---|---|
| A | 並列作業が物理分離（worktree/コンテナ）＋ 事故が事後検知され自動で止まる |
| B | 物理分離されている。事故の事後検知は無い |
| C | 物理分離は無いが、事故を検知するガードがあり作業を止められる |
| D | 規約で衝突を避けている。機械的な検知は無い |
| F | 対策なし。並列作業が同一ツリーで無防備に走る |
```

## 2. 測られる側

採点対象は、個人技術ブログの記事公開パイプラインにした。Zenn / Qiita / note の 3 媒体に記事を出す一連の流れで、1 年ほど運用している。

構成要素はこうなっている。

- 執筆・レビュー用の Skill 6 本、Command 14 本、レビュー用サブエージェント 5 本
- 検証スクリプト 17 本（`npm run check` に集約）
- Git hook 3 本（main 直コミット禁止、キャッシュ混入禁止、GitHub アカウント誤りの検知）
- 公開の台帳として `docs/publish-queue.md`
- 公開手順は `/publish-zenn` `/publish-qiita` としてコマンド化済み

数だけ見ればそれなりに部品はある。この状態で採点した。

## 3. 採点結果

F はひとつも出なかった。

| モジュール | G | 落ちた条件 | 証拠 |
|---|:-:|---|---|
| Automations | C | B の「仕事の発見が自動」 | `docs/publish-queue.md:21`「補充は手動。次テーマが決まったら行を追加」 |
| Memory / State | C | B の「状態遷移が定義されている」 | 台帳のセクションは Queue / Done の 2 値のみ。遷移条件も異常停止も未定義 |
| Sub-agents | B | A の「基準に基づき自動でエスカレーション」 | 合否基準は `check-publish-readiness.js` の `blocked` / `mustHigh` として存在。ただし `STRICT=1` 未設定時は WARN 止まり |
| Skills | B | A の「自己テストを持つ」 | 17 本の check に対し self-test は 3 本 |
| Connectors | C | B の「主要な外部系に API/CLI で到達」 | note のインポートと公開が管理画面の手作業 |
| Isolation | C | B の「物理分離されている」 | `git worktree list` = 1 |

B が 2、C が 4。

低評価が出なかったこと自体はどうでもいい。効いたのは、落ちた 4 軸の理由が読み比べると 1 つに収束していたことだった。

> 工程を実行する仕組みはあるが、次に何をやるかを決める仕組みと、異常を自分で申告する仕組みが無い。

パイプラインの後半、つまり「公開する」という工程だけが徹底的に機械化されていて、前半の「何を書くか決める」と、全体を横断する「今どこで止まっているか」が、人間の頭の中にしか無かった。

部品の数を増やす方向にはずっと投資してきたが、それは全部後工程だった。

### 却下した採点案

条件文に照らして落とした評価が 2 つある。これを残しておかないと、後から自分でも検証できない。

Automations を D にする案。「工程間の受け渡しは人間」に見えたので D を検討した。却下した理由は、D の条件文が指す事象と違うからだ。`/publish-zenn` はフェーズ 0 から 3 までを 1 コマンドで進行させる。止まるのは著者ゲート 2 箇所だけで、これは自動化の欠落ではなく、不可逆操作に意図的に置いた停止点だ。「受け渡しが人間」と「停止点が人間」は別の状態を指している。

Sub-agents を C にする案。C の条件は「合格条件が『致命的なし』しか無い」。実際には `mustHigh`（未対応の高重要度指摘数）と `loops`（改善ループ回数）を別フィールドで持っていて、致命的の有無とは独立に判定できる。条件文を読む限り C ではない。

どちらも、条件を文章で書いておいたおかげで機械的に決着した。「なんとなく D な気がする」で終わらなかったのはルーブリックの効果だと思う。

## 4. 直す

共通原因が 2 つに絞れたので、そこだけ直した。

### 台帳に状態と異常停止を定義する

台帳は「Queue に書いてあるもの」と「Done に移したもの」の 2 値だった。進行中のものがどこで止まっているのか、正常に進んでいるのか異常なのかが、行を読んでも分からない。

7 つの状態と、次へ進む条件を定義した。条件はすべて実行可能なコマンドにした。

```markdown
| state | 次へ進む条件（機械判定） |
|---|---|
| backlog          | 締切が設定され、一次情報の参照先が1つ以上ある |
| ready            | 対応する articles/<slug>.md が存在する |
| drafting         | npm run check が通る |
| in-review        | publish-readiness が blocked=false かつ mustHigh=0 |
| ready-to-publish | npm run check:zenn-pace が FAIL でない |
| requires-human   | （機械では進めない） |
| done             | — |
```

そのうえで、異常停止 `requires-human` に落ちる条件を別立てで書いた。

```markdown
- in-review で改善ループが 5 回を超えても mustHigh > 0 が残る
- 改善ループ 2 回連続で mustHigh が減少しない
- check:zenn-pace が FAIL（rate-limit 抵触）
- check:publish-readiness が stale（レビュー後に本文が変わった）
- 一次情報の参照先が実在しない
```

数値を決め打ちにしたのには理由がある。「収束しなければ人間に上げる」だけでは、エージェントは収束していないことを自分では認めない。回数という外形的な基準にすると、判定に主観が入る余地が消える。5 回 / 2 回連続という値自体は現時点の暫定で、実測が溜まったら見直す。この数値も仮説として扱っている。

### 仕事の発見を人間の仕事から外す

台帳の最後の行はずっとこうなっていた。

> 補充は手動。次テーマが決まったら行を追加

「次テーマが決まったら」の主語は人間だ。ここが Automations の B を止めていた条件そのものなので、スクリプトにした。

リポジトリ内から 3 種類のシグナルを拾う。

- S1: 学習ログ（`AGENT_LEARNINGS.md`）の日付付きエントリのうち、見出しに含まれる識別子がどの記事にも出てこないもの
- S2: `scripts/` 配下のスクリプトのうち、ファイル名がどの記事本文にも出てこないもの
- S3: 同じカテゴリタグが閾値以上たまっているもの（シリーズ候補）

設計で 1 点だけ決めたことがある。一次情報が実ファイルとして存在することを検証できない候補は、そもそも起票しない。確信度が低い候補を人間に投げて判断させるのではなく、検証できないならノイズとして捨てる。人間の判断は「起票された候補を採用するか」の一点だけに集約したかった。

見出しからキーワードを取る部分はこうしている。

```js
// 見出しから照合用キーワードを取り出す。
// バッククォートで囲まれた識別子（コマンド名・ファイル名）を優先する。
// 識別子が無い見出しは照合の信頼性が低いため空配列を返し、候補から落とす。
function keywordsOf(title) {
  const ticks = title.match(/`([^`]+)`/g) || [];
  return ticks
    .map((t) => t.slice(1, -1).trim())
    .filter((t) => t.length >= 4 && !t.includes(" "));
}
```

純関数だけを切り出して self-test を同梱した。`npm run test:suggest-theme` で走る。

### 想定していなかったこと

最初の実行で 34 件出た。

```
[suggest:theme] 34 件の候補を検出

- [backlog] (zenn): 「check-article-faq-coverage.js が解いている問題」…
- [backlog] (zenn): 「check-doc-freshness.js が解いている問題」…
- [backlog] (zenn): 「check-gh-account.sh が解いている問題」…
（以下 31 件）
```

34 件の backlog は、0 件の backlog と実質的に同じだ。人間は読まない。

「起票できること」と「起票すべきこと」は別問題だった。シグナルの強さでスコアを付けて足切りするようにした。

```js
// 候補に採用スコアを付ける。
//   S1 実インシデント由来 = 強い（既に痛みが発生している）
//   S2 道具の存在だけ     = 弱い（誰かが困った証拠がない）。
//                          自己テストや規模で補強されて初めて強い
//   S3 クラスタ           = 件数が閾値の 2 倍を超えたらシリーズとして強い
function scoreCandidate(c, facts = {}) {
  if (c.signal.startsWith("S1")) return 3;
  if (c.signal.startsWith("S2")) {
    return 1 + (facts.hasSelfTest ? 2 : 0) + (facts.lines >= 150 ? 1 : 0);
  }
  if (c.signal.startsWith("S3")) {
    const n = Number(c.signal.split(":")[2] || 0);
    return n >= CLUSTER_THRESHOLD * 2 ? 3 : 1;
  }
  return 0;
}
```

`ADOPT_SCORE = 3` 未満を捨て、1 回の起票を `ADOPT_LIMIT = 5` 件に制限した。34 件が 5 件になった。

```
[suggest:theme] 5 件の候補を検出

- 「check-article-humanizer.js が解いている問題」  score:4
- 「check-publish-readiness.js が解いている問題」  score:4
- 「suggest-next-theme.js が解いている問題」       score:4
- 「Zenn の /api/articles は全件を返さない…」      score:3
- 「sync-release-zenn.sh の公開影響プレビューは…」 score:3
```

3 件目で自分自身を候補に挙げてきたのは想定外だった。条件上は正しい（self-test を持ち、150 行を超え、どの記事にも登場していない）。

## 5. 同じルーブリックで測り直す

軸は変えていない。`rubric.md` は v1 のままだ。

| モジュール | Before | After | 変化の根拠 |
|---|:-:|:-:|---|
| Automations | C | B | 台帳の補充が `npm run suggest:theme` による自動起票に変わった。実行して 5 件が台帳に反映された |
| Memory / State | C | B | 7 state と遷移条件、`requires-human` の遷移条件 4 件を定義 |
| Sub-agents | B | B | 変化なし |
| Skills | B | B | self-test は 3 → 4 本。17 本の check に対して依然として部分的 |
| Connectors | C | C | 変化なし |
| Isolation | C | C | 変化なし |

B が 2 から 4 になった。`npm run check` は exit 0、self-test は 17 項目すべて通過している。

A に届かなかった理由も、上がった 2 軸で共通していた。

- Automations が A でないのは、稼働監視と通知が無いから
- Memory が A でないのは、台帳の state を読んで動く機械が 0 本だから（書き込むのは `suggest-next-theme.js` の 1 本だけ）

言い換えると、機械が状態を書くようにはなったが、状態を読んで動くようにはなっていない。次の一手はそこだと分かった。

## 6. 残ったもの

### 評価基準は「観点」ではなく「失敗条件」で書く

多観点でレビューする仕組みは、それ自体では合否を決めない。観点をいくら増やしても、合格条件が「致命的な指摘がないこと」しか無ければ、判定は毎回グレーゾーンに落ちる。

条件文を「〜が失敗したときに止まる」の形に統一したことで、採点のブレがほぼ消えた。副次的な効果として、D にすべきか C にすべきかで迷ったときに、条件文を読み直すだけで決着がつくようになった。

### 自動化は判断を消さず、判断の総量を決める仕事に置き換わる

これが一番効いた学びだった。

仕事の発見を自動化すれば人間の判断は減ると思っていた。実際には、34 件の候補を前にした人間は、以前より多く判断させられる。自動化されたのは起票までで、取捨選択はそのまま人間に転嫁されていた。

足切り基準（スコアと件数上限）を入れて初めて、人間の判断が「5 件のうちどれをやるか」に縮んだ。自動化の設計で決めるべきなのは、何を自動化するかよりも、人間に何件届けるかのほうだったと思う。

## 終わりに

やってみて分かったのは、この手の記事で一番作りにくいのが改善パートではなく採点パートだということだった。採点が再現しないと、改善したかどうかも本当は分からない。

ルーブリックは v1 で、条件文はまだ荒い。特に Connectors と Isolation は自分の環境に寄りすぎている。別の環境で使ってみて条件が判定不能になったら、それはルーブリック側の問題なので教えてもらえると助かる。

- `docs/loop-audit/rubric.md` — 評価基準
- `docs/loop-audit/result-before.md` / `result-after.md` — 採点結果と証拠
- `scripts/suggest-next-theme.js` — 仕事の発見
