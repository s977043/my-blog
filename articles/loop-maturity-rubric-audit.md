:::message
この記事で得られること

- AI に自分の開発フローを採点させるとき、結果が再現しない原因と、その直し方
- 「観点」ではなく「失敗条件」で評価基準を書くルーブリックの実物（全文）
- 実際に採点 → 改善 → 同じ基準で再採点したときの、測定値の変化

前提にするもの: Git リポジトリで管理された個人の執筆・公開フロー。特定のツールに依存する話ではなく、npm script と Git hook が動く環境なら読み替えられる。
:::

## この記事の出発点

自分の開発フローを AI に採点させて、低い評価を突きつけられ、そこから改善する。この流れの記事をいくつか読んで、自分でもやってみようと思った。

先に断っておくと、後で出てくる 6 軸（Automations / Memory / State / Sub-agents / Skills / Connectors / Isolation）という切り口自体は自分の発明ではなく、AI コーディング環境の成熟度を診断する既存の枠組みを踏襲している。この記事が足したのは軸ではなく、各グレードを「失敗したときに止まる条件」として書き直し、採点者に証拠の提出を義務づけた部分だ。

やってみて最初に詰まったのは、改善のほうではなかった。採点のほうだった。

「あなたのフローを 6 つの観点で採点して」と投げると、AI は普通に答えを返す。F が出る。D が出る。もっともらしい理由もつく。しかし、同じことをもう一度聞くと評価が変わる。プロンプトを少し変えても変わる。何より、その F がどういう条件で F なのかが、返ってきた文章のどこにも書かれていない。

改善記事の骨格は「Before で F、After で B」という差分に全体重を預けている。その差分を支える測定が再現しないなら、改善したのかどうかも本当は分からない。

なので、採点を作るところから始めた。

## 1. 採点を採点可能にする — ルーブリックの書き方

### 条件は「ある」ではなく「止まる」で書く

最初に書いたルーブリックはこうだった。

```text
B: 評価者が合否基準を持っている
C: 評価者はいるが、合否基準が曖昧
```

これは採点できない。「持っている」の判定が採点者の解釈に落ちるからだ。実際、同じフローに対して自分は B をつけ、AI は C をつけた。どちらも間違っていない。条件文が判定を決めていないので、判定する側の気分が決めている。

書き直した。

```text
B: 評価者が合否基準を持つ。基準は機械可読なフィールドとして存在し、
   値が閾値を超えたときに終了コードが変わる
C: 評価が多観点で行われるが、合格条件が「致命的な指摘がないこと」しかない
```

違いは、条件が外形的に確認できるかどうかだけだ。前者は grep と終了コードで決着がつく。後者はつかない。

この書き換えの過程で使った原則を、ルーブリックの先頭に置いた。

> 条件は「〜がある」ではなく「〜が失敗したときに止まる」で書く。存在は能力の証明にならない。

チェックスクリプトが 17 本あることと、そのチェックが実際に何かを止めていることは別の話だ。前者は ls で数えられるが、能力とは関係がない。実際この記事の初稿でも「17 本を `npm run check` に集約している」と書いてしまい、外部レビューで `npm run check` が呼ぶのは 13 本だと指摘された。自分で立てた原則に自分で引っかかった。

### 採点者に証拠の提出を義務づける

もう一つ足した規則がある。

> 採点者は各条件に検証コマンドまたは参照パスを添える。添えられない条件は自動的に不成立とする。

これは AI の自己申告への対策になる。「〜ができています」という報告そのものを疑うのではなく、報告のフォーマットを、検証コマンドを書かないと成立しない形にする。書けなければ不成立に倒れるので、採点者は無理に高い評価をつけられない。

### ルーブリック全文

6 軸ある。Automations（人間の起動なしに仕事が進むか）/ Memory / State（状態が会話の外にあるか）/ Sub-agents（実装者と評価者が分離されているか）/ Skills（手順が再利用可能な部品になっているか）/ Connectors（外部系に機械が到達できるか）/ Isolation（並列作業が互いを壊さないか）。長いが、この記事で唯一そのまま持ち帰れるものなので、目的・共通ルール・採点手順を含めて、畳んだうえで全文を置いておく。表中の `G` はグレード（A〜F）を指す。

なお v1 では E を定義したのは Automations と Memory / State だけで、残り 4 軸は D の次が F になっている。この 4 軸で D を割った対象をどう落とすかは条件文が決めておらず、v1 の既知の穴だ。

:::details ループ成熟度ルーブリック v1（全文）

```markdown
**目的**: 開発フローを「AI の印象」ではなく観測可能な条件で採点する。各グレードは
検証コマンドで真偽を判定できる条件のみで定義する。採点者（人でも AI でも）は
条件を上から順に評価し、**満たせなくなった一段下**を採点結果とする。

## 共通ルール

- 条件は「〜がある」ではなく「〜が**失敗したときに止まる**」で書く。存在は能力の証明にならない。
- 採点者は各条件に**検証コマンドまたは参照パス**を添える。添えられない条件は自動的に不成立とする。
- 差し戻し: 証拠を伴わない評価は無効。「たぶん動いている」は F と同じ扱い。
- **下位グレードは上位グレードの機能の不在を条件にしない。**「〜が無い」と書くと、上位の
  機能を足した瞬間に下位の条件も不成立になり、梯子が単調でなくなる。上位機能について
  下位グレードが言えるのは「問わない」までとする。

## 評価軸（6モジュール）

### Automations — 人間の起動なしに仕事が進むか

| G | 条件 |
|---|---|
| A | 仕事の発見が自動（シグナルからタスクが起票される）＋ 実行が自動 ＋ 稼働状況が監視され異常が通知される |
| B | 仕事の発見が自動 ＋ 実行が自動（稼働監視・通知は問わない） |
| C | 実行は自動だが、仕事の発見は人間。人間が起動トリガを引く |
| D | 一部工程がスクリプト化。工程間の受け渡しは人間 |
| E | 検証だけ自動（CI/hook）。生成・判断は全て人間起動 |
| F | 都度プロンプトで人間が起動する。自動化された停止・進行判断が無い |

### Memory / State — 状態が会話の外にあるか

| G | 条件 |
|---|---|
| A | 台帳がリポジトリにあり、状態遷移が定義され、異常停止が専用ステータスで可視 ＋ 機械が読み書きする |
| B | 台帳がリポジトリにあり状態遷移が定義されている（異常停止ステータス・機械の読み書きは問わない） |
| C | 台帳はあるが自由記述で、状態が定義されていない（人が読んで解釈する） |
| D | 決定の記録はあるが、進行中タスクの状態を持たない |
| E | 断片的なメモのみ |
| F | 会話コンテキストにしか状態が無い |

### Sub-agents — 実装者と評価者が分離されているか

| G | 条件 |
|---|---|
| A | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ ＋ 基準に基づき自動でエスカレーションする |
| B | 実装者 ≠ 評価者 ＋ 評価者が合否基準を持つ（エスカレーションが人間判断でもよい） |
| C | 実装者 ≠ 評価者。評価は多観点だが合格条件が「致命的なし」しか無い |
| D | 役割定義はあるが、同一セッション/同一エージェントが実装と評価を兼ねる |
| F | 書いた者が自分の仕事を採点している |

### Skills — 手順が再利用可能な部品になっているか

| G | 条件 |
|---|---|
| A | 主要手順が Skill/Command 化 ＋ 自己テストを持つ ＋ 呼び出し条件が明文化 |
| B | 主要手順が Skill/Command 化され、呼び出し条件も明文化（自己テストは一部でよい） |
| C | Skill/Command 化されているが、いつ呼ぶかが人間の記憶に依存 |
| D | 手順書（散文）はあるが実行可能な部品になっていない |
| F | 毎回プロンプトを書き起こしている |

### Connectors — 外部系に機械が到達できるか

| G | 条件 |
|---|---|
| A | 公開先・計測先すべてに API 経由で到達 ＋ 公開後の反映を機械が検証する |
| B | 主要な外部系に API/CLI で到達（反映検証は一部手動でよい） |
| C | 一部の外部系のみ機械到達。残りは管理画面での手作業 |
| D | 到達手段はあるが認証・実行が毎回手動 |
| F | すべて人間が画面を操作する |

### Isolation（Worktrees）— 並列作業が互いを壊さないか

| G | 条件 |
|---|---|
| A | 並列作業が物理分離（worktree/コンテナ）＋ 事故が事後検知され自動で止まる |
| B | 物理分離されている（事故の事後検知は問わない） |
| C | 物理分離は無いが、事故を検知するガードがあり作業を止められる |
| D | 規約（口頭・文書）で衝突を避けている。機械的な検知は無い |
| F | 対策なし。並列作業が同一ツリーで無防備に走る |
```

:::

## 2. 測られる側 — 記事公開パイプラインの構成

採点対象は、個人技術ブログの記事公開パイプラインにした。Zenn / Qiita / note の 3 媒体に記事を出す一連の流れで、1 年ほど運用している。

測定日は 2026-08-26、対象は自分のリポジトリ 1 つ。以降に出てくる件数はこの時点のスナップショットで、後述の `suggest:theme` は台帳に既にある行を重複として除外するため、実行時点の台帳状態によって出力件数は変わる。

構成要素はこうなっている。

- 執筆・レビュー用に、Claude Code の Skill 6 本、Command 14 本、レビュー用サブエージェント 5 本（`.claude/` 配下）
- 検証スクリプト 17 本。うち `npm run check` が実行するのは 13 本（`check:qiita-drift` / `check:qiita-remote-cache` / `check:pr-staleness` / `check:publish-readiness` はレート制限や実行文脈の都合で個別実行）
- Git hook 2 本（pre-commit / pre-push）。pre-commit は main 直コミット・キャッシュ混入・記憶ブロック混入・リネーム取りこぼしの 4 件、pre-push は GitHub アカウント誤りを検知する
- 公開の台帳として `docs/publish-queue.md`
- 公開手順は `/publish-zenn` `/publish-qiita` としてコマンド化済み

数だけ見ればそれなりに部品はある。この状態で採点した。

## 3. 採点結果 — 落ちた 4 軸の理由が 1 つに収束した

F はひとつも出なかった。

| モジュール | グレード | 落ちた条件 | 証拠（参照先） |
|---|:-:|---|---|
| Automations | C | B の「仕事の発見が自動」 | 改善前の `docs/publish-queue.md` 末尾行「補充は手動。次テーマが決まったら行を追加」（採点時点の記録は `docs/loop-audit/result-before.md`） |
| Memory / State | C | B の「状態遷移が定義されている」 | 台帳のセクションは Queue / Done の 2 値のみ。遷移条件も異常停止も未定義 |
| Sub-agents | B | A の「基準に基づき自動でエスカレーション」 | `check-publish-readiness.js` の `blocked` / `mustHigh` |
| Skills | B | A の「自己テストを持つ」 | 17 本の check に対し self-test は 3 本 |
| Connectors | C | B の「主要な外部系に API/CLI で到達」 | note のインポートと公開が管理画面の手作業 |
| Isolation | C | B の「物理分離されている」 | `git worktree list` = 1 |

Sub-agents が A に届かないのは、合否基準そのものは機械可読なフィールドとして存在するのに、`STRICT=1` を付けない限り WARN 止まりで、エスカレーションが人間判断に残るためだ。

B が 2、C が 4。

低評価が出なかったこと自体はどうでもいい。効いたのは、落ちた 4 軸の理由が読み比べると 1 つに収束していたことだった。

> 工程を実行する仕組みはあるが、次に何をやるかを決める仕組みと、異常を自分で申告する仕組みが無い。

パイプラインの後半、つまり「公開する」という工程だけが徹底的に機械化されていて、前半の「何を書くか決める」と、全体を横断する「今どこで止まっているか」が、人間の頭の中にしか無かった。

![記事公開パイプライン6工程の担当を Before / After で色分けした比較図](/images/loop-maturity-rubric-audit/pipeline-before-after-ja.svg)

部品の数を増やす方向にはずっと投資してきたが、それは全部後工程だった。

### 却下した採点案

条件文に照らして落とした評価が 2 つある。これを残しておかないと、後から自分でも検証できない。

Automations を D にする案。「工程間の受け渡しは人間」に見えたので D を検討した。却下した理由は、D の条件文が指す事象と違うからだ。`/publish-zenn` はフェーズ 0 から 3 までを 1 コマンドで進行させる。止まるのは著者ゲート 2 箇所だけで、これは自動化の欠落ではなく、不可逆操作に意図的に置いた停止点だ。「受け渡しが人間」と「停止点が人間」は別の状態を指している。

Sub-agents を C にする案。C の条件は「合格条件が『致命的なし』しか無い」。実際には `mustHigh`（未対応の高重要度指摘数）と `loops`（改善ループ回数）を別フィールドで持っていて、致命的の有無とは独立に判定できる。条件文を読む限り C ではない。

どちらも、条件を文章で書いておいたおかげで機械的に決着した。「なんとなく D な気がする」で終わらなかったのはルーブリックの効果だと思う。

## 4. 直す — 台帳の状態定義と、仕事の発見の自動化

共通原因が 2 つに絞れたので、そこだけ直した。

### 台帳に状態と異常停止を定義する

台帳は「Queue に書いてあるもの」と「Done に移したもの」の 2 値だった。進行中のものがどこで止まっているのか、正常に進んでいるのか異常なのかが、行を読んでも分からない。

7 つの状態と、次へ進む条件を定義した。条件は人が解釈せずに真偽を決められる形にそろえてある。`docs/publish-queue.md` に置いた定義から、意味列を落として抜粋する。

| state | 次へ進む条件（機械判定） |
|---|---|
| backlog | 締切が設定され、一次情報の参照先が 1 つ以上ある |
| ready | 対応する `articles/<slug>.md` が存在する |
| drafting | `npm run check` が通る |
| in-review | publish-readiness が `blocked=false` かつ `mustHigh=0` |
| ready-to-publish | `npm run check:zenn-pace` が FAIL でない |
| requires-human | （機械では進めない） |
| done | — |

そのうえで、異常停止 `requires-human` に落ちる条件を別立てで書いた。

- in-review で改善ループが 5 回を超えても `mustHigh > 0` が残る
- 改善ループ 2 回連続で `mustHigh` が減少しない
- `check:zenn-pace` が FAIL（rate-limit 抵触）
- `check:publish-readiness` が stale（レビュー後に本文が変わった）
- 一次情報の参照先が実在しない

数値を決め打ちにしたのには理由がある。「収束しなければ人間に上げる」だけでは、エージェントは収束していないことを自分では認めない。回数という外形的な基準にすると、判定に主観が入る余地が消える。5 回 / 2 回連続という値自体は現時点の暫定で、実測が溜まったら見直す。この数値も仮説として扱っている。

### 仕事の発見を人間の仕事から外す

台帳の最後の行はずっとこうなっていた。

> 補充は手動。次テーマが決まったら行を追加

「次テーマが決まったら」の主語は人間だ。ここが Automations の B を止めていた条件そのものなので、スクリプトにした。

リポジトリ内から 3 種類のシグナルを拾う。

- S1: 学習ログ（`AGENT_LEARNINGS.md`）の日付付きエントリのうち、見出しに含まれる識別子がどの記事にも出てこないもの
- S2: `scripts/` 配下のスクリプトのうち、ファイル名がどの記事本文にも出てこないもの
- S3: 同じカテゴリタグが閾値以上たまっているもの（シリーズ候補）

設計で 1 点だけ決めたことがある。一次情報の実在を確認できない候補は、そもそも起票しない。確信度が低い候補を人間に投げて判断させるのではなく、検証できないならノイズとして捨てる。人間の判断は「起票された候補を採用するか」の一点だけに集約したかった。

シグナルごとに確認の仕方が違う。S2 はファイルパスなので `fs.existsSync` で足りる。S1 は学習ログの見出しから抜いた文字列でしかないので、実在するものを指しているとは限らない。そこで、ディスク上に実在するか、あるいは学習ログ以外の追跡ファイルに出現するかを確認して、どちらも取れないものは捨てている。

```js
// 候補の一次情報が「実在するもの」を指しているか判定する。
// S1 の識別子は学習ログの見出しから抜いた文字列でしかなく、`<figure>` のような
// 一般語も混じる。リポジトリ内に実体を確認できたものだけを一次情報として認める。
// （学習ログ自身への出現は根拠にしない。そこに書いてあるのは当たり前だから）
function isVerifiableEvidence(facts) {
  return Boolean(facts.existsOnDisk || facts.occursOutsideLearnings);
}
```

この判定で `<p><img>` のような、記述の中にしか存在しない断片が落ちる。一方 `<figure>` は note の WXR 生成スクリプトが実際に出力するタグなので残る。

見出しからキーワードを取る部分はこうしている。

```js
// 見出しから照合用キーワードを取り出す。
// バッククォートで囲まれた識別子（コマンド名・ファイル名）を優先する。
// 識別子が無い見出しは照合の信頼性が低いため空配列を返し、候補から落とす。
function keywordsOf(title) {
  const ticks = title.match(/`([^`]+)`/g) || [];
  return ticks
    .map((t) => t.slice(1, -1).trim())
    .filter((t) => t.length >= 4 && !t.includes(" "));
}
```

純関数だけを切り出して self-test を同梱した。`npm run test:suggest-theme` で走る。

### 想定していなかったこと

台帳がまだ空だった初回実行で、`npm run suggest:theme` は 34 件を出してきた。

```text
[suggest:theme] 34 件の候補を検出
```

内訳は S1 の学び 8 件、S2 の道具 20 件、S3 のクラスタ 6 件。20 件が「`check-doc-freshness.js` が解いている問題」のような、スクリプト名を機械的に題名にしただけのものだった。

34 件の backlog は、0 件の backlog と実質的に同じだ。人間は読まない。

「起票できること」と「起票すべきこと」は別問題だった。シグナルの強さでスコアを付けて足切りするようにした。

```js
// 候補に採用スコアを付ける。
//   S1 実インシデント由来 = 強い（既に痛みが発生している）
//   S2 道具の存在だけ     = 弱い（誰かが困った証拠がない）。
//                          自己テストや規模で補強されて初めて強い
//   S3 クラスタ           = 件数が閾値の 2 倍以上ならシリーズとして強い
function scoreCandidate(c, facts = {}) {
  if (c.signal.startsWith("S1")) return 3;
  if (c.signal.startsWith("S2")) {
    return 1 + (facts.hasSelfTest ? 2 : 0) + (facts.lines >= 150 ? 1 : 0);
  }
  if (c.signal.startsWith("S3")) {
    const n = Number(c.signal.split(":")[2] || 0);
    return n >= CLUSTER_THRESHOLD * 2 ? 3 : 1;
  }
  return 0;
}
```

`ADOPT_SCORE = 3` 未満を捨てると 34 件が 15 件になり、そこに 1 回の起票上限 `ADOPT_LIMIT = 5` を掛けて 5 件になった（34 → 15 → 5 はいずれも台帳が空だった初回実行時の値。2 回目以降は起票済みの候補が重複判定で落ちるため、同じコマンドでも別の 5 件が出る）。

![34件がスコア足切りで15件に、件数上限で5件に絞られるファネル図](/images/loop-maturity-rubric-audit/adopt-funnel-ja.svg)

初回実行では 3 件目に `suggest-next-theme.js` 自身が挙がってきた。条件上は正しい（self-test を持ち、150 行を超え、どの記事にも登場していない）。

なお、この 34 → 15 → 5 は台帳が空だった初回実行の値で、そのままでは追試できない。起票した行が次回以降は重複判定で落ちるからだ。中間件数を毎回標準出力に残すようにして、実行時の値をその場で確かめられるようにした。

```text
[suggest:theme] raw=21 scored=6 adopted=5 (ADOPT_SCORE=3, ADOPT_LIMIT=5)
[suggest:theme] 5 件の候補を検出
```

実行ログは `docs/loop-audit/evidence-suggest-theme.txt` に置いてある。

言い換えると、機械が状態を書くようにはなったが、状態を読んで動くようにはなっていない。次の一手はそこだと分かった。

## 6. 残ったもの — 失敗条件で書くこと、判断の総量を決めること

### 評価基準は「観点」ではなく「失敗条件」で書く

多観点でレビューする仕組みは、それ自体では合否を決めない。観点をいくら増やしても、合格条件が「致命的な指摘がないこと」しか無ければ、判定は毎回グレーゾーンに落ちる。

条件文を「〜が失敗したときに止まる」の形に統一したことで、採点のブレがほぼ消えた。副次的な効果として、D にすべきか C にすべきかで迷ったときに、条件文を読み直すだけで決着がつくようになった。

### 自動化は判断を消さず、判断の総量を決める仕事に置き換わる

これが一番効いた学びだった。

仕事の発見を自動化すれば人間の判断は減ると思っていた。実際には、34 件の候補を前にした人間は、以前より多く判断させられる。自動化されたのは起票までで、取捨選択はそのまま人間に転嫁されていた。

足切り基準（スコアと件数上限）を入れて初めて、人間の判断が「5 件のうちどれをやるか」に縮んだ。自動化の設計で決めるべきなのは、何を自動化するかよりも、人間に何件届けるかのほうだったと思う。

### 外部レビューで壊れた 2 箇所

公開前に、この記事と関連ファイルを別系統のレビューにかけた。観点は分けてある。片方は構成と読者視点、もう片方は「記事の数値・コード・参照がリポジトリの実物と一致するか」だけを見て、指摘には必ず検証コマンドとその出力を添えさせた。同じ観点を重ねても同じ検証手段しか取らないので、同じ穴が残る。

自分では気づけなかった指摘が 2 つ出た。どちらも記事の主題そのものに刺さっている。

1 つ目は、ルーブリックの梯子が単調でなかったこと。Memory / State の B 条件を「状態遷移が定義されている。異常停止ステータスが無い」と書いていた。異常停止ステータスは A の要件なので、それを足した瞬間に B の条件も不成立になる。改善したら評価が付かなくなる基準だった。共通ルールに一行足して直した。

> 下位グレードは上位グレードの機能の不在を条件にしない。上位機能について下位グレードが言えるのは「問わない」までとする。

2 つ目は、さきほど設計原則として挙げた「一次情報の実在を確認できない候補は起票しない」が、実装では S2 にしか適用されていなかったこと。S1 は無条件で通していた。原則を書いた本人が実装で守っていない。指摘を受けてから `isVerifiableEvidence` を足したので、本文に載せた 34 → 15 → 5 はこの検証が入る前の値だ。

「存在は能力の証明にならない」と書いた記事が、条件文の不備と実装漏れを両方抱えていた。自己申告を疑う仕組みを作っても、それを作った自分の申告は別のところから見てもらわないと落ちない。

## 終わりに

やってみて分かったのは、この手の記事で一番作りにくいのが改善パートではなく採点パートだということだった。採点が再現しないと、改善したかどうかも本当は分からない。

ルーブリックは v1 で、条件文はまだ荒い。特に Connectors と Isolation は自分の環境に寄りすぎている。別の環境で使ってみて条件が判定不能になったら、それはルーブリック側の問題なので教えてもらえると助かる。
