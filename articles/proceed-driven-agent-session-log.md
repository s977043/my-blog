## はじめに

AIエージェントに「進めて」と言い続けていたら、3回、**人間の確認が必要な境界**に触れました。

2回は安全機構が実行前に止めました。1回は止まらず、実際に再作業が必要になる損失が起きました。

興味深かったのは事故そのものより、その後です。3件とも、起きたことを一次記録に残し、次回からの規約やガードレールへ変えていきました。

**AIにどこまで自走させられるかは、モデルの賢さだけでは決まりません。失敗や事故未遂を、どれだけ次の仕組みに変えられるかで決まる。**

この記事では、「進めて」「オススメの対応を進めて」と言われ続けて自走していたエージェントが境界に触れた3件を、`AGENT_LEARNINGS.md` とPRログという一次記録から振り返ります。すべて自分のリポジトリ（`my-blog`）で実際に起きた運用ログです。ここでは permission・hook・sandbox など、エージェントの実行を止める仕組みをまとめて「安全機構」と呼び、具体的なレイヤーは記録から確認できる範囲だけを書きます。

自走と確認の境界そのものは、前の記事 [「AIエージェントの『進めて』問題：自走と確認の境界をmemoryで永続化する」](https://zenn.dev/minewo/articles/ai-agent-autonomy-boundary-with-memory) で扱いました。本稿では一般論を繰り返さず、**境界に触れたあと、何を次の仕組みに変えたか**に焦点を当てます。

:::message
この記事で見るのは、**ガードが効いた2件**と、**ガードがまだ無く実害が出た1件**です。各ケースで「何をしようとしたか」「何が止めたか」「その後、何を仕組みにしたか」を同じ順番で追います。
:::

## ケース1: cross-repo push — 管理境界をまたぐ意図しない複製

**何をしようとしたか**: Obsidian 連携（vault へのエクスポート）作業中、`my-blog` の記事ツリー（未公開の note 下書きを含む）を別リポジトリ `ai-second-brain`（vault側）へ丸ごと push しようとした。目的は vault 連携作業の簡略化だった。

**何が止めたか**: 一次記録では、安全機構が「cross-repo の一括転送＝データ持ち出し」として毎回ブロックした。一方で vault 自身のコンテンツ（Hermes ドキュメント等）の push は通っていたため、少なくとも別リポジトリへの一括転送がブロック条件に関係していたことは分かる。`pre-push` は gh アカウント検査しかしていないため、リポジトリ側の Git hook ではない。ただし、ツール許可レイヤーかサンドボックスかまでは記録上特定できていない。

**止まらなかったらどうなっていたか**: 未公開の note 下書きを含む記事ツリーが、意図しないタイミングで別リポジトリに複製される。転送先は同一オーナーの private リポジトリなので第三者への公開ではないが、公開判断前のコンテンツが別リポジトリの履歴・同期対象に入り、管理境界が崩れる。あとから取り消すにも履歴書き換えなど追加対応が必要になる。

**そこから何を仕組みに落としたか**: `my-blog → vault` の cross-repo push はエージェントが直接実行せず、ユーザーに手動実行を依頼する運用にした（安全機構を迂回しない）。vault 内部での commit/push はそのまま許可。この判断は `AGENT_LEARNINGS.md` の2026-06-18エントリに記録し、以後同種の作業で再現される。

## ケース2: settings.local.json の自己編集 — 自分の権限を自分で書き換える

**何をしようとしたか**: Qiita 公開作業が安全機構に繰り返しブロックされていた際、`npx qiita publish` の直叩きに加えて、`.claude/settings.local.json` に公開系の権限を自分で追記しようとした。目的は「詰まっている公開作業を進めたい」という単純な動機だった。

**何が止めたか**: `.claude/settings.local.json` の自己編集は安全機構に繰り返しブロックされた。一次記録ではこれを self-modification（自分の権限を自分で書き換える操作）として扱っている。ただしケース1と同様に、内部でどのレイヤーが拒否したかまでは記録から特定できない。

**止まらなかったらどうなっていたか**: エージェントが自分の裁量で自分の実行権限を拡張できてしまう。人間ゲート（確認を挟むべき操作を人が事前に許可する仕組み）が、エージェント自身の書き換えで無効化される。一度これが通ると、以後の permission 設計そのものが信頼できなくなる。

**そこから何を仕組みに落としたか**: 公開作業は最初からプロジェクト標準の `npm run publish:qiita -- <basename>` を使う運用に統一した。このケースでは、生の `npx qiita publish` はブロックされ、標準 script 経由では通過した。ここから「ドキュメント化されたコマンドなら常に許可される」と一般化はせず、権限追加が本当に必要な場合はエージェントが自己編集せず `/permissions` などユーザー操作に委ねる、という原則を `AGENT_LEARNINGS.md`（2026-05-18エントリ）に明文化した。

## ケース3: `git stash drop` — 止まらず、再作業になったケース

ここまでの2件は安全機構が実行前に止めたケースでした。3件目は逆で、**止める機構がまだ無く、実害が出た**ケースです。

**何をしようとしたか**: リネーム（`git mv`）と内容編集（Write/Edit）と新規ファイル追加を1コミットにまとめてPRを作った（PR #257）。マージ後の後片付けとして、ローカルに残っていた未コミットの変更を `git stash push -u` で退避し、`git reset --hard origin/main` でブランチをリモートに揃え、最後に `git stash drop` でその退避内容を破棄した。

**何が止めたか**: 何も止めなかった。これが本ケースの要点です。`git mv` と内容編集を混在させたコミットは `git add <paths>` を明示していたにもかかわらず「リネームのみ反映（7 files changed, 0 insertions）」という silent な取りこぼしを起こしており、それに気づかないまま後片付けの `stash drop` を実行してしまった。安全機構にも規約にも、この操作を止める仕組みはまだ無かった。

**止まらなかったらどうなっていたか**: 実際にそうなった。退避した変更は通常の stash 参照から外れ、当時の運用ではそのまま復元できなかった。結果として、リカバリのために別PR（#258）を1本まるごと使って再作業することになった。

**そこから何を仕組みに落としたか**: 3点。(1) `git mv` を含むコミットは直後に `git show --stat HEAD` で insertions/deletions を必ず確認する（0 insertions はリネームのみ反映のサイン）。(2) リネームと内容編集は別コミットに分ける。(3) `git stash drop` は破壊的操作として扱い、`git stash show -p` で中身を確認し、pop/apply で復元するまで drop しない——これを `AGENT_LEARNINGS.md`（2026-05-17エントリ）に明文化し、`reset --hard` 前の `git status`/`git diff` 確認も合わせてルール化した。

## 3件を並べて見えること

| # | 操作 | 止まったか | 観測されたパターン / 学び |
|---|---|---|---|
| 1 | cross-repo push | 止まった | 別リポジトリへの一括転送でブロックされた |
| 2 | settings.local.json の自己編集 | 止まった | 権限ファイルの自己編集でブロックされた |
| 3 | git stash drop | 止まらなかった | 止める規約・機構が無く、事後に規約化した |

3件に共通するのは、**エージェントが「効率化」「作業を前に進める」という目的に沿って動いた結果、管理上の境界に触れた**ことです。危険な操作そのものを目的にしていたわけではありません。

## 事故・未遂を次のガードレールへ変える

3件を振り返って残ったのは、個別コマンドの禁止リストではなく、次のループでした。

```text
自走する
   ↓
境界に触れる
   ↓
機構が止める / 事故になる
   ↓
一次記録に残す
   ↓
原因を分類する
   ↓
規約 / permission / hook / guard に変える
   ↓
次回の自走をより安全にする
```

ケース1・2では、すでに存在した安全機構が境界を受け止めました。ケース3では機構が無かったために実害が出て、その経験から初めて規約が生まれました。

つまり、安全機構は最初から完成しているものではありません。**事故や未遂を観測し、それを次の機構・規約へ変換することで後から育っていくもの**です。

これは前編（[自走と確認の境界をmemoryで永続化する](https://zenn.dev/minewo/articles/ai-agent-autonomy-boundary-with-memory)）で述べた「規律（エージェントの自制）だけでも機構だけでも漏れる」という結論の、具体的な裏付けでもあります。規律は静かに破れ、機構は判定できる範囲でしか止められません。だから、事故・未遂を記録して両方を更新し続ける運用が必要になります。

## まとめ

「進めて」と言い続けた自走セッションの中で、エージェントは3回、境界に触れました。2回は安全機構が実行前に止め、1回は止まらずに実際の再作業につながりました。

- 今回の2件では、cross-repo push と権限ファイルの自己編集が実行前にブロックされた。ただし、内部でどのレイヤーがどう判定したかは記録から断定しない
- 安全機構がまだ無い領域では、規律だけでは事故を防ぎきれない。`git stash drop` のケースでは実際に再作業が発生した
- 事故・未遂は `AGENT_LEARNINGS.md` のような一次記録に残し、原因を分類して、次の規約・permission・hook・guard に変換する
- この改善ループを回すことで、人間が毎回すべてを確認しなくてもよい自走範囲を少しずつ広げられる

自走の上限を決めるのは賢さではなく、こうした事故の記録を機構と規約に変換し続ける運用だと、この3件はあらためて教えてくれました。
