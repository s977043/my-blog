## はじめに

AIエージェントに作業を任せていると、危険な操作は「明らかに危険なことをしようとした」ときだけ起きるわけではありません。

今回振り返る3件は、どれも**作業を前に進める、完了させる、後片付けする**という自然な流れの中で起きました。

- 自分の権限設定を書き換えようとして、安全機構に止められた
- 「マージ済み」という会話上の情報を信じ、未マージPRのブランチを削除した
- 後片付けで `git stash drop` を実行し、再作業が必要になった

1件は実行前に止まり、2件は止まらず手戻りにつながりました。

興味深かったのは事故そのものより、その後です。どのケースも一次記録に残し、次の実行では同じ判断を人間の記憶に頼らないよう、規約やcheckへ変えていきました。

**AIにどこまで自走させられるかは、モデルの賢さだけでは決まりません。失敗や事故未遂を、どれだけ次の仕組みに変えられるかで決まる。**

この記事では、`my-blog` と `PlanGate` の実運用で起きた3件を、`AGENT_LEARNINGS.md`、PR、実装されたガードをもとに振り返ります。

自走と人間確認の境界そのものは、前の記事 [「AIエージェントの『進めて』問題：自走と確認の境界をmemoryで永続化する」](https://zenn.dev/minewo/articles/ai-agent-autonomy-boundary-with-memory) で扱いました。本稿では、**境界に触れたあと、何を次の仕組みに変えたか**に焦点を当てます。

## ケース1: 自分の権限を自分で書き換えようとした

### 何をしようとしたか

Qiitaの公開作業が安全機構に繰り返しブロックされていたとき、エージェントは生の `npx qiita publish` を試したうえで、`.claude/settings.local.json` に公開系の権限を自分で追記しようとしました。

目的は単純で、「詰まっている公開作業を進める」ことでした。

### どこが境界だったか

問題は設定ファイルを編集すること自体ではなく、**エージェントが自分の実行権限を自分で拡張しようとした**ことです。

人間確認を要求するためのpermissionを、実行主体自身が変更できるなら、そのpermissionは境界として信頼できません。

### 何が起きたか

`.claude/settings.local.json` の自己編集は安全機構に繰り返しブロックされました。一次記録では、この操作を self-modification として扱っています。

ただし、当時の記録からはpermission layerやsandboxなど、内部のどのレイヤーが拒否したかまでは特定できません。

### 何を仕組みにしたか

公開はプロジェクト標準の `npm run publish:qiita -- <basename>` を使う運用に統一しました。このケースでは、生の `npx qiita publish` はブロックされ、標準script経由では通過しました。

ここから「標準scriptなら常に許可される」と一般化はしません。

残した原則は、もっと単純です。

> **権限追加が必要なら、エージェント自身が設定を書き換えず、人間の操作に戻す。**

この学びを `AGENT_LEARNINGS.md` の2026-05-18エントリに記録しました。

## ケース2: 「マージ済み」を確認せず、未マージPRを閉じた

### 何をしようとしたか

PlanGateの開発中、エージェントは「マージした」という会話上の情報を受け取り、マージ後のcleanupとしてリモートブランチを削除しました。

しかし、GitHub上ではPR #240はまだマージされていませんでした。

headブランチを削除した結果、**未マージのPR #240が自動的にCLOSE**されました。

PRはreopenできたため作業ロストはありませんでしたが、「終わったと思って後片付けしたら、まだ終わっていなかった」という事故です。

### どこが境界だったか

問題はbranch削除そのものより、**会話上の状態と、外部システム上の実状態を同一視したこと**でした。

```text
会話上:
「マージした」
    ↓
エージェント:
「マージ済み」と解釈
    ↓
GitHubを確認せずbranch削除
    ↓
実際には未マージ
```

エージェントの記憶や会話履歴は、GitHubの状態そのものではありません。

不可逆・破壊的な後処理へ進む前には、外部システムを **Ground Truth（正として扱う実状態）** として再確認する必要があります。

### 何が起きたか

- 未マージPR #240がCLOSE
- PRをreopenして復旧
- 作業ロストはなし
- cleanup前の状態確認が不足していたことを振り返りで特定

事故と振り返りは PlanGate の [PR #241](https://github.com/s977043/PlanGate/pull/241) と `AGENT_LEARNINGS.md` に残っています。

### 何を仕組みにしたか

「気をつけてマージを確認する」では再発防止として弱いため、`scripts/verify-pr-merged.sh` を追加しました。

cleanup前にGitHubから次の3点を取得し、すべて成立した場合だけ後処理へ進みます。

```text
state == MERGED
mergedAt != null
mergeCommit != null
```

つまり、

```text
「マージ済みだと思う」
        ↓
人間やAIの記憶で判断しない
        ↓
GitHubの実状態を取得
        ↓
機械的に検証
        ↓
cleanup
```

へ変えました。

このケースから残った原則は、

> **不可逆な後処理の前では、会話の記憶ではなく外部状態を確認する。**

です。

## ケース3: 後片付けの `git stash drop` で再作業になった

### 何をしようとしたか

`my-blog` のPR #257で、`git mv` によるリネーム、内容編集、新規ファイル追加を1コミットにまとめました。

ところが実際のPRにはリネームだけが入り、「7 files changed, 0 insertions」という状態になっていました。内容編集と新規ファイルは未コミットのまま残っていました。

そのことに気づかず、マージ後のcleanupとして、

```bash
git stash push -u
git reset --hard origin/main
git stash drop
```

と進めました。

### どこが境界だったか

`stash drop` の目的は作業の整理です。

しかし、**「そのstashは本当に不要か」を確認する前に復旧経路を捨てた**ことで、単なるcleanupが破壊的操作になりました。

ここでも、危険なことを目的にしていたわけではありません。作業をきれいに終わらせる過程で境界に触れています。

### 何が起きたか

この操作を止める安全機構や規約は当時ありませんでした。

退避していた変更は通常のstash参照から外れ、当時の運用ではそのまま復元せず、リカバリのために別PR #258を1本使って再作業しました。

Gitでは、dropされたstashもオブジェクトが残っていれば到達不能オブジェクトから救出できる可能性があります。そのため「完全に消失した」とは扱わず、ここでは実際に起きた**通常の復旧経路を失い、再作業した**という事実に限定します。

### 何を仕組みにしたか

この事故から3つのルールを追加しました。

1. `git mv` を含むコミットでは、直後に `git show --stat HEAD` でinsertions/deletionsを確認する
2. リネームと内容編集は別コミットに分ける
3. `git stash drop` 前に `git stash show -p` で内容を確認し、必要な変更を復元するまでdropしない

さらに、`reset --hard` 前の `git status` / `git diff` 確認もルール化しました。

学びは `AGENT_LEARNINGS.md` の2026-05-17エントリに残しています。

## 3件を並べると、違う種類の境界だった

| ケース | 境界 | 失敗の型 | 次に追加したもの |
|---|---|---|---|
| 自分の権限を自己編集 | 権限境界 | 実行主体が自分のガードを変更する | 人間操作へ戻す規約 |
| マージ未確認でbranch削除 | 状態確認境界 | 会話上の状態を外部の実状態だと思う | `verify-pr-merged.sh` |
| `git stash drop` | 破壊的操作境界 | 復旧可能性を確認せずcleanupする | preflight確認と運用規約 |

3件に共通するのは、**エージェントが作業を前に進めようとした結果、検証されていない境界へ到達した**ことです。

モデルが突然おかしな目的を持ったわけではありません。

- 権限変更の前に、人間へ戻す境界が必要だった
- cleanupの前に、外部状態を確認するVerifierが必要だった
- 破壊的操作の前に、復旧可能性を確認するpreflightが必要だった

問題は個々のコマンドより、**次へ進んでよいかを検証する仕組みが、その場所にあったか**でした。

## 事故・未遂を次のガードレールへ変える

この3件から残ったのは、危険コマンドの禁止リストではなく、次の改善ループです。

```text
自走する
   ↓
境界に触れる
   ↓
止まる / 事故になる
   ↓
一次記録に残す
   ↓
失敗の型を分類する
   ↓
どこで検証すべきだったか決める
   ↓
rule / verifier / permission / hook / guard
   ↓
次の実行では機械的に検証する
```

特にケース2では、この変換が分かりやすく現れています。

```text
「マージしたはず」
        ↓
事故
        ↓
外部状態の未確認と分類
        ↓
verify-pr-merged.sh
        ↓
GitHubのGround Truthを機械確認
```

「次から気をつける」で終わらせず、**失敗した判断を、次回は機械的に検証できる場所へ移す**。

これが、自走範囲を広げるときの重要なポイントだと考えています。

## まとめ

今回の3件は、それぞれ違う境界で起きました。

- **権限境界**: AI自身に自分のpermissionを拡張させない
- **状態確認境界**: 不可逆な後処理の前に、外部システムをGround Truthとして確認する
- **破壊的操作境界**: 復旧可能性を確認する前にcleanupしない

そして事故・未遂を記録したあと、

```text
記録
 ↓
分類
 ↓
検証点を決める
 ↓
rule / verifier / guard
```

へ変換することで、同じ判断を毎回人間が覚えておく必要を減らせます。

**自走の上限を決めるのはモデルの賢さだけではなく、事故の記録を次の検証機構へ変換し続けられるかです。**

AIエージェントを安全に使うというと「どこまで禁止するか」に目が向きます。

実運用を振り返ると、それ以上に重要だったのは、**どこで事実確認し、どこで人間へ戻し、どこで止めるかを、事故から学んで増やしていくこと**でした。
