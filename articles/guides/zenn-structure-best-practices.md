# Zenn記事の構成ベストプラクティス

Zenn向けの記事を、技術的に正確で、読者が理解・再現しやすく、将来も参照できるストック資産へ近づけるための実践ガイド。

2026-08-26時点のZenn公式コミュニティガイドライン、Markdown仕様、Tech / Idea のカテゴリー定義と、このリポジトリの運用実績をもとに整理した。

## 正本の境界

- **媒体の役割・多媒体展開の方針**: `docs/content-channel-strategy.md`
- **Zenn記事の構成判断**: このファイル
- **レビューの実行手順・出力形式**: `.claude/agents/article-reviewer.md` と `.claude/commands/review-article.md`

このガイドは固定テンプレートではない。記事の目的・検索意図・読者・検証内容を優先する。

## Zennで最も重視すること

Zenn公式は、生成AIで一般知識を得やすくなった今、**実体験・具体的な試行錯誤・書き手自身の考察**を含むことを推奨している。また、タイトルを内容に合わせ、冒頭で概要や得られる情報を示し、対象読者・環境・発生条件を明確にすると理解・再現しやすいとしている。

そのため、読後に少なくとも次のどれかができる状態を目指す。

- 同じ条件で再現できる
- なぜその設計を選んだか判断できる
- 同じ障害を切り分けられる
- 将来、逆引きリファレンスとして使える

## まず分ける：Zennカテゴリーと記事構成タイプ

Zennの Front Matter にある `type: tech | idea` と、記事の構成タイプは別物として扱う。

### Zennカテゴリー

Zenn公式の定義では、おおむね次のように選ぶ。

- **Tech**: ソフトウェアやハードウェアを実際に動かして検証した内容、具体的な技術的洞察、実装・性能比較・トラブルシュートなど
- **Idea**: 技術に関する抽象的な考え方や情報のまとめ、キャリア・マネジメント、イベント体験、サービス紹介など

技術的な深掘りが主ならTech、紹介やまとめが主ならIdeaを第一候補にする。判断が難しい場合は、Zenn公式もどちらを選んでもよいとしている。

### 記事構成タイプ

カテゴリーとは独立して、記事を次のような構成タイプに分類する。

- 実装 / ハウツー
- トラブルシュート
- 設計 / アーキテクチャ
- 概念解説 / 考察 / まとめ
- 混合

たとえば `type: idea` でも「技術トレンドのまとめ」と「設計思想の考察」では構成が異なる。`type` だけで記事骨格を決めない。

## 最重要原則

### 1. 冒頭で「誰に・何が分かるか・どの条件か」を示す

必要なものを選んで冒頭に置く。

- 対象読者
- 解決する問題 / 得られる知識
- 対象技術・バージョン・環境
- 記事で扱わない範囲

長文や専門性の高い記事では `:::message` で前提を切り出してよい。

### 2. 長文は結論を先に出す

長文では `## TL;DR` や導入の要約で、本文を全部読まなくても価値を判断できるようにする。

```text
対象・前提
↓
結論 / TL;DR
↓
全体像
↓
詳細
```

短いトラブルシュートなどは独立したTL;DR章を作らず、冒頭1〜2段落で結論を示してよい。

### 3. 結果だけでなく再現条件を残す

記事内容に応じて、必要なものだけを記載する。

- OS / ランタイム / ライブラリ / CLIのバージョン
- 対象リポジトリや構成の前提
- 入力条件
- 実行コマンド
- 期待結果
- 失敗時の症状
- 検証日

再現に関係しない環境情報まで機械的に並べない。

### 4. 手順より判断を残す

一般的なコマンド一覧より、次の情報を優先する。

- なぜその方法を選んだか
- 他に何を試したか
- 何が失敗したか
- どの条件なら別案を選ぶか
- 実際に観測した結果

基本候補は次の流れ。

```text
課題
↓
仮説 / 選択肢
↓
実装・検証
↓
結果
↓
判断
```

### 5. 本筋と再現用詳細を分ける

- **本筋**: なぜ / 何を / どの順で / 何が分かったか
- **詳細**: 長い設定全文 / ログ / 補助テンプレート / 一度だけ確認する情報

補助的な詳細は `:::details` を検討する。ただし記事の核心となるコードや差分は畳まない。

## 構成タイプ別の骨格

### 実装 / ハウツー

```text
対象読者・前提
結論 / TL;DR
全体像
環境・バージョン
実装
重要なコード・設定
ハマりどころ
検証結果
判断・制約
次に試すこと
```

### トラブルシュート

```text
症状
先に結論
発生条件
切り分け
原因
修正
確認方法
再発防止 / 適用範囲
```

検索流入を狙う場合は、タイトルと冒頭で対象技術・症状・解決方向が分かるようにする。

### 設計 / アーキテクチャ

```text
解きたい問題
制約
結論 / TL;DR
全体構造
選択肢
採用した設計
トレードオフ
実装 / 運用
検証
適用できる条件 / できない条件
```

図だけで終わらず、境界・責務・状態遷移を選んだ理由を残す。

### 概念解説 / 考察 / まとめ

```text
問題提起
主張または整理軸
前提 / 定義
根拠となる実体験・検証・一次情報
比較 / 反例 / 限界
一般化
読者が判断するときの観点
```

抽象論や情報の再整理だけで終わらず、書き手独自の検証・比較・判断を可能な範囲で加える。

## タイトル・見出し

### タイトル

一覧や検索結果で「自分の問題に関係するか」を判断できるようにする。

優先する要素:

1. 対象技術・固有名詞
2. 問題または目的
3. 解決・発見

本文で検証していない効果を断定しない。SEO語を詰め込んで意味を崩さない。

このリポジトリのSEO主導型記事では「具体製品名 + 問題語 + 解決示唆」を第一候補とする。実測に基づく媒体戦略は `docs/content-channel-strategy.md` を参照する。

### 見出し

Zenn公式Markdownガイドは、アクセシビリティの観点から本文見出しを `##` から始めることを推奨している。

`概要` / `詳細` / `その他` のような管理ラベルだけでなく、見出しだけで論理が追えるようにする。

## コード・Zenn記法

- コードブロックには適切な言語指定を付ける
- コピペ可能な例を優先する
- 省略した箇所は明示する
- 実行結果が重要なら期待出力を示す
- 長い補助設定・ログは `:::details` を検討する
- 重要な前提は `:::message`、破壊的操作や重大な注意は `:::message alert` を検討する
- 複数案の比較・条件差・責務分離は表が有効か検討する
- 記法は装飾目的で機械適用しない

## 事実検証

技術的な主張は、可能な範囲で一次情報と実測を対応させる。

- API / ライブラリ / CLI仕様 → 公式ドキュメント、README、CHANGELOG
- 自分の実装の挙動 → 実コード、テスト、ログ
- 数値 → 計測スクリプトを再実行
- 「存在しない」「0件」 → 検索範囲と観測限界を確認

観測できなかったものを0件と断定しない。古いバージョンの情報を現在仕様として書かない。

## AIを使って書く場合

Zennは生成AI利用を禁止していないが、公式ガイドラインは、正確性を確認しない投稿やスコア目的の乱造を避けるよう求めている。

一般知識の再構成だけでなく、次のどれかを含める。

- 実際に試した結果
- 失敗・ハマりどころ
- 独自の比較
- 計測値
- 設計判断
- 一次ソースとの照合

AIが生成した説明そのものを技術的主張の根拠にしない。

## 記事終盤

本文の再掲だけで終わらず、記事タイプに応じて次のいずれかへつなぐ。

- 実践Tips / 最小導入
- 判断基準
- 制約・適用範囲
- 次に検証すること
- 関連記事
- 公式ドキュメント / GitHubリポジトリ

## レビュー時の優先順位

### P1

- タイトルと本文の主張がずれている
- 対象読者・得られること・必要な前提が分からない
- 再現条件が不足している
- 技術的主張が一次情報または実測で裏付けられていない
- コード / コマンドの成立性が確認できていない

### P2

- 長文なのに結論や全体像へ到達しづらい
- 手順だけで、失敗・理由・判断基準がない
- 長い補足が本筋を埋めている
- 見出しだけでは論理を追えない
- 適用範囲・制約がない

### P3

- Zenn記法や表で読みやすくできる
- 関連記事への導線を追加できる
- topics / emojiを改善できる
- 図で構造理解を速くできる

## noteとの違い

同じテーマをnoteとZennに出す場合、本文をそのまま使い回さない。

| 観点 | note | Zenn |
| --- | --- | --- |
| 主役 | 一次体験・背景・意思決定 | 技術設計・実装・検証 |
| 冒頭 | 問題 + 持ち帰り | 対象 + 結論 + 前提条件 |
| 本文 | 具体 → 失敗 → 学び | 課題 → 設計/実装 → 検証 → 判断 |
| 詳細 | 読みやすさ優先で圧縮 | 再現に必要な詳細を残す |
| 終盤 | 一般化・チェックリスト | 適用条件・Tips・次の検証 |
