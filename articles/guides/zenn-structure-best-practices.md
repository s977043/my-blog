# Zenn記事の構成ベストプラクティス

Zenn向けの記事を、技術的に正確で、読者が理解・再現しやすく、将来も参照できるストック資産へ近づけるための実践ガイド。

2026-08-26時点のZenn公式ガイド、コミュニティガイドライン、Markdown仕様、Zenn上の技術記事の構成、およびこのリポジトリの実測運用をもとに整理した。

## Zennで最も重視すること

noteが一次体験・背景・意思決定の物語を主役にするのに対し、Zennでは**技術的な再現性と体系化**を主役にする。

読者が記事を読み終えたとき、少なくとも次のどれかができる状態を目指す。

- 同じ環境で再現できる
- なぜその設計を選ぶのか判断できる
- 同じ障害を切り分けられる
- 将来、逆引きリファレンスとして使える

Zenn公式コミュニティガイドラインでも、実体験や考察、具体的な試行錯誤、正確なタイトル、冒頭の概要、対象読者、環境や発生条件の明示が推奨されている。

## 最重要原則

### 1. 冒頭で「誰に・何が分かるか・どの条件か」を明示する

技術記事では、読者が自分の状況に適用できるかを早く判断できることが重要。

冒頭では必要に応じて次を示す。

- 対象読者
- 解決する問題 / 得られる知識
- 対象技術・バージョン・環境
- 記事で扱わない範囲

長文や専門性の高い記事では `:::message` を使って「想定読者 / 前提」を切り出してよい。

### 2. TL;DRで結論を先に出す

長文記事では、本文を全部読まなくても価値を判断できるようにする。

```text
前提・対象読者
↓
TL;DR
↓
全体像
↓
詳細
```

TL;DRは3〜5項目程度を目安にし、本文の見出しと対応させる。

短い記事や単一のトラブルシュートでは、独立したTL;DR章を作らず、導入1〜2段落で結論を出してよい。

### 3. 「結論」だけでなく再現条件を書く

技術記事の価値は結果だけではなく、**どの条件でその結果になったか**にある。

最低限、必要なものを選んで記載する。

- OS / ランタイム / ライブラリ / CLIのバージョン
- 対象リポジトリや構成の前提
- 入力条件
- 実行コマンド
- 期待結果
- 失敗時の症状
- 検証日

再現に不要な環境情報まで羅列しない。

### 4. 手順より「判断」を残す

AIで一般的な手順を取得しやすくなったため、コマンド一覧だけでは記事価値が弱い。

次を優先して残す。

- なぜその方法を選んだか
- 他に何を試したか
- 何が失敗したか
- どの条件で別案を選ぶべきか
- 実際に観測した結果

```text
課題
↓
仮説 / 選択肢
↓
実装・検証
↓
結果
↓
判断
```

という流れを基本候補にする。

### 5. 本筋と再現用詳細を分離する

長いコマンド、設定全文、ログ、PRテンプレートなどが本文を埋めると、設計意図が読みにくくなる。

- 本筋: なぜ / 何を / どの順で / 何が分かったか
- 詳細: コマンド全文 / 設定全文 / 長いログ / 補足

詳細は `:::details` に畳むことを検討する。

ただし、記事の核心となるコードや差分は畳まない。

## 記事タイプ別の構成

Zennでは `type: tech` と `type: idea` を意識し、記事タイプごとに骨格を変える。

### Tech: 実装・ハウツー

```text
対象読者 / 前提
TL;DR
全体像
環境・バージョン
実装手順
重要なコード / 設定
ハマりどころ
検証結果
判断・制約
まとめ / 次に試すこと
```

「手順だけ」ではなく、ハマりどころと判断基準まで残す。

### Tech: トラブルシュート

```text
症状
先に結論
発生条件
切り分け
原因
修正
確認方法
再発防止 / 適用範囲
```

検索流入を意識し、タイトルと冒頭に**製品名・症状・解決方向**を含める。

### Tech: 設計・アーキテクチャ

```text
解きたい問題
制約
TL;DR
全体構造
選択肢
採用した設計
トレードオフ
実装 / 運用
検証
適用できる条件 / できない条件
```

設計図だけでなく、なぜその責務分離・境界・状態遷移を選んだかを書く。

### Idea: 技術的な考察・提案

```text
問題提起
主張
前提 / 定義
根拠となる実体験・検証
反例・限界
一般化
読者が判断するときの観点
```

Ideaでも、抽象論だけで終わらず一次体験・コード・計測などの根拠を入れる。

## タイトル設計

タイトルは、一覧・検索結果で「自分の問題に関係するか」を判断できるようにする。

優先順位:

1. 対象技術・固有名詞
2. 問題または目的
3. 解決・発見

例:

- `Claude Codeで承認前の実装を止めるHook設計`
- `Next.jsでServer Actionsの型エラーを再現・切り分ける`
- `DESIGN.mdをAIエージェント向けの設計入口にする`

避ける:

- 内容が分からない抽象タイトル
- `〜してみた` だけで結果が分からないもの
- 本文で検証していない効果の断定
- SEO語を詰め込みすぎて意味が崩れたタイトル

このリポジトリでは、SEO主導型の記事では「具体製品名 + 問題語 + 解決示唆」を第一候補とする。媒体役割と実測方針は `docs/content-channel-strategy.md` を正本とする。

## 見出し設計

Zenn公式Markdownガイドは、アクセシビリティの観点から本文の見出しを `##` から始めることを推奨している。

見出しは目次として機能するため、見出しだけ読んでも論理が追えるようにする。

悪い例:

```text
## 概要
## 詳細
## その他
```

良い例:

```text
## 承認前に実装が始まる原因
## Hookで止める場所を決める
## 強制しすぎると別の問題が起きる
```

手順記事では番号付きでもよいが、単なる `Step 1` より目的が分かる副題を付ける。

## コード・コマンドの扱い

- コードブロックには言語指定を付ける
- コピペ可能な例を優先する
- 一部を省略した場合は明示する
- 実行結果が重要なら期待出力を示す
- 10行を大きく超える補助的な設定・ログは `:::details` を検討
- Before / Afterが重要なら並べて差を明確にする
- コード自体より設計判断が重要な記事では、コード量を増やしすぎない

## 表・メッセージ・detailsの使い分け

### `:::message`

使う候補:

- 想定読者
- 前提条件
- 重要な制約
- 読み飛ばすと誤解する注意

### `:::message alert`

使う候補:

- 破壊的操作
- セキュリティ上の注意
- 互換性・データ損失リスク

装飾目的で多用しない。

### `:::details`

使う候補:

- 長いログ
- 設定全文
- 補助的なテンプレート
- 一度確認すればよい詳細

### 表

使う候補:

- 複数案の比較
- バージョン差
- 責務分離
- 条件と挙動

3〜4列程度を目安にし、セルに長文を詰め込まない。

## 事実検証と一次情報

Zenn記事は公開前に、技術的な主張を一次情報と実測の両方から確認する。

- API / ライブラリ / CLI仕様 → 公式ドキュメント、README、CHANGELOG
- 自分の実装の挙動 → 実コード、テスト、ログ
- 数値 → 計測スクリプトを再実行
- 「存在しない」主張 → 検索範囲と観測限界を明示

観測できなかったものを0件と断定しない。

コマンドや数値を載せる場合、可能なら記事公開前に再実行する。

## AIを使って書く場合

Zennは生成AI利用自体を禁止していないが、公式コミュニティガイドラインは、正確性を確認しない投稿やスコア目的の乱造を避けるよう求めている。

記事には、一般知識の再構成だけでなく次のどれかを含める。

- 実際に試した結果
- 失敗・ハマりどころ
- 独自の比較
- 計測値
- 設計判断
- 一次ソースとの照合

AIが生成した説明は、技術的主張の根拠として扱わない。

## 記事終盤の設計

Zennでは、読後に次の行動へ移れる状態を作る。

候補:

- 実践Tips
- 最小導入手順
- 判断基準
- 制約・適用範囲
- 次に検証すること
- 関連記事
- 公式ドキュメント / GitHubリポジトリ

まとめは本文の再掲だけにせず、「どの条件ならこの方法を採用すべきか」まで残す。

## 公開前の構成チェック

### P1

- タイトルから対象技術・問題・目的が分からない
- 冒頭で対象読者・得られること・前提が分からない
- 再現条件が不足している
- 技術的な主張が一次情報または実測で裏付けられていない
- コード / コマンドが実行可能か未確認

### P2

- TL;DRや全体像がなく、長文を最初から読まないと価値が分からない
- 手順だけで、失敗・理由・判断基準がない
- 長い補足が本筋を埋めている
- 見出しだけでは論理を追えない
- 適用範囲・制約が書かれていない

### P3

- `:::message` / `:::details` / 表で読みやすくできる
- 関連記事への導線を追加できる
- topicsやemojiを改善できる
- 図を加えると構造理解が速くなる

## noteとの違い

同じテーマをnoteとZennに出す場合、本文を使い回さない。

| 観点 | note | Zenn |
| --- | --- | --- |
| 主役 | 一次体験・背景・意思決定 | 技術設計・実装・検証 |
| 冒頭 | 問題 + 持ち帰り | 対象 + 結論 + 前提条件 |
| 本文 | 具体 → 失敗 → 学び | 課題 → 設計/実装 → 検証 → 判断 |
| 詳細 | 読みやすさ優先で圧縮 | 再現に必要な詳細を残す |
| 終盤 | 一般化・チェックリスト | 適用条件・Tips・次の検証 |

媒体の役割定義そのものは `docs/content-channel-strategy.md` を正本とする。
