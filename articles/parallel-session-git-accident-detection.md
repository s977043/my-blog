この記事で得られること

- `git worktree` による事前分離が「隔離しないもの」の具体例
- 同一ワーキングツリーで実際に起きた Git 事故の型と、そのときの実測ログ
- GitHub の PR diff が実害を隠す条件と、3点比較で見る方法
- 検知スクリプトが誤検知で信用を失い、判定軸ごと作り直した経緯
- ガードに入れなかったもの（承認ゲートを壊さないための線引き）

前提は個人の記事公開リポジトリ（Zenn / Qiita / note）で、Claude Code を複数セッション並列で動かしている環境。すべて自分のリポジトリでの実測で、一般化した統計ではない。
:::

## 出発点：隔離したはずのワークフローが、別の場所で成果物を作っていた

2026-09-05、note 記事のレビュー改善ワークフロー（5ループ）を、PR ブランチの worktree で起動した。worktree を切ったのは「並列で別 PR も触るから、入力ファイルが差し替わらないようにする」ためだった。

ワークフローは正常終了した。全エージェントが成功、異常なし。

にもかかわらず、成果物は 2 箇所に分裂していた。実行中に私（オーガナイザー側のセッション）が別 PR の作業のために作業ディレクトリを worktree → 別 worktree → main の checkout と移した結果、**後半ループのエージェントが相対パスを main checkout 基準で解決**し、そこに記事のコピーを untracked ファイルとして作って編集を続けていた。worktree 側は途中ループ止まり、main checkout 側が最終版。最終検証を担当したエージェントが見ていたのは後者だった。

ここで効いたのは、worktree が防いでくれなかったという事実そのものよりも、**完了報告に一切現れなかった**という点だ。返り値は全部グリーンだった。

事前分離は「他人が私のツリーを動かす」ことは防ぐ。しかし「私が自分の cwd を動かす」ことは貫通する。そして貫通したとき、報告は正常に見える。

これが、事前分離だけに寄りかかるのをやめて、**事後検知**を足すことにした直接のきっかけになった。

なお、この結論に至る評価軸そのもの（Isolation を A〜F で採点する話）は [AIに開発フローを採点させたら、採点基準のほうが壊れていた](/articles/loop-maturity-rubric-audit) で扱っている。本記事はその採点で自分のパイプラインが **C**（物理分離は無いが、事故を検知するガードがあり作業を止められる）に落ちた、その「C の中身」を書く。ルーブリックの説明は繰り返さない。

## 同一ツリーで実際に起きた事故の型

観測できたのは大きく 3 型ある。時系列で見ると、**検知できるタイミングが後ろにずれていく**のが特徴だった。

```text
型1  ブランチ切替       … commit する前に気づける
型2  commit の他ブランチ着地 … push して PR に乗るまで気づけない
型3  stale base での巻き戻しマージ … main に入るまで気づけない
```

### 型1：意図しないブランチ切替

単一セッション内で意図外のブランチ切替が **3 回**発生し、いずれも `stash` → `switch` → `pop` の手順で **3/3 復旧**した（Round 3 の観測ログ）。害は出ていない。`git branch --show-current` を打てば気づけるので、口頭のチェックリストで一応回る範囲だった。

### 型2：commit が他人のブランチに着地する

`git switch -c <new>` で main から新ブランチを切ったつもりが、並列セッションが先に作成・push 済みの別ブランチに切り替わっていた。結果、私の commit がそのブランチと、そこに紐づく既存 PR に積まれた。

このときは実害が無かった（両者とも公開を発火しない独立変更だった）ので、PR の説明文を「2 変更を含む」に書き換えてまとめてマージした。ただし型1と違い、**commit した後、しかも push されて PR に乗るまで検知できていない**。

### 型3：長時間処理の入力が実行中に差し替わる

2026-09-03、3ループ・18エージェント・約 45 分のレビューワークフローの実行中に、並列セッションがワーキングツリーを `main` に切り替えた。ワークフローは切り替わった先の**古い記事（282 行・再構成前）を編集し続け**、319 行の成果物を作って正常終了した。

返り値は `abortedForDrift=false` / `finalPassed=true` / `unresolvedImportant=0`。全部成功を示していた。成果物は前提が違うので丸ごと破棄した。**45 分と約 130 万トークン**を失っている。

検知できたのは「再構成で入れたはずの語句が本文に 0 件」という中身の実測だった。返り値からは分からない。

冒頭の cwd 分裂（2026-09-05）は、この型3のドリフト源が「並列セッション」から「自分自身」に変わったバリエーションにあたる。

## GitHub の PR diff は実害を隠す

事故として一番高くついたのは、上のどれでもなく**マージの巻き戻し**だった。

記事 1 本を PR #401〜#403 で段階的に磨き込んだ直後、並列セッションが作った PR #404 がマージされた。#404 の base は #401 のマージ前の古い main だった。

```console
$ gh pr view 404 --json state,additions,deletions,mergeCommit
{"additions":242,"deletions":122,"mergeCommit":{"oid":"0f29cb7..."},"state":"MERGED"}
```

**+242 / -122**。GitHub 上ではごく普通の改善 PR に見える。実際にはこれで #402・#403 が足した分が消えた。

数えてみる。#402 と #403 のマージコミットが記事ファイルに追加した行は、重複を除いて 13 行だった。

```bash
export LC_ALL=C
F=articles/ai-review-rate-limit-fallback.md
{ git diff a7f13b5^ a7f13b5 -- $F; git diff 0b3501a^ 0b3501a -- $F; } \
  | grep '^+[^+]' | sed 's/^+//' | sort -u > /tmp/added13.txt
wc -l < /tmp/added13.txt          # => 13

git show 0f29cb7:$F | sort -u > /tmp/m404.txt
comm -12 /tmp/added13.txt /tmp/m404.txt | wc -l   # => 0
```

**13 行のうち 13 行が、#404 マージ後の版から消えていた。**

さらに現在の main で同じことをすると、

```bash
git show origin/main:$F | sort -u > /tmp/mnow.txt
comm -12 /tmp/added13.txt /tmp/mnow.txt | wc -l   # => 0
```

**0/13。今も復元されていない。** 上書き合戦を避けて後発側を正とし、不足分だけを非破壊的に足す形で収束させたので、消えた 13 行そのものは戻していない。「事故は復旧した」とは書けない。

### 見かけの diff と実害の関係

同じ系列でもう 1 本、PR #405 があった。こちらは「#404 で消えた版の上に図を足した」PR で、GitHub 上の diff は **+14 / -0**。追加しかしていないように見える。

しかし base が古い版なので、現在の main に対しては記事全体を巻き戻す変更だった。#405 は 3点比較で気づいて **CLOSED にした**（マージしていない）。差を図にするとこうなる。

```text
                 A ── B ── C ── D   (現在の main。C, D で磨き込み)
                 │
                 └── E             (PR #405 の head。base は A)

GitHub が見せる diff :  A ... E        →  「+14 / -0」
実際に main に入る差分:  D ... (merge)  →  C, D の内容が消える
```

`gh pr` 上の diff は **head の base に対する差分**なので、base が現 main からズレていると実害が見えない。見るべきは 3点比較のほうだ。

```bash
git fetch origin main <branch>
git diff origin/main...origin/<branch> --stat
```

## 事前分離ではなく、事後検知に寄せる

型2・型3・巻き戻しに共通するのは、**事前に禁止しても防げず、事後に測れば分かる**という性質だった。だからガードは「起きたことを測って止める」側に置いた。

マージ前チェックは `scripts/check-pr-staleness.sh` にまとめてある。

```bash
npm run check:pr-staleness -- <PR番号またはブランチ名>
```

やっていることは 3 つ。

1. `gh pr view` で state を見る（並列セッションが先にマージ済みなら何もしない）
2. `git fetch` して 3点比較を取る
3. **マージのシミュレーション**をして、「マージすると main から消える行」を数える

3 番目が本体だ。PR の diff ではなく、マージ結果と現 main を比べる。exit 1 が返ったらマージを中止する。

## 検知系は誤検知で死ぬ

初版はこの「消える行」をそのまま巻き戻し判定に使っていた。結果、**1 日で 4 件の STALE 誤検知**を出した（#459 / #456 / #444 / #462）。いずれも「その PR が意図して削除・改稿した行」を巻き戻しと判定していた。

原因は 2 つあった。

| 原因 | 内容 |
|---|---|
| lookback の和集合 | 「main が直近追加した行」を merge-base 以降＋直近 commits の和集合で定義したため、merge-base より前に main へ入った行（＝PR のベースに元からあり、PR が意図的に消した行）まで巻き戻し候補に数えていた |
| macOS の collation | UTF-8 ロケール下で `comm -12` が無関係な日本語行を一致と誤判定した（交差ゼロのはずが 3 行一致） |

1 日 4 件は、検知系としては死んでいる。人間はその時点で結果を読まなくなる。

PR #464 で判定軸そのものを差し替えた。

- 「消える行」ではなく **resurrection**（マージが、main の lookback 内で削除された古い行を復活させるか）を軸にする。意図的削除は CLEAN、#404 型の古い作業コピーによる上書きは STALE のまま
- `export LC_ALL=C` でバイト比較に固定する
- append-only な main への上書きは resurrection ゼロですり抜けてしまうので、消える行が閾値以上なら **STALE ではなく WARN（exit 0）** に落として目視へ誘導する

**STALE と WARN を分けたのが実質的な修正だった。** 「止める」と「見せる」を同じ出口にしていたのが誤検知を致命的にしていた。

判定を変える以上、検出力が落ちていないことは機械で担保する必要がある。回帰テストを付けた。

```console
$ bash scripts/test-check-pr-staleness.sh
...
PASS: case6 warn/exit0 (PR による main 既存行の意図的削除) (exit=0, 'WARN' を検出)
PASS: case7 stale (#404型 behind>0 でも巻き戻し検知) (exit=1, 'STALE' を検出)
PASS: case8 warn/exit0 (PR による main 既存行の意図的改稿) (exit=0, 'WARN' を検出)
PASS: case9 warn/exit0 (#404変種 append-only 巻き戻しをサイレント CLEAN にしない)
self-test: 全ケース PASS
```

**10 ケース、全 PASS。** case7 が「検出力を落としていない」側、case6 / case8 が「誤検知を再現させない」側にあたる。安全装置の判定を緩める変更では、この 2 方向を両方テストに残しておかないと、次に誰かが「誤検知が多いから閾値を上げる」で無力化できてしまう。

## ガードに入れなかったもの

後片付けも 1 コマンドにまとめた（`npm run cleanup:pr`）。`gh pr merge <n> --squash --delete-branch` は、そのブランチを worktree が掴んでいると必ず失敗する。

```text
failed to delete local branch ... used by worktree at ...
```

その後始末に `git worktree remove` → `git branch -D` → `git fetch --prune` → detach 復旧の 4 手を毎回打っていた。1 セッションで **6 回**発生したのを機にスクリプト化している（PR #610 の記録）。

初版はここに `gh pr merge` まで含めていた。敵対的レビューで潰された。

- Claude Code の Bash は**常に非 TTY** なので、「非 TTY なら拒否」は人間ゲートにならず `--yes` を強制する装置として働く
- PreToolUse ガードは `gh[[:space:]]+pr[[:space:]]+(create|merge|edit)` のコマンド文字列マッチなので、`npm run cleanup:pr` はすり抜ける
- 「自動マージ禁止」という規約は、`gh pr merge` を人が打つという**物理的な摩擦**に依存している

結局、マージ機能ごと外して後片付け専用にした。

```bash
npm run cleanup:pr -- 610 --pre-merge        # worktree を detach（任意）
gh pr merge 610 --squash --delete-branch     # ← 人間ゲートはここ。従来どおり手で打つ
npm run cleanup:pr -- 610 --remove-worktree  # ブランチ削除 / prune / worktree 削除
```

**便利にする方向と、承認ゲートを維持する方向がぶつかったときは、ゲートを優先する。** 「1 コマンドにまとめる」は、承認の摩擦まで一緒にまとめてしまうことがある。

こちらも hermetic な回帰テストを持たせた。

```console
$ bash scripts/test-cleanup-pr-worktree.sh
...
PASS: case15 空白入りパスでも既定コマンドを実行できる (exit=0)
[test-cleanup-pr-worktree] all cases passed
```

**19 ケース・59 アサーション、全 PASS。** 実 API を叩かないので CI に載せられる。

## commit / push の水際は Git hook に置いた

マージ前より手前、commit と push の時点で機械的に止められるものは hook にした。`git config core.hooksPath scripts/hooks` を有効にすると発火する。

| hook | 内容 |
|---|---|
| pre-commit | main への直 commit を **BLOCK** |
| pre-commit | qiita-cli 専用キャッシュ `Qiita/public/.remote/` の混入を **BLOCK** |
| pre-commit | `AGENTS.md` への記憶コンテキストブロック混入を **BLOCK** |
| pre-commit | `git mv` + 内容編集の同一 commit（0-insertion リネーム取りこぼし）を **WARN** |
| pre-push | `gh` の active account が期待値でない状態の push を **BLOCK** |

**BLOCK 3 件、WARN 1 件、push 側 1 件。** 型1・型2（ブランチ違い・混入）のうち、明確に「常に間違い」と言えるものだけを BLOCK に置き、判断が要るものは WARN に落としている。判定を分ける発想は staleness チェッカーと同じで、誤検知したときに全体が無視されるのを避けるためだ。

ただし、これらが実際に何件の事故を止めたかの統計は取れていない。「hooks があるから事故が防げている」とは書けない状態にある。

## 現状の限界

現時点で分かっている穴を並べておく。

**1. staleness チェックは `npm run check` に入っていない。**
集約ランナーが回すのは 20 チェックで、`check:pr-staleness` はその中にいない。マージ対象の PR 番号を引数に取る性質上、集約に混ぜられていない。つまり**マージ前に人（またはエージェント）が思い出して手で打つ必要がある**。忘れたら発火しない。事故の直接原因だった #404 型を止める仕組みが、いまだ人間の記憶に依存している。

**2. hook は `core.hooksPath` の設定が前提。**
clone 直後は発火しない。`--no-verify` で明示的にバイパスもできる。「リポジトリに hook が存在する」ことと「その clone で有効になっている」ことは別だ。

**3. pre-push は fail-open。**
アカウント検査スクリプトが見つからなければ `exit 0` で素通りする（CI などスクリプト非配置の環境を想定した設計）。安全側に倒していない箇所として自覚しておく必要がある。

**4. 検知は事後である。**
staleness チェッカーが実際に事故を止めた記録は、まだ確認できていない。実装（#448 / #464）はいずれも事故の**後**に入ったものだ。「効いている」と主張できる材料は今のところ回帰テストの PASS 数しかない。

## まとめ

- **worktree は「他人が私のツリーを動かす」ことは防ぐが、「私が自分の cwd を動かす」ことは貫通する。** そして貫通したとき、エージェントの完了報告は全部グリーンで返ってくる
- **GitHub の PR diff は head の base に対する差分**なので、base が現 main からズレていると実害を隠す。`git diff origin/main...origin/<branch>` の 3点比較で「現 main に対して実際に入る差分」を見る
- **検知系は誤検知で死ぬ。** 1 日 4 件の誤検知を出した時点で人間は読まなくなる。「止める（STALE / BLOCK）」と「見せる（WARN）」の出口を分けるのが実質的な修正だった
- **判定軸を緩める変更には、検出力側の回帰テストを必ず残す。** 残さないと、次の誤検知が「閾値を上げる」で無力化される
- **便利さと承認ゲートがぶつかったらゲートを優先する。** 非 TTY 環境では「対話確認」は人間ゲートとして機能しない

ここに書いたのはすべて、自分の 1 リポジトリでの観測にすぎない。それでも「事前分離を厚くする」より「事後に測って止める」に投資したほうが、実際に起きた事故には効いていた、というのが現時点の判断になる。
