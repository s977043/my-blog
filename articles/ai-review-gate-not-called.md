**この記事で得られること**

- 品質ゲートは「効くかどうか」の前に「呼ばれるかどうか」を測る必要がある、という視点
- ゲートが起動・記録・検証・採否の各工程で、それぞれ別の理由で漏れること
- 強制しない品質活動を続けるための「採否は自由、記録は必須」という形

**想定読者**: AIコーディングエージェントを日常運用し、レビューや検査の仕組みを自分で組んでいる人
**この記事の規模**: 2026-07-17〜08-18 の約1か月。記事8本を変更し、レビューの実行記録が残ったのは2本。findings は現存6件（別に3件が記録工程の失敗で失われています）。この規模で一般化するのは「ゲートを測る」という発想の1点に限ります
**この記事が扱うもの**: リリースを止めるゲートではなく、公開を止めない「観測用のゲート」です。AI生成の判定器でも品質保証器でもなく、34パターンによるヒューリスティックな検出にすぎません
:::

## はじめに：設計は動いた。ただ、ほとんど呼ばれていなかった

AIに技術記事を書かせると、独特の定型感が残ります。同じ接続詞が段落頭に並ぶ。文末が揃う。根拠のないまま「重要です」で締める。

この「AIっぽさ」を消すツールは既にいくつもあります。私が避けたかったのは、その中でも本文を自動で書き換えるタイプでした。技術記事でそれをやると、主張・数値・コード・引用が一緒に書き換わる可能性があります。文体を直したいだけなのに、事実が動く。

そこで、**検出だけして書き換えないレビュー**を作りました。2026年7月17日のことです。

設計自体は動きました。根拠の薄い数値を1件、私に差し戻してくれました。

そして1か月後、数えてみました。

**この間に8本の記事を書き直し、そのうちレビューの実行記録が残っていたのは2本でした。**

効果があったかどうかを議論する以前の話です。私は、このゲートが何回呼ばれたのかを一度も数えていませんでした。

この記事は、その記録です。

## 検出と修正を分離する — review-only を指示ではなく権限で縛る

まず、何を作ったのかを簡単に共有します。この記事の主題は設計ではなく運用なので、要点だけにします。

出発点の仮説は「**文体の改善は、主張の改変と地続きになる**」でした。「この段落は冗長です」という指摘に従って書き直すと、削られた部分に主張が含まれていることがあります。だから、指摘と修正を構造的に分離することにしました。

具体的には3つです。

**1. 保護リスト**

Front Matter、コードブロック、URL、引用、数値・日付・バージョン、製品名やAPI名、そして**記事の主張**と筆者の実体験。これらは指摘の対象にしません。文体上の問題が保護領域を含む文にある場合も、保護要素そのものは変えず、周辺の文だけを対象にします。

**2. リスク昇格**

保護領域に触れる可能性がある指摘は、内容にかかわらず `high` へ引き上げます。「この数値の根拠が薄い」という指摘は、たとえ表現の問題として出てきても、数値に触れる以上は `high` です。`high` は自動修正の対象外で、著者の判断に戻します。

**3. 権限による強制**

そして、これが一番効いていると考えている部分です。

```yaml
allowed-tools:
  - Read
  - Grep
  - Glob
```

このレビューを実行するスキルには、`Edit` も `Write` も渡していません。「本文を書き換えないでください」という指示ではなく、**書き換える手段を持たせない**という形にしました。

> 指示は破られますが、権限は破れません。

ただし、この言い方はそのままでは強すぎます。成立するのは、`allowed-tools` が実行ホストによって実際に強制される場合に限られます。

現在の設定が崩れていないか（`Edit` / `Write` / `Bash` が混入していないか）は、静的チェックで機械的に検証しています。

```bash
npm run check:article-humanizer   # 現行の設定を検査する
npm run test:article-humanizer    # 検査器そのものの自己テスト（フィクスチャで検証）
```

検証しているのは設定が壊れていないことであって、実行時に権限が本当に効いていることではありません。

さらに、正直に書いておくべき非対称があります。単独でスキルを実行するときは書き込み権限を渡していませんが、レビュー全体を回すワークフローの側は、スキルの定義を読むだけで権限スコープを明示的に渡してはいません。そちらの工程は自然言語の禁止文で守っています。**同じ仕組みの中に「権限で守っている領域」と「言葉で守っている領域」が併存していて、後者は未検証です。**

この非対称は、後で効いてきます。

## 止めるか、止めないかで考えていた

もう一つ、当時決めたことがあります。

**このレビューで `high` の指摘が出ても、記事の公開はブロックしない。**

理由は明確でした。ブロックすると、AIの文体判定が人間の主張を却下する構造になります。「この段落は根拠が薄い」という判定で公開が止まるなら、それは文体レビューではなく検閲です。主張を守るために作った仕組みが、主張を却下する側に回るのは本末転倒です。

この判断自体は、今でも正しかったと考えています。

ただし、**私は「止めるか、止めないか」の二択で考えていました。そこが誤りでした。**

第三の形があります。

> **採否は自由。ただし、記録は必須。**

指摘を受け入れるかどうかは著者が決める。しかし「確認した」という事実だけは残す。ブロックはしないが、素通りもできない。

このときの私は、この形に気づいていませんでした。

## 1か月後に数えたら、8本中2本だった

2026年8月、ゲートの導入から1か月が経ったので、状況を確認しました。

計測範囲は **2026-07-17（ゲート導入日）から 2026-08-18 まで**、この記事のドラフト自身は母集団に含めません。

まず、この期間に変更した記事の本数です。

```bash
git log --since=2026-07-17 --until=2026-08-19 --name-only --pretty=format: -- articles/ \
  | grep -v '^$' | sort -u
```

8本ありました。新規執筆も、既存記事の改稿も含みます。

次に、レビューの実行記録が残っている記事です。このレビューは成果物をファイルとして残すので、そのディレクトリを見れば分かります。

```bash
git log --since=2026-07-17 --until=2026-08-19 --name-only --pretty=format: -- reviews/zenn/ \
  | grep -v '^$' | sort -u
```

**2本でした。**

ここで数えているのは「通過した本数」ではありません。記録が残った本数です。2本のうち1本は `passed: false`（`high` の指摘が1件出た状態）で、修正して解消しています。合格したかどうかとは別の話です。

記録カバレッジ25%。8本のうち6本は、ゲートを通した形跡がないまま公開・更新されています。

弁解として「忙しくて回せなかった」と言いたくなりますが、後で見るとおり、データがそれを否定します。

ここで言えることと、言えないことを分けておきます。

- **言えること**: このゲートは呼ばれていなかった（母集団8本に対する実測）
- **言えないこと**: このゲートに効果があるかどうか（記録2本では判定できません）

効果を測る以前に、呼ばれた回数を測っていませんでした。

## ゲートは工程ごとに別々に漏れる

数え始めると、漏れは「呼ばれない」だけではありませんでした。しかも、それぞれ原因が違います。

ゲートを一続きの工程として並べ、各工程で数が何本まで残るかを見ると、こうなります。

| 工程 | 数えるもの | 実際 |
|---|---|---|
| 1. 対象になる | 変更した記事 | 8本 |
| 2. 起動する | レビューを実行した記事 | 2本 |
| 3. 結果を受け取る | 結果が返ってきた記事 | 2本 |
| 4. 記録が残る | 構造化された結果が保存された記事 | 0本 |
| 5. 形式を検証する | 識別子がレジストリと一致しているか検査した記事 | 0本 |
| 6. 採否を記録する | 指摘を採用/不採用と判断した記録 | 0件 |

工程2で8本が2本に落ち、工程4以降はゼロです。結果は返ってきているのに、後段が丸ごと存在しない。

工程2の内訳には、単純な「やらなかった」以外のものが含まれます。6本のうち1本は、3周のレビューを回しながらこの工程だけを飛ばしていました。ゲートがワークフローの外側にあり、他のレビューを回すことと手順として繋がっていないため、迂回できてしまう。「忙しくて回せなかった」ではなく、「回す導線に乗っていなかった」です。

工程3から先を見ていきます。

### 工程4が落ちる：記録が残らない

2回目の実行で、レビュー結果をファイルに書き出す工程がモデルの利用上限に達して失敗しました。結果自体は返ってきていたので、成果物は手で作り直しました。

このとき「実行は失敗したが結果は手元にある」と処理してしまい、事故として扱いませんでした。しかしこれは、その回の生データが失われたということです。後から検証しようとしても、手で書き直したものしか残っていない。

損失は具体的に測れます。**現在のリポジトリから追える findings は6件です。** 実行は3回あり、通算では9件出ていましたが、最初の回の3件は再生成のときに上書きされ、いまは Git の履歴を掘らないと出てきません。

この記事を書きながら、私はここで一度つまずきました。当初の草稿には「累計9件」と書いていたのですが、それは**失われたはずのデータを確定値として使っている**ことになります。読者が現在のリポジトリを確認しても6件しか見つかりません。以降は現存6件を基準に書きます。

### 工程5が落ちる：識別子が集計キーにならない

検出パターンには `F01`〜`F05`（書式）、`S01`〜`S14`（語彙・文体）、`T01`〜`T15`（論証構造）という識別子を定義してあります。合計34個です。

記録された識別子を並べると、こうなっていました（かっこ内は現存か、履歴のみか）。

- `T04` / `F05` / `S08` — 定義どおりの識別子（現存）
- `S12-recurring-importance-closer` / `S10-list-intro-template` — 識別子＋自由文のスラッグ（現存）
- `S08-corrective-frame-density` / `F-table-header-empty-cell` — 同上、および連番すらない形（履歴のみ）

混在しています。当初、私はこれを「スキーマで列挙型を指定しなかったから、モデルが値を創作した」と解釈しました。実際、同じスキーマの中で `layer` と `risk` は列挙型で縛ってあり、そちらは一度も壊れていません。

しかし、それは正しい説明ではありませんでした。

スキル定義書の出力例を見ると、こう書いてあります。

```json
"pattern": "S01-repeated-connectors"
```

**識別子＋スラッグの複合形を、仕様書自身が例として教えていました。** 一方、正本のパターン表は裸の識別子です。仕様が自己矛盾していて、モデルは例のほうに従っていた。制約の欠如だけが原因ではありません。

そして、書式の混在よりも厄介な問題があります。**識別子は合っているのに、意味が違う**ケースです。

`S12` の定義は「意義づけの付け足し（事実の後に『示唆している』『浮き彫りにする』を反復する）」ですが、実際の指摘内容は「各章の締めが『重要です』で単調」でした。別のパターンです。識別子だけ見ていると気づきません。

さらに根が深いのは、**構造化された結果がどこにも永続化されていない**ことです。記録工程は、生のJSONをモデルに渡して「読みやすいMarkdownにしてください」と依頼する形になっています。決定論的にJSONを保存する経路がありません。仮に識別子へ制約を張って正しい値が返っても、この転記で潰れれば結果は同じです。

:::message
**一般化の限度について**

「制約を張らない列は必ず創作される」とは書けません。同じスキーマの `id` は列挙型ではなく正規表現 `^H-[0-9]{3}$` で縛られており、確認できる範囲では守られています。正しくは「**制約のない列は drift し得る**」であり、今回は仕様例の不整合という別要因も重なっています。統制された対照実験ではなく、自然観察です。
:::

### 工程6が落ちる：採否が記録されない

3回目の実行では、`low` の指摘が2件出ました。「章の締めの語彙が単調」「箇条書きの導入が同じ鋳型で反復」というものです。

その記事は既に公開されています。確認してみます。

```bash
grep -c "重要です\|重要になります" articles/ai-merge-ready-state-machine.md
# → 4
grep -c "たとえば、次の" articles/ai-merge-ready-state-machine.md
# → 3
```

指摘された表現が、そのまま残っています。

これ自体は設計どおりです。`low` は任意の推敲であり、ブロックしません。問題は、採用しなかったという判断がどこにも記録されていないことです。検討した上で見送ったのか、そもそも読んでいないのか、後から区別できません。

## なぜ1か月気づかなかったか

各工程の漏れは、原因がそれぞれ違います。呼び出しの導線がないこと、工程が分離していて迂回できること、モデルの利用上限、仕様書の自己矛盾、永続化の不在、採否責任の不在。ひとつの原因に還元できる話ではありません。

**そして、ここを取り違えないようにしたいのですが、「数えていなかったこと」はこれらの原因ではありません。** 回数を数えていれば導線が生えるわけでも、利用上限が消えるわけでもない。数えていなかったことが奪ったのは、これらの失敗に気づいて手を打つ機会です。

その意味で、共通していることが1つだけあります。

> **どの工程も、回数を数える仕組みを持っていませんでした。**

- 呼ばれた回数を数えていない → 採用率25%に気づかない
- 完走した回数を数えていない → 記録工程の失敗が事故にならない
- 記録の形式を検査していない → 識別子の drift が見えない
- 採否を数えていない → 指摘が無視され続けても誰も困らない

### 器は用意してあった

ここが自分でも意外だった点です。記録の場所は最初から用意してありました。

スキル定義書には「## 誤検知・過剰指摘」という記録欄が定義してあります。誤検知が出たらここに書いて、パターンの調整に使う想定でした。

その形式で書かれた成果物は、1本も存在しません。

理由を追うと、記録工程のプロンプトが検出結果しか要求しておらず、誤検知欄に何かを書けとは一言も指示していませんでした。器は用意したが、器へ流し込む配線がなかった。

置き場所があることと、情報が流れることは別です。私は前者をもって後者を確保したつもりになっていました。

### 空の器を機能させる最小条件

同じ構造は、ツールの外側でもよく見ます。

| 空の器 | 埋まらない理由 | 機能させる最小条件 |
|---|---|---|
| ふりかえりのアクション欄 | 実行しなくても次が回る | 次のふりかえりを、前回アクションの結果から始める |
| 品質レビューの記録欄（本記事） | 無視しても誰も困らない | 採否の記録だけを必須にする（中身は自由） |
| チェックリストの項目 | 判定根拠が人手で検証不能 | 判定を自動化するか、見る人を1人指名する |

共通するのは、器を機能させるのは置き場所ではないということです。**①誰が ②いつ ③何を見て ④どう判断するか**、この4点が決まって初めて器は埋まります。

### 経験主義の三本柱として見ると

この構造は、スクラムの経験主義（透明性・検査・適応）と同じ形をしています。透明性がなければ検査が成立せず、検査がなければ適応が無意味になる、という依存関係です。

ただし、ドミノのように順番に倒れたのではありません。検査と適応は一度機能してから壊れたのではなく、土台がないので最初から成立し得なかった。倒れた順番ではなく、積み上がらなかった順番です。

ひとつ限定を付けます。ここではスクラムを厳密に適用した話をしているのではなく、経験主義のレンズとして借りているだけです。この運用は設計者も実行者も記録者も私ひとりで、「作業する人にも受け取る人にも見えている」の両側を同じ人間が担っています。ガイドはこの2つが別人であることまでは求めていませんが、少なくとも私の場合、見えていなかったのは将来の自分と、検査の材料に対してでした。

チームであれば早く露見したかもしれない、とは書けます。ただしそれは推測です。可視化されていなければ、チームでも同じように見逃し得ます。人数は透明性の代わりにはなりません。

なお、「検出だけの段階が終わったら、低リスクの指摘は自動修正へ進める」という移行条件は、当初「誤検知したパターンを調整済みであること」と決めていました。しかし工程5のとおり、誤検知率を算出する手段が初日から存在しませんでした。

測る手段のない完了条件は、条件ではなく願望です。

## 採否は自由、記録は必須 — 次に変える6点

直す順番には主張があります。**透明性から直す。ただし、透明性だけ直しても同じことが起きます。**

見る場と判断基準がなければ、可視化された数値は新しい空の器になるだけです。だから検査と適応まで一続きで置きます。

**透明性**

1. **検出結果の生JSONを、ワークフローから直接ファイルへ書く**（モデルを経由しない）。工程4と工程5の共通原因なので、これが最優先です
2. **識別子に制約を張る。同時に、仕様書の出力例を裸の識別子へ直す**。例を直さないと、仕様に忠実な出力がスキーマで弾かれます。この依存関係を見落とすと、直したつもりで壊れます
3. **出力側を静的チェックで検証する**。現在のチェックはスキル定義（入力側）しか見ていません。ただし1が前提です

**検査**

4. **見る場を固定する。ただし分子と分母を同じイベントで定義する**。今回の分母は「変更した記事」なので、確認の単位も「公開ごと」ではなくレビュー対象になった記事変更ごとにします。公開単位にすると、下書きや公開済み記事の改稿を取り逃がし、母集団が最初の計測とずれます

**適応**

5. **閾値を、測る前に決める。同時に見直し条件も決める**。未知の誤検知率に固定値を置くだけでは恣意性は消えないので、初期閾値・分母（findings 数か記事数か）・判定者・見直し時期の4つを先に書き出します。「測ってから決める」と、都合のいい線を引きます

**設計**

6. **採否の記録を完了条件に入れる（採否の中身は問わない）**。前章の第三の道です。受け入れは強制せず、確認した事実だけを残す。これは止める仕組みではないので、「公開をブロックしない」という判断を1ミリも曲げません

   ただし、ここには穴があります。公開を止めないなら、記録しないまま公開することもできてしまう。「必須」と言い切るには、未記録のときの挙動が要ります。未記録は `unverified` として残し、次の確認の場に必ず持ち越す。そこまで決めて初めて「必須」で、決めなければ実態は「推奨」です

### 何を記録するか

ここまでの話はツール固有に見えるかもしれませんが、記録すべき項目はそうではありません。1回の実行につき、この程度が残っていれば足ります。

```json
{
  "target_revision": "対象の記事とそのリビジョン",
  "eligible_at": "レビュー対象になった時刻",
  "started_at": "起動した時刻（未起動なら null）",
  "result_received_at": "結果が返った時刻",
  "record_status": "persisted | failed | missing",
  "schema_valid": true,
  "decision": "accepted | skipped | deferred | unrecorded",
  "decision_reason": "そう判断した理由"
}
```

この形にすると、私が数えられなかったものが全部数えられます。`started_at` が null の件数は起動漏れ、`record_status` が `failed` の件数は完走漏れ、`schema_valid` が false の件数は識別子の drift、`decision` が `unrecorded` の件数は判断漏れです。

主張を「数えよう」から一段進めるなら、何を、どの失敗状態まで数えるかがここに当たります。

:::message alert
**チームに持ち込むときの注意**

これらの数字は、プロセスと成果物を検査するためのものであって、人を検査するためのものではありません。評価や査定に使った瞬間、数字は作られるようになります。透明性のために入れた仕組みが、透明性を壊します。
:::

## おわりに：終わっているのは検査までです

検出と修正を分離する設計は動きました。保護リストとリスク昇格は、根拠の薄い数値を1件、私に差し戻しました。ただし正確に言えば、**止めたのは仕組みで、直したのは人**です。そのまま無視して公開することもできました。

そして1か月後に数えたら、変更した8本のうち、記録が残っていたのは2本でした。ゲートは、起動・記録・検証・採否の各工程で、それぞれ別の理由で漏れていました。

ゲートを呼ばれなくした原因は複数あります。導線の不在、迂回できる構造、モデルの利用上限、仕様の自己矛盾、永続化の欠如。**回数を数えていなかったことは、その原因ではありません。それらの失敗を検知して手を打つ機会のほうを失わせました。**

強制しない品質活動が消えるのは、動機が足りないからではありません。呼ばれた回数を誰も数えていないので、消えたことに気づかないからです。

この記事の時点で終わっているのは、**検査までです**。適応——上に挙げた6点の実装と、閾値の設定——はこれからです。その結果は、数字とともに続報として出します。

うまくいかなかった過程を書いたこと自体を成果だと言い切ってしまうと、それこそ「器を用意して満足する」の再演になります。透明性は、次の観察がここに戻ってきて初めて成立します。
