Claude Code や Codex で長い作業を続けていると、どこかで迷います。

- このままの会話で続けるか、新しいセッションに切り替えるか
- 切り替えるなら、何を残しておけば続きを失わないか

切ると、積み上げた文脈が消えそうで怖くなります。切らないと、古い判断や失敗した試行を引きずります。どちらを選んでも不安が残ります。

この記事の結論を先に書きます。

> セッションを切り替えるかは使用率ではなく作業の区切りで判断し、会話の要約ではなく、フェーズが変わるたびに更新する正本から再開する。

ここでいう**正本**（source of truth）は、作業中から更新し続ける計画・状態・証跡のファイルのことです。セッションを閉じる直前に会話を要約して書く引き継ぎ書（handoff）とは、書くタイミングも役割も違います。

:::message
この記事の根拠は、筆者が作っている PlanGate（Claude Code / Codex 向けのプラグイン）の設計と、筆者の個人リポジトリに残っている記録です。区切りで切ることの効果を、使用率で切る場合と比べて計測したわけではありません。「こう設計している」「こういう記録がある」という範囲で読んでください。
:::

## 長い会話は重くなり、圧縮だけでは足りない

まず前提を短く確認します。

Claude Code の公式ドキュメントは、コンテキストが埋まるほど性能が落ちること、無関係なタスクの間では `/clear` で会話をリセットすることを勧めています。コンテキストが上限に近づくと自動で圧縮（compaction）が走りますが、そのとき会話は要約に置き換わります。プロジェクトルートの CLAUDE.md やプランモードで作った計画はディスクから読み直されますが、会話の中だけにあった判断は要約に残ったものしか残りません。

Anthropic のエンジニアリングブログも、長時間動くエージェントについて「compaction isn't sufficient」と書いています。新しいコンテキストで始めるエージェントには、進捗ファイルや git の履歴から状態を把握させています。入力が長くなるほど性能が落ちる現象や、長い文脈の中ほどの情報が使われにくい現象の研究もありますが、この記事では背景にとどめます。

つまり、どこかで会話を区切り、何かを残して次へ渡す必要があります。問題は「どこで区切るか」と「何を残すか」です。

## 紹介されている実践例：使用率で区切る、作業単位でリセットする

Claude Code のセッションの引き継ぎについては、いくつかの実践例が紹介されています。筆者が読んだ範囲では、区切り方に2つの系統がありました。

| 区切り方 | 紹介されている例 |
|---|---|
| 使用率を目安にする | コンテキストが7〜8割に達したら止め、引き継ぎ書を作って次のセッションに渡す |
| 作業単位でリセットする | タスクの区切りでセッションをリセットし、引き継ぎ書で決定事項や捨てた選択肢を渡す |

引き継ぎ書の作り方も一様ではありません。会話から自動で生成して次のセッションに注入するもの、Claude に書かせるもの、決定事項や捨てた選択肢まで項目を決めて書くものがあります。どれも、それぞれの状況でよく考えられたやり方です。

この記事で扱うのは、これらの実践例そのものではなく、次の型です。

> 会話を要約した一度きりの引き継ぎ書だけに、作業の状態を預ける運用

引き継ぎ書を使うこと自体は問題ではありません。後で書くように、正本を指す入口として使うのはむしろ便利です。気をつけたいのは、引き継ぎ書が状態の置き場として唯一のものになっているときです。

また、使用率を目安にすると、作業のまとまりとは関係なく区切りが来ます。テストを直している最中に7割を超えれば、その途中で切ることになるかもしれません。これは構造から来る懸念で、筆者が比較して確かめたものではありません。

## 残したものは古くなる：要約も正本も

筆者の個人リポジトリには、残したものが古くなった記録がいくつかあります。要約型（会話をまとめて一度書く引き継ぎ書）と正本型（作業中に更新し続けるファイル）に分けて並べます。

**要約型：引き継ぎ書が完了状態に更新されていなかった（2026-04）**

PlanGate の初期の運用では、タスクの完了時に `handoff.md` を1回発行していました。2026-04-24 のセッションの振り返りでは、この発行が後続のセッションでの一括対応になっていました。2026-04-26 には、`handoff.md` が完了状態に更新されておらず、受け入れ条件の一部が「実装中」のまま残っていて、後から修正しています。振り返りには「前回セッションでも同じ問題が観察されており、改善が定着していない」と書かれていました。

**要約型：引き継ぎメモの前提が3つとも外れていた（2026-09）**

2026-09-23 には、セッション間の引き継ぎメモに書いてあった前提3つが、すべて外れていました。「13件が判断待ち」と書かれていたうち12件は、13日前にすでに閉じられていました。「A より先に B を閉じてはいけない」という制約は、向きが逆でした。

**正本型：最初に読む索引が、1セッションで3回古くなった（2026-07）**

正本も古くなります。PlanGate では、セッションの開始時に最初に読む索引ファイル（`INDEX.md`）を置いています。2026-07-31 に起票した issue #945 では、この索引が同じセッションの中で3回、実態とずれたことを記録しています。

| 時点 | 索引に書かれていたこと | 実態 |
|---|---|---|
| 計画の承認後 | 承認待ち | 承認済み |
| 計画の再編集後 | 承認は有効 | 再編集で再承認が必要になっていた |
| 実行の完了後 | 検証は PASS | 条件付き PASS（WARN） |

issue には、このままでは「次セッションが誤った地点から再開する」と書かれています。索引の更新規定が生成時のものしか無かったことが原因で、フェーズが変わるたびに更新する規定を足して閉じました。

ここから言えるのは、**要約も正本も、書いた時点から古くなり始める**ということです。正本にしておけば古くならない、というわけではありません。違いは、正本は「作業の途中で更新する」ことを前提に置ける点です。

## 区切りの2種類：必ず切る区切りと、判断材料にする区切り

では、どこで区切るか。PlanGate の Context Lifecycle では、区切りを2種類に分けて定めています。

- **必須の区切り**: 担当が変わるときなど、会話を持ち越すこと自体が不自然な場面。PlanGate のスキルでは、standard 以上の規模のタスクで切ると定めています
- **推奨の区切り**: 切ると役に立つことが多いが、状況で判断する場面

判断表にするとこうなります。

| 区切り | 扱い | 理由 |
|---|---|---|
| 担当の交代（別のワーカー・エージェント・モデル・実行環境へ） | 必須 | 前の担当の会話を渡しても、次の担当はそれを前提に動けない。ファイルで渡す |
| 独立レビューの開始 | 必須 | レビュアーは実装側の会話ではなく、成果物・差分・証跡から読む |
| 担当間の引き継ぎ（実装からレビューへ、ワーカー間） | 必須 | 同上。引き継ぐのは会話ではなく状態 |
| 外部待ち・使用量上限による意図的な中断 | 必須 | 再開までに状況が動く。戻ったときに正本から読み直す |
| 圧縮やコンテキスト逼迫が近いとき | 推奨 | 圧縮の要約に判断を預ける前に、正本へ書き出しておく |
| フェーズ遷移で、必要な作業セットが変わるとき | 推奨 | 計画から実装へ移るときなど、前のフェーズの議論が不要になる |
| 修理・レビューのループで古い議論が溜まったとき | 推奨 | 却下された案や古い判断が、次の判断を引っ張る |
| 不要な探索が溜まったとき | 推奨 | 調べたが使わなかった情報が場所を取る |
| 同じ問題の途中で、前進しているとき | 切らない | 会話に残っている推論の流れに価値がある |
| 簡単なタスク | 切らない（任意） | 区切りの手続きが作業より重くなる |

使用率は主な基準にしません。ただ、信頼できる使用量が取れるなら、補助情報として判断に使ってかまいません。PlanGate でも、ツールに依存しないトークンの閾値は推測で作らず、使用量が確かなときだけ補助に使う扱いにしています。

推奨の区切りの例を1つ挙げます。2026-08-12 に起票した issue #1061 では、サブエージェントへ作業を委託するとき、オーケストレーター役の AI が、直前に自分で書いた事実を委託文から落としました。受け取ったワーカーは、その事実を知らないまま600秒進まずに止まっています。同じセッションの AI とのやり取りは約29往復でした。

記録には、脱落の原因は書かれていません。筆者は、長いセッションで判断や事実が積み重なっていたことが一因だと考えていますが、特定はできていません。

必須の区切りについては、独立レビューの記録があります。2026-09-24、Context Lifecycle を入れた PR #1411 の独立レビューは、レビュー対象のコミットを指定して始め、重大な指摘は0件、軽微な指摘が2件でした。マージ後の 2026-09-29 に行った別の敵対的レビューでは、重大2件・軽微2件の指摘が出ています。新しいコンテキストでレビューしたことと、レビューの質の関係は、この記録からは言えません。

ここまでが PlanGate の設計の事実です。区切りを目安にすると迷いが減る、作業の途中で切れる事故が減る、という効果は仮説で、計測はしていません。

## 正本はいつ古くなり、いつ更新するか

ファイルを正本にして再開する考え方そのものは、[アジャイルでAI駆動開発をどう回すか: PlanGateの考え方とテンプレート](/articles/plangate-ai-coding-workflow)で書きました。ここでは、その正本を「いつ更新するか」と「どの順に読むか」に絞ります。

### 更新するのは、フェーズが変わるたび

前の章の索引の例では、正本が古くなったのは次の3つのタイミングでした。

- 計画が承認されたとき
- 計画を再編集したとき
- 実行が終わったとき

どれもフェーズが変わる瞬間です。フェーズが変わると、正本に書いてある「今どこにいるか」が一斉に古くなります。だから、セッションを切るかどうかとは関係なく、**フェーズが変わるたびに正本を更新する**ことを要件にします。

切る前にも、正本を更新してから切ります。PlanGate では、切る前に次の順で書き出します。

1. 最終的な判断を、計画や判断記録へ書く（会話にだけ残さない）
2. 入口の索引と現在の状態を、実態に合わせて更新する
3. テストやレビューの結果は証跡の置き場へ保存し、索引には参照と要約だけを書く
4. 担当が変わるなら、会話ではなくファイルで渡す

### 読む順は、入口の索引 → 現在の状態 → 必要なときだけ詳細

新しいセッションでは、前の会話を貼り付けずに、次の順で読みます。

1. **入口の索引**: どのタスクの、どのフェーズにいるか
2. **現在の状態**: 何が終わり、何が途中で、次に何をするか
3. **必要なときだけ詳細**: 証跡・判断記録・過去の経緯は、具体的な問いがあるときだけ読む

最初から全部を読まないのがポイントです。目的は「コンテキストを小さくすること」ではなく、「最小で十分な、今の状態を読むこと」です。

### 切る前のひな形（2項目）

状態の書き方そのものは既存のテンプレートに任せて、切る前に確認する項目だけを2つに絞ります。

```markdown
## このフェーズで更新したもの
- 計画 / 判断記録: （更新した・変更なし）
- 入口の索引 / 現在の状態: （更新した）
- 証跡: （保存先へのリンク）

## 持ち越さないもの
- 却下した案（理由は判断記録に書いた）
- 調べたが使わなかった情報
- 生のツール出力（結果は証跡に保存済み）
```

「持ち越さないもの」をわざわざ書くのは、次のセッションに渡したくないものを意識するためです。PlanGate でも、隠れた思考過程、会話のログそのもの、証跡で代わりが利く生のツール出力、秘密情報は持ち越さないと決めています。

### PlanGate を使わない場合の最小手順

PlanGate を入れていなくても、同じことはできます。

1. リポジトリに作業状態のファイルを1つ置く（例: `docs/current-state.md`）。書くのは「今のフェーズ」「終わったこと」「次の一手」「未解決のこと」
2. フェーズが変わるたびに、そのファイルを更新する。切るときも、先に更新してから切る
3. 新しいセッションの最初に「まず `docs/current-state.md` を読み、今のフェーズと次の一手を宣言してから始めて」と伝える

引き継ぎ書を書く習慣がすでにあるなら、やめる必要はありません。引き継ぎ書には状態を書き写さず、「正本はここ」と指す入口として使うと、引き継ぎ書と正本の食い違いが起きにくくなります。

## 同じ問題の途中では切らない

ここまで読むと「こまめに切ればいい」と受け取られるかもしれませんが、そうではありません。

OpenAI の Codex のベストプラクティスには、同じ問題を扱っているなら同じチャットで続けるほうが推論の流れを保てて良いことが多く、作業が本当に分岐したときだけ fork する、と書かれています。Claude Code のベストプラクティスにも、複雑な1つの問題に深く取り組んでいて履歴に価値があるときは、文脈を積み上げるべき時もある、とあります。

筆者もこれに同意します。前進しているなら、そのまま続けます。

一方で、Claude Code の公式ドキュメントは、同じ問題で2回を超えて修正を繰り返したら `/clear` し、学んだことを入れたプロンプトで始め直すことを勧めています。失敗した試行が会話に溜まっているからです。この案内は Claude Code のものなので、他のツールや、あらゆる作業にそのまま当てはめるものではありません。

分けるとこうなります。

- 同じ問題で前進している → 続ける
- 同じ修正を繰り返している → Claude Code の案内に沿って、切って始め直す

切らずに正本を読み直す、という使い方もあります。OpenAI のブログで紹介されている長時間タスクの例では、仕様・計画・制約・状況を markdown に書き、Codex に繰り返し読み直させていました。計画のファイルは、マイルストーンごとの正本として扱われています。区切りで切ることと、正本を読み直すことは、どちらか一方ではなく併用できます。

簡単なタスクには、ここまでの手続きを課しません。PlanGate でも、小さなタスクでは必須の区切りも任意にしています。区切りの手続きが作業より重くなるなら、意味がありません。

## まとめ

- セッションを切り替えるかは、使用率ではなく作業の区切りで判断する。使用率は補助情報として使う
- 区切りは2種類。担当の交代・独立レビュー・担当間の引き継ぎ・外部待ちでは切る。圧縮前・フェーズ遷移・修理ループの蓄積などは判断材料にし、前進しているなら続ける
- 再開は会話の要約からではなく、正本から。入口の索引 → 現在の状態 → 必要なときだけ詳細、の順に読む
- 要約も正本も古くなる。だから正本は、フェーズが変わるたびに更新する

PlanGate では、この考え方を Claude Code / Codex のプラグインの中に組み込んでいます。振り返ると、2026-04 の引き継ぎ書の更新漏れから始まり、07 月に圧縮前の鮮度チェック、08 月に索引の更新規定、09 月に Context Lifecycle と、少しずつ仕組みにしてきました。ただ、仕組みがなくても、正本を1つ決めて、フェーズごとに更新するところからは始められます。
