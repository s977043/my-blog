Claude Code や Codex で長い作業を続けていると、このまま続けるか、新しいセッションに切り替えるか、切り替えるなら何を残せばよいかで迷います。切ると、積み上げた文脈が消えそうで怖くなります。切らないと、古い判断や失敗した試行を引きずります。

この記事の結論を先に書きます。

> セッションを切り替えるかは、使用率ではなく作業の区切りで判断する。切ると決めたら、会話の要約ではなく、フェーズが変わるたびに更新する正本から再開する。

先に、2つの言葉の役割を分けておきます。

- **正本**（source of truth）: 現在の状態と判断の置き場。計画・現在の状態・判断記録のファイルで、作業中から更新し続けます。テスト結果やレビュー結果などの証跡は、正本から参照します
- **引き継ぎ書**（handoff）: 次の担当やセッションへの入口。作業の終わりに書く文書です

この記事で問題にするのは、引き継ぎ書を使うことではなく、**一度きりの要約だけを状態の唯一の置き場にする運用**です。

:::message
対象は、Claude Code / Codex で長時間続く作業です。区切りの判断表は「区切りの2種類」の章に、PlanGate を使わない場合の最小手順は「正本はいつ古くなり、いつ更新するか」の章にあります。

根拠は、筆者が作っている PlanGate（Claude Code / Codex 向けのプラグイン）の設計と、筆者の個人リポジトリに残っている記録です。区切りで切ることの効果を、使用率で切る場合と比べて計測したわけではありません。
:::

## 長い会話は重くなり、圧縮だけでは足りない

Claude Code の公式ドキュメントは、コンテキストが埋まるほど性能が落ちるとし、無関係なタスクの間では `/clear` でリセットすることを勧めています。コンテキストが上限に近づくと、会話を要約して容量を空ける圧縮（compaction）が自動で走ります。プロジェクトルートの CLAUDE.md などはディスクから読み直されますが、会話の中だけにあった判断は、要約に残ったものしか残りません。

Anthropic のエンジニアリングブログも、長時間動くエージェントについて「compaction isn't sufficient」と書き、新しいコンテキストで始めるエージェントには進捗ファイルや git の履歴から状態を把握させています。

どこかで会話を区切り、何かを残して次へ渡す必要があります。問題は「どこで区切るか」と「何を残すか」です。

## 紹介されている実践例：使用率を目安にする、作業単位でリセットする

Claude Code のセッションの引き継ぎについては、いくつかの実践例が紹介されています。筆者が読んだ範囲では、区切り方に2つの系統がありました。

| 区切り方 | 紹介されている例 |
|---|---|
| 使用率を目安にする | コンテキストが約8割で警告を出す、約7割で作業を止める。そのうえで引き継ぎ書を作り、次のセッションに渡す |
| 作業単位でリセットする | タスクの区切りでセッションをリセットし、引き継ぎ書で決定事項や捨てた選択肢を渡す |

引き継ぎ書の作り方も一様ではありません。この記事の分類（一度きりの要約だけに状態を預ける運用）は、これらの実践例をそのまま指すものではありません。

使用率を目安にすると、作業のまとまりとは関係なく区切りが来るので、テストの修正の途中で切ることになるかもしれません。これは構造から来る懸念で、比較して確かめたものではありません。

## 残したものは古くなる：要約も正本も

筆者の個人リポジトリには、残したものが古くなった記録があります。要約型（作業の終わりに一度だけ書く引き継ぎ書）と正本型（作業中に更新し続けるファイル）に分けて並べます。

**要約型：引き継ぎ書が完了の状態で渡らなかった（2026年4月）**

PlanGate では、タスクを完了したときに一度だけ `handoff.md` という引き継ぎ書を作ります。2026年4月、これが完了の状態で次のセッションに渡らず、後から直すことが2回続きました。

- 2026-04-24: 引き継ぎ書の発行そのものが、後続のセッションに回った
- 2026-04-26: 受け入れ条件の一部が「実装中」のまま渡り、後から修正した

4月26日の振り返りには「前回セッション（2026-04-24）でも同じ問題が観察されており、改善が定着していない」と書かれています。

**要約型：引き継ぎメモの前提が3つとも外れていた（2026年9月）**

2026-09-23 には、セッション間の引き継ぎメモに書いてあった前提3つが、すべて外れていました。

- 「13件が判断待ち」と書かれていたうち12件は、13日前にすでに閉じられていた
- 「A より先に B を閉じてはいけない」という制約は、向きが逆だった
- 2つの issue は紐付いていると書かれていたが、API 上の紐付けは無く、本文中の参照だけだった

**正本型：最初に読む索引が、1セッションで3回古くなった（2026年7月）**

正本も古くなります。PlanGate では、セッションの開始時に最初に読む索引ファイル（`INDEX.md`）を置いています。2026-07-31 に起票した issue #945 には、この索引が同じセッションの中で3回、実態とずれたことが記録されています。

| 時点 | 索引に書かれていたこと | 実態 |
|---|---|---|
| 計画の承認後 | 承認待ち | 承認済み |
| 計画の再編集後 | 承認は有効 | 再編集で再承認が必要になっていた |
| 実行の完了後 | 検証は PASS | 条件付き PASS（WARN） |

issue には「次セッションが誤った地点から再開する」とあります。更新規定が生成時のものしか無かったため、フェーズが変わるたびに更新する規定を足して閉じました。

これらは、メモや索引の鮮度管理が必要だと示す実例です。セッションを切る効果や、更新方式の優位性を比べたものではありません。**要約も正本も、書いた時点から古くなり始めます。** 違いは、正本は「作業の途中で更新する」ことを前提に置ける点です。

## 区切りの2種類：必ず切る区切りと、判断材料にする区切り

PlanGate の Context Lifecycle では、区切りを2種類に分けて定めています。

- **必須の区切り**: 前の会話を前提にできない場面。PlanGate の working-context スキルでは、タスク規模の区分が standard（中規模）以上のとき必須とし、ultra-light / light（小規模）では任意にしています
- **推奨の区切り**: 切ると役に立つことが多いが、状況で判断する場面

判断表にまとめます。「区切り」と「扱い」は PlanGate の規定で、「理由」の列は筆者の補足です。

| 区切り | 扱い | 理由（筆者の補足） |
|---|---|---|
| 担当の交代・担当間の引き継ぎ（別のエージェント・モデル・実行環境へ、実装からレビューへ） | 必須 | 前の会話にアクセスできない担当へ、ファイルで状態を渡す |
| 独立レビューの開始 | 必須 | レビュアーは実装側の会話ではなく、成果物・差分・証跡から読む |
| 外部待ち・使用量上限による中断 | 必須 | 再開までに状況が動くので、正本から読み直す |
| 圧縮やコンテキスト逼迫が近いとき | 推奨 | 圧縮の要約に判断を預ける前に、正本へ書き出しておく |
| フェーズ遷移で、必要な作業セットが変わるとき | 推奨 | 前のフェーズの議論が不要になる |
| 修理・レビューのループで古い議論が溜まったとき | 推奨 | 却下された案や古い判断が、次の判断を引っ張る |
| 不要な探索が溜まったとき | 推奨 | 調べたが使わなかった情報が場所を取る |
| 簡単なタスク | 任意（ultra-light / light では必須の区切りも任意） | 区切りの手続きが作業より重くなる |

使用率は主な基準にしません。ただ、信頼できる使用量が取れるなら、補助情報として判断に使ってかまいません。PlanGate でも、ツールに依存しないトークンの閾値は推測で作らず、使用量が確かなときだけ補助に使う扱いにしています。

ここまでが PlanGate の設計の事実です。区切りを目安にすると迷いが減る、作業の途中で切れる事故が減る、という効果は仮説で、計測はしていません。

推奨の区切りを置く理由として、筆者が気にしている記録があります。2026-08-12 に起票した issue #1061 では、サブエージェントへ作業を委託するとき、オーケストレーター役の AI が、直前に自分で書いた事実（timeout の扱い）を委託文から落としました。受け取ったワーカーは600秒進まずに止まっています。同じセッションの AI 同士のやり取りは約29往復（人間待ちは4回）でした。

記録は、委託の手順を適用する仕組みが無いことを構造的な原因に挙げています。停止の直接の原因は、timeout の情報が欠けたことです。筆者は、長いセッションで事実が積み重なったことも一因だと考えていますが、記録からは言えません。

独立レビューについては、Context Lifecycle を入れた PR #1411 で、レビュー対象のコミットを指定して始めた記録があります。比較できる条件がないので、指摘の件数はここでは挙げません。

## 正本はいつ古くなり、いつ更新するか

ファイルを正本にして再開する考え方そのものは、[アジャイルでAI駆動開発をどう回すか: PlanGateの考え方とテンプレート](/articles/plangate-ai-coding-workflow)で書きました。ここでは、その正本を「いつ更新するか」と「どの順に読むか」に絞ります。

### 更新するのは、フェーズが変わるたび

前の章の索引が古くなった3つの時点（承認後・再編集後・実行完了後）は、どれもフェーズの変わり目でした。ここでいうフェーズの変わり目は、現在の担当・承認状態・完了条件・次の作業が変わり、再開地点に影響するときです。そのとき、正本に書いてある「今どこにいるか」は一斉に古くなります。

だから、セッションを切るかどうかとは関係なく、**フェーズが変わるたびに正本を更新する**ことを要件にします。切るときも、最終的な判断を計画や判断記録へ書き、索引と現在の状態を実態に合わせてから切ります。テストやレビューの結果は証跡の置き場へ保存し、正本には参照だけを書きます。

### 読む順は、入口の索引 → 現在の状態 → 必要なときだけ詳細

新しいセッションでは、前の会話を貼り付けずに、次の順で読みます。

1. **入口の索引**: どのタスクの、どのフェーズにいるか
2. **現在の状態**: 何が終わり、何が途中で、次に何をするか
3. **必要なときだけ詳細**: 証跡・判断記録・過去の経緯は、具体的な問いがあるときだけ読む

読んだ内容は鵜呑みにせず、外部の状態（issue や PR、ブランチ）と照合し、変わっていれば作業の前に正本を更新します。

### 切る前のひな形（2項目）

状態の書き方そのものは既存のテンプレートに任せて、切る前に確認する項目だけを2つに絞ります。現在の状態のファイル（例: `current-state.md`）の末尾に追記する想定です。

```markdown
## このフェーズで更新したもの
- 計画 / 判断記録: （更新した・変更なし）
- 入口の索引 / 現在の状態: （更新した）
- 証跡: （保存先へのリンク）

## 持ち越さないもの
- 却下した案（理由は判断記録に書いた）
- 調べたが使わなかった情報
- 生のツール出力（結果は証跡に保存済み）
```

現在の状態のほうは、たとえば次のように書きます。

```markdown
- フェーズ: 実装
- 完了: 認証 API の追加
- 未完了: 失敗しているテストの修正
- 次の一手: 対象のテストを実行して失敗内容を確認する
```

PlanGate では、持ち越さないものとして、隠れた思考過程、会話のログそのもの、証跡で代わりが利く生のツール出力、秘密情報を決めています。

### PlanGate を使わない場合の最小手順

PlanGate を入れていなくても、同じことはできます。

1. リポジトリに作業状態のファイルを1つ置く（例: `docs/current-state.md`）。書くのは「今のフェーズ」「終わったこと」「次の一手」「未解決のこと」
2. フェーズが変わるたびに、そのファイルを更新する。切るときも、先に更新してから切る
3. 新しいセッションの最初に「まず `docs/current-state.md` を読み、今のフェーズと次の一手を宣言してから始めて」と伝える

引き継ぎ書を書く習慣がすでにあるなら、やめる必要はありません。引き継ぎ書には状態を書き写さず、「正本はここ」と指す入口として使えば、引き継ぎ書と正本で状態を二重に持たずに済みます。

## 同じ問題の途中では切らない

Codex のベストプラクティスは、同じ問題なら同じチャットで続けるほうが推論の流れを保てて良いことが多く、作業が本当に分岐したときだけ fork するとしています。Claude Code のベストプラクティスにも、履歴に価値があるときは文脈を積み上げるべき時もある、とあります。

一方で Claude Code の公式ドキュメントは、同じ問題で2回を超えて修正を繰り返したら `/clear` し、学んだことを入れたプロンプトで始め直すことも勧めています。この案内は Claude Code のもので、他のツールやあらゆる作業にそのまま当てはめるものではありません。

- 同じ問題で前進している → 続ける
- 同じ修正を繰り返している → Claude Code の案内に沿って、切って始め直す

切らずに正本を読み直す使い方もあります。OpenAI のブログで紹介されている長時間タスクの例では、仕様・計画・制約・状況を markdown に書き、Codex に繰り返し読み直させていました。区切りで切ることと、正本を読み直すことは併用できます。

## まとめ

- セッションを切り替えるかは、使用率ではなく作業の区切りで判断する。使用率は補助情報として使う
- 区切りは2種類。担当の交代・引き継ぎ・独立レビュー・外部待ちでは切る。圧縮前・フェーズ遷移・修理ループの蓄積などは判断材料にし、前進しているなら続ける
- 切ると決めたら、会話の要約からではなく正本から再開する。入口の索引 → 現在の状態 → 必要なときだけ詳細、の順に読む
- 要約も正本も古くなる。だから正本は、フェーズが変わるたびに更新する

PlanGate では、この考え方を Claude Code / Codex のプラグインの次のリリースで配布する予定です。関連する変更の日付は、2026-07-07（圧縮前に作業の状態の鮮度を確かめる仕組み、外部の実行プロトコルの取り込み調査がきっかけ）、2026-08-25（索引の更新規定）、2026-09-29（Context Lifecycle）です。仕組みがなくても、正本を1つ決めて、フェーズごとに更新するところからは始められます。
